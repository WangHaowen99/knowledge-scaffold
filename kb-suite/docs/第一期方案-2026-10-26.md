# DA × WeKnora × Swarm 第一期方案（2026-10-26）

前提：
- WeKnora 只移植有用的部分，用 Python 写成一个新服务，下文称 **kb-service**；
- DA 负责分析 agent；
- Swarm 是统一入口。

本方案和《JiuwenSwarm 接入 DeepAnalyze-Java 技术方案（2026-10-12）》、《运行时状态盘点（2026-10-12）》里已经定下的内容保持一致。

## 1. 第一期目标

打通一条最小闭环，三方共用**同一个知识库**：

1. 在 Swarm 里管理知识库并上传文档；
2. kb-service 完成入库；
3. Swarm 主 agent 能做日常问答，DA 能做深度分析，两边查的都是这个知识库。

**第一期不做**：Wiki、知识图谱、FAQ 和标签、分析报告写回、Docling 和 Whisper 解析、多用户身份映射、把 DA 接成 Team 成员、bundled 插件、`graph_build` 和 `timeline_build`、表格分析、数据源同步、IM。

## 2. 总体结构

```
                      ┌────────────── Swarm（入口与编排）──────────────┐
  用户 ─ Web/桌面 ──> │ 会话：主 agent（openJiuwen）                    │──── MCP ───────────┐
                      │ 会话：DA 专家（DeepAnalyzeHarness provider）    │── HTTP+SSE ─┐       │
                      │ 「知识库」插件页面 ─WS─> 插件后端 extension.py │── REST ──┐  │       │
                      └────────────────────────────────────────────────┘          │  │       │
                                                                                   │  ▼       │
                                                    DA 分析服务（Java，openJiuwen）│ /api/agents
                                                      kb 工具 ── kb-query ─────────┼──┐       │
                                                                                   ▼  ▼       ▼
                                  kb-service（Python，从 WeKnora 移植的部分）
                                    对外接口：管理 API ／ kb-query API ／ MCP
                                    入库流水线（异步任务）、检索（向量 + 全文 + rerank）
                                    存储：Postgres ／ Redis ／ 对象存储
                                           │ 调用
                                  解析与模型服务
                                    docreader（直接复用 WeKnora 的 Python 实现）
                                    DA 模块矩阵（NPU）：MinerU ／ PaddleOCR-VL ／ BGE-M3 向量 ／ rerank
                                    大模型端点（用于摘要和图片描述）
```

## 3. 模块和归属

### kb-service（新 Python 服务，从 WeKnora 移植）

| 编号 | 模块 | 内容 | WeKnora 参照 |
|---|---|---|---|
| K1 | 平台底座 | FastAPI；服务密钥、租户头、知识库范围校验（移植 API Key 的能力模型和 kb_access）；异步任务（Celery 或 arq）；Postgres；只接一种对象存储；配置和日志 | `types/tenant_api_key.go`、`middleware/auth.go`、`middleware/kb_access.go`、`repository/task_queue.go` |
| K2 | 知识库与模型配置 | 知识库 CRUD；解析、切分、检索参数；模型端点统一走 OpenAI 兼容协议（对话、向量、rerank、VLM） | `service/knowledgebase.go`、`service/model.go` |
| K3 | 入库流水线 | 上传（文件、URL、文本）→ 解析 → 切分 → 图片 OCR 和描述（可选）→ 向量化 → 索引 → 文档摘要；状态、重试、删除、重处理 | `knowledge_process.go`、`knowledge_create.go`、`knowledge_post_process.go`、`knowledge_delete.go`、`chunk.go` |
| K4 | 解析接入 | 复用 docreader；MinerU 和 PaddleOCR-VL 指向 DA 的 NPU 服务；溯源定位 SourceLocator | `infrastructure/docparser/`、`infrastructure/chunker/`、`types/source_locator.go` |
| K5 | 检索 | 混合检索 + rerank；按范围过滤；按阅读顺序读、按分块取上下文、在文档内查找；文档清单附带摘要 | `service/retriever/`、`knowledgebase_search.go`、`agent/tools/read_document.go`、`list_documents.go` |
| K6 | 对外接口 | 管理 API（给 Swarm 插件）、MCP（给 Swarm 主 agent） | `handler/knowledge*.go`、`mcpserver/` |
| K7 | DA 工具契约兼容层 | 按 DA 原契约实现 `POST /v1/tools/{kb_search,expand,doc_grep,wiki_browse,reprocess_document}`，并校验四个上下文头。要模拟 DA 的知识语义：L0 是文档摘要；L1 是完整的结构化 Markdown，Excel、CSV 要给全表，图片要带 VLM 描述和 OCR；L2 是原始结构或定位；还有 pageId、pageTypes 和 `{docId}:{type}:{index}` 格式的锚点。用 DA-java 的 `parity-goldens` 做契约测试 | DA 原版 `tool-setup.ts`；DA-java `tools/openapi/tool-platform.engine.json` |

### DA（更正：DA-java 源码不需要改，只改部署配置）

核对依据：agent-solution 仓的 `origin/common` 分支，提交 e7596b979（2026-10-26）。

DA-java 已经不在 Java 里实现知识库工具了：
- `kb_search`、`expand`、`doc_grep`、`wiki_browse`、`timeline_build`、`graph_build`、`reprocess_document` 都走 OpenAPI 通道，由 `DaServiceTools` 按描述文件里的原名挂载。见 `resources/tools/tool-metadata.yaml`、`resources/application.yml:139-163`。
- 每次调用都带 `X-Session-Id`、`X-Tenant-Id`、`X-Kb-Scope`、`X-Request-Id` 四个上下文头。
- 已经预留了 `knowledge-service` 插槽（`DA_KNOWLEDGE_SERVICE_URL`、`DA_KNOWLEDGE_SERVICE_SPEC`），排在 `tool-platform` 前面。两个服务提供同名工具时，用排在前面的那个。
- 每个服务都可以用 `include_tools` 参数限定只挂载哪些工具（`DaServiceTools.java:61,103-109`）。
- main 代码里已经没有对 `wiki_pages` 的直读，也不解析锚点格式。Java 代码里只出现工具名，比如 loopguard、压缩和 workflow 的名单。

| 编号 | 内容 |
|---|---|
| D1 | 配置 `DA_KNOWLEDGE_SERVICE_URL` 指向 kb-service；`DA_KNOWLEDGE_SERVICE_SPEC` 指向 kb-service 发布的描述文件，里面包含 kb_search、expand、doc_grep、wiki_browse、reprocess_document |
| D2 | 给 tool-platform 配 `include_tools`，把 kb-service 第一期不提供的知识库工具（graph_build、timeline_build）排除掉，免得挂上平台版去读旧知识库 |
| D3 | 配置访问 kb-service 的服务凭据，用 authHeaders（外部配置的具体键名还要确认） |
| D4 | 为 Swarm 这条链路部署一套不依赖 TS 的 DA 实例（10-12 文档的阶段 0）。原有入口继续用原来的知识库后端 |
| D5 | 模块矩阵里的 MinerU-NPU、PaddleOCR-VL、BGE-M3 以服务形式提供给 kb-service |

**前提**：kb-service 要按 DA 原来的工具契约实现，下面的 K7 就是做这件事的。第二期如果加新工具（比如 Wiki 检索），要改 jar 里的 `actrule.yaml`、`tool-metadata.yaml` 和提示词资源，然后重新打包，但仍然不用改 Java 代码。

### Swarm

| 编号 | 内容 |
|---|---|
| S1 | 知识库管理插件，做成 iframe 型应用插件。前端用 React，复用 Swarm 的设计变量。页面包括：知识库列表、新建和设置；文档列表、上传、状态、删除、重处理；分块预览；检索测试。插件后端是 `extension.py`，通过插件自己的 WebSocket 路由调用 kb-service 的管理 API，服务密钥只放在后端；大文件在 WebSocket 上分块上传 |
| S2 | 在 `config.yaml` 的 `mcp.servers` 里加上 kb-service（streamable-http + Bearer） |
| S3 | DeepAnalyzeHarness provider 加 HarnessAgentAdapter，即 10-12 文档的阶段 1–2。第一期的检索范围默认取当前租户的全部知识库，以显式列表下发 |
| S4 | 第一期一个 Swarm 部署对应 kb-service 里的一个租户 |

## 4. 组合方式：四条链路

1. **入库**：插件页面 →（WS）→ 插件后端 →（REST，插件密钥）→ kb-service 管理 API → 异步任务 → docreader 或 MinerU、PaddleOCR-VL → 切分、向量化、索引 → 文档摘要。
2. **日常问答**：Swarm 主 agent →（MCP，只读密钥，限定知识库）→ kb-service 检索 → 带出处的回答。
3. **深度分析**：用户在 Swarm 里选 DA 专家 → provider 调 `POST /api/agents/run-stream`，带上 scope 和租户 → DA 的 kb 工具调 kb-query → DA 流式输出事件 → provider 把事件映射成 harness 事件 → Swarm 界面展示。
4. **溯源**：每条引用都带分块 ID 和定位（页码、章节、bbox），插件页面按这些信息打开原文所在位置。

## 5. 先定的接口契约

| 编号 | 接口 | 双方 | 内容 |
|---|---|---|---|
| I1 | DA 工具契约 | kb-service ↔ DA | 直接沿用 DA 现有的 `POST /v1/tools/{kb_search,expand,doc_grep,wiki_browse,reprocess_document}`，以及四个上下文头。这份契约不用另外设计，只需按 DA-java 的描述文件和 parity-goldens 对齐 |
| I2 | 管理 API | kb-service ↔ Swarm 插件后端 | 知识库 CRUD、上传（分块上传会话）、文档状态、分块列表、检索测试、模型端点配置 |
| I3 | MCP | kb-service ↔ Swarm 主 agent | `list_knowledge_bases`、`search_knowledge`、`list_documents`、`read_document`、`grep` |
| I4 | 插件 WS 协议 | 插件前端 ↔ 插件后端 | RPC 消息格式，加上传分块 |
| I5 | Harness | Swarm ↔ DA | 沿用 10-12 文档（`/api/agents` 的 run-stream、stream、cancel、answer、inject） |

**锚点格式**和**范围规则**（必须带租户；kbIds 不能为空；知识库必须属于该租户）也在这一步一起定下来。

## 6. 推进策略：接口先行，后端可以替换

- **M1（约 2 周）**：冻结 I1–I4、锚点格式、租户和范围规则、部署拓扑。
- **M2（再 4–6 周）**：用 WeKnora Go 原版实例加一个薄适配层，先把 I1–I3 实现出来。DA 和 Swarm 基于它并行联调，三条链路先跑通。
- **M3（再 8–12 周）**：Python 版 kb-service 按模块完成 K1–K6。用同一批文档和原版做差分对比，达标后替换适配层，同时补齐插件页面，完成验收。

这样做的好处是：Swarm 和 DA 的接入不用等移植完成；原版 WeKnora 正好充当差分测试的参照。

## 8. 验收

- 用 DA 评测集里的文档测试入库：成功率达标，页码定位正确。
- 检索结果和 WeKnora 原版做差分对比，top-k 命中率不低于约定阈值；DA 评测题的准确率不比原管线差。
- 三条链路在 Swarm 里都跑通：上传后能检索到；主 agent 回答带出处；DA 的分析里有锚点引用，并能回到原文定位。
- 权限测试：范围为空被拒绝，跨租户访问被拒绝，插件密钥不出现在浏览器里。

## 10. 仓库与构建部署（2026-10-26 补充）

**原则：** 我们自己的代码放进一个新仓，外部组件只按版本引用产物，不拉它们的源码一起编译。

**外部组件现在的发布方式：**
- DA-java：在 agent-solution 仓里用 `mvn package` 打包，再用 `deploy/Dockerfile` 构建镜像。
- Swarm：通过 PyPI 发布，包名 `workswarm`。
- Swarm 插件：放进 `~/.jiuwenswarm/application_plugins/` 或 `extensions.extension_dirs` 配置的目录，重启 Gateway 即可生效，不用编译 Swarm。

**新仓的结构：**

```
kb-suite/
  service/kb-service/  → 镜像 kb-service（kb-api、kb-worker 用同一个镜像，启动命令不同）
  swarm-kb-plugin/     → Swarm 应用插件包（extension.yaml、extension.py、frontend/dist），只是插件，不是 Swarm 前端
  swarm-da-provider/   → DeepAnalyzeHarness provider 的 wheel
  contracts/           → 管理 API、给 DA 的工具描述文件、MCP 工具清单、插件 WS 协议
  deploy/              → compose 或 helm、versions.lock、配置模板（不放密钥）
  tests/e2e/
```

**CI 各管各的：**
- 新仓：kb-service 跑单测和契约测试，然后出镜像；插件用 vite 构建后打成 zip；provider 打成 wheel。插件和 provider 的测试锁定 `workswarm` 版本，作为开发依赖。
- DA 团队的流水线发布 `deepanalyze-java:<版本>` 镜像。
- Swarm 按 PyPI 上的版本使用。

**部署顺序：**
1. Postgres（pgvector + zhparser）、MinIO。
2. docreader、MinerU-NPU、PaddleOCR-VL、BGE-M3、rerank。
3. kb-service：先跑 alembic 迁移，再启动服务，然后初始化租户和三把服务密钥（DA、Swarm 插件、Swarm MCP）。
4. DA-java：配置 `DA_KNOWLEDGE_SERVICE_URL`，以及 `DA_KNOWLEDGE_SERVICE_SPEC`（挂载 kb-service 导出的描述文件；非 classpath 路径会被直接使用，见 `DaServiceTools.withLocalSpec`）；配置 tool-platform 的 `include_tools` 和访问凭据。
5. Swarm：安装锁定版本的 `workswarm`，放入插件包，安装 provider wheel，在 `config.yaml` 里配好 MCP 和插件设置，然后重启 Gateway。
6. 冒烟测试：上传文档后能检索到；MCP 问答带出处；DA 能调用 kb_search 和 expand。

**唯一可能要用 Swarm 源码构建的情况：** 把 DA 接成 Swarm 主 agent（10-12 方案 B）需要改 Swarm 的 `agent_adapters.py`，并新增 HarnessAgentAdapter。这部分应该提 PR 给 Swarm 上游。上游发版之前要联调的话，就用我们 fork 分支临时打一个 wheel，并在 versions.lock 里标明是临时版本。
- 补充：Swarm 最新的 develop（10-26）已经支持上传自定义 provider wheel 作为团队成员（`common/custom_agent_runtime.py`）。所以按团队成员方式接入（方案 C）也许不用改代码，比 10-12 文档的判断更乐观，需要实测确认。
