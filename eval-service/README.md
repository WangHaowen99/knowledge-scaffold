# 独立知识包评测（eval1）

在 Hub2 之后接入：从 Hub 固定版本下载 → 在评测页面配置用例和数据源 → 生成 mapping → consumer 问答 → Judge 判分 → 按需发布派生版本。服务不读取建模工作区或 Core 数据库，不保存建模项目信息，不运行建模 Agent；「评测任务」与执行详情直接展示本轮知识包引用中的名称和本体标识。

## 本地运行

```bash
cd eval-service
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
cd frontend
npm ci
npm run build
cd ..
# 在进程环境注入运行配置后启动
.venv/bin/python run.py
```

打开 `/evaluation/`；直接访问服务根路径（如 `http://127.0.0.1:5180/`）会跳转到该页面。开发前端可用 `npm run dev`，代理默认本机 5180，可通过 `EVAL_DEV_API_URL` 覆盖。单独启动开发端口不与建模共享浏览器存储，免重复登录需从建模页面以直连方式打开（见下文）。

## 评测工作台

- 页面配色和字号与消费前端一致：文字对比度不低于 4.5:1，最小字号 12px。左侧导航分「评测」（评测任务、用户反馈）和「配置」（评测集、数据源、判分模型），评测任务旁显示进行中的数量，用户反馈旁显示待确认的轮次数；顶栏显示当前位置。内容区随窗口铺满，1280px 以下导航收成图标栏，768px 以下移到底部，列表变成卡片。
- 「评测任务」每个知识包一行，同一知识包的多次评测合并；进行中的评测置顶显示进度。按全部、进行中、需处理、已结束筛选，可搜索知识包名称、知识包 ID、任务 ID 和评测集。结果列为结果分布条加“得分 · 通过率”，进行中的显示判分进度；“建模处理”列显示建模对优化建议的处理进展；中断原因写在状态下面。列表与执行详情每 5 秒更新，切回页面立即同步。
- 得分和通过率：得分沿用报告口径，通过 1 分、部分通过 0.5 分，只算有效判分的用例，执行异常、判分异常和待人工不计入；没有有效用例时显示“未形成有效评测”（不是 0 分）。通过率 = 通过 ÷ 全部用例，部分通过、未通过、异常、待人工都不算通过。反馈轮次不计算得分。
- 新建评测按“知识包版本 → 数据源 → 评测集 → 确认启动”执行。知识包、数据源和评测集都是单选行，数据源旁注明本轮使用哪个工作空间；选中上传数据或图导入的数据源后自动预览映射，缺字段、未绑定数据表等问题写在表格上方。问题可逐条编辑或导入 JSON；无参考答案的用例保留为待人工判定。
- 执行详情：标题为知识包名称、版本和状态，主操作是停止、恢复或再次评测，复制链接、发布派生版本、删除收进“更多”。结果卡以得分为主，旁边是通过率；点结果分布可筛选下方用例，“接下来”列出待人工判定、异常、未通过等待办。“交付建模”四步条显示报告和建议的生成、建模通知、建模处理和在新版本上验证。页签为用例结果、评测报告、优化建议、历史记录、本轮配置；报告和建议直接显示，可下载。用例抽屉可上一条、下一条，非活动任务可人工改判，原因必填并保留历史。
- 任务地址为 `/evaluation/#/runs/<run_id>`。关闭页面或重新登录后，从「评测任务」或原地址重新进入。查看任务不触发恢复执行；待授权与已中断任务需要明确确认恢复，停止任务需要确认并等待远端对账。映射派生版本的发布单独确认，正式回执来自 Hub。
- 数据源和评测集有独立管理入口；修改定义不会改写已有任务快照。
- 求解验证：新建评测时把评测类型选为“求解验证”，用求解验证集逐条让 consumer 智能体调用知识包的求解能力，按工具调用、入参、权威结果与候选数做确定性判定，不需要判分模型，也不提供人工改判。需要 Neo4j 业务数据源（开启图数据导入，或使用已有数据的 Workspace 范围）；每集最多 20 条用例，并发默认 1、最多 4。可导入建模侧导出的验证用例 JSON。字段与失败码见 `API.md`“求解验证”。
- 数据评测执行详情的“交付建模”卡片中，建模通知“已送达”时，在日期时间后提示前往建模服务“已发布版本（知识包评测）”的“优化建议”弹框点击知识包优化。

## 配置与权限

变量见 `.env.example`；该文件仅是占位说明，不是可直接运行的凭据文件。部署时的实际配置由部署脚本维护在 `deploy/.env`（权限 600，不入库），或通过 `EVAL_ENV_FILE` 从仓库和构建上下文之外注入，见下文“独立部署”。

- `EVAL_AUTH_URL`、`EVAL_AUTH_ISSUER`：与 Hub 使用同一可信账号及稳定身份命名空间。
- `EVAL_HUB_URL`、`EVAL_HUB_SERVICE_TOKEN`：对应 Hub 的 evaluation 服务身份（Hub 的 `HUB_EVALUATION_SERVICE_TOKEN`），不复用 modeling 凭据。
- `EVAL_CONSUMER_API_URL`、`EVAL_CONSUMER_SERVICE_TOKEN`：后者对应 consumer 的 `EVALUATION_SERVICE_TOKEN`，与其 modeling 密钥不同；用户身份仍必需。
- `EVAL_DATA_DIR`：独立卷。默认 `.runtime/` 仅用于合成数据本地开发，部署必须使用外部运行卷。
- `EVAL_ENCRYPTION_KEY`：Fernet 密钥，用于连接配置、页面保存的 Judge API Key、上传数据、执行数据快照，以及数据飞轮委托保存的后台评测登录。部署脚本首次部署时生成并保存在 `deploy/.env`，不在数据卷内；备份时须与数据卷分开、同样受控保管。变更或丢失密钥会导致已有加密数据无法解密：已有数据卷而缺少密钥时部署脚本拒绝生成新密钥。
- `EVAL_JUDGE_BASE_URL`、`EVAL_JUDGE_API_KEY`、`EVAL_JUDGE_MODEL`、`EVAL_JUDGE_CONFIG_REVISION`：临时 Judge 部署配置。问答模型在发起评测时选择：consumer 全局模型池或当前用户个人模型池中已启用的模型，或 consumer 默认模型；记录其非敏感配置摘要。此方案标记 **MODEL-CONFIG-01，待 eval2 整改**。
- 页面配置 Judge：登录后进入侧边“评测判分模型配置”。所有用户可查看生效来源、模型和配置版本，只有管理员（账号服务中 role 为 admin）可修改，因为该配置对所有用户的评测生效，并会收到题目、参考答案和回答。
  - 管理员填写网关地址、模型和 API Key，可先“测试连接”（与轮次预检相同的结构化判分检查）再保存。保存的配置整体替换部署配置，“恢复部署配置”删除它。
  - API Key 用 `EVAL_ENCRYPTION_KEY` 加密存入数据卷，接口和页面从不返回。网关不变时 Key 可留空沿用；更换网关必须重填，部署 Key 不会被发往新地址。
  - 配置版本自动生成；值变化后，排队及进行中的轮次会停止判分并提示重新创建轮次。可选 NL2SQL 使用默认 Judge 配置（不随个人配置变化）。
  - 管理员页面分两部分：“我的判分模型”与其他用户相同；“默认判分模型”维护供所有用户使用的默认配置，并带启用开关。停用后，没有个人配置的用户（含勾选“使用默认配置”的管理员）不能发起新评测，提示先填写自己的判分模型；这些用户排队及进行中的轮次停止判分并中断。重新启用不改变配置版本，中断的轮次可恢复。个人配置不受影响，NL2SQL 仍使用默认配置。开关缺省为启用。
- 个人判分模型：“评测判分模型配置”页面默认勾选“使用默认配置”。取消勾选后可填写自己的网关、模型和 API Key，保存后成为本人单独的配置，只覆盖本人新发起的评测；重新勾选即删除个人配置、切回默认配置。生效顺序为 个人配置 > 管理员页面配置 > 部署配置；默认配置停用时“使用默认配置”不可勾选。没有可用的判分模型时，新建向导的“开始评测”仍可点击，点击后提示未配置的原因并可前往配置。
  - 个人配置的 Key 同样加密存储、从不返回；留空时只沿用本人此前保存的 Key（同一网关），不会借用默认配置的 Key。
  - 判分时会把本人评测的题目、参考答案和回答发送到个人配置的网关；管理员修改默认配置不影响已设置个人配置的用户。
- 优化建议同样由该用户生效的判分模型生成。除失分用例的题目、参考答案、回答和判分理由外，还会把知识包文档节选，以及用例结算时记录的工具调用发送到判分模型网关。工具调用记录包括工具名、参数与结果的截断预览（脱敏后每项不超过 200 字）、错误码和错误信息；每个用例最多附 6 次调用。预览中可能包含从评测数据源查出的数据。工具调用记录单独存放在评测数据库中，每个用例最多保留 12 次调用，随评测记录一同删除。
- 失分用例按单次约 3.2 万字的输入分批分析，适配 32k 上下文的判分模型；与同一知识包文档相关的用例放在同一批，每批只带与本批相关的文档。文档按问题、参考答案、判分理由、工具调用和回答的相关度挑选：工具调用直接点名的脚本文档、所查数据表对应的对象文档优先；长文档保留开头和匹配的章节；各 index.md 合计不超过文档份额的 15%；数据映射超出份额时只保留所选文档对应的对象。网关返回“输入超出上下文”时自动按一半大小重新分批，无需配置。多批时再调用一次合并同一根因的条目，合并失败或丢失用例时直接拼接各批结果。单次生成最多预先规划 8 批、发起 14 次请求，超出上限或所在批次失败的用例会在建议开头列出。推理型判分模型可能思考数分钟，单次请求最多等待 10 分钟、整次生成最多 30 分钟；请求超时后按一半大小重新分批，不原样重发。生成期间执行详情显示当前批次与已等待时长；仍超时则提示判分模型思考时间过长，可稍后重新生成或换用响应更快的模型。
- dataset 可选配置：`EVAL_SQL_CONFIG` 为 MySQL 连接参数 JSON，`EVAL_NL2SQL_URL` 为 consumer 可达的评测查询入口，路径 `/evaluation/api/nl2sql`。每轮只管理 `eval_<run_id>` 数据库；查询使用绑定 scene 的 HMAC 凭据、SQL AST 检查及只读事务。数据库账号应按评测库前缀限定权限。
- `EVAL_TRUSTED_ORIGINS`：可选，允许向评测页面交接登录的建模页面来源，逗号分隔（如 `https://modeling.example.com`）。留空时只信任与评测页面主机名相同的建模页面；`localhost`、`127.0.0.1` 与 `[::1]` 视为同一台本机。
- `EVAL_MODELING_URL`：建模服务地址，用于发送评测完成通知，以及兼容接口 `GET /evaluation/api/modeling-projects` 按当前用户登录查询关联项目；「评测任务」与执行详情显示知识包名称时不调用该接口。置空则不查询、不发通知。
- `EVAL_MODELING_SERVICE_TOKEN`：发送评测完成通知的服务凭据，与 onto-modeling 的 `ONTO_EVALUATION_SERVICE_TOKEN` 相同，整栈与分离部署自动传入；留空时只告警、不发通知。建模服务登记和使用数据飞轮委托（`/delegations`、委托读取与 `/runs/{id}/reruns`）时也用它证明身份，留空时不接受委托。

有效建模登录复用 `onto-access-token` 和 `onto-refresh-token`，刷新直连账号服务。不能通过 Onto 后端转发，也不能在跳转 URL 放 token。建模页面只通过独立地址打开评测，入口地址只由建模部署变量 `ONTO_WEB_EVAL_PUBLIC_URL` 决定：

- 直连（默认）：未设置该变量时，建模页面打开与自身同主机的 `http://<主机>:5180/evaluation/`；评测在其他主机、端口或经 HTTPS 时设为完整地址（如 `http://eval.example.com:5180/evaluation/`）。无需网关。
  - 点击评测时建模页面打开新窗口；评测页面就绪后，建模页面用 `postMessage` 把登录只发给该地址的来源。评测页面只接受打开它的窗口发来、且来源受 `EVAL_TRUSTED_ORIGINS` 信任的交接。
  - 评测端口默认开放所有网卡，供其他机器的浏览器访问。只允许本机访问时部署设置 `EVAL_BIND_ADDRESS=127.0.0.1`；它与 `EVAL_PORT`（默认 5180）都会记入 `deploy/.env`。
  - 评测页面保存的是登录副本，在建模页面退出不会同步清除。

当前权限为用户私有包；不复制项目成员共享权限。

## 输入和发布

评测集最多 50 个、每集 500 用例。用例格式是 JSON 数组，或包含 `cases` 数组的对象（`{"cases": [...]}`），每项含 `question` 和可选 `reference`（也接受 `groundTruth`）。数据源支持 none、dataset、connection，上传 CSV/XLSX，单文件及合并总量最多 50 MiB、每源最多 20 个文件。连接检查失败阻止用例执行。

- none 不要求数据库或 mapping。
- dataset 将数据写入本轮独立 MySQL 库，配置 consumer 的 NL2SQL 连接。
- connection 支持外部 NL2SQL 或 Neo4j 查询。外部 SQL 不执行覆盖导入；上传数据导入使用 dataset。Neo4j 导入须明确选择；配置范围存在旧图数据时，先确认替换，再删除并导入新数据。

两类 NL2SQL（`nl2sql_http`、`nl2sql_template`）的数据源表单提供“测试连接”：向数据服务的 `POST /api/v1/sql` 发送固定 `SELECT 1` 与当前 Scene，验证连通性和访问权限，不调用模型、不读取表结构，也不保存配置。单次测试最多等待 10 秒，响应最多 64 KiB；编辑已有配置时可沿用已保存的凭据，地址变更时须重新填写。测试失败显示受控错误，不回显对端正文或凭据；修改连接信息会清除旧测试结果。

新建评测的“准备与确认”对这两类 Provider 始终沿用所选知识包版本中的映射，不重建映射、不生成派生快照；旧数据源中保存的表字段定义也不会覆盖知识包映射。“保存并继续”独立保存有效连接，不要求先完成测试。

数据源配置页面提供“不使用数据源”“上传数据”和“外部连接”，Neo4j 外部连接中的业务数据表导入仍可使用。

评测隔离范围不在数据源编辑页填写：在新建评测选中外部连接数据源后，卡片内展开隔离范围，Neo4j 为 Workspace 隔离字段与对应值、Ontology 隔离字段与对应值（对应值由本轮知识包自动带入、只读），NL2SQL 为评测工作空间 ID；保存后随数据源保存，之后选择它的评测沿用，填好并保存后才能进入下一步。保存连接时可暂不填写，准备评测时缺少则返回 scope_required。Neo4j 按 Provider 展开 URL、Database、User、Password，隔离字段默认 `d2o_workspace_id`、`d2o_ontology_id`（与 consumer 图数据一致）；查询已有图库无需手填表结构。图导入支持“不导入 / 示例数据 / 业务数据表”，未接入示例种子时置灰。选择业务数据表后上传 CSV/XLSX，保存后预览实体、实例、关系与字段匹配；预览不发布包、不写图库。导入使用配置的 Workspace 字段与对应值、Ontology 字段与当前知识包 ID，两组条件同时匹配。可在向导中检查旧图数据；开始评测时必须重新检查，发现旧节点及范围内关系后，用户确认才删除旧数据并导入新数据，取消保留原数据。跨范围关系会阻止替换；清理和导入在同一事务中，导入失败回滚。每个范围在图库保存独立导入回执，响应丢失后恢复先核对回执，避免重复清理；后续导入已替换该范围时，旧任务不能继续查询新数据。同一范围的活动评测互斥。检查最多 10 万个节点、20 万条关系，确认有效期 10 分钟；范围节点或关系已变化时中断，需重新创建并确认。旧版本按 `eval_<run_id>` 写入的图数据不会迁移到配置范围。删除评测任务仍不清理外部图数据。连接回读只返回允许展示的字段与凭据已配置状态；地址或账号变化时不能沿用旧凭据。

原包 mapping 可被替换，仅派生副本改变。mapping 变化先提交 Hub 内部评测快照；同一基础版本加相同 mapping 复用已提交的快照。快照由 Hub 命名为 `<基础版本>-eval.<n>`（如 `0.1.10-eval.2`），不占用正式版本号；此前已提交的快照保留原版本号。任务列表“知识包版本”只显示所选发布版本，评测快照版本在执行详情中单独列出。正式“发布知识包版本”由用户显式触发，创建新版本，不重标历史快照，不自动激活。未修改 mapping 时直接运行原 Hub 版本。

接口统一在 `/evaluation/api` 下。主要资源为 `/packages`、`/eval-sets`、`/data-sources`、`/inputs`、`/package-preparations`、`/package-publications`、`/runs`。定义使用 revision 乐观并发，准备、发布和运行使用稳定 request_id。输入中不接受建模 project_id。响应限额和明细规则见 `API.md`。

## 独立部署

完整安装、升级及旧版迁移必须同时提供 Consumer、Onto Modeling、Hub、评测四个发布包：
`--consumer-package`、`--onto-modeling-package`、`--knowledge-hub-package`、`--evaluation-package`。
交互入口同样要求四个必需包，不允许留空，也不以复用运行服务替代提供发布包。

```bash
# 从仓库根执行；consumer 与知识包 Hub 需已部署
bash deploy/deploy.sh --eval-only
```

- 运行配置：未设置 `EVAL_ENV_FILE` 时，`deploy/deploy.sh` 读写 `deploy/.env`，保存凭据、显式配置及选定的网络和 Auth 默认值；取值顺序为进程环境 > `.env` 已有值 > 默认值：
  - 首次部署生成 `EVAL_ENCRYPTION_KEY`。
  - 评测凭据沿用 Hub 的 `HUB_EVALUATION_SERVICE_TOKEN` 与 consumer 的 `EVALUATION_SERVICE_TOKEN`，由根目录 `deploy/deploy.sh` 读取后注入，两者分别由 Hub 部署脚本和 consumer 部署生成。
- Auth 身份：`EVAL_AUTH_URL` 和 `EVAL_AUTH_ISSUER` 缺失时均默认 `http://auth-server:5056`，已有运行配置或进程环境优先。Compose 将两者传入容器；使用 `EVAL_ENV_FILE` 时脚本不改外部文件，进程环境中的默认值仍会传入容器。实际 Auth 契约不同时应配置真实值。Hub、Consumer 地址的默认值 `http://knowledge-hub:8200`、`http://backend:5055` 写在 Compose 中。手动执行 Compose 并使用外部配置时，也需要加上 `--env-file <配置文件>`。
- 网络：`CONSUMER_NETWORK` 缺失时默认 `onto-auth-network`，评测容器加入该网络，按服务名访问依赖。网络仍须已存在；根目录部署脚本会自动探测并注入，部署脚本会把实际网络名记入本地 `.env`。使用其他共享网络时，在进程环境或 `.env` 中配置实际网络名，并把依赖地址改为该网络可达的地址。
- Judge：`EVAL_JUDGE_BASE_URL`、`EVAL_JUDGE_API_KEY`、`EVAL_JUDGE_MODEL`、`EVAL_JUDGE_CONFIG_REVISION` 是部署默认值（OpenAI 兼容 `/chat/completions`，需支持工具调用），已在 `deploy/docker-compose.eval-service.yml` 中声明但不含值。缺失时部署只告警；写入 `deploy/.env` 或进程环境后重新部署，或由管理员在评测页面保存 Judge 配置，即可开始评测。
- 外部配置：设置 `EVAL_ENV_FILE` 指向仓库之外、仅运行账号可读的配置文件时，脚本原样使用、不改写，也不自动补齐凭据。
- 镜像源：构建时 npm 默认 `registry.npmmirror.com`，PyPI 默认华为云镜像。可用 `EVAL_NPM_REGISTRY`、`EVAL_PIP_INDEX_URL`（或 `NPM_REGISTRY`、`PIP_INDEX_URL`）覆盖，源码部署和离线包构建都生效；未设置时不传构建参数，沿用 Dockerfile 中的默认值。基础镜像 `node:24-bookworm-slim`、`python:3.12-slim-bookworm` 仍从 Docker Hub 拉取，需要加速时在 Docker 守护进程中配置 registry mirror。

已有服务使用独立 Docker 网络时，可设置 `EVAL_COMPOSE_OVERRIDE` 指向受保护的 Compose 覆盖文件，接入共享网络；不添加同源评测网关。

独立 Compose 不启动账号、Hub、consumer 或建模依赖。默认全栈 `bash deploy/deploy.sh` 会在其他服务之后部署评测；`--onto-modeling-only` 不包含评测。默认映射为宿主端口 5180 → 容器端口 5180（所有网卡），网关按实际网络配置访问；直连方式见“配置与权限”。`/evaluation/api/health` 只报告进程活性，不能替代依赖与模型协议验证。

升级旧部署时，原运行配置不会被自动覆盖。要统一使用 5180，须同步检查评测的 `EVAL_PORT`、建模的 `ONTO_WEB_EVAL_URL`（容器网络地址）与 `ONTO_WEB_EVAL_PUBLIC_URL`（浏览器地址），以及消费反馈发送地址、反向代理和使用评测内置 SQL 适配器时的 `EVAL_NL2SQL_URL`。显式设置的旧端口仍会覆盖新默认值。变更运行配置后需重新创建相应容器，单纯 restart 不会重新加载环境变量。

离线包：`bash eval-service/build.sh <version> [amd|arm]`，产物为 `eval-service/dist/evaluation-<version>-linux-<arch>.tar.gz`（顶层目录 `eval-service/`），包含镜像、Compose、部署脚本和说明。目标机解压后执行包内 `deploy/deploy.sh`（自动加载镜像），或交给分离部署脚本的 `--evaluation-package`；运行配置规则同上。不包含运行配置和数据。根目录 `bash deploy/build.sh <version> [amd|arm]` 生成的完整离线包也包含评测镜像、部署脚本及网关配置示例，并同时在 `eval-service/dist/` 生成上述独立发布包（同版本旧包会被覆盖）。

## 恢复与清理

SQLite 请求记录及独立文件锁保证单实例写入；两个后台线程、每用户一个活动任务、最多 16 个排队/执行任务。每轮按发起时设置的并发数（1 到 16，默认 4）同时向 consumer 提问，每条用例只更新自己的结果；consumer 限流、不可用或超时时按 Retry-After 退避重试同一请求（最多 6 次），某条用例失败不影响其他用例，连续 3 条同类依赖失败才停止提交其余用例。用户令牌只在内存，重启后轮次标记中断，用户通过有效登录授权恢复。发起、恢复和停止评测时，页面一并交出 refresh token（请求头 `X-Refresh-Token`），同样只在内存：执行引擎在 access token 到期前 2 分钟内自动换新，身份每分钟最多向账号服务核验一次，因此评测时长不受 access token 15 分钟有效期限制，关闭页面也不会中断。用户退出登录（refresh token 被吊销）或 refresh token 过期后，令牌用尽时轮次进入待授权，提示“登录凭证已过期，请重新登录后点击‘授权并继续’”；判分模型网关拒绝 API Key 时提示检查判分模型配置，不当作登录过期。恢复时轮次立即显示为准备中，不等预检与数据检查完成。远端提交未知时复用原 session/幂等键对账，不新建会话。consumer 以 `SESSION_PREPARE_FAILED`（会话运行状态准备失败，常见于同一工作空间并发提问时撞上会话整理）结束运行时，问题并未真正作答，该用例按 2、4、8…秒（上限 30 秒，含随机抖动）退避后换新会话重新提交，连同首次最多 6 次；重试次数记在用例上，对账时按当次的 session/幂等键重放，等待期间停止评测立即生效；仍失败时执行异常说明中注明已重试次数。其他运行失败不重试。Judge 失败只重判，不重复问答。

用例结算时回放 consumer 执行事件，工具调用证据（失败优先、脱敏截断）落库，供报告「工具失败」和优化建议归因使用；取不到时明确显示 `not_collected`。人工改判保留原判定、原因、操作者身份键和时间。

「评测任务」“···”菜单和执行详情提供“删除评测记录”：已结束的轮次可直接删除；中断或待授权的轮次在 consumer 侧没有执行中或待对账的问题时可删除，否则须先停止评测并完成对账；排队或执行中的轮次须先停止。删除清理进度落库，失败后重新执行删除继续处理。只删除自有消费空间和 dataset 库，不删除外部图/SQL。外部连接数据源的轮次在数据源指定的 consumer 工作空间中执行（Neo4j 取“Workspace 对应值”，NL2SQL 取“评测工作空间 ID”，与原建模评测一致），以当前用户权限调用 consumer 的通用工作空间接口：不存在时创建，名称与 ID 一致（计入该用户的工作空间数量上限）；已存在时只复用本人所有且未共享的空间，并在其中导入、激活本轮知识包版本（同版本以 Hub 内容覆盖）；该空间跨轮次复用，删除轮次时不删除。建模项目删除不影响独立评测和 Hub 包。未引用上传 24 小时后清理，被定义/准备/运行引用的文件保留。

```bash
# 下列路径为通用运维示例；快照目标必须不存在
python -m evaluation.maintenance backup --data-dir /var/lib/evaluation --snapshot /backup/evaluation.sqlite
# 停止新服务后恢复到空目录；必须提供最新删除记录库
python -m evaluation.maintenance restore --data-dir /restore/evaluation --snapshot /backup/evaluation.sqlite --deletion-records /var/lib/evaluation/evaluation.sqlite
```

数据库包含加密的输入、连接配置与页面保存的 Judge API Key，备份应同样受控。恢复重放删除标记、执行完整性检查，running 转 interrupted 等待重新授权；不能通过旧备份复活已删轮次。

## 数据飞轮：消费反馈与建模回写

- **建模回写**：建模按优化建议修改并发布新版本后调用 `POST /runs/{id}/modeling-result`，评测核对 Hub 版本后记在原轮次上；执行详情的“交付建模”、历史记录和「评测任务」的“建模处理”列显示处理结果，可“在新版本上再次评测”（即已有的再次评测，预选新版本）。
- **消费反馈**：`EVAL_FEEDBACK_ENABLED=true` 时接收消费推送的反馈（`EVAL_FLYWHEEL_SERVICE_TOKEN` 与消费 `FLYWHEEL_SERVICE_TOKEN` 相同，一键安装器自动生成）。后台线程按知识包版本归属、只认每轮最新投票、确认追问纠错、改写多轮问题、归簇和分拣，就绪的问题簇并入“反馈轮次”；满 10 个问题簇或 60 分钟没有新问题簇时封板生成报告。反馈轮次只有在 Hub 上能看到该包的用户可见，在评测页“用户反馈”中补标准答案、标记误判、生成优化建议，确认后才通知建模。需要模型的步骤用管理员默认判分配置。反馈正文加密，保留 `EVAL_FEEDBACK_RETENTION_DAYS`（默认 90）天。
- **用户反馈页**：按知识包处理，后台自动分出的反馈批次对用户不可见。列表每个知识包一行：状态（待确认、交付中、待建模处理、处理失败、收集中、已处理）、待确认的问题和建议条数及优化建议是否已生成、待建模处理的交付次数、最近处理结果、累计反馈、最近反馈时间；导航角标为有待确认反馈的知识包数，交付后立即刷新。知识包页分「待确认」「交付记录」两个页签：交付卡分三步（生成优化建议（自动）→ 核对问题（可选）→ 交付建模），只有「交付建模」一个主操作，生成失败时多一个「重新生成」；下面是问题表（点行看回答和工具失败，可补充标准答案、标记误判）、用户建议和优化建议。交付记录一行一次交付，带编号列，合并写成“已合并到 <编号>”。不再提供驳回。
- **自动生成优化建议**：反馈整理时没有用户登录，读不了知识包。整理完成后，只要有在 Hub 上能看到该知识包的用户打开评测页面（导航每 5 秒查询一次反馈，请求带上登录续期凭证），评测就用这个用户的登录在后台生成建议；判分模型用默认配置，与反馈归簇、改写问题相同。补充标准答案或标记误判后，该批建议自动重新生成。建议还在生成时也可以交付：记下交付请求，全部生成完后按收到先后自动交付，最新一批带上其余；生成中不能再改判，生成失败后可以再改判或重新生成。
- **建议拼接**：建模对每个版本和来源只保留最新一轮，较早的轮次会被新一轮盖住。因此一轮交给建模时（评测轮次生成报告时，反馈轮次负责人确认时），评测把同一来源、同一知识包版本中仍待建模处理的较早轮次一起带上：评测来源是同一用户、同一知识包同一版本的评测轮次，反馈来源是同一知识包同一版本已交付的反馈轮次。两种来源分开拼，不同版本也不拼，各自在建模对应版本下出现。
  - 不限轮数，同一版本所有待处理的较早轮次都带上。处理失败的轮次不带。
  - 从新到旧逐条判断，以最新结论为准：本轮或较新的轮次已有结论的问题不再带，只归因为运行异常的问题不带；建议条目只保留仍引用的问题并重新编号，用户建议去重。本轮全部通过时照样推送历史建议。
  - 历史问题接在报告「逐用例明细」后面、编号接着往下排，并注明来自哪一轮、何时交给建模；历史建议放在建议的「历史未处理建议」一节，不重新调用判分模型。总览、得分和通知中的统计只算本轮。文件超过大小上限（报告 8 MiB、建议 256 KiB，与建模接收的上限一致）时，从最早交给建模的一轮起少带，少带的保持待处理，报告头注明。没有待处理的历史时，文件与原来逐字节相同。
  - 建模回写本轮结果时，被带上的轮次一起记为同样的结果，注明“随某轮一起处理”。页面标出“这次一起带上…”、历史轮次的“已并入…”或“未能一起带上”，用户反馈页确认前提示之前交给建模、还没处理的反馈也会一起带上。建模侧不需要改动。
- **兼容**：开关关闭时接收接口返回 503，其余评测行为不变；`EVAL_NOTIFY_FEEDBACK_RUNS` 打开前不向建模发送反馈轮次的通知。配置项见 `.env.example`。

### 记录定位与交付内容

评测历史增加可复制编号、类型筛选和“正在查看”标记；已合并记录可按承接交付编号跳转。评测任务直接提供“新建数据评测”“新建求解验证”，并汇总历史失败及待处理交付入口。执行详情的“交付内容”与反馈交付详情的“全部交付内容”支持本轮、历史、全部范围切换，历史内容不计入本轮分数。

反馈确认交付前可以查看后端计算的预览；预览是当前状态的预计结果，其他待确认批次交付后可能进一步去重。最终以交付报告为准。反馈抽屉跟随最新轮次刷新，页签、筛选、分页和选中交付通过 URL 保存，浏览器返回可恢复。满分且没有历史待办时显示“无需优化”；建议生成、通知送达和建模处理分别展示，运行异常提示诊断。

### 评测前的对象关系校验

评测读取存量关系名称，不因名称包含对象名或写成 `1:N` 而拒绝；图导入保留关系类型原文，并使用带转义的 Cypher 引号。名称中的控制字符、反斜杠及超长值仍拒绝，对象名和字段名的标识符限制保持不变。

所有数据源模式在准备知识包时检查原始关系声明：缺失端点、同一对象文档内重复的完整关系身份、缺失或单边关联字段返回 `EVALUATION_PACKAGE_INVALID`（422），页面显示文件和行号，不创建评测轮次或导入数据。源对象和目标对象文档各声明一次的同一关系合并为一条。自关联允许；同源、同名、同目标但字段对不同的关系分别保留。没有物理表的概念对象可保留语义关系，其图导入跳过原因单独提示。

准备结果保存关系校验规则版本和知识包摘要；旧准备记录在重新使用或启动新轮次前补校验。执行时核对固定版本摘要并校验取回的包，再创建消费工作空间和导入。历史轮次与判分不重写；历史导出已经丢失的关系无法从缺失内容恢复，需要从原工作区重新导出。

查询型数据评测会分别校验答案内容和实际执行依据。编辑评测集时可选择自动识别、必须查询业务数据或纯规则推理；详细结果中可查看答案原判、执行核验和判分时保存的查询回执。没有必要查询不会因答案一致而通过；缺失或截断的轨迹显示无法核实，查询工具失败进入诊断。自动识别仅覆盖明确查数表述，复杂题请明确配置执行要求。历史结果不重算，执行依据问题不会自动生成知识包补答案建议。字段和兼容说明见 [API.md](API.md#查询题执行依据校验issue-382)。
