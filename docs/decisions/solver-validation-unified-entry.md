# 求解验证并入统一评测入口

## Context

求解适配要求求解契约在 consumer 中端到端跑通：Agent 调用对应的求解工具，入参与用例一致，得到权威结果。原先由建模发起这一验证，经 Modeling Workbench 的评测链路在 consumer 中执行，结论作为正式发布的门禁：当前契约修订没有通过且权威的验证记录，就不能发布到 Hub。

数据评测已经独立为 eval-service，只认 Hub 的固定版本：先发布，再评测，再优化。两条链路因此冲突：

- 端到端验证要在发布前通过，而评测只能在发布后进行，门禁形成死循环。
- 求解验证依赖已下线的旧评测链路。旧项目级数据源的增删改已返回 410，新项目只能选"不使用数据源"；Neo4j 场景按项目 ID 查图，而独立评测按 Hub 包 ID 导入，两者的隔离范围不一致。
- 入口不统一：求解验证在建模的求解面板，数据评测在评测页面。

取消发布前的端到端门禁后，发布前只剩静态检查。实测发现，建模检查全部通过的包，有 9 种情况会被 consumer 上游 common 分支拒绝导入：

- 对象数、Operation 数、对象属性行数、单个 Operation 字符数超过上限；
- 字段 key 重复，或同一字段名、字段别名指向多个字段；
- 对象 key 只差大小写，或对象文件名含 `|`。

另外，common 对求解契约问题不再拒绝导入，而是把操作标记为不可用，运行时才失败。

## Decision

- 求解验证与数据评测共用入口：在"已发布版本（知识包评测）"中点"评测"，打开独立评测页面，选择"求解验证集"执行，结果通知建模。两者的入口、时机和评测对象（同一个 Hub 正式版本）一致。
- 求解验证在 eval-service 中作为新的轮次类型执行，复用工作空间、包安装、数据源、并发、对账、登录续期和通知能力。判定用确定性断言，不走 Judge：
  - 是否调用了对应的求解工具；
  - 入参是否与用例一致；
  - 结果是否权威，是否有权威事件佐证；
  - 证据是否齐全，候选数是否符合期望。
- 正式发布取消端到端门禁，只受静态检查约束。启用了求解契约的项目发布时必须确认"求解能力尚未验证"，服务端同样强制。四处提示未验证状态：发布检查弹窗、发布成功提示、已发布版本列表、求解面板。
- 发布前增加结构自检：
  - 规则来源：建模侧保存 consumer 导入校验规则的副本，来源为 consumer 上游 common 分支，在 `PROVENANCE.md` 中记录提交号，由人工同步。两个仓库在远端各自独立，所以不做跨仓库的共享模块。
  - 执行时机：导出后、提交 Hub 前执行，不通过时不可降级发布。
  - 求解契约：由现有静态检查覆盖，与 common 的准入规则对齐。
- 契约修订摘要纳入数据绑定。它只用来提示"当前修改尚未发布和验证"，不再拦截发布。
- 方案只修改 onto-modeling 和 eval-service。consumer 只作为既有接口被调用，旧评测链路暂不下线，只关闭求解验证在建模侧的发起入口。

## Alternatives considered

- **保留建模侧发起**：仍依赖已下线的链路和旧数据源，Neo4j 隔离范围也不一致。
- **建模后端调用评测服务创建轮次**：违背"轮次由用户在评测页面创建"的边界，而且建模后端拿不到用户的 refresh token，长时轮次无法续期。
- **发布前先发 Hub 评测快照再验证**：要多出"快照"这个概念，两次评测分散在快照和正式版两个对象上，快照还会改写建模的 Hub 基线。
- **consumer 抽出校验函数供建模复用**：需要跨仓库协作和发布；副本可以在建模环境独立运行，代价是需要人工同步。
- **按整包摘要判断是否需要重新验证**：改任何文档都会触发提示，噪声过大。

## Consequences

- 未验证或验证未通过的求解版本可以进入 Hub，第一阶段只提示，不做下游限制。
- 规则副本可能与 consumer 漂移。同步时需要用真实上游跑对照测试；部署方调整了 consumer 的数量上限时，要同步设置建模的同名环境变量。
- 求解验证要求 Neo4j 业务数据源，这是 consumer 求解评估器的要求。
- 旧链路保留期间，求解断言存在两份实现，但旧入口已关闭，不会再被用户触发。
- 原先"未经端到端验证的求解包不能发布"的约定（onto-modeling ADR 0009 和 0011 中门禁相关的表述）随之变更。
