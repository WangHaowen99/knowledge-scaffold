# Neo4j 后台图导入采用协作式取消

## Context

Neo4j Excel 图导入在后台事务中分批写入节点和关系。任务启动后，页面刷新、用户主动放弃临时文件或删除项目都无法停止正在执行的写入，用户只能等待任务自然结束。

仅把数据库中的任务状态改为失败或已取消并不能停止 Neo4j 事务。若随后删除项目或重新执行导入，旧事务仍可能继续写入同一组 Workspace 与 Ontology 隔离数据。

## Decision

- 每个 modeling 进程为每个项目最多维护一个活动图导入任务，并为任务持有独立的 `AbortController`。
- 取消请求通过 `AbortSignal` 传递到 Neo4j writer；writer 在事务边界和每个批次前后检查信号。
- 任务运行中收到取消信号时关闭 session 和 driver，使当前 Neo4j 事务退出并回滚。
- 取消接口必须等待后台任务完成清理后再返回，随后把审计状态记录为 `cancelled`。
- 用户停止后台任务时保留临时 Excel 和映射，允许重新输入密码后再次执行；显式删除上传文件时先取消对应任务，再删除临时文件。
- 删除项目时先取消并等待活动图导入退出，再执行项目数据清理，避免删除完成后仍有旧事务写入。
- 活动任务登记只保存于当前进程内；服务重启时沿用既有恢复逻辑，把数据库中遗留的 `running` 任务标记为失败。

## Alternatives considered

- 只更新任务状态：实现简单，但不能停止真实 Neo4j 事务，审计状态会与外部写入状态不一致。
- 只在批次之间检查布尔标记：无法中断正在等待的数据库请求，取消响应时间取决于单次请求耗时。
- 为每个任务启动独立进程并强制终止：隔离更强，但会增加连接、进程管理和部署复杂度，当前单事务写入可通过驱动关闭可靠中断。
- 删除项目时继续返回忙碌冲突：不会产生并发写入风险，但把可由服务安全完成的清理转嫁给用户。

## Consequences

- 用户可以从图导入面板停止排队中或运行中的任务，并在历史记录中看到“已取消”。
- 取消响应会等待 Neo4j 会话和事务退出，可能受驱动关闭耗时影响，但返回后不会继续后台写入。
- 当前活动任务表是进程内状态；多实例部署需要保证同一项目的图导入和取消请求路由到同一实例，或在后续引入共享任务协调层。
- 取消不会持久化一次性 Neo4j 密码，失败与取消审计继续保持脱敏。
