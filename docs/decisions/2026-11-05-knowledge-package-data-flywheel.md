# 知识包数据飞轮：委托驱动的后台优化、发布与评测循环

- 日期：2026-11-05
- 状态：已实现（onto-modeling 飞轮、评测服务的委托接口；Hub 复用 MCP 发布已有的发布授权）

## Context

独立评测服务完成评测后，用户要手动导入优化建议、让建模助手修订、检查、发布，再回评测页面评测新版本，循环往复。数据飞轮要把这条链路按开关自动化，并满足三个约束：

1. 用户关掉页面后也要继续执行。但建模服务原本只在用户请求里拿得到登录，后台没有任何代表用户调用评测服务和 Hub 的凭据。
2. 不修改账号服务（auth-server）。它的刷新令牌不会因为刷新而作废，也不能单独作废某一个，只能整体吊销某个用户的全部令牌。
3. 自动化不能静默做不可逆的事：发布要通过全部检查；Neo4j 图导入会删除评测范围内的旧数据。

## Decision

- **两个开关，按用户和项目隔离。**「自动化处理优化建议」承接当前版本的评测建议，保存快照后让建模助手修订（`/ontology-evolution … --flywheel`），再执行发布检查。「自动化确认发布与发起评测」把通过检查的结果发布为 Hub 正式版本，再沿用触发本轮优化的评测配置评测新版本。仍有用例未通过时结果进入下一轮，全部判为通过（待人工判定不算）时停止；连续自动处理受 1/3/5 轮上限约束（默认 3 轮），也可选无限次，由用户自行承担每轮都发布正式版本的存储增长，全部通过或手动确认一次优化后重新计数。每轮都发正式版本，Hub 每个版本存一份完整包，不做增量。新版本发布后等待评测时，只有项目已有提交时间更晚的版本才跳过它的评测：同步时读到的关联还没更新、或关联留给定期维护补记，都不算有了更新的版本。评测中的运行可以随时“不再等待”（评测服务里的评测照常进行，结果到达后照常进入飞轮）；用户本人的登录也查不到的评测任务（如已在评测页面删除）转为可重新评测或跳过，不会一直停在评测中。
- **用户反馈也进入飞轮。** 包负责人在评测服务确认交给建模的消费反馈轮次（`notified`）建成运行。反馈常针对旧版本，所以不按版本过期，而是让助手以 `--flywheel-recheck` 先核对最新内容、只修仍存在的问题；反馈没有评测集，发布即结束，不进入评测循环，也不占轮数上限。只有助手写下“已全部解决”的结论才算已解决：没改文件也可能是条目要专家拍板或复检后回退，不能据此推断。核对后不需要修改时也要告诉评测服务，否则那一轮会一直停在“待建模处理”：回写接口为此新增结果 `resolved`（最新版本已解决，可带核对的版本），由用户本人的登录回写。为让后台也能处理，评测服务的委托可以读取该知识包中由委托人本人确认交给建模的反馈轮次（只读，其他反馈轮次与接口不变）。
- **用委托代替保存用户令牌。** 打开开关时，用户在场，用其登录向评测服务（读取本包评测结果）和 Hub（发布本包正式版本）各登记一次委托。句柄由建模生成，登记时交给评测服务，评测服务只存它的 SHA-256 摘要；登记前建模先把新句柄（Hub 的登记编号同样）记入待撤销列表，确认登记成功或明确被拒才移出，答复丢失或进程中断时这次登记照样会被撤销；结果不明的登记撤销之前不再重新登记，待撤销的登记不会越积越多；后台调用必须同时出示句柄和建模已有的服务凭据。Hub 复用 MCP 发布已有的发布授权（`/api/package-delegations`）：建模生成登记编号，用用户登录登记；后台每次请求 Hub 都现签一个授权头，用 Hub 服务凭据签名，绑定方法与路径，5 分钟内有效且只能用一次。两种委托都只能操作登记的知识包，离开建模的服务凭据都无用。关闭开关时委托立即停用并通知服务撤销；服务暂不可达时，委托只为重试撤销而保留，每 5 分钟重试，直到服务确认或委托在服务端到期：评测服务的在后台重试，避免继续为无人能用的委托续期登录；Hub 只接受用户本人的登录撤销，在用户下次打开项目时重试。有效期由用户选择（1/3/7/30 天或无限制，无限制按 3650 天登记），从最近一次访问起算：用户在场时两边都续期，Hub 用同一登记编号重新登记。只关发布开关而评测服务重新登记失败时，带着登录的旧登记同样停用并撤销。委托只给后台会代其执行的用户：项目未归档、用户凭自己的项目角色可以编辑。不是项目成员的管理员不登记（打开开关时页面说明原因）；项目被删除或归档、用户失去编辑权限后，后台撤销其委托，评测服务的凭句柄当即撤销，Hub 的等用户下次访问时撤销或到期失效。
- **后台评测的登录由评测服务保存。** 评测要以用户身份访问 Consumer 和 Hub，且一跑很久，所以打开发布开关时，浏览器经 `X-Refresh-Token` 把刷新令牌交给评测服务。评测服务用它换出一份本委托专用的刷新令牌，用 `EVAL_ENCRYPTION_KEY` 加密保存并定期续期；转交来的令牌不落盘，建模也不保存。销毁委托时删除这份登录。账号服务拒绝续期时删除登录，飞轮提示重新授权：账号服务退出登录时吊销该用户已签发的全部刷新令牌，所以用户在任一设备退出登录、改密码或账号被删除，都会让这份登录作废；读取评测结果、优化与发布的委托不受影响。
- **图数据替换按导入回执判断。** 评测服务在导入回执中记下导入后范围内数据的指纹（图快照）。重跑时先检查范围：数据与映射都没变且图未被改动时直接沿用；数据正是该用户某轮评测导入后的原样数据时自动替换；否则停下，由用户本人在飞轮里确认删除，委托不能代为确认。确认只删除提示时的那份数据：提示之后范围内数据又有变化时重新提示，按新的数量再确认。跨范围关系一律拒绝。
- **成员之间的飞轮不同时改动工作区。** 各成员的飞轮共用一个工作区：另一位成员的飞轮正在优化或发布时，不启动新的优化，也不发布、重新检查或回退；自动执行只是等其结束，不转为人工确认，建模助手正忙于对话时开始优化也一样。开始优化、发布从检查到记下本次状态，回退从检查到恢复内容，都在同一把锁里完成；重新检查和回退后发布恢复版本时的检查过程不在锁内，其间混入的别人的修改会让发布前复核停下。这样两次修订不会混进同一份快照和候选内容，飞轮不会发出别人改到一半的内容，也不会回退抹掉别人正在进行的修订；建模助手正在对话中时也不回退；中止只打断飞轮自己那一轮，那一轮已结束、助手在处理别人的对话时不中止，打断后助手仍在执行也不恢复快照，否则助手尚未提交的修改会被抹掉或写在恢复的内容上。回退与中止恢复快照时，项目元数据（成员、角色、归档）、运行状态与仓库配置保持当前值，与版本回退一致；网页发布页与 MCP 发布不受此约束（与之前相同）。优化中与发布中的运行一定会结束：后台为其就地收尾（结束本轮、检查结果、清理中断的发布都在本地，不带凭据，也不启动下一步），用户已离开项目、项目已归档或用户是非项目成员的管理员时也一样。对方等待确认发布的候选内容不拦，因为对方可能长期不来：在其上开始的优化会把它一并纳入新的候选内容（提示含此前未发布的修改）。
- **评测优化的回写只认该得的版本。** 项目只记最近一次评测优化，优化之后第一个算数的正式版本回写成它的处理结果。这个版本在记下 Hub 关联时就钉进记录，之后的发布、回退的恢复版本都不会顶替它（评测快照不算正式版本；本功能之前记下的关联没有发布人，仍按当前版本判断，此前已开始的待重试回写沿用当时的版本）。飞轮的优化还在修订时不回写，这期间记下的版本也不算，因为至多含一半修订（本地记账失败、修订结束后才补记的个别版本除外）；没能交给助手的优化按没有修改处理。修订因条目要人处理而没有修改知识包时，只有优化者本人此后发布的版本才算（可能是手工处理剩余条目后发布），别人发布的版本不算，为此 Hub 关联记下当前版本的发布人（定期维护只补记缺失的新版本，不重写当前版本）。由飞轮开始的优化已全部通过、最新版本已解决、被忽略或被中止，且还没有钉住版本时，记录清除；回退撤回快照之后的全部修改，还没有钉住版本的记录一并清除。写回只用优化者本人的登录，后台连续多轮时要等其下次访问：一次评测优化被下一次替换时，已钉住而还没写回的版本另行留存（最多 10 条），届时一并写回，不会被后一轮覆盖。
- **飞轮不代用户确认求解能力尚未验证。** 启用了求解契约的知识包，飞轮发布与网页发布同一规则：当前求解契约修订已在更早的版本通过求解验证时免确认；否则不创建发布请求，运行停在「求解能力尚未验证」，用户完成求解验证后重试，或在发布检查中确认后手动发布。
- 不新增部署变量，沿用现有的评测与 Hub 服务凭据。

## Alternatives considered

- **在建模服务保存用户的刷新令牌**：放弃。建模是用户最多、暴露面最大的服务，令牌落在这里，泄露影响面最大；委托句柄离开服务凭据就无用。
- **在账号服务增加可单独作废的服务令牌或账号存在性回调**：曾实现，后按决策撤回。代价是改动全局认证组件，而委托由开关控制生命周期已能满足需求。
- **后台评测只用页面上的短期登录**：放弃。access token 撑不到评测结束，页面关闭后就无法发起评测。
- **后台评测遇到图导入一律停下**：放弃。用图导入数据源时循环无法无人值守；改为只在数据被改动过时要求确认。
- **只发评测快照、通过后再发正式版本**：放弃。用户选择每轮都发正式版本，换取版本可追溯、评测对象与发布对象一致。
- **另一位成员有待发布候选时也不启动优化**：曾实现，后放弃。候选只在其本人同步时推进，对方关了自动发布后长期不来，或离开项目，会一直挡住其他成员的飞轮。
- **在 Hub 为飞轮另建一套委托接口**：曾实现，合入 MCP 发布后改为复用其发布授权，Hub 上不保留两套作用相同的授权。

## Consequences

- 页面关闭后飞轮继续运行；委托不随改密码失效，直到关闭开关或到期。这是已接受的取舍。
- 账号服务不能单独作废刷新令牌：评测服务保存的登录若在销毁前泄露，副本在其自身有效期内（最长一个刷新周期）仍然有效。用户退出登录或改密码会使其作废。
- 反过来，用户在任一设备退出登录都会让后台评测登录作废（账号服务只能吊销用户的全部刷新令牌）：此后新版本发布后要用户确认才评测，回到飞轮重新授权后恢复。这是已接受的限制，不为此改动账号服务。
- 每轮正式发布都在 Hub 新增一份完整包，存储随轮数线性增长；轮数上限限制了单次连续增长。
- 本功能上线前留下的图导入回执没有数据指纹，上线后第一轮图导入评测需要用户确认一次。
- 新增接口：评测服务 `/delegations`、`/delegations/current[/renewal]`、`/runs/{id}/reruns` 及三个可委托读取的接口；Hub 不新增接口。飞轮的 Hub 登记编号与 MCP 发布同一格式（`mcp-flywheel-…`）。
- 委托读取看不到消费反馈轮次（核对 Hub 可见性需要用户登录）：后台对账只替换评测轮次，评测优化处理结果的回写也留到用户本人访问时。
- 成员可以在别人未发布的候选内容上继续优化：之后原候选只要内容已变就不能直接发布，需要其本人重新检查；项目只记最近一次评测优化，原候选那一轮评测收不到回写；其本人此后回退那次运行，会把之后的修订一并撤出工作区（修订仍保留在迭代历史中）。
