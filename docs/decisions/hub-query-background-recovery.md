# Hub 列表读取与后台恢复

## 背景

包列表逐包读取全部发布请求，列表与版本查询还会在全局存储排他锁内恢复及检查全部归档，查询延迟随发布历史和文件规模增长。

## 决策

两个列表接口直接读取原子写入的元数据和已提交发布记录，不获取存储锁。一次收集记录后在内存中选取、排序、分页；包列表增加与摘要 `version` 相同的 `latest_release_version`，只有快照时取快照版本。

查询允许稍早结果，不保证跨文件或跨页事务快照。并发删除产生的文件缺失可跳过，损坏或不可读取的记录仍报存储错误。身份、授权、删除状态检查保留。

响应发送后通知独立维护线程，周期任务兜底。维护通过专用非阻塞文件锁合并跨进程任务，继续在原存储锁内运行恢复与完整性检查；存储锁忙时下轮重试。默认周期及冷却为 60 秒，可用 `HUB_MAINTENANCE_INTERVAL_SECONDS` 调整。后台异常只记录通用错误，不输出存储正文。启动恢复和其他接口行为保持不变。

## 考虑过的方案

- 缩小查询前检查范围：仍然让列表等待恢复和完整性检查。
- 查询共享读锁：可允许查询并发，但仍等待后台排他锁。
- 数据库事务或全量快照：提供更强一致性，超出当前接受稍早结果的需求。

## 后果

列表不再保证所列归档刚通过完整性检查，首次发布恢复前可能暂不可见。后台维护仍与写操作互斥；此次不解决写接口锁等待。现有文件布局仍要求扫描全部发布请求 JSON，无关记录损坏仍可能导致查询失败。

跨进程维护锁及冷却时间保存在数据根目录 `.maintenance.lock`，不属于知识包数据，不改变现有归档协议。
