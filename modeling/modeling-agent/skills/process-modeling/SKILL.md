# 业务流程建模

在项目唯一状态进入 `process` 后使用。这个阶段的主产物是 `diagrams/*.mmd`，目标是先让专家确认业务过程，再沿已确认流程抽取知识结构。

## 产物边界

- 只把资料支持的业务步骤、判断、输入和输出写入流程图。对象属性表、统一状态模型、规则全集属于后续知识建模，不得代替流程主产物。
- 一张图只表达一个可独立判断的过程或一个明确装置范围。跨装置共性与装置差异分开表达，不用一张“通用模板”掩盖差异。
- 每个文件对应一个 `change_group`；业务走向或判断用 `caliber`，纯图形结构整理用 `structural`。一次确认不超过 5 组。

## 证据与假设

- 每个关键步骤、判断或一组同源连线旁边写 Mermaid 注释：`%% evidence: material:<document id>#<锚点>`。document id 必须从 `list_documents` 原样复制。
- `write_file.evidence` 复用正文中的同一批 token。不要在正文直接写 `doc_...#锚点`，也不要用不存在的文件简称代替稳定 token。
- 多分区流程图至少要命中两个不同的原文位置；不能读取文档开头后，让原料、反应、分离、分馏和产品等全部分区共用 `offset=0`。先按关键设备或章节检索，使用实际命中位置；确实找不到的分区写“待定位”。
- 证据必须支持紧邻它的完整主张，不能只证明“对象存在”却拿来证明对象之间的物流，也不能用输入字段证明输出关系。遇到 `input`、`output`、`source`、`destination`、`from`、`to` 等方向字段，先读取表结构和对应行再决定箭头方向。
- 百分比、温度、压力、能力、罐号和质量指标等精确值，必须引用实际包含该值的表格或段落；只列出产品名称或用途的章节不能证明具体数值。找不到包含原值的锚点就删除精确值或标为待确认。
- 原文没有直接支持的连线不得画成已确认实线。需要保留时用虚线并在节点或边上明确写“待确认假设”，同时记录到项目开放问题。
- 专家选择稍后补充时，继续推进不依赖该答案的流程，但不得把缺口静默填成行业常识。

## Mermaid 约束

- 使用 `flowchart TD` 或 `flowchart LR`，节点 ID 只用 ASCII 字母、数字和下划线。
- 每条连线单独书写为 `A --> B` 或 `A -.->|待确认| B`，不要用一行多段链式连线，保证工作台可以逐节点渲染和高亮。
- 提交前重新读取文件，逐项复核“图中主张 → 紧邻证据 → 原文/表格实际字段”的方向和数值，再检查关键节点、分支标签、证据注释和未决标识完整；发现无法渲染或证据只能支持部分主张就先修复，不把问题交给专家。

## 确认前动作

1. 调用 `focus(kind='flow', target='<path>', node='<最需要判断的节点>')`，让中栏先展示该流程和分支。
2. 用 `request_confirmation` 提交对应流程图的变更组；摘要说明本轮能确认什么、哪些假设仍未决。
3. 只有所有流程图取得绑定修订的确认记录后，才尝试进入知识建模阶段。
