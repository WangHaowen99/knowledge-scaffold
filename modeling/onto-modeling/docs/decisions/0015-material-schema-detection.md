# 0015 表格资料按结构识别数据表，预填 schema 用途

## Context

`schema` 用途决定了对象「# 数据来源」能取哪些表名、属性英文名能用哪些列名，发布与评测的绑定
核对也只认它（见 0005、0007）。但用途完全靠用户手动选，默认是「由助手判断」：

- 用户常常不知道要把样例库表标成 `schema`，结果建模时 `TABLE_HEADERS` 为空，对象来源全填
  「无」，助手只能反过来问专家，还会让专家去手改平台维护的 `materials.json`；
- 也有把术语表、知识清单这类文档表格误标成 `schema` 的情况，它们的中文表头会被当成列名。

判断一份表格是不是「数据库表样例」是结构问题，不需要业务理解，交给模型既慢又不稳定，而模型
本来也不得修改 `materials.json`。

## Decision

- 新增 `services/material_detect.py`：逐 Sheet 只看前 30 行的结构。首行列名不重复、无合并
  单元格、英文标识符占比 ≥80% 判为数据表，50%～80% 为疑似；表头同时出现「字段名」类和
  「类型/说明」类词的是数据字典；`__说明__`、`总览` 等说明页忽略。全部有内容的 Sheet 都是
  数据表或疑似、且至少一张数据表，整份才判为数据表。按（路径、修改时间、大小）缓存。
- 上传时用户没指定用途（`auto`）且该路径没有人工标注：判为数据表就写
  `{"purpose": "schema", "auto_detected": true}`，上传接口返回 `detected`；替换文件时只重判
  此前自动标注的条目，判定不再成立就撤掉。用户在资料区改用途即覆盖（`auto_detected` 随之消失）。
- `GET /resource-meta` 增加 `schema_candidates`：用途仍是「由助手判断」、结构判为数据表的
  存量资料，资料区显示「疑似数据表 · 设为 Schema」一键标注。
- 工作区规则：没有 `schema` 资料但有像数据表的表格时，请用户在资料区标注，不再让用户编辑
  `materials.json`；聊天附件上传后告知助手哪些文件已自动标为 `schema`。

## Alternatives considered

- 让模型判断并标注：结果不稳定，且与「`materials.json` 平台维护、模型只读」冲突。
- 识别后只提示、不预填：新上传的样例库表仍然大量漏标，回到原问题。
- 对所有表格（含人工标过的）强制按识别结果改：会覆盖用户的明确选择，放弃。

## Consequences

- 首行是英文列名的样例库表上传即可参与建模约束与发布核对，无需用户理解用途体系。
- 首行是中文列名的真实数据表不会自动标注（判为文档或疑似），仍需人工选择；这是有意偏保守：
  错标会让文档表头变成硬约束，比漏标更难发现。
- 识别只用 openpyxl 读取前若干行，大文件（>8 MB）跳过合并单元格检查。
