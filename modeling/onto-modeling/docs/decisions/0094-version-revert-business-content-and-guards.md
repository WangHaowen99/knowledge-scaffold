# 0094 版本回退只恢复业务内容，并在有人在改时挡住

## Context

**目标**：用户（或经 MCP 的外部 Agent）把项目退回到某个版本时，得到的正是那个版本的业务内容，作为一个新版本留下；
不丢任何人手上还没保存的东西，也不把别人的半成品带进回退提交。成功标准：

- 回退后知识包、资料、能力锁和目标版本一致，项目名、所有者、仓库配置、运行状态保持现在的；
- 助手在跑、有积压消息、自主构建在跑、Studio 有草稿、主线有没提交的改动时回退不发生，界面和 MCP 都说清原因；
- 预览之后主线前进了，按旧预览执行的回退被拒绝；
- MCP 回退要先预览再确认，确认凭据只对发起预览的那个 Token、那个用户、那个项目有效。

**现状（本分支）**：V-06 经写入事务整树恢复，范围是目标版本与 HEAD 之间不同的路径（只排除元数据与工具状态）；
写入范围锁（助手这一轮没结束、合入冲突）回 423，自主构建回 409；`.gitignore` 跟着回退；没有 `expected_head`；
主线上没提交的改动不挡，只是不带进提交。develop（!567、!570）的做法：只恢复业务内容、五类情况挡住、回退后回收会话并作废续接点、
删掉 `.ontology-state` 里的派生回执、MCP 三个版本工具加进程内预览凭据。

**基本约束**

1. 回退是破坏性操作，入口有两个：网页（所有者）和 MCP（所有者签发的 Token，外部 Agent 发起，输入不可信）。
2. 主线是唯一真相；助手在副本里改（方案 C7），每轮结束合入主线。
3. 派生文件（目录 `index.md`、脚本描述符）由写入事务按改动重新生成（方案 C6）。
4. 验收回执绑定内容指纹（`research_review`：输入一变回执立即失效），存放在不进 git 的 `.ontology-state/`。
5. 会话池是全局的，一把 `asyncio.Lock` 管所有项目的会话绑定。

## Decision

1. **恢复范围 = 业务内容**（`workspace/versions.py` 的 `rollback_managed`，预览、执行、未提交改动检查同一口径）：
   排除 `.git*`、`.claude`、`CLAUDE.md`、`README.md`、`tmp`、`.ontology-state`、项目元数据、`.onto/run/`，以及
   `INDEX_DIRS` 下的 `index.md`。依据：仓库配置和助手装配不是用户的内容，跟着回退会把忽略规则、装配链接退回旧样子；
   `index.md` 是投影，单独算改动会出现「只差索引也能回退」的空版本，写入事务会按恢复后的文件重新生成。
   **资料（`resource/`）随回退恢复**：它是知识包的输入，且每次上传、删除、改用途都是独立版本，回退到某版本就该看到当时的资料；
   与 develop、详设「整树恢复」一致（主控 11-11 裁定）。
2. **挡住回退的情况**（`services/version_revert.blockers`，提示文字照 develop）：助手在跑或排队（`session_busy`，
   会话池 `workspace_busy`）、Studio 有暂存草稿（`studio_draft_pending`）、主线有没提交或暂存的业务改动（`workspace_dirty`），
   另有本分支独有的写入范围锁（423）与自主构建在跑（`autobuild_running`）。暂存了不随回退的路径（元数据等）时执行也拒绝。
   V-05 全部列出（`ready`、`blockers`），V-06 取第一条报错。develop 还挡「数据评测在跑」「求解验证在跑」：本分支这两种运行
   已移到评测服务，没有可查的状态，不挡。依据：有人正在改时回退会和它交错；草稿的 `base_revision` 指向回退前的内容；
   没提交的改动在被恢复的路径上会被覆盖。插件化分支早先「不挡、只是不带进提交」的做法因此改掉（`test_writepath` 对应用例）。
3. **两次检查 + 会话锁**：V-06 先在会话锁里查一遍（锁住期间不会绑定新的一轮），再在写入事务的项目锁里经 `busy_check` 查一遍，
   之后才动文件。`expected_head` 与 `V-05` 的同名字段对上才执行，否则 `head_moved`。
4. **执行**：先删目标版本之后才有的路径、再从目标版本写回（文件与目录互换时顺序反了会写进去又删掉）；用 `git restore --worktree`
   只写工作区，提交仍由写入事务用临时索引做；符号链接不跟随（写入事务新增 `touch_tracked`）；失败时按 HEAD 复原再由事务按快照恢复。
5. **回退之后**：回收该项目的助手会话（默认原因，同 develop）、清空积压消息、全部对话续接点作废；删掉 `.ontology-state` 里由回退前
   内容得出的派生状态（eval、progress、research-*、script-verifications、solver-validations、artifact-reviews、studio-review），
   删不掉时结果带 `warning`。依据：模型上下文和这些结论都还是回退前的内容。
6. **提交说明**照 develop：「revert: 回退到版本 N（短提交号）」，N 用主线版本号（即界面上的「迭代 N」）。
7. **MCP**：`list_project_versions`（版本号即界面 `v0.N` 的 N，游标绑定主线版本）、`preview_project_version_revert`
   （给 `preview_id`，绑定项目、Token、用户、目标版本、预览时主线版本，十分钟过期）、`revert_project_version`（`confirm: true`，
   执行过的一小时内重放返回同一结果）。凭据只在进程内存，重启作废，不把待执行的破坏性操作落盘。错误码沿用 develop 的大写码。
8. **历史时间线**（第二轮对齐 develop）：移植 `version_history.py`，`GET /api/v1/projects/{id}/history` 把迭代与 Hub 发布版本
   按时间合并分页，Hub 失败时带 `release_error`、之后的页不再读 Hub，没有统一账号时只列迭代。版本页左栏按 develop 的「历史」页签
   列出：「迭代 N」「发布版本 X」、发布行的「下载」「评测」、迭代行的「标记」「回退到此版本」，回退与标记的提示、确认框文字照 develop。
   `Version.release`（V-01）仍取发布记录，给发布页的版本下拉用。

## Alternatives considered

- **资料不随回退**：回退只退知识包，资料保持最新。回退之后报告、对象和资料对不上，「资料变了要刷新」的提示会一直亮；且与 develop、详设不一致。不采用。
- **只挡与回退路径相交的未提交改动**：保留原来「无关改动不挡」的行为。与 develop 不一致；不相交的未提交文件仍会被目录索引收进回退提交里引用。不采用。
- **派生回执按指纹自己失效、不删**（第一轮的做法）：回退没动到的回执仍有效。与 develop 不一致，第二轮改回删除。
- **按项目设「回退中」标记、不占全局会话锁**：回退期间别的项目也能开新的一轮。要改会话池的发送路径（另一子任务的文件），收益是回退那几秒里别的项目不排队。暂不采用，见代价。
- **预览凭据落盘**：重启后还能确认。等于把待执行的破坏性操作存进项目，过期清理和权限变化都要跟着处理。不采用，与 develop 同。

## Consequences

- 代价：回退持全局会话锁期间（git 恢复与提交，通常一两秒），所有项目的新一轮要等它结束；git 卡住时由 `_run_git` 的 60 秒超时兜底。
- 代价：Studio 留下的旧草稿会挡住回退，要先去保存或放弃（提示照 develop，不给去处）。
- 代价：回退后验收回执等派生状态清空，资料分析的验收、脚本核验要重新跑。
- 代价：回退后对话的模型上下文清空，用户下一条消息要重新交代背景。
- MCP 版本工具与 `project.version.revert` scope 的登记依赖知识包 Hub 底座对 `onto_mcp/tokens.py` 的改动，见契约变更记录。
