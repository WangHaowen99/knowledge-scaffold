# 0088 空闲回收不打断等你回复的那一步

## Context

**目标**：会话空闲回收只是平台省内存的手段，用户应当感觉不到。命令停下来等用户回复（助手在对话里问了「要处理哪些，回复全部或编号」），
用户想了十几分钟再回，回来应当照常接着做，不该看到「上次没做完：校验在『等你确认』中断」的卡、还要点「继续」或「按新版重新做」。

**现状**：`_recycle` 把这条对话里还开着的执行一律记为中断（原因 recycled）、放续跑卡。端到端验证里，校验的语义检查用文字问用户，
空闲回收（默认 600 秒）后用户回来看到的就是中断卡。

**基本约束**

1. 回收后续接靠续接点（稳定引擎 native resume，内测引擎 replay），上下文能恢复。
2. 执行记录「等待」表示这一轮已经正常结束、命令停着等下一句；下一条普通消息由 `turns.begin` 接着这份执行（`continue_running`）。
3. 命令锁的持有者是引擎实例；回收后新实例拿锁时，旧持有者已不在，`state_helper acquire` 直接接过，不会冲突。
4. 开着确认卡的会话不回收：`_recyclable` 和 `_busy` 都排除有待确认请求的会话（空闲回收、池满驱逐、切换对话都不碰它），
   确认卡挂在引擎进程里，回收会让它失效。
5. 停机、服务重启的中断语义不变（启动扫描把所有开着的执行改判为「服务重启中断」）。

## Decision

- 回收原因是 recycled（空闲回收、池满驱逐、切换对话、运维手动回收）时，执行记录是「等待」的不动：不记中断、不放续跑卡。
  依据约束 1～3：回收前后对这份执行没有区别，下一条消息照常接上。
- 执行还在跑（不是「等待」）时被回收（只有运维手动回收会遇到），照旧记中断、放续跑卡。
- 删除对话时照旧中断（对话没了，执行不该一直等着）。
- 开着确认卡时不新增机制：约束 4 已经保证它不被回收，回答照常交给助手。

## Alternatives considered

- **回收时把「等待」的执行也记中断，界面把 recycled 原因的续跑卡藏起来**：执行状态和用户看到的不一致，待处理和建议条还会按「中断」走。
- **等回复的会话不回收**：最省事，但用户可能一去不回，空闲进程一直占着会话池的槽位（每个几百 MB），池满时别的项目排队。
- **开着确认卡也允许回收、回答时把答复转成一条消息发给助手**：能多回收一些内存，但要在进程外保存问题、改回答接口和孤儿问题清理，
  改动大、主链路风险高；确认卡通常很快就答，收益小。

## Consequences

- 用户想多久再回复都行，回来照常接着做；对话里不再出现因空闲回收而来的中断卡。
- 切换到另一条对话再切回来，原来那条对话里等回复的命令也还在等，不再被记成中断。
- **最强的反对理由**：续接点恢复失败（续接 token 失效、内测引擎回放截断）时，助手可能记不清自己在等什么。原来的中断卡至少让用户
  知道「这一步断了」。缓解：执行记录仍是「等待」、命令锁还在，助手续上后查锁（`check-lock` 得到 stale 或 own）会按命令模板的
  恢复步骤接着做；建议条在这时给「『xx』在等你回复上面的问题」，用户知道该回什么。
- 开着确认卡的会话照旧占着引擎进程，直到回答或打断。
