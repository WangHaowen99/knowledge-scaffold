# 0012 规则与指标按分类分流：提取阶段直接落到各自目录

## Context

资料分析报告的 `# 核心业务逻辑候选` 段没有类型边界：规则和操作混在一起列加粗候选名，
`extract-operation-agent` 按加粗名全量提取（它的候选来源还包括"小节标题"和"动宾短语"，
而规则名天然是动宾短语），于是规则被逐条写成 `ontology/operation/*.md`。

后果是：报告的 `# 分类小计` 明明已经把条目分成了对象、规则、操作，落盘时规则却全部
进了 `ontology/operation/`，`ontology/rule/` 与 `ontology/metric/` 为空——报告自己分好了类，
却没有任何一环拿这份分类去分流。

放错目录不是整洁问题。实体类型由所在目录决定（`ontology_checker.load_ontology`），
而 `backend/app/services/package_archive.py` 按目录映射发布包
（`ontology/operation` → `operations`、`ontology/rule` → `rules`），
`backend/app/services/studio.py` 同样按目录建图谱节点。规则留在 operation 目录，
就会以「操作」的身份进入知识包和图谱，五元组（ADR-0004）整条链路失真。

原有的 `/ontology-extract-rule-metric` 是可选增强阶段，输入是**已落盘的 operation 文档**
与 object 属性规则列——也就是说"规则先寄生在 operation、之后再升格"本来就是既定数据流，
与"按类型直接分目录"的预期相反。

同时没有任何一处检查反验内容与目录是否匹配：`ontology_scope_guard.sh` 只拦 `ontology/`
下的自创目录，operation/rule/metric 都在白名单；`ontology_checker.py` 对 operation 目录
只查 operation 必填段落，规则只要按 operation 模板写就静默通过。

## Decision

1. **分类成为报告的一等信息。** `# 业务项清单` 新增「分类」列，取值枚举
   `对象 / 操作 / 规则 / 指标`；候选段按分类分家为四段（新增 `# 核心规则候选`、
   `# 核心指标候选`）。判据措辞与 `rule-metric-extraction-agent.md` 同一口径，不写两套。
2. **分类纳入确定性对账。** `research_checker.py` 新增 `_check_categories`：分类取值合法，
   候选段归属与清单分类**双向**逐项一致（候选必须在清单里有分类，清单项也必须出现在它
   那一类的候选段里）；`分类小计` 从"只校验总和"改为按分类逐类对账。
3. **提取阶段按分类分流。** `/ontology-extract-operation` 新增 Step 1.6 把候选拆成
   操作 / 规则 / 指标三组：操作组交 `extract-operation-agent`（报告来源的操作从此只认
   `OPERATION_CANDIDATES`，不再自行从小节标题和动宾短语里找，文件名逐字使用报告名称）；
   规则与指标组交 `rule-metric-extraction-agent` 的新 `SOURCE_MODE=report`，按 rule/metric
   模板直接写入 `ontology/rule/`、`ontology/metric/`，**不经过 operation 文档中转**。
   提交范围随之扩为三个目录。拆分由 `report_reconcile.py plan` 确定性完成，不让模型读表。
4. **补一条确定性门禁。** `ontology_checker.py` 新增「目录归属」检查（错误级，
   `pre_commit_check.sh` 据此阻止提交），两条判据都不靠猜：
   报告清单对这个文件名声明的分类，或文档自身就是 rule/metric 模板的段落集。
   名字只是"少了规则/指标后缀"（报告里有「XX规则」，operation 目录下有「XX」）的
   只给**警告**、不拦提交：它可能是提取时丢了后缀的规则，也可能是流程图来源的同名
   操作，检查器分不出来，判成错误会把后一种正常文档挡在提交之外。除此之外不按文件名
   反推类型；命名约束放在生成侧的 agent 指令里。
   提交钩子的暂存筛选**不含** `ontology/rule` 与 `ontology/metric`，与本 ADR 之前一致。
   从知识包导入的规则、指标是知识包契约的格式（规则内容 / 判断条件 / 知识证据，业务口径 /
   计算边界 / 空值策略 / 维度 / 知识证据），与工具箱模板不同，结构检查会把它们整篇判为
   缺章节。分流写出的规则、指标由 `/ontology-validate` 检查。
5. **`/ontology-extract-rule-metric` 保留**，定位改为"从存量 operation 文档与 object
   属性规则列补抽"（`SOURCE_MODE=workspace`）。纯流程图来源的项目没有报告分类，
   仍然走这条路。
6. **阶段判定不动。** `逻辑已提取` 继续以 operation 目录为准。若某轮只产出规则/指标，
   命令明确告知阶段仍停在「对象已提取」——codegen / trace / validate 都依赖 operation
   文档，放行到空目录只会把问题推后。
7. **增量与重做按"生成得回来"划界。** 命令同时产出 operation / rule / metric。增量把
   `ontology/rule|metric` 下已有的文件名作为 `EXISTING_FILES` 传给
   `rule-metric-extraction-agent`，已存在的不重新生成（校验阶段修过的规则不会被覆盖）。
   重做总是清空 `ontology/operation/`；规则与指标目录只在本轮用了调研报告时才清空——
   这时规则与指标以报告为准，清掉才不会留下报告里已经没有的旧规则。本轮没用报告时
   这两个目录一律保留：里面的文档可能是从知识包导入的，也可能是补抽的，本轮都生成
   不回来。
8. **流程图与报告结合时：报告条目全部落地，流程图可以补充，差异必须有来源。**
   报告只对自己的条目负责，流程图里有、报告没收录的流程照常生成操作——只认报告会丢掉
   流程图，而只认流程图又回到"规则被写成操作"的老问题。为了不让"生成的与报告不一致"
   悄无声息地发生，提取前后各对一次账（`scripts/report_reconcile.py`，只比名称与分类）：
   - `plan`（提取前）：同名的流程图与报告操作合成一份；报告没收录的流程图作为补充；
     流程图与报告里的规则 / 指标 / 对象重名的，由用户在提取前决定改报告、改名生成或
     不单独成文，而不是等到提交时被目录归属检查拦下。
   - `check`（提取后）：报告里有、没生成的；生成在错误目录的；生成了、报告里没有的
     （标明来自流程图，或本轮没动的已有文档如知识包导入的规则）。每一处差异要么处理掉，
     要么由用户逐条确认原因，确认的原因写进提交说明；未处理也未确认的不进提交。
   名字不同但实为同一流程的，由逻辑提取 agent 并入报告里的操作并在「合并」一栏写明，
   对账会列出"没有同名操作文档的流程图"供核对。

## Alternatives considered

- **只在提取侧用启发式分流**（名称以「规则」结尾、规则 ID 前缀为 `RULE-`）：不可靠。
  报告模板不限制哪一类条目能填规则 ID，操作行同样可以填，前缀区分不了规则与操作；
  而且判据会与
  `rule-metric-extraction-agent` 的既有口径各写一份。
- **保持"先写 operation 再升格"**，只是把 `/ontology-extract-rule-metric` 改成自动调用：
  复用现成 agent 最省事，但抽完 operation 目录里的原文档还得人工删，且在升格之前
  发布出去的知识包仍是错的。
- **新字段设为可选、不打回存量报告**：分类信息可缺失，分流只能退回启发式，等于把
  根因留在原地。既然失效方向只向不放行（ADR-0011），宁可让分类错误的报告重做。
- **把 rule/metric 纳入 `STAGE_ORDER`**：会让依赖 operation 的命令在没有操作文档时
  被放行，换一个更难查的问题。
- **把规则、指标纳入提交钩子**：曾经这样做过。从知识包导入的项目里，规则、指标整篇
  不符合工具箱模板，任何改到它们的提交都会被拦，报错还会引导把文档改写成工具箱模板，
  离知识包契约更远。两套格式的对齐另行处理，不在本 ADR 范围内。
- **重做总是清空三个目录**：曾经这样做过。从知识包导入、没有调研报告的项目会因此丢掉
  全部规则与指标，提取流程又生成不回来。
- **两者结合时只认报告的操作名单**：曾经这样写过（名单被称为"本次要提取的操作全集"）。
  流程图里有、报告没收录的流程会被漏提，而且没有任何检查能发现。
- **两者结合时严格一致**（流程图独有的流程先补进报告再生成）：数量天然一致，但按推荐顺序
  （调研 → 流程图 → 提取）走的项目，画完流程图后每次都要多做一轮追加调研。没有采用，
  改为允许流程图补充、由对账标明来源。

## Consequences

- 存量报告缺「分类」列与两个候选段，会被判结构缺失、退回「调研待核验」，需重跑调研。
  检查项变了，`research_review.CHECKER_VERSION` 随之升到 2：存量回执按「检查器已升级」
  一并失效，而不是继续沿用旧结论——方向只向不放行。回执的输入指纹只覆盖报告与源资料，
  不覆盖检查器本身，所以检查项增减必须靠版本号让旧回执失效。
- 存量项目里已经误放的文档，在迁到 `ontology/rule|metric` 之前，提交会被 pre-commit 拦下。
  修法是重跑 `/ontology-extract-operation`（重做），不提供一次性迁移脚本。
- 门禁对存量误放的生效时机取决于报告：旧报告没有分类列时判据一失效，而误放文档通常
  是按 operation 模板写的、判据二也不命中，因此在重跑调研产出带分类列的新报告之前，
  这些文档不会被拦。报告带上分类列之后，名字完全对上的报错误，丢掉「规则」后缀的
  改名形态报警告；两种情形都由 `backend/tests/test_entity_placement.py` 的合成用例覆盖。
- 分流写出的规则、指标文档提交时不做结构检查，结构问题要到 `/ontology-validate` 才会
  发现。`/ontology-validate` 对从知识包导入的规则、指标会照常报结构缺失，这一点本 ADR
  之前就存在，未改动。
- 覆盖率检查按类型分别统计（`CHECK_TYPE` 支持 `operation,rule,metric` 组合），
  规则不再计入操作覆盖率的分母；同名文档出现在错误目录时按未覆盖报出。
- 前端与项目进度无需改动：`LeftPane.jsx` 的「规则与指标（可选）」阶段与
  `WorkspaceManager.STAGES` 本来就是 `ontology/rule|metric` 目录探针，分流后自动点亮。
- `ontology/rule/`、`ontology/metric/` 的文档结构校验沿用既有的
  `RULE_REQUIRED_SECTIONS` / `METRIC_REQUIRED_SECTIONS`，没有新增校验口径。
- 用了调研报告的逻辑提取，生成结果与报告仍可能不完全相同（流程图补充、用户确认不生成的
  条目），但每一处差异都出现在对账结果和提交说明里。对账只在逻辑提取命令里做，不进提交
  钩子：校验、更新等其它流程的提交不受它影响。
- 对账按名称比对：报告来源的条目改了名字就会被报成"报告里有、没生成"加"来源不明的新增
  文档"，需要用户处理——这是有意的，名字是对账的唯一锚点。
- "本轮改动"靠 `git status` 判断；工作区不是 git 仓库、或不是仓库根目录时，所有报告外的
  文档都按本轮改动处理，宁可多报。

## 本轮不覆盖的范围

- `/ontology-overview` 的整体视图仍只统计对象与操作，没有把规则/指标画进关系图。
- 既有项目的误放文档不做自动迁移，也不自动重写成 rule/metric 模板。
- object 侧的候选提取（`extract-objects-agent`）未改：对象候选段本身没有混类问题，
  只是现在多了一层报告侧的分类对账。
