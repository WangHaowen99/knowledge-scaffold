# 0088 配额按成本口径计：缓存读按 1/10，默认值按一整轮建模定

## Context

**目标**：配额（ADR-0043）是成本护栏。管理员按 token 设上限，用户在上限内能把一个项目建完；超出时拦下的是真花了钱的用量。
成功标准：一个完整建模流程（资料分析、对象、操作、校验、场景模拟、发布）在默认配额下一天内能走完；同样的花费，计入配额的数也大致相同，
不因对话长短差出几倍。

**现状**：台账按「输入 + 缓存读 + 输出」计。端到端验证实测（合成门店补货场景，内测与稳定引擎同一模型）：一整轮建模原口径约 1650 万
token，其中约 1594 万是缓存读；资料分析加两轮提取就用了 326 万，默认每人每天 200 万挡在第三轮。

**基本约束**

1. 缓存命中的单价约是输入的十分之一（各家定价大体如此），缓存写约等于输入；输出贵，但输出量远小于输入。
2. 台账从会话历史增量入账，已入账的是聚合后的数，拆不回各分项。
3. 项目用量（P-16）、运维用量图、时间线里的 token 是给人看「用了多少」的原始数，口径不能悄悄变。
4. 自主构建不另设预算上限（F6），运行中每一步走同一道配额检查；它记的用量要和配额同口径，否则界面上「用了多少」和「还剩多少」对不上。
5. 配额出错放行（ADR-0043）。

## Decision

**推导**

- 约束 1：计入配额的数要跟成本同比例。最简单、跨模型都站得住的折算是「输入 + 缓存写 + 输出 + 缓存读 // 10」：缓存读按单价比例折算，
  其余按 1 计。输出不乘倍数——按单价加权要随模型变，管理员拿 token 上限和供应商账单对账时也更难解释。
- 约束 2：口径变了，旧台账的聚合数没法换算，只能从会话历史重建。台账记一个口径版本（`meta.counting`），对不上时清掉用量、去重指纹和
  读取位置，下次同步从头入账（台账本来只管本月和上月）。
- 约束 3：只改限额用的计数（`quota._usage_of`）和自主构建记的用量（`model_pricing.tokens_of`，约束 4），展示用的原始数不动。
- 默认值：实测一整轮建模折算后约 215 万。每人每天 1000 万（约四到五轮完整建模，或一轮建模加反复的校验与修改），每项目每月 1 亿
  （按每天一轮、一个月的工作量）。

**做法**

1. `model_pricing.tokens_of`：成本口径的计数；`quota._usage_of` 用它。
2. 台账加 `meta` 表记口径版本 `cost-v1`，打开库时核对，不一致就重建。
3. `PER_USER_DEFAULTS.daily_tokens = 10_000_000`，`PER_PROJECT_DEFAULTS.monthly_tokens = 100_000_000`；已在系统设置里改过的值不动。
4. 系统设置配额页在「每日 token 预算」下写一行「缓存命中按 1/10 计」，只这一处。

## Alternatives considered

- **只调大默认值，口径不变**：改动最小。但计数和花费不成比例：同样一轮建模，对话越长缓存读越多，计入的数能差出几倍；管理员设的上限
  拦的是「对话长」而不是「花得多」。
- **按单价表加权**（输入、输出、缓存各按模型单价折算成金额，配额按金额）：最准。但单价表（SY-18）可以没配，配了也按模型变，
  管理员设「每天多少钱」又要另一套界面；现在先用 token 口径，单价表落地后再议。
- **缓存读不计**：缓存读不是零成本，长对话会被低估。

## Consequences

- 升级后第一次同步会从会话历史重建本月和上月的台账；**已删除项目的用量随之丢掉**（会话历史跟项目一起删了），当天删项目再建的人
  能多用一点。代价小于继续沿用放大近十倍的旧数。
- 自主构建运行页的「已用 token」变成成本口径，比原来小；项目用量、运维用量图仍是原始数，两边数字不同是口径不同，不是漏记。
- **最强的反对理由**：1/10 是近似，个别供应商缓存读折扣是 1/2 或没有折扣。那时这个口径会低估成本；管理员可以把上限调低，或等单价表接入后
  按金额管。
- 输出不加权，输出很多的任务（比如生成大量测试数据）计入偏少；输出量在建模里远小于输入，可以接受。
