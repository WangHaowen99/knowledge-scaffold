# 0016 资料用途与阅读方式改由平台判定，上传时不再让用户选择

## Context

0015 之后，上传表单仍要求用户为每份资料选「用途」（由助手判断 / 建模目标依据 / 数据 Schema /
术语表 / 通用业务依据）和是否「全文精读」。逐项看这些选择的作用与信息来源：

- 数据 Schema、术语表：决定表名列名、命名别名的依据，信息在表格结构里，程序能判断；
- 建模目标依据：确认分析主题时优先引用，哪份文档在说明场景与目标，读内容即可判断；
- 通用业务依据：与「由助手判断」没有实质区别；
- 全文精读：是阅读成本与注意力的取舍，用户无从判断，应由资料类型与篇幅决定。

让用户选的代价：新建任务要对每份资料做两项选择，用户分不清各用途的差别；错标成 Schema 会把
文档表头变成硬约束，漏标又让提取无表头可依，两者都要到提取或发布时才暴露；用途作为内部概念
还会漏进助手对用户的提问（如「某文件在 materials.json 未标 purpose=term，怎么处理」）。

原则：只向用户要只有用户知道、且会改变结果的信息。资料用途可由内容推断，不属于这类信息。

## Decision

- 新建任务页不再显示逐个资料的「用途」与「全文精读」选择，上传一律按「由助手判断」提交；
  资料区保留用途下拉，用于查看和修改识别结果，去掉「全文精读」勾选。
- `material_detect` 增加术语表识别：表头同时出现「术语」类列与「别名 / 英文 / 释义」类列
  （单独的「名称」列不算）判为术语表；全部有内容的 Sheet 都是术语表时整份预填 `term` 并记
  `auto_detected`。新增 `detect_material` 统一返回识别出的用途，`detect_data_table` 保留给
  资料区的「疑似数据表」候选。
- 阅读方式由平台规则决定（工作区规则 8.1）：条目显式写了 `reading_mode` 时照旧；没写时文档类
  资料全文读取，篇幅过长时可按需检索并在报告注明，表格、图片、流程图按需检索。
- 没有 `goal` 标注时，资料分析从文档类资料中找出说明场景、目标或范围的文档优先引用并注明来源。

## Alternatives considered

- 保留上传时选择、只改默认值：用户仍要面对一组不理解的选项，错标问题不变。
- 把用途识别全部交给模型并写回清单：结果不稳定，且与「`materials.json` 平台维护、模型只读」
  冲突；表格结构类判断交给程序更可靠。
- 同时取消资料区的用途修改：识别会有漏判（如中文列名的数据表），需要保留人工修正入口。

## Consequences

- 新建任务只需上传资料、填写名称与目标说明；数据表、术语表上传即被识别并显示「自动识别」。
- 存量项目里人工标注的用途与 `reading_mode` 继续生效，接口保持兼容（上传与修改接口仍接受
  `purpose`、`reading_mode` 参数）。
- 首行是中文列名的数据表、混合了多种内容的表格不会自动预填，需要时在资料区修改。
- 新建任务填写的「目标说明」目前只用于项目卡片展示，不传给助手；作为后续改进，可在会话开始时
  一并告知助手，替代「建模目标依据」标注。
