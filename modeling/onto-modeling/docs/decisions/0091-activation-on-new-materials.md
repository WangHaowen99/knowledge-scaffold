# 0091 包的节点按事件触发：增量构建在上传新资料时出现

## Context

**目标**：启用了增量构建的项目，从 0 建模或者没传新资料时不受任何影响；已经建了一部分又上传新资料时，自动进入「圈定范围 → 范围内修改 → 传播核对」。
包作者要能在包定义里写清楚触发条件。成功标准：触发规则在 `flow.yaml` 里看得到、能静态检查；没触发时不挡发布、不限修改。

**基本约束**

1. 包代码不在内核里跑（ADR-0083 约束 4），包不能带判断脚本。
2. 助手的输出不可信：触发结果和锁定不能由助手决定，触发记录要放在它写不了的地方。
3. 「先建后传」有先后顺序。只看当前状态分不清「先传资料再建模」和「建了一部分再传资料」，前者不算增量。
4. 触发之后助手可能马上开始改，已有条目要在范围确认之前就受保护。
5. 一次可能传好几个文件，触发不能每个文件都开跑一次模型。

## Decision

1. **声明**：`flow.yaml` 顶层 `activation: {event, requires, session}`。`event` 取内核枚举（现在只有 `materials_added`；字段不叫 `on`，YAML 1.1 会把它解析成布尔值）；`requires` 写本包探针；`session` 是这一轮的状态文件。节点写 `visible_if: activated`，要抢在主线前面的再写 `preempt`。依据：约束 1，包只声明，判断在内核。
2. **事件发生时算一次前提**（`flow/activation.py`，上传入口 `save_resource` 调用），成立就记到主线工作区的 `.onto/run/activation.json`。依据：约束 3，事件时刻的状态天然带先后顺序，不用靠 git 历史反推；启用插件之前上传的资料也不会误触发。约束 2，`.onto` 助手写不了，上传入口只有平台能走。
3. **之后不看事件，只看记录和状态文件**：这一轮开着（`status` 是 active，基线之后没发布过），或者触发还没处理（`covers` 不包含触发时的提交）时节点出现。没有另外的状态要维护，发布之后自动恢复，这一轮期间又传资料的，结束后再次触发。
4. **锁定**：`confine.lock_on_activation` 为 true 时，触发了而范围还没确认，已有条目全部只读，由内核守卫执行。依据：约束 2、4。
5. **触发只让节点出现、下一步建议推「圈定范围」，不自动调用模型**。依据：约束 5。
6. **节点完成判定带 `{kernel: session_open}`**：新一轮触发时，上一轮留下的范围文件不会让节点直接算完成。
7. **「结束本轮」要求改动已核对干净**：节点消失后发布拦截也消失，不能靠结束本轮绕过核对。

## Alternatives considered

- **节点写固定条件 `visible_if: materials_after_modeling`**：少一块声明，但触发规则藏在内核里，看包定义看不出来；先后顺序要靠 git 历史反推，启用插件前传的资料会误触发。
- **包自带脚本判断**：违反约束 1。
- **按用户消息关键词提示**：靠猜测，不能决定节点出现和只读。
- **有基线（发布或导入过）就要求所有修改先圈定范围**：改错别字也要走一轮，和「不涉及增量建模就不触发」不符。

## Consequences

- core 升到 0.5.0（内核认 `activation`、`visible_if: activated`、`preempt`、`lock_on_activation`），增量构建包 0.2.0 依赖 core >=0.5。
- **最强的反对理由**：目前只有增量构建一个包用，新增了一块声明和一处上传调用，有过度设计之嫌。保留它，是因为触发规则写在包定义里才能静态检查，开发 Skill 也能教第三方包照着写。
- 事件只能从内核枚举选，要加新事件得改内核。
- 不走上传的修改不触发：人在网页上改条目、助手在对话里改条目（没传资料时）都不受限，也不进传播核对。
- 触发后、范围确认前新增的条目不受限，也不在这一轮的基线差异里（基线取确认时的主线）。
- 部分建模时触发：这一轮开着期间继续建模同样受范围限制，核对过后说「结束本轮」恢复。
- 自主构建运行中上传资料，已有条目同样会被锁定，自主构建的写入会被拒绝；这个组合没有专门处理。
- 每次读流程：没有触发记录和这一轮时不起 git 进程；有的话多 1～2 次。

## 补充（2026-11-17，ADR-0101）

增量构建包已删除。事件激活机制（`activation`、`materials_added`、`visible_if: activated`、`preempt`、`lock_on_activation`）保留，接下来改给内核的增量更新用；本 ADR 里关于增量构建三个节点的部分作废。

## 补充（2026-11-18，节点模型重构 3）

`activation` 机制现在给内核的 `core.update` 用：增量更新写 `need: {when: materials_added}`，条件由内核算（`flow/activation.materials_pending`），
不要求有包声明 `activation`。

- 记录：同一个 `.onto/run/activation.json` 里加内核项 `kernel:materials_added`（包名不带冒号，不会撞）。上传时主线上已经有对象或操作
  就记下 `{commit, at, files}`；和包的触发一样在事件时刻判前提，先传资料再建模不算。
- 这一轮处理完：上传之后开始的一次增量更新执行完成、触发之后发布过（和 `round_open` 同一口径）、用户选了「这一轮不处理」（FL-03）。
  内核没有包那样的状态文件可看，只能看执行记录，而执行记录会被修剪，所以处理完时在记录上写 `handled`，之后不再翻执行记录、不起 git。
- 这一轮没处理完时再上传，文件累加、时间换成这一次的：这次的资料也要有一次增量更新看过。上传时已经在跑的那次不算。
- 包级的 `activation`、`need: {when: activated}`、`lock_on_activation` 照旧支持，和内核项各记各的；`FL-03` 不能结束包的这一轮
  （那由包自己的状态文件管）。
- 内核项不锁定已有条目（没有 `lock_on_activation` 的对应物）：增量更新命令自己出变更清单让用户确认。
