# 0011 声明式求解评估器：建模助手只生成取数映射与参数，计算全部交给 Consumer

## Context

求解契约（0009、0010）引用 `ontology/scripts/` 下的一个评估器，由 Consumer 在求解前调用，产出求解事实。
此前唯一可用的接口是「旧式评估器」：脚本须自带取数与路线指标的计算代码，并导出 `SOLVER_CONTEXT`
等契约符号。这带来三个问题：

- 建模助手的资产里没有接口说明，生成的脚本是「自己选路线」的决策逻辑，Consumer 无法使用；
- 包内计算结果必须与 Consumer 求解引擎的复算逐位一致，否则校验器的摘要比对失败。也就是说，
  每个知识包都要带一份引擎公式的副本，而这份副本本身就是不一致风险的来源；
- 用户只能手写或请开发人员代写评估器，违背「业务用户只做确认」的目标。

调研确认，包内公式的输出只用于生成路线指标，而引擎会用 Consumer 构造的上下文重算全部候选。
所以包内公式在功能上是冗余的。

## Decision

- **格式**：声明式评估器是 `ontology/scripts/` 下的纯字面量 Python 文件。只允许出现：
  - 可选的 docstring 和 `from __future__ import annotations`；
  - 对固定名字的顶层单目标字面量赋值。这些名字是旧接口的 14 个常量、`SOLVER_CONTEXT`，以及新增的
    `TABLE_SOURCES`。`TABLE_SOURCES` 为每张逻辑表声明 `{object, fields}`：取哪个本体对象，
    逻辑列对应对象的哪个属性。
  - 本对象没有、但能经另一个对象查到的列，在 `fields` 中写成一跳关联
    `{"lookup": 关联对象, "match": {本对象属性: 关联对象属性}, "field": 关联对象属性}`。
    Consumer 按原值等值匹配：匹配不到的行不参与评估（内连接），匹配到多条记录时评估失败。

  文件只用 `ast.literal_eval` 读取，**任何一侧都不执行**。取数和计算全部由 Consumer 完成（见
  Consumer 侧同名决策）。
- **判定与发现**：
  - 顶层定义了全部 4 个旧符号的是旧式评估器；否则只要给 `TABLE_SOURCES` 赋值，就是声明式评估器。
  - 自动发现时，两类评估器合计必须恰好一个，否则须在契约中指定 `evaluator_path`。
- **共用检查模块**：`assets/workspace-toolkit/scripts/solver_evaluator_contract.py` 只用标准库，有两个用途：
  - 后端按路径加载，替代原先内嵌在 `solver_contract.py` 的接口常量与符号解析；
  - 在工作区作为 `.claude/scripts/` 下的 CLI 供助手自检。

  因此面板静态检查和助手自检是同一份实现。它检查：
  - 结构与取值规则（与 Consumer 镜像）；其中 `SOLVER_CONTEXT.production_condition` 只能是接口常量
    `NO_JET`，因为 Consumer 求解引擎和问题 schema 只接受它。模板直接预填该值，助手不应换成业务文档里的工况名称；
  - `SOLVER_CONTEXT.yield_unit` 声明收率属性按百分数（`percent`）还是小数（`fraction`）书写，Consumer
    统一换算成百分数。它没有默认值：写错一个数量级，路线指标会差 100 倍，却不会报错；
  - `ATMOS_DIESEL_FEED`、`ATMOS_HC_FEED`、`SOLVER_CONTEXT.route_stream_products` 三组产品名互不重叠。
    同一产品出现在两组时，Consumer 只按先匹配到的角色计算；
  - `vgo_product_yield.VGOUnitID` 必填（可以经 lookup 取得），二次加工收率不再默认归属到 `VGO_UNIT_ID`；
  - 残留的 `<...>` 模板占位符；
  - 对象 key 与属性 key 在本体文档中是否存在，lookup 的关联对象、`match` 两边的属性和 `field` 同样核对。

  ID 列映射到数值类型属性、lookup 的 `match` 两边一个是数值一个不是，都按错误阻断：前者丢失前导零后
  与路线常量匹配不上，后者按原值等值匹配永远匹配不上，结果都是事实悄悄缺失。
  逻辑表与列是封闭清单，须与 Consumer 逐项一致（`test_table_columns_match_consumer` 锁定）。
- **后端**：
  - 旧式评估器的检查与提示文案不变。
  - 声明式评估器的问题按类别映射到既有错误码：
    - 结构或取值问题 → `solver_contract_invalid`
    - 引用缺失 → `solver_contract_reference_missing`
    - `SOLVER_CONTEXT` 缺失 → `solver_context_missing`

    只有错误进入发现，警告留给自检输出。
  - 修订摘要额外计入声明式评估器 `TABLE_SOURCES` 引用的对象文档（含 lookup 关联对象）。这些文档一改，
    已有验证就过期。
- **助手**：新增 `/ontology-solver-evaluator [solver_key]` 命令与模板 `solver-evaluator-template.py`，流程如下：
  1. 只读契约目录，确定要写的评估器文件；遇到旧式评估器时停下询问，不改写它。
  2. 从对象文档、业务知识和用户回答中收集参数，不编造，也不使用 mock 数据；本对象缺的列用 lookup，
     不为凑列修改对象文档或补造属性。
  3. 只替换模板占位符。
  4. 反复运行自检直到无错误，再跑脚本契约检查。
  5. 提交后提醒用户重新验证。

  前置条件为「对象已提取」，规则 8.06 同步说明两类评估器。
- **面板**：评估器字段下方增加「让助手生成评估器」按钮，向会话发送 `/ontology-solver-evaluator <solver_key>`。
  助手只读已保存的契约，它的提交还会改变修订，所以契约未保存或面板有未保存的修改时，点击后先弹出保存确认框，
  保存成功后再按保存后的求解标识发送命令；保存被拒、冲突或出错时不发送。按钮旁的说明文字会标明「先保存」。
  以下情况按钮禁用，悬浮提示给出原因：
  - 需要先保存，但草稿有问题未修正或即时检查判定保存会被拒（与「保存」按钮同一条件）；
  - 求解标识不合法。

## Alternatives considered

- **给助手提供接口说明，继续生成旧式评估器**：公式必须与引擎逐位一致，靠提示词无法保证。
  每个知识包仍会带一份公式副本。
- **把 Consumer 的计算代码作为模板放进建模侧**：建模侧要长期保存一份与 Consumer 相同的代码，
  两边会漂移。引擎更新后，已发布的包也不会随之更新。
- **执行声明文件读取取值**：需要沙箱，而且字面量就足以表达全部声明。用 `literal_eval` 读取后，
  评估器不再是可执行代码。
- **由面板表单直接生成评估器**：取数映射需要阅读对象文档和业务知识并做判断，适合交给助手；
  确定性保证由共用检查模块承担。以后可在此基础上增加表单。
- **缺列时让助手给对象补属性，或要求导入数据自带全部逻辑列**：源数据通常按业务表组织，有些列只记在
  关联对象上。补造的属性在图谱中不存在，取到的只会是空值。改用一跳 lookup。
- **支持多跳关联或表达式**：一跳等值匹配已覆盖已知场景；更复杂的关联难以审查，留给将来的 profile 契约。

## Consequences

- 业务用户不再手写评估器：助手生成，专家确认参数，自检与面板检查同口径。
- 含声明式评估器的知识包需要支持该格式的 Consumer。旧版 Consumer 找不到旧式符号会拒绝取数，
  这个问题会在发布前的端到端验证中暴露。
- 自动发现变严：旧式与声明式评估器并存时必须指定 `evaluator_path`，这是有意为之。
- 导出知识包时，未绑定 operation 的评估器（旧式或声明式）只带 `scripts/*.py` 源码，不写脚本描述符，
  也不进 `scripts/index.md`。modeling 把每个描述符都当 operation 的可执行实现校验，评估器描述符没有
  `bound_operation`，会让评测与发布整包被拒；Consumer 扫描 `scripts/*.py` 发现评估器，不依赖描述符。
- 导出知识包时，受管模板的输入 Schema 按评估器补可选值：`diesel_unit_no` 加 `DIESEL_UNIT_IDS` 键的
  `enum`，`crude_origin` 的描述列出 `CORRECTION_FACTORS` 的品种（各超过 64 项时不补）。Consumer 的 Agent
  据此填参，不会把装置名称当编号传入，而在取数阶段才以 `fact_snapshot_invalid` 失败；越界的装置编号在绑定
  阶段即被拒绝。原油品种不做 `enum`：Consumer 按规范化名称匹配，逐字比较会拒掉等价写法。
  - `enum` 只限定取值：用户说的装置不在可选值里时，Agent 会就近挑一个照样求解，回答里也看不出换过。
    所以两个字段的描述还写明「对应不上时不要改用其他值，先向用户确认」。
  - `DIESEL_UNIT_IDS` 的键应写用户对单元的称呼（业务名称），值才是 RefineryUnitID：Agent 按键匹配
    用户说法，结果文字也原样显示这个键。模板注释与助手命令都按此引导，自检不强制。
  工作区文件保持模板原样，受管判定与修订摘要不受影响；导入时识别出投影产物就还原成模板字节，
  投影随评估器重新生成。手写的输入 Schema 原样导出。
- 建模侧的文本规则比 Consumer 更严：不允许首尾空白，限 128 字符，不允许控制字符，图谱名不允许反引号。
  因此通过自检的声明一定能被 Consumer 接受。
- 此前通过自检的声明可能不再通过：缺 `yield_unit`、`vgo_product_yield` 未映射 `VGOUnitID`、产品名组重叠，
  或 ID 属性是数值类型。按自检提示补齐或修正对象文档即可。数据层面的问题（空值、重复行、引用缺失）
  由 Consumer 在取数后报错，见 Consumer 侧同名决策的「严格校验」。
- 逻辑表、列和接口常量变更时，须同时修改两侧清单与模板。表名、列名沿用现有接口，不新增行业术语。
  模板与测试只用合成占位符。
