# 0099 领域包扩展：以导入的领域本体包为底座，只新增不改动

## Context

**目标**：领域团队把领域本体包（对象、操作、规则、指标、脚本）发布到知识包 Hub，业务团队要在它上面加自己的功能（合成例子：
在「订单」领域包上加「限时配送」）。加出来的东西不能动领域包的任何要素，这样领域包升级、换版本时，业务团队的扩展和领域包之间
始终分得清。成功标准：

- 助手改不动、删不掉领域包的条目，工具调用时当场拒绝；
- 不管谁改的（助手、网页、Studio、MCP、版本回退），领域包条目和导入时只要差一个字节，发布前就被列出来，撤回之前不能发布；
- 新功能都落成新增条目，用链接引用领域包条目；
- 没启用这个插件的项目和现在完全一样；
- 只做插件，不改内核（用户 11-16 定）。

**基本约束**

1. 底座从哪来：Hub 导入（HB-04）和上传发布包（P-11）都会新建项目，把包按工作区布局物化进 `ontology/`，原包逐字留底在
   `.imported-package/`（ADR-0008），留底区写入禁止。导入的项目发布时是一个新的 Hub 包（`ontology_id` 由项目 id 算），
   领域包本身不受影响。
2. 助手的写入不可信（ADR-0085 约束 1）；内核已有通用的 `confine`：范围文件在主线上、`status` 是 `active` 时，
   基线提交里有、`editable` 里没有的条目助手不能写也不能删，新增不限。
3. `confine` 一次装配只允许一个包声明；基线之后发布过就算这一轮结束，限定自动解除（ADR-0091）；拒绝时的提示语是为增量构建写的
   （「要扩大范围请重新圈定」「结束本轮」）。这三点都是内核行为，这次不改。
4. 网页、Studio、MCP 的人工编辑不经守卫（ADR-0085 约束 3）。
5. 包的脚本在助手所在的工作区里跑，有 git；`kind: script` 节点在沙箱里跑，没有 `.git`，输入最多 200 个文件、96 KB，装不下一个真实的领域包。
6. 给助手看的输出有上限（CLAUDE.md 第 6 节）。

## Decision

**推导**

- 「底座」要有一个助手改不了的定义（约束 2）。导入那次提交是 git 历史，`.imported-package/` 写入禁止，所以底座 = 最早带上
  `.imported-package/` 的提交里 `ontology/` 下的文件（`index.md` 是派生物，隐藏文件不算）。不另存一份清单当依据：清单是普通文件，
  助手能改。
- 助手这一层直接用 `confine`（约束 2）：范围文件写 `baseline.commit = 导入提交`、`editable = []`，只读的就是底座条目，
  新增条目不受限。范围文件只在「锁定底座」命令运行时能写，放宽只认主线上的版本（内核已有）。
- 发布后限定自动解除（约束 3）：锁定底座的完成条件带上 `{kernel: session_open}`，发布后节点变回待做，下一步建议先推它；
  再锁定时基线改成主线 head，已有的新增条目全部列进 `editable`，只读的仍然只有底座。重新锁定之前的空档由发布关卡兜：
  底座核对的完成条件也带上锁定，没锁定就挡发布。
- 人工编辑不拦（约束 4），所以要有一个看结果的关卡：底座核对按文件内容逐字比导入提交里的 blob（不看提交历史、不看谁改的，
  没提交的改动也算），改了、删了、搬走了的都列成 `[ ]`，挂 `blocks: [core.publish]`、`stale_on` 全部本体类别。
  搬走的另记新位置；新增条目和底座条目同名也列成 `[ ]`，否则 `[[名称]]` 会指歧义。
- 核对节点做成助手节点跑本地脚本，不做成脚本节点（约束 5）。代价是报告文件助手能伪造，和 ADR-0085 接受的一样：护栏不是安全边界。
- 撤回：底座条目被改后，助手经守卫写不回去。核对命令带 `restore`：用户在确认卡上选「撤回」后，脚本把被改、被删的底座条目
  写回导入提交里的字节，不删任何文件。脚本内部的写入守卫看不到（ADR-0085 已列的绕过方式），这里只用来恢复底座原字节，
  不会引入改动。
- 新增功能要用户说要什么，自主构建不做（`autobuild: false`，同增量构建）；锁定和核对是确定的脚本，自主构建照做。
- 常驻规则（`rules`，每轮拼进工作区 `CLAUDE.md`）写四条：底座不改、新功能只用新增条目、被拒不是范围问题、用哪两条命令。
  core 的命令（校验修复、增量更新）也会碰到底座，只在插件命令里写不够。拒绝提示语的「重新圈定」「结束本轮」由规则和一条提示规则纠正（约束 3）。
- 和增量构建不能同时启用（约束 3 的第一点）：两个包都声明 `confine`，启用第二个时装配返回 422，描述里写明。

**做法**

1. 新官方能力包 `domain-extend`（领域包扩展）0.1.0：`default_on: false`，`depends: {core: ">=0.5"}`；命令 `/domain-extend-bind`、
   `/domain-extend-add`、`/domain-extend-check`，脚本 `domain_extend.py`（`bind`、`status`、`catalog`、`added`、`check`、`restore`），
   常驻规则 `domain-extend-rules.md`，提示规则命中「结束本轮」「重新圈定」。
2. 主线：建模 → 锁定底座 → 新增功能 → 底座核对 → …… → 发布。三个节点 `spine`、`required`；底座核对 `blocks: [core.publish]`，
   完成条件是 `ext/domain-extend/check.md` 存在、没有 `[ ]`、底座锁定生效。
3. 状态文件都在 `ext/domain-extend/`：`scope.json`（内核读 `status`、`baseline.commit`、`editable`；另记 `base.import_commit`、底座包的
   id、名称、版本）、`base.json` / `base.md`（底座清单）、`plan.md`（新增规划）、`added.json`（新增条目和各自引用的底座条目）、
   `check.md` / `check.json`。
4. 新增的做法写在 `/domain-extend-add`：底座对象要多存信息 → 新建扩展对象关联它，关系写在扩展对象上；底座操作要多步骤 →
   新操作调用底座操作；口径要变 → 新规则、新指标说明差别；只有改底座才做得到的列进「做不到的」，请用户去改领域包、发新版本。
5. 输出上限：标准输出最多 20 条，md 每节最多 50 条，后面写「还有 N 条没列出」，json 是全量。

## Alternatives considered

- **小改内核**（允许多个包声明 `confine` 取只读并集、Studio 里底座只读、发布后不解除）：能和增量构建同时用，人工编辑当场拦，
  也没有发布后的空档。用户定先做纯插件；需要时再按这三点改内核，插件这边只要去掉重新锁定的那一步。
- **底座按 `.imported-package/` 原包算**（发布格式 → 工作区格式再比）：最贴近「领域包的要素」。但格式转换在后端的发布适配器里，
  包的脚本用不了；导入提交就是那次转换的结果，按它比是同一个口径。
- **输出只含扩展部分、声明依赖底座的分层包**：最干净，但 consumer 和 Hub 都不认包依赖，发出去用不了。现在发布的是底座加新增的完整包，
  底座条目逐字不变。
- **核对做成沙箱脚本节点**：报告由平台写，助手伪造不了。但沙箱没有 git，输入上限装不下真实的领域包（约束 5）。
- **直接用增量构建包**：它的范围是「这一轮要改哪些」，可以改已有条目，和「底座一律不改」相反；而且一轮发布就结束。

## Consequences

- 启用后，助手改底座条目当场被拒；人工在网页上改的，发布前核对列出来，确认后一键写回导入时的内容。
- **代价（最强的反对理由）**：保护有空档，而且有两层只是护栏。发布后到重新锁定之前，助手写底座不会被拒，只能靠发布前核对兜底；
  `confine` 只拦工具调用里看得出路径的写法，核对报告助手也能伪造（ADR-0085 已列）。真正挡住「底座被改了还发出去」的，
  是核对脚本按导入提交逐字比——前提是它真的跑了。要堵上空档和伪造，得改内核（见 Alternatives 第一条）。
- 拒绝写底座时内核的提示语是增量构建的说法（「要扩大范围请重新圈定」「结束本轮」），靠常驻规则和提示规则纠正，不改内核就去不掉。
- 不能和增量构建同时启用；同一项目要先停用一个。
- 只能用在从已发布知识包导入的项目上（Hub 导入或上传发布包）；工作区压缩包、迁移包导入的项目没有 `.imported-package/`，
  锁定时直接说明。
- 常驻规则每轮占一段提示词（四条，约 300 字）。
- 底座本身有问题（校验报错）时插件不修，只能请领域团队改领域包、发新版本，业务项目重新导入后再把扩展搬过去；这次不做「换底座版本」。
- 没启用的项目：组装出的 flow.yaml 没有 `confine`，也没有这三个节点，守卫和发布关卡的行为不变，测试覆盖。
