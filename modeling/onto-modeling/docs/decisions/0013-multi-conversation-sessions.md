# 0013 建模项目支持多会话：新建、切换续聊、重命名、删除

## Context

每个建模项目原来只有一条会话：事件历史固定在 `DATA_DIR/sessions/{pid}.jsonl`，Claude 续接
token 在 `{pid}.meta.json`，会话池、排队、回收都按 `project_id` 管理。用户想换个话题从空白上下文
开始时，手上只有一个「重启会话」按钮，而且它和预期不符：

- 确认文案写「模型上下文经 resume 续接」，实际 `close()` 会清掉续接点；
- Jiuwen 引擎连接时把整份项目历史回放成上下文，`close()` 对它不起作用，上下文只增不减。
  小窗口模型下，这会让项目越聊越容易撞上窗口上限。

需求：每个项目可以有多条会话；聊天面板顶部的下拉列出全部会话，可新建、切换到任一历史会话续聊
（各自保留模型上下文）、重命名、删除。

## Decision

**每个项目仍只有一个在线引擎，会话只决定引擎绑定哪份历史和哪个续接点。** 同一项目的所有会话
共用一个 git 工作区，并行运行会互相改文件，所以会话池、排队、空闲回收、运维回收继续按
`project_id`，`Session` 只多一个 `conversation_id` 字段。

**服务端不记「当前会话」。** 选中哪条由前端决定，相关接口都带可选的会话 id
（`?conversation=` 或 body 里的 `conversation_id`）。省略时取在线引擎绑定的会话，没有在线引擎
则取最近更新的那条，Studio 提交、设置页和旧客户端因此不用改。只读用户可以浏览任意会话，
协作者之间互不影响。

**切换在发送时生效。** 翻看历史不动引擎。发消息时如果引擎绑定的是另一条会话：

- 那条会话忙（运行中、排队、连接中、正在投递，或有待确认的权限卡）→ 返回 409；
- 那条会话空闲 → 回收引擎（续接 token 已落盘），再为目标会话建 `Session`。

「解析会话、回收旧 Session、登记新 Session」整段在管理器的 `_lock` 里完成。`_recycle` 要 await
断开且第一步就把 Session 移出字典，不加锁时并发的跨会话发送会各建一个 Session，被覆盖的那个
带着引擎游离在外。`_connect` 完成后再核对一次 Session 仍是字典里的那个，否则断开引擎。

**存储零迁移。**

- 会话 `default` 沿用旧路径 `sessions/{pid}.jsonl` / `{pid}.meta.json`，存量项目不搬文件；
- 新会话存 `sessions/{pid}/{cid}.jsonl` / `{cid}.meta.json`，`cid = uuid4().hex[:12]`；
- `sessions/{pid}/index.json` 存标题、是否手动命名、创建时间，是「会话是否存在」的唯一依据；
  `updated_at` 取历史文件的 mtime。索引缺失时由磁盘文件推出，读路径不落盘，首次变更才写入；
- cid 必须匹配 `^(default|[0-9a-f]{12})$` 且在索引中，否则 404；
- 列表永不为空：删掉最后一条时在同一次操作里补一条空会话；
- 删除会话前把其中的 `result` 事件（只含成本与 token）追加到 `sessions/{pid}/deleted-usage.jsonl`，
  项目累计用量和运维按日统计不因删除而减少。

**标题。** 首条用户消息自动生成标题（去掉上传资料的前缀行，压缩空白，截 30 字）；手动重命名
（1–60 字）后不再被覆盖。

**引擎。** Claude 引擎按 (pid, cid) 存取续接 token。Jiuwen 引擎的上下文 sid 为 `onto-{pid}`
（default）或 `onto-{pid}-{cid}`，回放的只是本会话历史，新会话从空上下文开始。切换引擎时清掉该项目
全部会话的续接 token；删除项目（永久删除，见 0010-permanent-project-delete）清掉全部会话的
历史、续接 token、索引和留存用量。

**前端。** `ConversationSwitcher` 放在聊天头部，下拉按最近更新排序，显示相对时间和「运行中」
标记，支持行内重命名、二次确认删除，旁边是「新建会话」按钮。当前会话运行、排队、上传或有待确认
卡片时禁用切换、新建、删除。选中的会话只存在组件状态里，刷新页面后回到在线会话或最近更新的会话。
`/stream` 在会话还没挂上 Session 时改为 1 秒短轮询补挂，ping 仍按 15 秒发，保证「先开流、后建
Session」时流式输出不延迟。

## Alternatives considered

- **每条会话一个在线引擎，可并行运行**：同一 git 工作区会被并发改写，审阅和回滚都无法归属；
  内存占用也会按会话数翻倍，突破 0003 的会话池预算。
- **服务端记录「当前会话」**：多个标签页或协作者互相覆盖，只读用户切换浏览也要写状态。
- **把现有历史迁移到 `sessions/{pid}/default.jsonl`**：要做一次性迁移和回滚预案，收益只是路径统一。
- **「新建会话」只是清空现有会话（重启会话的加强版）**：用户要求能回到旧会话继续，清空做不到。
- **切换时立刻回收引擎**：只是翻看历史也会打断空闲引擎的复用，并让只读用户能影响在线引擎。

## Consequences

用户可以随时开一条空白上下文的新会话，也能回到旧会话续聊；Jiuwen 引擎第一次有了截断上下文的
办法。「重启会话」的确认文案改成与实际一致：历史保留，按最新配置重连模型，Claude 引擎清空模型
上下文；要从空白上下文开始请新建会话。

已知限制：

- 同一项目同一时刻只有一条会话在跑。当前会话忙时不能切换；另一个标签页往别的会话发消息会得到
  409，需要等在线会话结束或被打断。
- 省略会话 id 且没有在线引擎时，消息发往最近更新的会话，可能是刚新建的空会话。前端始终带 id，
  影响的只有 Studio 提交等不区分会话的入口。
- Jiuwen 的影子工件区 `DATA_DIR/jiuwen/{pid}` 按项目共享，没有按会话隔离；Jiuwen 下「重启会话」
  不清上下文，只有新建会话能做到。
- Jiuwen 按 sid 隔离运行状态这一点只按 SDK 接口签名核对过，没有在真实运行时上验证。
