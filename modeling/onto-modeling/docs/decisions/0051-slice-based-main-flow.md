# 0051 主流程按详设 6.8 重排：建模按段，新增全局一致性与发布节点

## Context

详设 6.8（v1.1）把「一个阶段一个节点」改成按段纵向推进：主线显示为资料分析 → 建模（按段）→ 校验与走查 → 全局
一致性 → 发布；规则在分段里按资料出现、可以跳过，指标、流程图是旁支，增量更新按需。6.6 规定建模节点 `per_slice: true`、
在每段上各算一份状态、节点状态由各段汇总并给出「3/5 段」。B4b 的节点状态（ADR-0048）只按整节点算，core 0.2 的节点是
对象提取、操作提取、规则与指标、质量检查。

## Decision

1. **core 0.3.0 的 flow.yaml**：
   - `core.research`（含分段规划，ADR-0050）→ `core.model`（建模，`per_slice`，`steps`：对象、操作、规则〔可选〕、
     写入即查〔`derived`〕）→ `core.validate`（校验）→ `core.consistency`（全局一致性，新增）→ `core.publish`（发布，新增）；
     `core.metric`（指标）是建模之后的旁支，`core.update` 按需。
   - 命令归属：`extract-object`、`extract-operation` → 建模；`extract-rule-metric` 不带分段是指标旁支，带 `slice=` 时按
     建模节点的 `steps` 归到「规则」一步（命令按 steps 归属优先于 `commands`）。
   - `aliases`：`core.object`、`core.operation` → `core.model`，`core.rule_metric` → `core.metric`。跟随通道升级时 core
     先换（`packs/runtime.follow`），还没升级的包写的锚点、命令归属照样能组装。
   - 「写入即查」不单独跑命令：确认生效时的门禁（ADR-0046，合成树上跑规则检查只看新增错误）就是写入时的检查；前面的
     必经步骤都确认了它就确认，这一段还没确认的修改有新错误时是 `draft`。
   - 全局一致性：确定性脚本 `consistency_check.py`（关系：链接指不到、孤立对象；口径：蓝图统一了的叫法还在用别的；
     跨分段：用到别的段的对象却没声明依赖、不属于任何一段、规划了没建）写 `reports/consistency/consistency.md`
     （覆盖上一份，已勾掉的同一条结论保留）；命令 `/ontology-consistency` 调它、按结论修正。报告放子目录，不算进质量
     检查的 `reports_pending`。`blocks: [core.publish]` + `blocks_in: sliced`：只在按段建模时挡住发布。
   - 发布：`kind: human`，动作是去发布页（`{page: publish}`），完成判定是工作区里有 `release/*` 标签（新探针 `tags`）；
     `stale_on` 条目类别，发布之后改了内容显示过期。发布页的门禁链（PB-01）后面加流程关卡（`source.kind=flow`）：
     `blocks` 指向发布节点的节点，没确认就挡住发布、动作是去做这一步。不另写发布流程。
2. **包往分段里加步骤**（组装时，`assemble._apply_slice_steps`）：包的 `slice_steps` 往按段的节点里加步骤
   （`[{node, step}]`，`step.after` 指定放在哪一步后面），`node_titles` 改节点显示名（`{节点: 名称}`）。这是 6.6 说的
   「挂在 core.model 上的节点钩子」，但和节点前后追加命令的通用节点钩子（`hooks`，B5c）分开声明，两者互不影响。场景走查 0.10.0：「场景」一步挂在建模的分段里
   （写入即查之后），全量回归 `trace.trace` 串在校验之后（`placement: spine`：随 core 拆出、本来就在主线上，不算新插进来的
   可补做节点，ADR-0066），校验显示为「校验与走查」；`trace.mock` 去掉，示例数据按场景
   生成（`mock` 命令归 `trace.trace`）。没装场景走查就没有「场景」一步。codegen、evo 的锚点改成 `core.model`。
3. **按段的状态**（`services/flow/slices.py`）：

   | 状态 | 怎么算 |
   |---|---|
   | running | 没结束的执行记录，分段与步骤是这一段这一步 |
   | pending_confirm | 没确认的变更集做过这一段这一步（`slice_steps`），或改到了这一段这一步的条目 |
   | confirmed / auto | 这一段这一步的条目在主线上都有了，或这一步的变更集确认生效过；自主构建合入的带需复核显示 auto |
   | stale | 确认之后，这一步 `stale_on` 的上游变了：按段模式下对象、操作、规则只取这一段的条目，资料分析取全部 |
   | skipped | 可选步骤被跳过（FL-03 带 `slice_id`），或按段模式下这一段没规划规则（`no_rules`） |

   - 一段：`group` 取 now（在跑、或做了一部分）、wait（待确认、过期）、done、todo；`note` 只写最短的状态
     （「正在做「操作」」「待确认」「n 步过期」「停在「场景」」）。
   - 节点汇总：全部段确认 → 已确认；任何一段过期 → 过期；有在跑的 → 进行中；有待确认的 → 待确认；做了一部分 → 进行中；
     都没开始 → 按上游可开始 / 未就绪。`progress` 为「n/m 段」（全量模式不给）。按段模式下进度（x/N、P-01）里建模要
     全部段做完才算；P-01 的 `slices` 给每段一格。
   - 依据存在节点状态同一份文件的 `slices`、`slice_skips`；第一次看到已满足的步骤记基线。指纹从一次 `ls-tree` 里挑，
     全量模式下和节点输入指纹算法相同。
   - **全量模式**：没有蓝图或只有一段时，只有一段「全部」，条目就是整类目录；包加的步骤（场景）在全量模式下不挡建模
     完成（全量回归另有主线节点），和 0.2 的进度口径一致。
   - **存量项目**：第一次算时（`legacy_migrated`）把 0.2 节点上的记录映射过来：对象提取、操作提取、规则与指标 → 「全部」
     那一段的对象、操作、规则（沿用原来的输入指纹，原来过期的仍过期）；两者都确认过的项目，建模节点沿用对象提取的
     指纹记录；规则与指标的跳过 → 规则一步跳过、指标旁支跳过。需复核标记一起带过来。
4. **执行记录与变更集**：执行记录多 `slice`（`{id, name}`）与 `step`；命令带 `slice=` 用它（不存在或已排除时为 null），
   不带时取这一步还没做完的第一段，全量模式是「全部」。宿主写的 `.onto/run/exec.json` 带上分段（`blueprint.py brief`、
   `state_helper acquire` 读它）。变更集记 `slice_steps`（与第一段的 `slice_id`）；确认生效时 `wiring._confirm_nodes`
   把这几段这几步记为确认过（自主构建合入的带需复核）。一轮结束时这一段新建、还不属于任何一段的对象、操作、规则由后端
   用 `blueprint.assign` 记进副本里的蓝图（随这一轮一起确认）。
5. **下一步**（`flow_state.suggest`，后端与 `state_helper suggest` 同一份）：上下文多 `blueprint`（草案时主推「确认蓝图」，
   次选「调整分段」「重新划分」；蓝图就在这一轮的修改里时次选换成「撤回这一轮」，不再单列「确认生效」）与 `slice_next`
   （这一段的下一步，命令带分段）；建模节点过期时刷新的是过期的那一段那一步。没有蓝图、资料分析做完时次选多一个「分段规划」。
   FL-05 开始建模节点：带 `slice_id` 取这一段的下一步，不带取主线下一步。
6. 命令文档：资料分析加第 6 步分段规划（`phase=blueprint` 只做这一步）；对象、操作、规则提取与场景走查按 `SLICE_MODE.md`
   只做 `brief` 里的那一段，做完这一步就停下等确认生效。

## Alternatives considered

- **对象、操作、规则各自仍是主线节点，分段只是显示**：和 6.8、第 9 章「每段单独走完再确认」矛盾，写入范围也没法按段收窄。
- **「写入即查」单独跑一遍规则检查命令**：确认生效时的门禁已经在合成树上跑了同一份检查，再跑一遍只是多等。
- **全局一致性在全量模式下也挡发布**：存量项目升级后第一次发布就被挡，跨分段衔接在全量模式下也没有意义。
- **发布节点另起一个发布命令**：发布页（PB-01～PB-03）就是发布流程，节点只是把它放进主线、把流程关卡并进门禁链。
- **存量项目的 0.2 记录直接丢掉、重新记基线**：原来过期的会变成已确认，需复核标记也没了。

## Consequences

- 进度 x/N 按新节点数：对象、操作合成一个「建模」，多了全局一致性与发布；原来确认过的步骤在「全部」那一段里保持已确认，
  但只有对象没有操作的项目，建模节点显示进行中（原来对象提取算一个完成）。
- 已发布过、之后又改了内容的项目，发布节点显示过期。
- 按段建模的项目发布前要做全局一致性检查。
- 分段里的步骤只能由包加到按段的节点上；通用的节点钩子（节点前后追加检查）由 B5c 的 `hooks` 承担。

## 合进交付分支（与 B5c 节点包并存）

- `aliases` 也作用于节点钩子（`hooks`）的宿主节点；原来插在对象提取与操作提取之间的节点（`after` 与 `before` 映射到同一个
  建模节点）去掉 `before`、挂在建模之后。
- 节点状态在 `view.node_states` 一处算：按段汇总、按拿掉熔断节点 `blocks` 的流程调 `state.compute`；FL-01 之后再补熔断、
  可补做标记，待处理用同一份（不列熔断节点）。挡住建模的关卡没过时，建模做了一部分也显示「被挡住」（在跑、待确认、过期、
  做完的照常汇总）。
- 下一步：可补做节点不进主线候选（B5c），蓝图与按段的下一步照旧；项目进度先按段覆盖建模的完成判定，再按可补做扣分母。
- 发布节点只在发布页里做：FL-05 回 `400 invalid_argument`（`details.page="publish"`），不当成出决策卡的人工节点。
- 发布门禁链：平台门禁 → 包的门禁（B5c）→ 流程关卡（B4d）。
