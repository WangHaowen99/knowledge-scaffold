# 0096 数据 Schema 的 Sheet 范围与表头预检只读文本版

## Context

**目标**：一份标成「数据 Schema」的表格里，常混着封面、说明、字段字典、术语表这类 Sheet。它们被当成物理表，对象提取就会
从说明页里造字段，发布的数据绑定也会绑到不存在的表上。用户要能在资料区看清每个 Sheet 的表头问题（空列名、重名、合并），
选定哪些 Sheet 是数据表；对象提取、字段核对（工作区的 `table_profile`）和发布的数据绑定（后端的 `package_mapping`）都只认
选定的 Sheet。成功标准：

- 改用途为「数据 Schema」时先预检表头，没问题直接保存，有问题才让用户勾选；
- 用户勾选的范围绑定确认时的文件，文件换了就要重新确认，不悄悄换成别的范围；
- 后端和工作区脚本对同一份文件读出同一组表名和表头。

develop 的做法（提交 bee5e00a、a4328d1a）是在主服务里用 openpyxl 解析 Excel 原件，并扫描工作表 XML 找合并单元格。

**约束**：

- ADR-0076：解析不可信文件不在主容器里做，主容器只读连接器网关转出的文本版。这条用户定了保留。
- 工作区脚本跑在助手的环境里，导入不了后端代码；后端也不能依赖工作区脚本以外的第二份规则。
- Excel 刚上传时还没有文本版（转换是异步的），转换也可能失败。
- 旧项目的 `materials.json` 里只有文件级的 `schema` 标注，读的时候不能改写它。

## Decision

1. **规则只有一份，放在工作区脚本 `table_sources.py`（只用标准库）。** 后端 `services/table_sources.py` 按路径加载它，
   `material_detect` 的 Sheet 结构判定也改用它。工作区的 `table_profile.py` 直接 import。依据：两边必须同口径，
   而工作区那边只能用工作区里的文件。
2. **Excel 读文本版，CSV 直接读。** 文本版每个工作表一个位置标记加一张 Markdown 表，表头是第一个非空行，
   与转换器、`md_tables` 同口径；没有文本版时范围是 `pending`，表头为空，不去解析原件。
   网关的转换输出不用扩：Sheet 名、表头行、有数据的最右一列都已经在文本版里。
3. **合并单元格不单独检测。** 文本版里，被合并掉的格子是空的：下面有数据的列会报「没有列名」（错误，不能当数据表）；
   下面没有数据的列本来就是空列，按少一列处理不影响字段。所以结果与 develop 一致——有问题的 Sheet 勾不上——只是提示说的是
   「第 N 列没有列名」而不是「合并单元格」。
4. **表头是第一个非空行。** develop 把第一行为空的 Sheet 排除，是因为它的下游按物理第一行取表头，会错位；这里所有读表头的地方
   都读文本版，取的都是第一个非空行，不会错位，照常收进来。
5. **范围分两种。** 没存范围时按结构现算：用户手标的收数据表、疑似和文档形式的表（中文表头的手标表照旧可用），上传时自动识别的
   只收数据表和疑似；字典、术语表、说明页、空表都只作参考。用户在弹窗里确认的是人工范围，存进 `materials.json` 的
   `schema_selection`（`{version: 1, mode: "manual", included_sheets, revision}`），`revision` 是确认时文件的修订
   （sha256 前 16 位，与 `Material.revision` 同口径）。现算的范围不存：文件换了自动跟着变，也不会和规则调整打架。
6. **人工范围对不上当前文件就报错，不退回现算。** 后端翻成 `409 schema_scope_stale`，工作区脚本退出码 2 并提示到资料区确认；
   对象提取命令遇到它停下来，不退回遍历全部 Sheet。替换文件时留着人工范围，让读的地方发现并要求确认。
7. **接口**：R-01 的 `Material.schema_scope` 给范围摘要；新增 R-16 `GET …/resources/schema-preview` 给逐 Sheet 的表头与问题，
   只读；R-03 的请求体可带 `schema_selection`，保存时校验修订和表头错误。

上传那一刻判用途（`material_detect.detect_material`）仍读原件：那时还没有文本版。这是 ADR-0076 记下的遗留点之一，本 ADR 不扩大它，
Sheet 范围与表头预检都不走那条路。

## Alternatives considered

- **照搬 develop，在主容器里解析原件**：违背 ADR-0076，用户已否。
- **扩网关的转换输出，带上合并单元格**：要改转换器格式、升版本，已有的文本版要重转；按上面第 3 条，结果不变，只差提示的措辞，不值得。
- **把现算的范围也存下来（develop 的做法）**：存的是现算结果的快照，规则一调、文件一换就要处理新旧不一致；不存更简单，结果相同。
- **范围放在后端，工作区脚本调接口取**：工作区脚本没有到后端的通道，离线也要能跑。

## Consequences

- 刚上传的 Excel 在转出文本版之前，范围是 `pending`：资料区不显示范围，改用途为数据 Schema 时先只改用途；数据绑定在那之前读不到这张表
  （与 ADR-0076 之后的现状一致）。转换失败的表格预检报 `409 not_convertible`。
- 提示「第 N 列没有列名」也覆盖了合并表头的情况，措辞比 develop 少一层原因。
- 项目锁定的旧版 core 包里的 `table_profile.py` 没有范围参数，资料地图数字段时退回整本读，升级 core 包后一致。
- 最强的反对理由：文本版只转前 2000 行，「下面有数据、表头没列名」的检查只看得到这些行；更靠后的宽行发现不了。
  这只影响提示，不影响绑定（表头仍取自第一个非空行）；要补就在转换器里多给每张表的实际列宽，等真遇到再做。
