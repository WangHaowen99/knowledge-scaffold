# 0024 包仓库、项目锁文件与装配目录，core 包与契约库按锁定版本加载

## Context

提示词资产全局只有一份（`assets_admin`）：上传和回滚都是先移走旧目录再移入新目录，中间 `.claude`
指向空处；上传后 agent 立刻用新脚本，在线会话还用旧的 CLAUDE.md 和 hooks，后端 `toolkit.py`
缓存在 `sys.modules` 里的契约脚本要重启才换——详设 3.5 说的「三版本并存」。守卫写在资产包的
`settings.json` 里，上传一个不带它的包就能把守卫删光（方案 D1）。详设 4.6、8.1 要求包仓库、
清单与兼容检查、项目锁文件、装配器、生效控制、启动核对；方案 D1～D7、A16 给出改法；P1 验收要求
「装配过程中杀进程，重启后能自动恢复」「升级 core 包后从下一条消息开始生效，不再出现三版本并存」。

## Decision

1. **包仓库**（`services/packs/repository.py`）：`<数据目录>/packs/<名>/<版本>/` 不可修改，附
   `checksums.sha256`。入库先复制到临时目录、核对校验和再 rename；同名同版本内容不同一律拒绝。通道
   （stable / beta）是 `channels.json` 里的指针，可禁用版本。
2. **清单**（详设 5.2，`manifest.py`）：semver 与兼容范围（`>=1.0 <2.0`、`^`、`~`）；`kind` 决定热更新
   级别：knowledge → H0（下次读取生效），capability / node → H1（下一条消息生效），provider / exporter →
   H2（不能按项目启用）。包只能在 `contributes.hooks.PreToolUse` 里追加守卫，其他挂点清单解析即拒。
3. **静态检查**（`checks.py`，PL-15 的检查项）：清单、校验和、符号链接、声明的命令存在、兼容范围、
   名字冲突（非 core 包命令带包前缀、不和 core 重名、不占内核脚本名）、实体类型、写入范围不碰受保护目录、
   节点入口命令存在、hooks 只追加拒绝型、页面只选内置且不带前端代码（JS/TS/Vue/CSS、package.json；租户包
   的 HTML 带脚本也算）、凭据、脚本语法、提示词体积。只读不执行。
4. **锁文件** `.onto/packs.lock`（进工作区 git，详设 14#1）：排序 JSON；停用的包留 `enabled=false`；
   `follow=true` 表示跟随通道（方案 2.3 第 4 步）。改锁文件是一次带 `Onto-Source: plugin` 的提交
   （变更集在 P2）。
5. **装配器**（`assembler.py`）：内核守卫 + 已启用的包**复制**进 `<数据目录>/assembled/<哈希>/`（不用逐文件
   软链：有脚本按 `__file__` 找同目录模块），合并 `settings.json`（内核基线 + 包追加的守卫）、`CLAUDE.md`
   （各包规则片段）、`flow.yaml`（组装后的流程），最后写 `MANIFEST.json`（包与版本、每个文件的哈希）再
   rename。哈希 = 内核守卫摘要 + 启用的包；另算只含 H1 内容的哈希给会话指纹用。`.claude` 用临时软链 +
   `os.replace` 原子切换，`CLAUDE.md`、`README.md` 是指向 `.claude/` 的相对链接。装配失败不改锁文件。
6. **core 包**：`assets/workspace-toolkit` 原样迁成 core（加 `manifest.yaml`，命令名不变），工作区规则与
   说明作为它的规则片段与说明。镜像启动时入库，版本号是清单版本加内容摘要（`0.1.0+3f9a1c2d`），新镜像
   第一次启动把 stable 指向它。
7. **生效时机**（详设 3.5）：锁文件改了先把新装配目录装好；纯数据包马上切；能力包等下一条消息前由会话
   宿主切换并重连，正在跑的一轮跑完旧版本（会话指纹见 `session_host/fingerprint.py`）。
   跟随通道的项目在下一条消息前把锁升到通道版本。
8. **启动核对**（方案 D4）：清掉入库、装配中途停机留下的临时目录；没有锁文件的存量项目写一份并提交；
   `.claude` 指错、缺失、是旧版绝对链接，或装配目录内容与 MANIFEST 不符，都按锁文件重新装配并切换。
9. **共享契约库**（方案 A16、D5，`contracts.py`）：`toolkit.py`、`solver_contract`、`workspace` 三处加载器
   合成一个。模块名带版本（`onto_contracts.<标签>.<脚本>`），脚本间的同目录 import 用模块自己的
   `__import__` 解析到同版本兄弟模块；项目上下文里按装配目录锁定的 core 版本加载（文件按 MANIFEST 核对，
   对不上退回镜像版本）。发布渲染、资料分析验收、流程探针都用项目锁定的那一份。
10. **旧资产包接口**：上传改写到 PL-13，没有清单的资产包当作 core 新版本（去掉现在归内核的守卫，从镜像
    补规则、说明与流程定义），检查通过直接发布到 stable；O-30～O-34 改读包仓库，回滚只改 stable 指针，
    回滚前先备份包仓库。`assets_admin` 删除。

## Alternatives considered

- **装配目录用逐文件软链指向包仓库**：省空间，但 7 个脚本按 `__file__` 找同目录模块，软链会解析到包仓库
  里各自的目录，跨包 import 断掉；内容寻址后锁文件相同的项目共用一份，复制的空间代价可以接受。
- **契约库在 P1 就拆成独立的 contracts 包**：要同时锁两个必装包、处理它们之间的兼容；P1 代码生成还在
  core 里，没有第二个使用方。先按 core 版本加载，P2 拆可选包时再拆出来（方案 D7 后半）。
- **锁文件变了立即切 `.claude`**：正在跑的一轮会读到一半新、一半旧的命令和脚本；切换只放在没有一轮在跑的
  时刻（连接前、空闲时的下一条消息前、启动核对）。

## Consequences

- 每个项目多一个进 git 的 `.onto/packs.lock`；存量项目第一次启动多一次系统提交（主线版本号 +1）。
- 数据目录多出 `packs/`、`assembled/`、`pack-repo-backups/`；装配目录可以随时由锁文件重建，包仓库要进备份
  （备份范围在运维面，B3b 处理）。
- 镜像里的工具箱每改一次就是一个新 core 版本，旧版本留在包仓库里供回滚；不再用的装配目录目前不清理。
- 新增脚本、命令要同步 core 的 `manifest.yaml`。
