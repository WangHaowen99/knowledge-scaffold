# 0080 用户和管理员导入插件的权限一致

## Context

用户 2026-11-05 定：「用户和管理员导入插件的权限要保持一致，用户也能导入脚本和节点」。这取代 ADR-0079 做法第 2 条的白名单，
ADR-0079 其余条款不变。

**目标**：建模者不找管理员，也能把带脚本、流程节点的能力做成插件用到自己的项目里。成功标准：同一个包，普通用户和管理员上传，
静态检查结果相同；普通用户装好后能启用到自己的项目，节点和脚本都生效。

**基本约束**

1. 执行边界没有变（ADR-0079 约束 2）：助手的 Shell 以 `onto-agent` 身份在主容器里运行，所有项目的工作区都归这个身份可写，
   项目之间的隔离靠 PreToolUse 守卫；守卫只看命令文本，看不到脚本里做什么，hooks 和 `settings.local.json` 在守卫之外生效。
2. 包仓库全平台一份，往全局放东西会影响所有项目（ADR-0079 约束 3）。
3. 管理员的上传审核发布流程、已有接口不能破坏。

## Decision

**推导**

- 用户要的是「导入」这个动作的权限一致，所以按内容放开：普通用户上传不再有单独的白名单，检查和管理员上传租户包是同一份。
- 约束 2 决定了放开后的后果（见 Consequences），这个代价由用户接受。
- 约束 2 不涉及别人看不看得见这个包，约束 3 要求不进全局，所以可见范围照旧：用户导入的包只归自己，发布到全平台还是管理员的操作。

**做法**

1. 删掉 `private_scope` 检查和相关白名单。普通用户上传 `tenant=True`，和管理员带租户标签上传走同一份 `checks.run`，
   只多一项 `private_name`（包名没被占用）。
2. 这些不变：私有包只有本人可见和启用、包名先到先得、资源上限（zip ≤20 MiB，解压后 ≤64 MiB、≤2000 个文件，每人 20 个上传、
   50 个版本）、管理员能禁用和发布、`pack.upload`、`pack.private_install` 审计。
3. 全局注册项（配置、指标、告警）只遍历公开包，私有包里声明了也不生效，发布成公开包才生效。

## Alternatives considered

- **保留白名单，只加脚本和节点**：`settings.local.json`、hooks 的差别还在，不满足「权限一致」。
- **普通用户也能发布到全平台**：一个账号能影响所有项目，超出「导入」的范围，不做。
- **带脚本的包在沙箱里跑**：能保住隔离，但要改工作区脚本的调用方式，包里的脚本现在都假定能读写工作区（ADR-0079 已评估）。

## Consequences

- 普通用户能导入管理员能导入的全部内容，不用等人审核。
- **代价（最强的反对理由）**：导入不经过人工审核，脚本由助手直接运行，守卫看不到脚本内部。任何普通账号都能通过自己的包读写其他项目的
  工作区，项目之间的隔离对恶意用户不再成立，ADR-0079 的成功标准「别人的项目不受任何影响」不再由技术手段保证。现在只有审计和
  管理员禁用兜底，都是事后的。
- 这个取舍成立的前提是平台的账号都可信。部署到账号不可信的环境（比如多租户）之前，要先加开关或把包脚本放进沙箱。
- 数据接入包（`kind: provider`）能导入、在目录里看得到，但转换器要打进连接器网关的镜像才运行（ADR-0073：主容器不能往网关放代码）。
