# 0085 增量构建包：圈定范围、范围内修改、传播核对

## Context

**目标**：本体建好以后，要按一项业务变更改其中一部分（合成例子：「配送单加送达时效」）。建模人员先说清这一轮改哪些条目，助手只在这个范围里改，
受牵连的条目逐条过一遍，没过完不能发布。成功标准：

- 范围外已有的条目，助手改不动、删不掉；
- 每个受牵连的条目都说得出为什么在链上，例如「订单 → 下单（引用对象）→ 下单金额上限（引用操作）」；
- 范围外的改动（包括建模人员在网页上手工改的）在核对报告里列成待处理项，不并进范围或撤回就不能发布；
- 没启用这个包的项目和现在完全一样。

**基本约束**

1. 助手的写入不可信：命令文档里写「只改这几个」挡不住它顺手改别的。现有的写入范围守卫（方案 D11）只在命令运行期间按节点声明收窄，没有命令在跑时不限。
2. 助手在副本（git worktree）里干活，副本里的文件它都能写；一轮结束自动合入主线（F3）。
3. 建模人员在网页上的编辑不受助手的限制。
4. 内核不认识具体业务：限制写入的机制要通用，范围由包给；包停用后要完全恢复。
5. 守卫每次工具调用都跑，单次约 55～70 毫秒（容器内实测），不能明显变慢；守卫代码出错时拒绝（方案 D9）。
6. 传播关系要确定：同一份本体、同样的种子，每次得到同一条链，不靠模型判断。
7. 给助手看的脚本输出要有上限（CLAUDE.md 第 6 节）。
8. 自主构建按主线自动跑节点，没有建模人员在场说明「这一轮改什么」。

## Decision

**推导**

- 约束 1：只写进命令文档不够，要守卫拦。约束 4：拦截做成内核的通用声明 `confine`，包在 flow.yaml 里指定一个范围文件，
  内核只读文件里的 `status`、`baseline.commit`、`editable` 三项，不管范围怎么算出来。
- 约束 2：副本里的范围文件不能算数，否则助手改一下就扩大了范围。放宽只认主线 HEAD 上的版本（`git show`），助手改了要等合入主线、下一轮才生效。副本里确认的范围只能收紧（和主线的取并集），这样确认的这一轮接着改也受限。
  范围文件本身也只在声明它的节点的命令运行时可写。
- 合入在每一轮结束时发生：如果圈定范围在命令中途就写 `scope.json`，建模人员还没确认，这一轮结束它就生效了。所以拆成草稿（`scope.draft.*`）和确认，
  确认时才写 `scope.json`。
- 只读的是基线（圈定时的主线提交）里已有、不在 `editable` 里的条目。新增不受限：新增改不坏已有条目，核对会把新增列出来。
- 约束 3：网页编辑不拦。传播核对按「基线提交 → 当前工作区」的 git 差异算改动，范围外的改动不管是谁改的都列成待处理项，不能标记「不受影响」，只能重新圈定并进范围或撤回。
- 约束 5：读主线要起 git 进程，所以按主线 HEAD 缓存算好的只读集合（`.onto/run/confine-cache.json`）。范围文件读不出来、不是 `active`、
  基线提交不存在时不收窄：这时核对脚本也读不出范围，核对节点完成不了，发布照样挡着，坏文件不会悄悄放过发布。守卫代码本身出错仍然拒绝。
- 约束 6：传播链用确定的反向引用索引。一次扫完全部条目，建「谁引用了谁」，从种子沿反向引用广度优先走，默认 2 层，最多 5 层，
  每一项记下经过哪个条目、什么关系。core 已有的 `impact_analysis.analyze_impact` 只给一个条目的直接引用方，不看规则和指标，
  逐个节点调用要反复加载整个本体；所以另建索引，测试核对直接引用方覆盖 `analyze_impact` 的结果。
- 约束 8：节点加通用标记 `autobuild: false`，自主构建排计划时跳过。
- 只允许一个包声明 `confine`：两个包各有一份范围时，只读集合该取交集还是并集没有依据；现在只有这一个用例，先不支持。

**做法**

1. 新官方能力包 `incremental`（增量构建）0.1.0：`default_on: false`，`depends: {core: ">=0.4"}`；命令 `/incremental-scope`、`/incremental-apply`、
   `/incremental-check`，脚本 `incremental_chain.py`、`incremental_scope.py`、`incremental_check.py`，提示词「结束本轮」。
2. 主线：资料分析 → 建模 → 圈定范围 → 范围内修改 → 传播核对 → 校验 → 场景模拟 → 发布。三个节点都是 `spine`、`required`、`autobuild: false`；
   传播核对 `blocks: [core.publish]`、`stale_on: [object, operation, rule, metric]`，完成条件是 `incremental/check.md` 存在且没有 `[ ]`。
   建模做完后，下一步建议是圈定范围。
3. `incremental/scope.json`：`round`、`goal`、`baseline {commit, entries}`、`seeds [{action: add|modify|delete, path, reason}]`、
   `chain [{path, depth, via, relation, include, trail}]`、`editable`、`status: active|closed`、`max_depth`。`editable` 是种子加上链上 `include`
   的条目，脚本条目带上同名描述文件。开新一轮时，上一轮的 `scope`、`applied`、`check` 归档到 `incremental/history/<轮次>/`；
   上一轮还没结束就重新圈定，算扩大范围：基线沿用，种子、链、`editable` 合并，轮次加一。「结束本轮」把 `status` 改成 `closed`。
4. 传播关系：操作 → 对象（引用对象）、对象 → 对象（引用对象（字段：X））、操作 → 子操作（调用子操作）、操作 → 动作（调用动作）、
   规则或指标 → 对象、操作、规则、指标（引用对象、引用操作、引用规则、引用指标）、testcase → 操作（场景验证）、data-mock → 对象（测试数据）、
   scripts → 操作（脚本实现）。只算 `ontology/` 下的 object、operation、logic、rule、metric、action、data-mock、testcase、scripts；
   knowledge、diagrams 和 `index.md` 不算条目。
5. 范围内修改：命令结束前跑 `incremental_scope.py applied`，逐个核对种子在基线之后真的处理了（add 的存在、delete 的不在、modify 的有改动），
   处理不了的要写理由跳过，然后写 `incremental/applied.json`。
6. 传播核对：`incremental_check.py run` 写 `incremental/check.md` 和 `check.json`。不放 `reports/`，否则会影响校验节点的 `reports_pending` 探针。
   改动条目的上游引用方列成待确认项（`- [ ]`），`mark` 逐条写明不受影响的理由；改动占基线条目超过 30%（`--threshold` 可调）时提醒。
7. 内核：
   - flow.yaml 顶层 `confine: {scope_file}`。组装时检查：只有一个包声明；`scope_file` 是具体的相对路径，不在 `ontology/` 和受保护目录下，
     在本包某个节点的 `produces` 里。组装结果写成 `{scope_file, pack, node, entry}`。
   - 静态检查（PL-15）声明了 `confine` 时多一项 `confine`；开发 skill 的协议文档和离线检查同步。
   - scope 守卫最后加一步范围限定：Write、Edit、Bash 都查，只读命令不查；拒绝理由写明「范围外的条目只读，要扩大范围请重新圈定」。
   - 节点标记 `autobuild: false`；core 升到 0.4.0。
8. 输出上限：脚本 stdout 最多列 20 条，md 最多 50 条，后面写「还有 N 条没列出，完整清单见 <json>」，json 是全量。

## Alternatives considered

- **在 core 的增量更新（`core.update`）上扩展**：不用新包。但 `core.update` 是按需节点，响应的是资料变更；把范围、守卫、发布关卡加进去，
  所有项目都会跟着变，违背「没启用的项目不变」。做成可选包，停用就恢复。
- **只写命令文档，靠事后核对**：内核不动。但越界要到核对时才发现，那时改动已经合入主线，回退要在提交里挑，比工具调用时拦下代价大。
- **包自带拒绝型 hook，内核不加声明**：PL-15 允许包追加拒绝型 hook，最接近「内核不改」，是最强的备选。不选是因为从 Bash 命令里认出写入目标
  （重定向、`sed -i`、`python -c`、变量、`cd` 之后的相对路径、git 子命令）的解析在内核守卫里，包里再写一份会和内核分叉，
  绕过写法补在一处、另一处漏；装配时也没有地方检查「只有一个包在限定」。代价是内核多一个声明。
- **网页编辑器里范围外也只读**：口径一致，但建模人员发现范围圈错时只能先重新圈定再改，和约束 3 冲突。核对报告把人改的列成待处理项、发布前必须处理，就够了。
- **传播链交给模型判断**：能发现文档里没写成链接的隐含依赖，但每次结果不同，解释不了，也测不了，违背约束 6。隐含依赖留给建模人员在核对时看。
- **按节点逐个调用 `analyze_impact`**：复用现成代码，但不看规则和指标，多层时反复加载整个本体。
- **在命令中途就写 `scope.json`**：少两个草稿文件，但没确认的范围会在这一轮结束时合入生效。

## Consequences

- 启用后，建模人员说「配送单加时效」，助手先给出种子和传播链，确认后才动手；范围外的误改在工具调用时就被拒，提示去重新圈定。
- 实测（容器内，合成本体）：守卫单次 55～70 毫秒，范围生效时多 5～20 毫秒（2000 个条目，缓存命中时多 5～9 毫秒）；
  起草范围 200 个条目 0.19 秒，2000 个条目 0.37 秒。
- **代价（最强的反对理由）**：守卫只拦工具调用里看得出路径的写法。助手写一个 `tmp/x.py` 再运行，或用 `git reset`、`git stash` 改工作区，守卫看不到；
  助手也能自己跑 `state_helper.py acquire incremental-scope` 拿到写范围文件的身份（改动要合入主线、下一轮才生效）；`check.md` 没有守卫保护，
  助手可以不跑核对脚本，直接写一份没有 `[ ]` 的报告让节点完成。所以 `confine` 是护栏，不是安全边界。兜底是传播核对按 git 差异算改动，
  绕过去的范围外改动会在核对时列成待处理项、挡住发布，前提是核对脚本真的跑了。
- 一轮结束后再改本体，传播核对过期，发布被挡；要重新核对、开新一轮或停用包。启用了这个包的项目，每次发布前都要走完一轮。
- 扩大范围让轮次加一，上一轮的修改记录和核对标记归档，范围内修改和传播核对要重做。
- 范围生效时，在工作区根目录执行整体还原类命令（`git checkout .`、`git clean`）会被拒，因为会动到只读条目。
- 一个条目标记为不受影响之后，同一轮里它或它的上游又改了，标记不会自动失效，只在开新一轮时清空。
- 只能有一个包声明 `confine`；以后有第二个用例，要先定只读集合取交集还是并集。
- 包名 `incremental` 被内置包占着，用户上传同名包会被 `private_name` 拒。
- 导入的项目没有资料分析报告时，建议条先提资料分析，不直接到圈定范围；导入流程另行处理。
- 没启用的项目：组装出的 flow.yaml 没有 `confine`，也没有这三个节点，守卫和发布关卡的行为不变，全量测试覆盖。
