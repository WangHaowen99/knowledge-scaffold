# 0019 脚本入参与子操作的单独调用，对齐 consumer 智能体的调用方式

## Context

consumer 的智能体先从操作目录里选一个 operation，再执行它绑定的脚本。评测中出现过两类失败，都发生在脚本
逻辑之外：

1. **参数被 consumer 拒绝，对话终止。** consumer 在启动脚本前校验参数
   （`consumer/backend/agent/tools/execute_script.py`，设计见 `docs/script-argument-evidence.md`）：
   - 参数里的每个 JSON 对象都是一条记录，顶层参数整体也算一条。记录里能在本轮查询结果中按同名字段找到的
     字段有两个以上、其中有标识字段时，必须出自同一条查询结果（`evidence_record_mismatch`）；
   - 标识字段的取值必须出现在用户请求或查询结果里（`ungrounded_identity`）。
   被拒时脚本不运行，诊断只有错误码和字段路径；同一原因再失败一次，consumer 按停滞（`AGENT_LOOP_STALLED`）
   终止整轮对话。
   生成的脚本常要求智能体传「拼好的记录」，比如事件记录里带上别的对象的字段，或者顶层平铺多个分属
   不同对象的编号。另一种情况是记录里要求外键：智能体查询时只取它认为需要的字段，用作过滤条件的外键往往
   不在返回结果里，只能从别的记录补，于是被判为拼接。
2. **选中可单独调用的子操作，跳过主流程的前置检查。** 子操作标了「可单独调用 > 是」就有自己的脚本，
   可被直接选中。如果主流程在调用它之前有输入检查（如资料缺失、资料冲突的判断），这个子操作的脚本又没有
   同样的检查，单独执行时就会在资料有问题的情况下照常给出结论。子操作描述符的标题只写了它判断什么，
   没写它不含哪些检查；consumer 在执行结果里附的「只覆盖这一步」提示也是软约束，智能体可能不理会。
3. **假设场景里只能编造编号。** 用户只描述情况、不给编号时（如「假设某个订单……会怎样」），查询结果里也没有
   编号。脚本却把编号参数、或只含编号的记录参数设为必填，参数示例里又有编号，智能体照着示例填一个，
   consumer 判 `ungrounded_identity` 拒绝。
4. **「是/否」取值的表示不一致。** 图数据源导入时把「是/否」列推断为布尔值（modeling 的 value-inference），
   查询结果里是 `true` / `false`；脚本按 `== "是"` 判断，智能体原样拷贝的布尔值被当成缺失，结论变成资料不足。
   只有智能体自己把布尔值改写成「是/否」时才通过，结果不稳定。
5. **脚本缺编号就报错退出，对话直接终止。** consumer 把脚本的任何非 0 退出都判为终止性错误
   （`_terminal_execute_script_error`），本轮对话立即结束，智能体没有机会改参数重试；退出码 0、输出 `ok:false`
   的结果只算这次调用失败。编号改成可选之后，脚本在找不到编号时仍以 `INVALID_INPUT` 非 0 退出，或者用记录里
   有没有编号来判断记录缺不缺，用户只描述情况的提问因此全部失败。运行验证里「不传编号」的用例只去掉了
   顶层编号参数，记录里仍带着编号，所以没有发现。
6. **「记录已提供」却没给取值，没有传法。** 假设场景的题面常只写「某记录已完整提供」，不给这条记录的任何取值。
   描述符只告诉智能体编号没有就省略，智能体便整条不传；脚本按「有没有字段取值」判断记录在不在，
   于是一律判记录缺失、资料不足，后面的步骤都不执行；字段全为空的记录同样被当成缺失。
   运行验证只看退出码和 JSON 格式，用例又给这条记录编了题面不会给的字段，结论错了也照样通过。
7. **约定有了，智能体第一次仍然漏传；输出也答不全问题。** 加上「没取值传 `{}`」的约定后，假设场景题的智能体
   大多仍是第一次不传、看到「参数未传」后才改传 `{}` 重试，个别不重试就按记录缺失作答：参数说明开头是 codegen
   写的「不传时按缺少记录输出资料不足」，约定排在长说明后面，紧接着又是「编号没有就省略」。另外，评分步骤只输出
   结论和总分，用户问分项得分时无从回答；流程停止时最终结论只留 `null`，智能体回答「无法判断」。
8. **枚举字段自造取值，结论悄悄变错。** 对象属性清单写了枚举字段的允许取值，但智能体调用时只看参数说明，
   假设场景里又常不读对象文档，便按字面意思自造取值（如把产品名当成需求类型）。脚本不认识这个取值，
   当成条件不满足继续往下算，给出相反的结论，智能体照此作答。
9. **没有编号时，空编号被当成同一条记录。** 脚本在逐条判断里按顺序约定关联了记录，汇总和集合判断时却仍按编号
   匹配、去重：没有编号时两边都是空串，每条记录都匹配到第一条，不同记录被并成一条，`steps` 也按空编号互相覆盖，
   集合判断给出相反的结论。另外，题面用代号说明记录归属（如两条记录分属甲、乙）时，智能体按「编号没有就省略」
   的提示把代号也省掉，脚本无从发现不一致；流程停止时只给 `null`，面对引导式的提问，智能体会顺着问法给出与停止
   相反的结论。

## Decision

只在 onto-modeling 侧修正，让生成的知识包第一次调用就走对：

1. **入参按来源对象分组**：
   - 一个记录参数只装一个对象的查询结果，每项是一条查询结果；
   - 字段名逐字使用对象属性清单的英文名称，取值原样拷贝；
   - 不同对象分成不同参数，在脚本里按关联字段关联；派生值在脚本里算；
   - 顶层标量参数只放用户给的条件，不与对象属性同名。
   `script_argument_shape.py` 按 consumer 的判定口径（同名字段 + 标识字段）拦截两类写法：记录参数示例里的
   字段分属多个对象且含标识字段，以及顶层有两个以上与对象属性同名的参数且含标识字段。规则检查
   （`--include-scripts`）与知识包导出（`script_argument_shape`）共用这套检查，有错误时拒绝。
2. **标识字段与外键按可选处理**：脚本只在两边都有值时核对关联与一致性，缺失时按调用范围关联，
   不报错、不要求智能体补。记录是否提供只看参数传没传：传了就算提供，包括 `{}` 和字段为空的记录，
   缺哪个字段按该字段的规则处理；只有参数没传才算记录缺失。多条记录需要一一对应而没有编号时，
   按参数说明里写明的顺序约定关联，没有约定就输出资料不足。记录参数的描述符说明最前面自动写明「必须照传：
   记录存在就要传，没给任何取值时对象参数传 `{}`、数组参数每条传一个 `{}`；只有记录确实不存在时才不传」，
   后面补上「每项原样拷贝同一条查询结果；查询结果里没有的字段（包括外键）直接省略，不要从其他记录补」，编号的
   提示写明「只省略这些字段，省略后不剩字段就传 `{}`」。参数说明里写「不传时按缺少记录处理」的，规则检查给出警告。
   记录参数没传造成的缺失，脚本用模板的 `_missing_record` 写明参数未传与「已提供但没取值时传 `{}` 重新调用」。
3. **收紧「可单独调用」**：同时满足「会被单独询问或单独触发」和「单独执行时结论仍然成立」两条才填「是」。
   父 operation 在调用它之前有它所依赖的输入检查、评分、前置判断或停止条件时，填「否」。
   `operation_relations.stops_before_call` 按逻辑描述里第一次提到子 operation 之前有没有停止条件
   （「不满足前提时终止流程」等规范写法）来判断；规则检查对「是」与之同时出现的组合给出警告。
   确需单独调用时，前置检查写进库模块，主脚本与子操作脚本共用。
4. **描述符写明适用范围**：子 operation 自己的脚本，描述符标题加上「只覆盖「父流程」中的这一步」，用途里写明
   不含父流程之前的输入检查与前置判断，问题涉及资料缺失、资料冲突或要完整结论时改用父流程。
   这些内容由「与operation的关联」生成，工作区与导出同一渲染器。主脚本的 `steps` 除每一步的结论外，还给出
   这一步的中间结果（评分的分项取值与得分、总分与阈值，判断命中与未命中的条件）；流程停止时，最终结论按
   operation 文档的规则写出停止对应的结论（如「不通过」）及停在哪一步、原因，不只留 `null` 或「未执行」。
   这两条由 codegen 规则与复审 agent 约束，停止条件的验证用例用 `stdout_contains` 写明最终结论。
5. **按 consumer 的成败口径区分三类结果**：
   - 资料问题（记录、字段、编号缺失，记录无法关联，取值矛盾）是业务结论，退出码 0，写在输出字段里；
   - 参数形态错误（类型、格式、取值范围不对）由模板的 `_invalid_input` 输出退出码 0 的
     `{"ok": false, "error": {"code": "INVALID_INPUT", "message": 字段级原因}}`，智能体改了参数可以重试；
   - 只有脚本自身异常才非 0 退出，以 `SCRIPT_FAILED` 在 stderr 输出 `ONTO_PUBLIC_ERROR`（出错步骤与异常类型）。
   规则检查对没有输出 `ONTO_PUBLIC_ERROR` 的可执行脚本、以及 `_public_error("INVALID_INPUT", ...)` 这种非 0 退出的
   参数错误给出警告。运行验证按同一口径判定：成功用例输出 `ok:false` 判为失败，报错用例接受非 0 退出或 `ok:false`。
6. **编号参数不设必填**：标量编号参数（按 consumer 的标识字段口径判定）与只含编号字段的必填记录参数，
   规则检查与导出报错。描述符在编号参数、记录参数里的编号字段后注明「只在查询结果或用户问题里出现时才填，
   没有就省略；示例里的编号只是格式示例」。参数里有编号的对外脚本，`script_verify` 要求至少一个成功用例在
   argv 的任何位置都不带编号（顶层编号参数和记录里的编号、外键都去掉，题面没给取值的记录传 `{}`），
   并用 `stdout_contains` 写明预期结论（应与资料完整、带编号的同一场景一致），否则拒绝用例文件。
   `stdout_contains` 只比对执行器回传的 stdout 前 1500 字，不改沙箱网关的执行器协议，所以结论字段要放在输出最前面。
7. **「是/否」字段先归一**：模板提供 `_yes_no`，布尔值与 是/否/true/false/yes/no/y/n 都归一成「是」「否」，
   认不出返回 None。脚本里出现与「是」「否」字面量的比较、却没有 `_yes_no` 或 `isinstance(..., bool)` 时，
   规则检查给出警告（静态检查只能看写法，不能确定比较对象就是「是/否」字段，所以不报错）。运行验证要有传布尔值的用例。
8. **枚举字段写明允许取值并在脚本里校验**：对象属性清单里类型为「枚举」、写了「取值：a / b」的字段
   （「是/否」字段除外），描述符在点到它的记录参数说明里列出允许取值；工作区与导出同一渲染器，都从对象文档读取。
   脚本用模板的 `_check_choice` 校验，不在范围内时以 `_invalid_input` 返回字段位置与允许取值，智能体改正后重试；
   operation 文档对非法值另有规定时按文档处理。这条由 codegen 规则与复审 agent 约束，运行验证要有非法取值的用例。
9. **没有编号时按位置当键，主脚本给出最终结论**：
   - 记录之间的匹配、去重、分组和 `steps` 的键都用模板的 `_record_key`：有编号用编号，没有编号用数组位置，
     两个空编号不算同一条；参数说明里的顺序约定在汇总、集合判断时同样适用。运行验证的多条无编号用例要让
     各条结论不同，并逐条断言；
   - 描述符的编号提示补上「题面用名称或代号说明归属时，原样填进对应编号字段」，这些说法出现在用户问题里，
     consumer 不会判为编造；
   - 主脚本每条结论最前面放「最终结论」字段，一句话直接回答问题，停止时写明停止对应的结论、停在哪一步、
     不修改输入继续判断。
   编号提示由描述符自动写出；位置键与最终结论由 codegen 规则与复审 agent 约束。

以上规则只依据知识包的结构（调用关系、属性清单、逻辑描述里的停止条件），与具体业务无关。

## Alternatives considered

- **在 consumer 侧返回更详细的诊断、放宽停滞保护，或强制改道到主流程**：consumer 有意不在公开诊断里回显
  参数值，停滞保护用于防止循环；已部署的 consumer 也不会随之更新。
- **只靠提示词要求智能体不要拼字段、优先选主流程**：参数形态本身要求拼接，或子操作本身就有可执行脚本时，
  提示词改变不了结果，只能降低概率。
- **提取时完全禁止子 operation 单独调用**：会把确实独立成立、需要单独询问的步骤也挡住；改为按
  「结论是否依赖父流程的前置检查」判定。

## Consequences

- 存量知识包需要重新生成脚本的情况：
  - 脚本里有混合对象的记录参数，或顶层有多个与对象属性同名的参数：现在检查报错、导出被拒，需要按对象拆分参数，并改写脚本里的关联逻辑；
  - 「可单独调用」标为「是」、而父流程有前置检查的子 operation：会收到警告，改为「否」后用 `/ontology-codegen` 重新生成父流程脚本；
  - 编号参数或只含编号的记录参数设为必填：现在检查报错、导出被拒，需要改为可选，并让脚本在缺编号时按调用范围处理；
  - 按「是/否」字符串判断的脚本：会收到警告，改用 `_yes_no` 归一后重新验证；
  - 参数错误以非 0 退出、或缺编号时报错的脚本：会收到警告，重新生成时运行验证要求不带编号的成功用例。
    已有的验证记录按源码哈希保留，脚本改动后才按新要求重新验证；
  - 用「有没有字段取值」判断记录在不在的脚本：静态检查查不出来，重新生成时由带 `stdout_contains` 的不带编号用例暴露；
  - 记录参数说明写了「不传时按缺少记录处理」的脚本会收到警告；评分步骤只输出结论、流程停止时只留 `null` 的脚本，
    由复审 agent 报出，重新生成后补上中间结果与停止时的结论；
  - 枚举字段不认识的取值被当成条件不满足的脚本：由复审 agent 报出，重新生成时改用 `_check_choice` 校验；
  - 按编号匹配、去重或做 `steps` 键的脚本，以及结论里没有「最终结论」的主脚本：由复审 agent 报出，重新生成时
    改用 `_record_key` 并补上最终结论。
- 子 operation 的描述符内容变化，工作区刷新时自动重新生成；编号参数的说明也会多出「没有就省略」的提示，
  记录参数说明的最前面多出「必须照传、没取值传 {}」，点到的枚举字段多出允许取值，执行边界改写为资料问题、
  参数错误、脚本异常三类。
- 形态检查只覆盖参数说明里有示例的记录参数；停止条件按规范写法识别，写法不规范时可能漏报，由提取规则与复审 agent 兜底。
- 「用编号判断记录缺失」「只有一边有编号就判不一致」静态检查查不出来，靠不带编号的成功用例在运行验证里暴露；
  `stdout_contains` 的预期结论由 codegen 按 operation 文档写出，写错时仍可能放过错误的脚本。
- consumer 对用户问题里组装出的多条记录有分段一致性检查（`request_record_mismatch`）：多条记录共有的取值只在
  问题里写一次时可能误判，这一类需要在 consumer 侧修正，onto-modeling 无法规避。
