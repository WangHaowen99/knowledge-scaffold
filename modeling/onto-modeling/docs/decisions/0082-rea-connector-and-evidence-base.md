# 0082 REA 逆向连接器与证据层公共底座

## Context

**目标**：业务系统只有安装包、没有源码和文档时，建模者上传程序，拿到带锚点的候选对象、操作和外部调用，抽取时可以引用。
同一套底座（数据源、上传、任务、快照、检索、取证节点）之后接数据库和代码仓库连接器。

成功标准：

1. 上传一个 JS/Electron、.NET 或 PyInstaller 程序，采集任务成功，快照提交到 `resource/systems/<源>/<快照>/`；
2. 资料页的数据源、采集与快照、证据浏览器三个子页用真实接口能走通；
3. 启用系统逆向建模包的项目里，助手能检索快照，在产物里写 `bin:` 锚点，锚点能解析回记录；
4. 主容器从不解析目标程序；REA 从不运行目标程序，也连不上网络。

用户 11-05 定：方向按批量静态做；公共底座先用 REA 打通，再加数据库和代码连接器。

**基本约束**

1. 目标程序不可信，解析器自己也可能有漏洞（ADR-0076：主容器不解析不可信文件）。
2. REA 有一部分命令会运行目标、连设备或开浏览器，只有一部分是静态分析。
3. 程序里的字符串会原样出现在 REA 的结果里。11-05 的验证里，合成程序注释里的一句指令原样出现在输出中，所以结果要按不可信数据对待。
4. 真实程序的结果可能几百 MB；工作区进 git，快照在 git 里的部分要有上限（详设 5.8.4 建议 20 MB）。
5. 安装包常有几百 MB，资料上传上限是 20 MiB。
6. 逆向要有软件授权。
7. 要能离线部署，REA 更新频繁。
8. 以后网关会存数据库凭据、接业务网络（详设 5.8.2），网关里不能跑解析不可信文件的东西。
9. 智能体和后端在同一个容器里，能直接访问内部网络上的服务（详设 5.8.9）。

已核实的事实（11-05，rea-agents 6.8.0，Node 22）：在断网、只读根文件系统、非 root 的容器里能跑；
`analyze-javascript-application` 分析 6 个文件的合成 Electron 程序用 4.6 秒，输出 446 KB；输出是 REA 的 Evidence
（`subject`、`provider`、`confidence`、`limitations`、`normalized_result.semantic_graph` 等），没有稳定到跨版本的 ID。

## Decision

**推导**

- 约束 1、8 → REA 不能放主容器，也不能放网关，单独一个旁路容器 `rea-sidecar`，只有它碰目标程序的字节。
- 约束 9 → 旁路容器只接一个专用内部网络 `rea`，这个网络上只有网关；主容器不在上面，智能体没有路由过去，旁路容器因此不需要票据。
- 采集任务的票据、预算、审计、状态、快照包这些对所有连接器都一样，放网关统一做；所以内核不直连旁路容器，走「内核 → 网关 → 旁路容器」。
- 约束 2 → 旁路容器里的命令写死白名单，只放静态分析命令；不开 REA 的 MCP，不让智能体直接调。
- 约束 3、4 → 结果在旁路容器里就地转成标准记录（REA 输出已经在它内存里，不用再搬一遍大 JSON）。转出来的记录进工作区；REA 原始结果
  进工作区外按内容寻址的 blob 仓，下钻时再用。整份快照标 `untrusted_content`，给智能体的输出都带这个标记。
- 约束 5 → 单独做分块上传，原样存进 blob 仓，不进 `resource/` 和 git，主容器只算哈希，不解析。
- 约束 6 → REA 类数据源登记时必须写授权说明，每次采集记审计。
- 约束 7 → 镜像里固定 REA 版本，构建时装好，运行时不联网、不 `npx`。
- REA 的结果没有跨版本稳定的 ID → 锚点用名字生成（IPC 通道名、类名、模块路径、路由），不用偏移、不带版本号。同一系统的新版本是同一个
  数据源下的新快照，按「锚点 + 哈希」比较差异，和数据库连接器一样。

**做法**（接口细节见 `docs/plugin-architecture/design/evidence-collection.md`）

1. **旁路容器 `rea-sidecar`**：`node:22-slim` + procps + 固定版本的 `rea-agents`，非 root、只读根文件系统、`/scratch` 放任务目录，
   限内存、CPU、进程数；只接 `rea` 网络。一个没有依赖的 Node HTTP 服务：收目标程序 → 判定类型 → 跑白名单里的静态命令 → 转标准记录。
   同时只跑 1 个任务，每个任务有超时，结束清目录。
2. **网关加采集任务**：`POST /v1/jobs`（请求体是目标程序，边收边转给旁路容器，网关不落盘）、查进度、取消、取快照包、清理。
   提供方 `rea-static` 在网关里只是旁路容器的客户端，负责预算、组装快照包（清单、记录、摘要、原始结果）。
3. **内核底座**：数据源登记与项目授权、分块上传、采集任务（后台执行、进度推送、重启后标失败）、快照入库（校验 → 扫描 → 原始结果进
   blob 仓 → 经写入路径提交 → 建索引）、检索接口、锚点解析。索引是数据目录里每个项目一个 SQLite（FTS5），可以从工作区重建。
4. **自助登记**：提供方不要凭据、不连业务网络（REA 就是）时，登录用户可以自己登记，登记只有本人和管理员看得到，本人才能授权给自己的
   项目；要凭据的（数据库、代码仓库）仍然只有管理员登记。依据：自助类的风险是旁路容器里的解析，和谁登记无关；而凭据类会连业务系统。
5. **系统逆向建模包 `rev`**：资料页三个子页、取证节点 `rev.evidence`（串在资料分析和建模之间，项目有授权的数据源才出现）、
   命令 `/rev-evidence`、工作区脚本 `evidence.py`（检索、查看、相邻记录、被谁引用、快照差异；两个引擎都用命令行）。
   建模命令在有快照时先读摘要、用脚本检索，产物的「来源」写锚点；从系统里抽的结果都是候选，要确认。
6. **本轮范围**：第一批目标（JS/Electron、.NET、PyInstaller、安装目录清单）。下钻（`sample`）、REA 自己的版本对比、第二批目标
   （APK、原生程序，要 JDK、Ghidra）、HAR 和 SQLite（要先做脱敏）后做；凭据接口（EV-06、EV-07）等数据库连接器时一起做，本轮仍回 501。
   MCP 形式的 `evidence.*` 工具本轮不做，命令行两个引擎都能用。

## Alternatives considered

- **智能体直连 REA 的 MCP**：REA 默认就这么用，也最省事。但要把解析不可信文件的进程放进主容器（违反 ADR-0076），目标内容会不受限地
  进上下文，结果也没有稳定锚点、无法复现。
- **REA 放进网关镜像**：少一个容器。但网关以后会存数据库凭据、接业务网络，REA 解析器一旦被利用就能拿到凭据。
- **内核直连旁路容器**：少一跳。但票据、预算、审计、快照包格式就要为 REA 单独做一份，数据库连接器来了又是一份。
- **在网关里用 Python 转换 REA 结果**：转换逻辑和提供方 SPI 同语言。但几百 MB 的 JSON 要再序列化、传输、解析一遍，网关内存也要跟着放大。
- **锚点带版本号**（`bin:crm-client-3.2/...`）：按版本分开最直观，但每个版本的锚点都不同，产物要逐个改写，也违反详设 5.8.5 规则 1。

## Consequences

- 契约：新增 EV-31～EV-33（分块上传）；EV-02、EV-04、EV-05 对自助类提供方放开给登录用户；EV-10 多 `self_service`、`input` 字段。
  见 `contract-changes.md`「F13」。
- 部署多一个容器和一个内部网络；镜像约多 300 MB（Node 运行时 + REA 依赖 168 MB）。第二批带 JDK、Ghidra 后估计 1～2 GB，没实测。
- REA 每次升级都要重跑旁路容器的测试（`connectors/rea-sidecar/test`），记录映射可能要跟着改。
- 批量静态分析丢了 REA 交互追问的能力；以后确认需要，可以由内核代理一小部分只读命令，加票据和输出上限。
- 自助登记让任何登录用户都能让旁路容器解析任意文件。旁路容器断网、只读、限资源，最坏情况是这个容器里的进程被控制，拿不到凭据和
  其他项目的数据；分块上传占磁盘，用每人配额和单文件上限兜住。
- 详设 5.8.9 的缺口仍在：智能体理论上能读到签票据的密钥。对 REA 来说伪造票据也只能让旁路容器分析一个文件。
