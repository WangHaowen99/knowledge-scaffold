# 0043 配额：用量台账扫会话历史，发送前闸门，出错放行

## Context

方案 E9、详设 4.10.1：按项目和用户限制并发、token 预算、采集频率；自主构建的预算只能在这个上限之内设。
契约 SY-15、SY-16 给管理员读写默认限额与单独设置，超限返回 `429 quota_exceeded`。现状没有任何限制：
会话池只管全局在线引擎数，用量只在 P-16 里按项目汇总展示。

要定的是：用量从哪来、在哪一步拦、配额自己坏了怎么办。

## Decision

1. **用量台账**（`governance/quota.py`）：数据目录 `governance/quota.sqlite`，按（项目、所有者、UTC 日、来源）聚合
   token 与成本。来源是会话历史里的用量事件（和 P-16 同一口径，含删除会话时留存的用量文件）：按文件记读到的
   字节位置，只读新增的完整行；每条事件按指纹去重——文件截断、改写后从头重扫，会话删除后用量搬进留存文件，
   都不重复计数；已入账的用量不因删会话、删项目而减少（删项目不能绕开当日上限）。只管本月和上月。
2. **用量记在项目所有者名下**（本地模式是 `local`）；所有者变更后已入账的不跟着走。
3. **限额**：`governance/quotas.json`，默认值加单独设置（用户或项目），0 表示不限。默认：每用户并发会话 3、
   每日 200 万 token、每数据源每小时采集 6 次；每项目在线引擎 1（只读，会话池保证）、每月 2000 万 token、
   快照 git 20 MB（P3 证据快照落地后才检查）。
4. **在哪拦**：纯 ASGI 闸门 `QuotaGate`，挂在鉴权之内，只看两条路径——发消息（S-07）与发命令（S-20）。
   顺序：用户并发会话（发给已在线的项目不起新引擎，不算）→ 用户当日 token → 项目当月 token。只替项目所有者报
   配额，项目不存在、不是所有者交给路由回 404、403。`details` 带 `quota`、`scope`、`limit`、`used`、`reset_at`。
5. **出错放行**：配额自身出错（库坏、读历史失败）一律放行并记日志——配额不能拖垮服务。
6. **给 P3 的检查函数**：`check_collection`（证据采集，按用户和数据源计一小时窗口）、`autobuild_budget_cap`
   （自主构建预算只能设在用户当日与项目当月剩余的较小者之内）；证据采集、自主构建落地时调用。

## Alternatives considered

- **在会话宿主里记账**：每个引擎回报用量的地方都要改（B4a 正在重写宿主），而会话历史本来就是两引擎统一的
  落盘口径；扫历史与宿主解耦，宿主换了实现也不用动。
- **超限时打断正在跑的一轮**：一轮跑到一半停掉会留下半成品；只在发送前拦，正在跑的这一轮跑完。
- **出错拒绝（fail closed）**：配额是成本护栏，不是安全边界；一个坏掉的 SQLite 不应让所有人都发不了消息。

## Consequences

- 用量入账有最长约 1 秒的滞后（扫描节流），一轮跑完立刻再发可能多放一轮；可以接受。
- 配额只拦用户主动发起的对话；自主构建（P3）在启动前用 `autobuild_budget_cap` 卡预算，运行中的花费由自主构建自己的
  预算控制。
- 契约 SY-15 只写了 admin，实现让 ops 也能读（与治理平面「运维面只读接口 admin、ops 都能看」一致），写仍只有 admin。
