# 0070 命令锁的收尾：等用户回复的阶段、平台代为释放

## Context

执行记录（ADR-0035）按工具箱的命令锁判断命令有没有做完：一轮结束锁还在就记为等待。真实模型（V 阶段，内测引擎）
陪伴建模 5 个命令有 3 个结束时锁还在，主因是命令文档在收尾列「下一步建议」菜单，持着锁等用户回「完成」。53553af4
让建议条主推「继续」兜底，但分不清两种情况：命令正常停下来等用户回复（`/ontology-update` 第 3 步等「确认」），
和助手说做完了却没放锁。前者主推「继续」，模型可能把它当成「确认」，去执行用户还没看过的清单。

## Decision

1. **锁阶段约定**（STEP0_TEMPLATE 第 4、5 步）：命令停下来等用户回复前 `acquire <命令> confirm`，回复后切回接下来的
   阶段；做完时先 `release`，再写两三句小结，不列下一步菜单（下一步由建议条给出）。
2. **流程声明**：flow.yaml 的命令前置多一个可选字段 `lock_waits: [confirm]`，声明这条命令遵守上面的约定。core 的
   research、extract-object、extract-operation、extract-rule-metric、validate、consistency、update 与官方包里持锁的
   evolution、flowchart、codegen、solver-evaluator、mock、trace 都声明了；`test_f_lock_convention.py` 核对「文档里
   acquire 了锁的命令都声明了、文档里也切 confirm」。
3. **平台的判断**（`session_host/exec_records.py`）：
   - 锁在等回复的阶段（声明了的按声明，没声明的认 `confirm`、`awaiting_user`）：正常等待，建议条不主推「继续」；
   - 锁在别的阶段：没收尾，建议条主推「继续」（FL-02 与一轮结束推给界面的同一份）；
   - 一轮正常结束、没有等你回答的问题，命令声明了 `lock_waits`，这次执行保存过（有提交），副本里没有没提交的改动：
     平台代为释放（清锁与写入范围），执行记录记完成、`released_by=platform`。
4. **自己的锁**：`check-lock` 对本会话（同一引擎实例）拿的锁输出 `own:`，STEP0 写明不清理、不问用户。上下文压缩后
   助手不再把自己刚拿的锁当残留强制释放（自主构建里这会让策略作答，台账多出无意义的「假设」）。

## Alternatives considered

- **一轮结束锁还在就一律代为释放**：等用户回复、被迭代上限截断在半路的命令都会被记成做完，写入范围（段的保护）也丢了。
- **按助手正文判断「说做完了」**：不可靠，而且两种引擎写法不同。
- **只改命令文档**：旧项目锁着旧 core，要等跟随升级；模型也不一定照做。平台这一层对声明了的命令兜底。

## Consequences

- 锁定旧 core 的项目没有 `lock_waits`：平台不代为释放，照旧只主推「继续」，跟随升级后生效。
- 新加的持锁命令要在流程里声明 `lock_waits`，文档按约定切 `confirm`；只声明不切，等回复会被当成做完。
- 「保存过且副本干净」不等于语义上的做完：命令在两次提交之间停下来等用户、又没切 `confirm` 时会被代为释放；这时用户
  接着回复，助手照常往下做（`acquire` 总能重新拿锁），只是执行记录已经记完成。
