# 0067 插件运维：O-25～O-28 与按项目灰度

## Context

运维中心的「插件运维」表格调 O-25～O-29：列表、调灰度、回滚通道版本、禁用版本、熔断。B3b 留下登记点，B4c 接了
就绪检查的 `assembly` 项、O-29 的包查询、O-42 的包版本；O-25～O-28 一直 404，页面报错。灰度（详设 8.1 第 2 步、
P4 的「灰度通道」）要按比例放量；现有机制是 stable / beta 两个通道指针，锁定版本的项目不动，跟随通道
（`follow=true`）的项目下一条消息前换到通道版本；beta 的 `percent/by/targets` 由 PL-17 存着但没人用。

## Decision

1. **O-25 列表**（`services/packs/governance.ops_items`）：每个包的 stable 版本、beta 版本、项目在用的版本、禁用的版本
   各一行，即 O-25 的一项加 `rollback_to`（该通道历史里上一个还在、没禁用的版本；历史里没有时取更早的版本）。
   禁用的版本 `channel="retired"`、灰度 0。`error_rate_pct` 为 null（节点失败率还没有采集）。
2. **O-27 回滚通道**：改通道指针，锁定版本的项目不受影响，跟随的项目下一条消息生效；core 的 stable 同 O-32（先备份包仓库）。
3. **O-28 禁用版本**：记进包仓库通道记录的 `disabled`；`repository.channel()` 遇到被禁用的指针视为没设，`latest` 改取最新的
   可用版本——新项目不能再启用它，跟随通道的项目下一条消息前换过去。core 的默认版本不能禁用（`409 pack_required`，先回滚
   默认版本）。「已锁定它的项目进待处理」没做（待处理由 B4b 维护）。
4. **O-26 灰度只做按项目**：只能调 beta 通道上的版本（stable 恒为全量，调它回 400）。比例和名单存在 beta 记录里；
   `runtime.follow` 对跟随 stable 的项目，按项目编号的 SHA-256 取 0～99 的稳定分桶，落在比例里或在名单里就跟 beta 版本，
   比例收回时回到 stable 版本。按租户（`by=tenant`）回 `501 rollout_not_available`：单人项目没有租户归属，P4 再做。
   PL-17 发布到 beta 时带的 `rollout` 同样生效；`auto_breaker`（失败率超阈值自动熔断）没做。
5. **O-42** 多一行 `flow.lock` 格式版本（1）。

## Alternatives considered

- **O-26 全部回 501**：现有通道机制加一个分桶就能放量，比例、名单都已经有地方存，做到按项目不需要新的存储。
- **灰度按随机数抽项目**：同一个项目每次判断要一致，否则会在两个版本之间来回切；用编号哈希分桶。
- **禁用时把跟随的项目留在禁用版本上**：版本被禁用通常是有问题，跟随通道的项目本来就随通道走，换走更安全；锁定版本的项目不动。

## Consequences

- 运维中心插件运维页的五个按钮都能用；按租户灰度、自动熔断、错误率、禁用后进待处理是后续项（`_plan/gaps.md` B5c）。
- 跟随 stable 的项目可能因为灰度拿到预发布版本，版本号里能看出来（如 `0.3.0-rc.1`），撤回灰度后回到 stable。
