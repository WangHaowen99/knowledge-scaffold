# 0092 评测对接改为独立评测服务：入口、完成通知、以用户登录读回，评测优化成批反馈

取代 ADR-0020 的「反馈入」（X-05）和「onto 不主动调用评测服务」这一条；包出与验证回执（X-01、X-04）由 ADR-0098 取代。

## Context

**目标**：知识包发布到 Hub 之后，用户能在 onto 里对已发布版本发起评测、看到评测进度和结果（报告、优化建议、完整回答），
一键把这一轮的失分交给反馈演进修订本体，改完发布的新版本自动作为这一轮的处理结果回到评测服务。服务对象是建模项目的所有者。
成功标准：整栈走通「发布 → 去评测 → 完成通知 → 看报告与建议 → 评测优化 → 反馈演进 → 发布新版本 → 回写」，旧版评测留下的报告还能只读查看。

**现状（develop 已合入）**：评测服务（eval-service）独立部署，评测轮次与产物归它所有、按调用者隔离；它在轮次结束后向
`POST /api/internal/evaluation/notifications` 发完成通知（服务凭据，SQLite 发件箱，至少一次送达），报告正文不在通知里，
建模服务查看时以用户自己的登录读回。develop 的评测优化把报告、建议拉进 `reports/`，命令 `/ontology-evolution <报告>` 读报告。

本分支（插件化）在 ADR-0020 里把评测移出、改成三份契约：评测服务持服务令牌调 X-05 把反馈推进 `feedback/`，反馈演进包（evo）
按 `onto-feedback/v1` 读批次；资料区「外部反馈」分组、待处理、增量更新的外部反馈卡都读同一批次。X-05 实际没有调用方。

**基本约束**

1. 评测服务调用的两条外部路径不能变：完成通知（服务凭据）、`GET /api/hub/package-projects`（用户令牌，P1 负责）。
2. 评测记录按发起人私有：onto 不能用服务身份读，也不能让一个用户的轮次点亮另一个用户的按钮。
3. 评测服务的输入不可信（独立部署、版本可能更新）：响应体、地址、令牌不回显；字段严格校验、未知字段忽略；大小有上限。
4. 反馈演进是可选插件，输入契约只有一份（`onto-feedback/v1`）；内核不该为一个来源再造一条消费链。
5. 主容器不解析业务原件（ADR-0076）；评测数据源的业务数据不离开评测服务。
6. 旧链路的评测状态已被启动迁移删掉（ADR-0020），工作区里只剩 `reports/eval-<日期>-<时间>.md` 与 `.answers.json`。

## Decision

**推导**

- 约束 1、2 → 通知接口原样保留，免登录、只认 `X-Evaluation-Service-Token`；通知只更新按「Hub 包 × 评测服务所有者」存的状态索引，
  对账（用用户登录）整份替换。当前用户在评测服务的所有者标识从对账结果学来，不在本地按签发方推算。
- 约束 2、3 → 读报告、建议、完整回答都以当前用户的登录直连评测服务（`eval_client`），失败映射成固定文案；只有评测服务自己写给
  用户的 409 说明原样转出。这推翻了 ADR-0020「onto 不主动调用评测服务」：那一条是为服务令牌推送设计的，评测服务现在只认用户身份。
- 约束 4 → 评测优化不另造消费链：把一轮的产物整理成一批 `onto-feedback/v1` 反馈写进 `feedback/`，反馈演进、资料区、待处理、
  增量更新照常消费。批次加可选的 `attachments`（工作区相对路径）：报告（标准答案、工具失败的全文）、完整回答、优化建议（归因草稿）、
  数据源表头。报告和建议仍放 `reports/{stem}.md`，因为评测服务生成的报告里「完整回答」链接写死了 `reports/{stem}.answers.json`。
- 约束 5 → 数据源只拿表头，写成只有表头行的 csv 放 `.ontology-state/eval-service/tables/{stem}/`（不进 git），给 `table_profile.py` 三方对账。
  不再放 `.ontology-state/eval-data/`：那是旧链路目录，启动迁移每次都会删。
- X-05 没有调用方，评测优化已经覆盖它的用途 → 退役，`feedback.write` 权限范围随服务令牌的去留由 ADR-0098 一并处理。
- 约束 6 → 旧版评测记录只读（2026-11-28 随 develop !640 删除，见文末「后续」）：照 develop 的「评测执行详情」显示最近一轮（读 `.ontology-state/eval.json`，启动迁移不再删它），完整回答读报告附带的 answers.json，旧接口 `/api/projects/{id}/eval/*` 仍是 410，GET 的 successor 指向新接口。旧运行器与 modeling 服务已删，不能停止、续接旧任务。

**做法**

1. 后端：`services/eval_client.py`（用户登录调评测服务，响应上限、错误映射）、`services/evaluation_entry.py`（浏览器入口只来自部署配置）、
   `services/package_evaluations.py`（通知、索引、对账、读回、评测优化成批、建模回写）、`services/legacy_evaluations.py`、
   `routers/evaluations.py`（ES-00～ES-11，API 契约 3.21a）；`feedback_inbox` 拆出 `place()`（写批次不提交）与 `attachments`。
2. 配置：`ONTO_WEB_EVAL_PUBLIC_URL`（浏览器入口，空为同主机 5180）、`ONTO_WEB_EVAL_URL`（容器网络地址，空时不显示报告与建议）、
   `ONTO_EVALUATION_SERVICE_TOKEN`（通知凭据，空时拒收）。
3. 前端：`pages/evaluation/`——版本行的评测、求解验证、用户反馈三格，报告、建议、完整回答、标记处理失败的弹窗，旧版评测记录抽屉；
   挂在发布页的已发布版本表上。评测优化经 S-20 把 `/ontology-evolution feedback_id=…` 发到工作台对话。
4. evo 包 0.3.3：命令读 `attachments`，优化建议作归因草稿逐条复核，C 类对账用附带的表头。

## Alternatives considered

- **照 develop 只把报告放进 `reports/`，命令按报告文件名读**：反馈演进要认两种输入，资料区、待处理、增量更新看不到评测优化，
  内核和插件各有一条消费链。不取。
- **逐用例调评测服务的 `results/{case}/answer` 取标准答案**：最多 200 次请求，返回的是评测服务内部的用例结构，没有文档约定。
  标准答案和工具失败改从报告的逐用例明细里取，取不到时留空，助手读附带的报告全文。
- **X-05 保留给以后的外部来源**：没有调用方的写入口要维护服务令牌、校验、审计，出问题的面比收益大；以后真有来源再按需加。
- **表头写进批次 JSON**：`table_profile.py` 认 csv 路径，写成 csv 不用改脚本；表头不进 git，与 develop 的取舍一致。

## Consequences

- 评测要统一账号登录；本地模式与 develop 一样回 401「个人 Hub 包需要统一账号登录」（码 `login_required`，前端不当成登录过期），页面显示评测服务未配置。
- 评测优化要求反馈演进包已启用（`pack_not_enabled`）；没启用时能看报告和建议，不出「评测优化」。
- 评测服务换了报告的逐用例格式时，批次里的标准答案、工具失败会留空（不报错），反馈演进仍可读附带的报告。
- 每次评测优化往工作区提交报告、完整回答（最大 8 MiB）与批次；同一修订不重复提交。
- 发布流程（ADR-0098）在 Hub 发布成功后调 `package_evaluations.after_publish()` 立即回写；不调时下次打开已发布版本补写。
- 代价：评测优化依赖评测服务在线；评测服务不可达时只能看本地状态索引，不能看报告和建议。

## 2026-11-12 补充：除评测优化外与 develop 一致

用户要求除评测优化外，行为和页面元素都与 develop 一致（样式可按新 UI）。第一轮按「删掉多余文案」去掉或改写的元素全部改回：
已发布版本的说明与提示、评测格的空状态文字、置灰并说明原因的「报告」「优化建议」「评测优化」、「发起评测」「验证报告」、报告与建议弹窗的标题、
说明、「关闭」、错误与成功提示、标记处理失败的说明与示例、发布后的提示与 notifyPackagePublished、求解面板的「求解验证」卡、
左栏的「旧版评测记录（历史链路）」与「评测执行详情」。例外只有两处：评测优化仍成一批外部反馈（旧报告也一样，`ES-12`），
没有 develop 的「停止旧任务」「对账旧任务」（旧运行器按 ADR-0020 删除）。

## 补充（2026-11-17，ADR-0101）

反馈演进包已删除，评测优化（ES-07、ES-08、ES-12）和外部反馈批次一起去掉。评测入口、完成通知、报告查看保留。

## 补充（2026-11-22，ADR-0108）

评测优化以数据飞轮的形式回来（develop !630）：飞轮把评测产物导入 `reports/`，交 `/ontology-evolution … --flywheel` 修订，
发布后用用户本人的登录把处理结果回写评测服务。工作台的「评测优化」「标记处理失败」入口（ES-07、ES-08、ES-12）仍不恢复；
上面「发布流程调 `after_publish()` 立即回写」一条不再成立，回写在用户打开飞轮时做，只回写飞轮开始的优化。

`eval_client` 的原则从「从不带服务身份」改为：默认只用用户自己的登录；登记、续期、撤销用户本人的委托，或后台凭委托读取时，
才同时带建模的服务凭据（`X-Modeling-Service-Token`，值为 `ONTO_EVALUATION_SERVICE_TOKEN`）。服务凭据单独无用：评测服务要求它与
委托句柄一起出示，委托只能读登记的知识包。
