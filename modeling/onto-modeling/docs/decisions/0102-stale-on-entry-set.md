# 0102 重新提取只盯来源和条目增减，内容修改交给校验

## Context

**目标**：节点和步骤的「过期」只回答一件事：这份产物要不要重做、用哪个动作重做。给用户（节点状态、建议条）和自主构建
（`refresh_stale_first` 会自动执行过期项）用。成功标准：

- 校验修复、手工编辑改了对象或操作的内容，建模和指标不显示过期，自主构建不重跑提取；
- 资料分析变了，对象、操作照旧过期；新增或删除对象，操作照旧过期（可能要补提取，ADR-0090 的约束 2）；
- 一次「提取 → 校验 → 修复」之后状态收敛，不出现建模、校验互相弄过期的循环；
- 已部署项目升级后不因为定义变了整片变成过期。

**现状**：建模的「操作」一步 `stale_on: [object]`，「规则」一步与指标节点 `stale_on: [object, operation]`，比的是目录的内容指纹；
基线只在节点自己执行合入时重记。校验的写入范围是整个本体（`writes: ["ontology/*"]`），它修对象、操作的内容会让这几处一直过期。
ADR-0090 只调了建议条（不推刷新），节点仍显示过期。11-18 端到端实测（10 对象、11 操作的项目）：新逻辑校验确认、0 条待处理，
同一时刻建模显示「2 步过期」、建议条却写「必经步骤都已完成」；自主构建预览把「全部」判成「有过期」，再跑一次会重抽操作和规则（约
15 分钟），重抽又让校验过期。decisions-log 里「改一个对象就显示下游过期……过敏再调」那一条，这次用真实模型确认是过敏。

**基本约束**

1. 产物有多个写入者：提取、校验修复、工作台编辑、增量更新。不能假设产物只有提取一个作者，也分不出一次提交里谁改了哪一行。
2. 重新提取代价高（十几分钟），还会覆盖修复和人工改动；校验相对便宜、只改出问题的地方，过期后刷新只查改动（ADR-0100）。
3. 过期的展示、建议条、自主构建、发布关卡都读同一份节点状态，判定要确定、可解释，第三方包的声明照常可用。
4. 校验查一致性（字段对账、链接、语义），不查完整性：新增对象缺操作它补不出来（核对里只有「孤立动作」，没有「孤立对象」）。

## Decision

**推导**

- 「上游变了」有两种。来源（资料分析）变了，产物可能缺内容或错，要重新提取。本体内部的条目内容变了，引用它的条目可能对不上，
  这是一致性问题，正是校验的职责，校验的 `stale_on` 已经盯着对象、操作、规则、指标的内容。现在两种都让提取过期，用重新提取去处理
  一致性问题，代价高还会覆盖修复（约束 2）。
- 只有一种内部变化要重新提取：条目有增减。新增对象可能要补操作、新增操作可能要补规则和指标，校验补不出来（约束 4）。条目内容修改
  （补字段、改说法、补兜底）交给校验。
- 所以把「条目清单」做成单独的产物类别：`object_set`、`operation_set`，和 `object`、`operation` 同目录，指纹只取路径（增、删、改名
  才变）。提取类的节点、步骤盯来源和上游清单；内容修改只让校验过期。
- 可选的规则补抽、指标不盯资料分析：资料变了时必经的「操作」一步会过期，重抽操作连规则、指标一起抽（ADR-0012）；它们盯资料的话，
  ADR-0090 的「交给核对节点」判定就盖不住（校验不看资料），可选项会被单独推荐，回到 11-11 模拟里那个来回推的环。
- 交给核对节点的判定（`flow_state.handed_down`）里，下游盯着 `object` 也算盯着 `object_set`：增减时内容指纹一定变，判定口径不漏。
- 升级迁移（约束 3、成功标准 4）：记录里分类指纹的类别和现在声明的不同，说明是按旧定义记的，旧指纹没法比。按确认那一刻到现在主线上
  「现在声明的上游」有没有改动来定：没改就按新定义重记基线；改了判过期并记下是哪几类；找不到那一刻的提交也重记（旧指纹本来就比不了，
  资料变了对象一步照样会过期）。没存分类指纹的老记录按 ADR-0102 之前的定义（`STALE_ON_BEFORE_0102`）认。这条规则不点名节点，包升级
  改了 `stale_on` 也同样处理。

**做法**

| 位置 | 之前 | 之后 |
| --- | --- | --- |
| 建模 · 对象 | research | research（不变） |
| 建模 · 操作 | object | research, object_set |
| 建模 · 规则（可选） | object, operation | object_set, operation_set |
| 指标（可选旁支） | object, operation | object_set, operation_set |
| 校验、发布 | object, operation, rule, metric… | 不变 |

1. `flow/state.py`：`KIND_DIRS` 加两个清单类别；指纹按 `render_tree` 取文本（清单类别的行只留路径，没有清单类别时与原来逐字相同，
   已有记录接着用）；`changed_since` 对清单类别只看新增、删除、改名；`rebaseline_redefined` 做升级迁移，节点（`compute`）和按段的步骤
   （`slices._step_state`）共用。
2. `flow_state.py`：`_watched` 让内容类别盖住同目录的清单类别。
3. 说法：「对象清单有变化，刷新操作」。

## Alternatives considered

- **操作、规则、指标都只盯资料分析**：最简单，但新增对象后不再提示补提取操作，校验也查不出来（约束 4），丢掉 ADR-0090 要保的情况。
- **校验确认时把上游各步骤的基线一起重记**：ADR-0090 否掉过（建模没重新提取却显示已确认）；而且手工改对象、校验之前的修改都不经过它。
- **按提交里的节点标记过滤指纹变化**（校验的提交不算上游改动）：最精确，但工作台手改和助手改会混在一次提交里，牵涉面也最大。
- **同一个变更集里一步的输入和输出一起改了就重记**：校验只改对象不改操作时照样过期，规则说不清。

## Consequences

- 校验修完确认后，建模、指标、校验都是已确认，建议条和节点状态一致；自主构建不再因为校验的修复重跑提取。
- 新增、删除、改名对象：操作一步过期、建议条推「对象清单有变化，刷新操作」（校验已确认也推）。资料分析变了：对象、操作都过期。
- 对象内容改了：只有校验过期（「对象有变化，刷新校验」），刷新只查改动的条目（ADR-0100）。
- 规则补抽、指标只在条目有增减时过期，且交给校验、不单独推（与 ADR-0090 补充一致）。
- 部署新版本后，旧定义记下的记录第一次计算时按上面的规则迁移，写回新定义。
- **最强的反对理由**：对象内容的大改（拆字段、换主键）可能让操作在语义上过时，而这里只靠校验发现；校验查的是对得上对不上，
  某个操作「该重写」它不一定说得出。缓解：字段对账、链接、语义检查覆盖大多数对不上的情况；用户可以手动刷新建模（抽屉里的动作还在）。
- **代价**：多了两个产物类别，包作者写 `stale_on` 时要分清「内容」和「清单」（开发 Skill 里的类别列表自动带出）；用到清单类别的包要
  跑在带这版内核的镜像上，旧内核的静态检查不认。
- ADR-0090 里「校验修对象让操作过期、建议条不推」这一段不再出现：操作一步不会因为内容修改过期了；其余判定照旧。
