# 0087 工作台插件开发模式：在对话里做插件，一键装到本项目

## Context

**目标**：项目所有者（建模人员、交付人员）在工作台里用对话做出插件，点一下装到自己账号、启用到当前项目，切回建模就能用。
不下载开发 Skill，不用外部编码助手，不手工打包上传。成功标准：

- 一句需求做出草稿，平台预检的结果在对话里看得到；预检没过能让助手修，修到过；
- 点一下就装上并启用，切回建模，下一条消息起新能力生效；再改再装，自动换版本号；
- 装上的包和走「安装插件」上传的包完全一样：同一份静态检查，同样只归本人（ADR-0079、ADR-0080）；
- 插件开发时本体只读，草稿不混进发布的知识包；不用插件开发的项目和现在一样。

**基本约束**

1. 助手写的东西不可信：装之前必须走和上传同一份服务器检查，不能有捷径（ADR-0080）。
2. 助手在主容器里、在项目的助手副本（git worktree）里运行，能写什么靠 PreToolUse 守卫限；守卫只看命令文本，防误改，防不住有意绕过（ADR-0079 约束 2）。
3. 一个项目只归一个人，私有包也只归本人（ADR-0079）。
4. 一个项目同时只有一个引擎会话，绑定一条对话；换绑定会回收引擎、下一条消息续接（`agent_sessions._bind_session`）。会话配置指纹变了，下一条消息前重连，正在跑的一轮跑完（ADR-0022）。
5. 助手副本的路径每个项目固定（Claude 的续接记录按工作目录存），`.claude`、`CLAUDE.md` 是链接，每轮开始 `worktree.ensure` 会把链接修回指向主线的 `.claude`。
6. 发布只读 `PACKAGE_SOURCE_DIRS`（`ontology/` 下的固定目录和求解目录）。
7. 两种引擎都要能用（Claude CLI、Jiuwen）：两者都按同一套目录约定读装配目录（`CLAUDE.md` → system prompt，`settings.json` 守卫，ADR-0024）。
8. 陪伴建模、自主构建、开发 Skill 下载、「安装插件」页都要照常可用。

## Decision

**推导**

- **草稿放哪**：放项目工作区的 `plugins/<包名>/`。这样直接沿用助手副本、每轮自动合入成版本、撤回这一轮、版本历史（F3），不需要新的存储；
  `plugins/` 不在发布读取范围里（约束 6），不会进知识包。代价是草稿跟着项目走（见 Consequences）。
- **一条对话 = 一份草稿**：对话索引多两个字段 `kind: plugin`、`plugin: <包名>`。插件开发不是项目的构建方式（L2/L4 是项目设置），
  而是另一类对话；切模式就是换对话，约束 4 已经保证换对话时回收引擎，不用再造一套运行中切换。对话第一次写出草稿时绑定包名。
- **助手怎么变成插件助手**：约束 7 要求两个引擎同一份来源，约束 5 决定副本只能有一份。所以插件对话的那一轮，把副本的 `.claude` 链接指到一份
  **插件开发装配目录**（后端生成，内容见做法 3），`CLAUDE.md` 跟着链接走。为了不被这一轮里别处调用的 `worktree.ensure` 改回去，
  链接目标由副本旁的一个标记决定（`changesets/<项目>/claude-override`）：插件对话开始一轮时写，建模对话开始一轮、插件对话这一轮结束时清掉并修回。
  装配目录的内容来自开发 Skill 的同一份生成代码（ADR-0081 约束 2），不另写一份协议。
- **会话指纹**：插件对话的指纹不含 `assembly`、`flow`（项目装了新插件不该让插件助手重连），改含 `plugin_dev`（插件开发装配目录的哈希）。
- **能写什么**：约束 2，插件开发装配里的守卫只放行写到项目根下 `plugins/` 里；项目根内其他路径、数据目录下的其他项目一律拒；
  读不限（读本体才能让插件贴合项目），资料原件仍按 ADR-0076 拦。和别的守卫一样，防误改，不是安全边界。
- **检查**：两层。助手用装配里的 `pack_tool.py check` 离线查（同 ADR-0081）；平台在读草稿时（PD-01、PD-02）现查：把主线上的草稿复制到临时目录、
  写校验和，跑 `checks.run(tenant=True)` 加 `private_name`，再加一项「目录名和包名一致」。只出结果、不建上传记录，因为每人只留最近 20 个上传，
  每轮一条会很快挤掉真正的安装记录。结果按草稿目录的 git 树哈希缓存。
- **安装**：草稿卡上的按钮，只有用户能点（HTTP 接口要所有者登录，助手手里没有令牌）。点了以后从**主线**取草稿（不取副本里助手还没合入的），
  版本号已经在包仓库里的，自动升补丁号并作为一次平台提交写回草稿；然后走现有的私有上传、静态检查、安装、启用（或升级到新版本）。
  版本发布后不能改（约束 1、包仓库不可变），所以重复装必须换号；用 `-dev.N` 并清理旧版本的方案没采用，见 Alternatives。
- **支持的包**：能力包（含加流程节点的）、行业包、系统知识包。连接器包不支持：转换器要打进连接器网关镜像才运行（ADR-0073、ADR-0081）。
- **界面**（设计稿：工作台插件模式 8 个状态）：输入框模式菜单第三项「插件开发」；插件对话的顶栏只有草稿切换、「写草稿 — 检查 — 安装」三步、上下文和更多，
  不显示「新资料」「待处理」「建模步骤」；草稿卡写明启用后带来什么和预检结果，卡上「安装并启用到本项目」「让助手修复」「切回建模试用」「停用」
  「更新到本项目」；「查看文件」右侧抽屉看文件、改文件（网页上的改动按一次提交合入主线，可以撤回）。插件对话里没有建议按钮；
  从插件开发切回建模试用后，建模对话的建议条多一个「回到插件开发」。
- **不能切的时候**：自主构建在跑、另一条对话在跑时不能进插件开发（约束 4 已有的 `session_busy`、`autobuild_running`）。

**做法**

1. 对话：S-01～S-04 的对话视图加 `kind`（`modeling` | `plugin`）、`plugin`（绑定的包名，没绑为 null）；S-02 收 `{kind: "plugin"}`。
2. 新接口 PD-01～PD-06（契约 contract-changes「F17」）：草稿列表与详情（含平台预检、和已装版本的差异）、读文件、写文件、安装并启用。
   停用沿用 PL-09。
3. 插件开发装配目录 `<数据目录>/plugin-dev/<哈希>/`：`CLAUDE.md`（插件助手规则，`assets/plugin-mode/CLAUDE.md`）、`plugin-dev/<分类>/`（能力包、行业包、
   系统知识包三个分类各一份开发 Skill：`SKILL.md`、`platform.json`、`references/`、`scripts/pack_tool.py`、`scripts/checker/`，生成代码同 PL-27）、
   `scripts/`（内核守卫的公共实现、`plugin_scope_guard.sh`、`resource_read_guard.sh`）、`settings.json`。哈希按内容算，平台的公开包变了就换一份。
4. 宿主：一轮开始时按对话类型指副本的 `.claude`；插件对话的注入只带草稿状态（包名、版本、启用情况、上一次预检没过的项），不带阶段、下一步、包提示规则；
   插件对话不出建议条、不出通用的「这一轮改了什么」卡，改到草稿时出一张 `plugin_draft` 卡（带这一轮的变更集，可以撤回这一轮）。
5. 安装成功在插件对话里留一行通知；草稿变了、装了、停用了，项目流发 `plugin_drafts.changed`。

## Alternatives considered

- **草稿按人放**（不跟项目走，能跨项目改同一个插件）：要新做一种工作区，没有副本、合入、撤回、版本历史可用，改动大得多。先不做，以后可以加「从已装的包导入草稿」。
- **插件开发是项目级的第三种构建方式**（项目设置 build_mode 加一个值）：构建方式管的是建模怎么推进，和自主构建的运行、蓝图预览绑在一起；
  插件开发和建模要能来回切而不丢各自的对话，做成对话类型更直接。
- **只在消息前注入「你现在是插件助手」，不换装配目录**：建模的工作区规则和命令仍是 system prompt，助手会按建模流程走（取锁、跑状态脚本），两套规则打架。
- **插件对话用单独的副本**（第二个 git worktree）：变更集、合入、撤回都按一个副本写的，要大改内核；换 `.claude` 链接只动一处。
- **试装用 `0.1.0-dev.N` 并自动清理旧的开发版本**：省版本号，但包仓库的版本不可变、项目锁定过的版本不能删，清理规则要另做；每人 50 个版本的上限下，
  一个插件试装几十次的情况先接受，满了找管理员清理（ADR-0079 已有的规则）。
- **安装时弹确认框**：安装只影响自己和这个项目，停用就能撤，多一次确认没有保护到别人。

## Consequences

- 建模人员不离开工作台就能做插件、装插件、试插件；装上的包在「我的上传」里也有记录，和手工上传的一样能被管理员看到、禁用、发布。
- 插件草稿的每一轮修改也会合入成知识包的一个版本（版本号会涨），版本页能看到这些修改；草稿不进发布的知识包。
- 草稿跟着项目走：换项目接着改同一个插件不方便，复制项目会把草稿带过去。
- 每次重装都换版本号；私有包每人 50 个版本的上限会更快用到。
- **代价（最强的反对理由）**：门槛降低以后，带脚本的私有包会变多。ADR-0080 已经接受脚本由助手直接运行、守卫看不到脚本内部，这次让这类包更容易产生，
  风险出现的次数更多。插件开发守卫也只防误改：插件助手要有意改本体，守卫拦不住。缓解只有现有的：只装给本人、审计、管理员能禁用；
  真正隔离要等按项目隔离进程（P4）。部署到账号不可信的环境之前，要先加开关关掉插件开发。
- 换 `.claude` 链接依赖「一个项目同时只有一个引擎会话」。以后要支持同一项目多条对话同时跑，这里要跟着改成每条对话一个工作目录。
