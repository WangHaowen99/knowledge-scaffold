# 0013 数据评测编排改用专用线程池并限制并发轮数

## Context

一轮数据评测从打包知识包到收取报告都在一个同步函数里完成，其中包括每 6 秒一次的进度轮询，
一轮常见几分钟、最长 30 分钟。原实现用 `asyncio.to_thread` 执行整轮编排，占用的是事件循环的
默认线程池（容量 `min(32, CPU 核数 + 4)`）。

这个线程池还承担上传资料、建模发消息时读取 git 版本、统计工作区变更、项目导入与删除、
Jiuwen 引擎初始化等短任务。并发评测轮数达到线程池容量后：

- 后续评测排队，用户看到的状态仍停在上一轮，没有任何排队提示；
- 上传资料、建模发消息等短任务跟着排队，并发压测里 30 轮评测时上传最长等待 56 秒，
  建模发消息最长等待 54 秒，而服务 CPU 只有约 0.15 核。

## Decision

1. 评测编排（新一轮与续接）改在评测专用线程池里执行，不再占用默认线程池。
2. 同时执行的轮数由 `ONTO_WEB_EVAL_MAX_CONCURRENT_ROUNDS`（默认 16）限制：专用线程池与
   同容量的 asyncio 信号量一起把关，排队发生在事件循环里。
3. 排队态只叠加在 `/eval/status` 的视图上（`phase=queued`、`queue_position`），不写入
   `eval.json`：落盘的 `running` 会被「同题续接」误判为上一轮。
4. 排队中的轮次被停止时直接出队、取消等待，状态落 `stopped`，不产生任何 modeling 侧开销，
   随即可以重新运行；已开始执行的轮次仍走原有的协作式取消。
5. 前端执行详情在排队态下不点亮任何阶段，排队位次显示在状态文字里。

## Alternatives considered

- **调大默认线程池**：只是推后饱和点，评测和短任务仍然互相争抢；评测轮数也没有上限，
  下游 modeling 与 consumer 的并发跟着失控。
- **把编排整体改成 async（轮询用 `asyncio.sleep`、HTTP 用异步客户端）**：彻底不占线程，
  但要改写整条编排链路和全部测试，改动面远大于本问题；专用线程池已能隔离影响。
- **只限制评测并发、不分离线程池**：短任务仍会在评测高峰时排队。

## Consequences

- 评测高峰不再拖慢上传、建模发消息等操作；并发压测中两者恢复到几十毫秒。
- 超过上限的评测显示排队位次，排队中可以停止；默认上限 16 与原默认线程池在 12 核机器上的
  容量相同，评测吞吐不变。
- 调高上限可以提高评测吞吐，但每轮在 modeling 侧按用例并发调用 consumer，调高前需确认
  consumer 与模型网关的承载。
- 排队态只在本进程内存中：服务重启会丢弃排队中的轮次，用户需要重新发起；这与原实现中
  尚未开始的轮次的行为一致。
