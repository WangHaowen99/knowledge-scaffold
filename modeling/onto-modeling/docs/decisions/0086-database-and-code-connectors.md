# 0086 数据库与代码仓库连接器

## Context

**目标**：建模者在平台里接上业务数据库（MySQL、PostgreSQL）和代码仓库，拿到表结构、外键、约束、数据画像、脱敏样本，以及实体类、
接口、校验规则，抽取时引用；对象文档的「数据来源」可以直接写数据库锚点，发布时据此绑定真实表名、列名。

成功标准：

1. 管理员登记数据库源、写入凭据、测试连接（含只读自检），采集出快照，证据浏览器能看表结构、ER、样本、画像；
2. 代码仓库源按提交浅克隆，采集出实体、字段、接口、校验规则，带文件与行号；
3. 主容器里任何时候都拿不到明文凭据，也没有路由连到业务系统；
4. 任何一条写语句都到不了业务库；样本、画像里的个人信息默认遮蔽。

用户 11-05 定：REA 打通底座后接着做数据库和代码仓库连接器（ADR-0082）。

**基本约束**

1. 凭据泄露的波及面是整个业务系统；智能体和后端在同一个容器里，理论上能读到后端进程的东西（详设 5.8.9）。
2. 采集会打到生产库，慢查询、锁、连接数都会影响业务。
3. 连的是客户的真实数据，样本里有个人信息；快照进工作区 git，也会被智能体读到。
4. 代码仓库是客户自己的代码，但克隆过程（重定向、子模块、钩子、符号链接）和解析器仍是攻击面；令牌泄露能读整个仓库。
5. 网关已经有任务表、票据、预算、快照包（ADR-0082），内核已经有登记、任务、入库、检索。
6. 提供方随网关镜像发布，不走用户上传（ADR-0073）；离线部署要带驱动。

## Decision

**推导**

- 约束 1 → 凭据只在网关：内核收到密码立即转交网关 `PUT /v1/secrets`，自己不存；网关用主密钥加密存进只有它挂载的卷；
  采集时由网关解密，经 stdin 交给提供方子进程，不进命令行参数和环境变量。没有任何读出明文的接口。
- 约束 1 → 网络：网关加接 `biz-egress` 网络，主容器不接；连接目标必须在登记的出口白名单里，子进程里装审计钩子拦住白名单外的
  `socket.connect` 和域名解析（官方提供方也拦，作为纵深）。
- 约束 2、4 → 提供方跑在网关的子进程里（每个任务一个，限时、限内存、超了杀整组），崩了只算这个任务失败。子进程对外实现和
  旁路容器同一套接口，网关的任务表、预算、快照包、内核入库都不用改（约束 5）。
- 约束 2 → 只读三重保证：只读账号（测试连接时自检权限，账号有写权限就拒绝采集）、只读会话、语句白名单（我们自己生成的语句也过
  词法检查：单条、首个关键字是 SELECT / SHOW / DESCRIBE / EXPLAIN / WITH、不含写关键字）。另有单条超时、每秒查询数、单表读取行数上限。
- 约束 3 → 默认脱敏 `mask-v1`：按列名和取值识别手机号、证件号、姓名、地址、邮箱、银行卡、金额、口令；口令类丢弃，标识类掩码，
  金额分桶，需要关联的加盐哈希（盐按项目，内核生成）；判断不了的文本列按敏感处理。样本每表最多 20 行；画像只给低基数且不敏感列的
  top-k、数值列的统计量。快照回到内核时再扫一遍个人信息和密钥。
- 约束 4 → 克隆加固：只允许 https、不跟重定向、不拉子模块、钩子目录指向空、不建符号链接、按提交浅克隆、单文件和总量上限；
  令牌经 askpass 读 0600 临时文件，克隆完删除。解析只用纯 Python（Python 的 `ast`、Java 的 `javalang`、TS 用正则识别装饰器），
  不执行代码、不装依赖。
- 约束 6 → 驱动用纯 Python 的 PyMySQL（MIT）和 pg8000（BSD-3），只装进网关镜像；网关镜像加 git。

**做法**（接口细节见 `evidence-collection.md` §8～§10）

1. 网关：凭据库与 `PUT/DELETE /v1/secrets/{源}`、`POST /v1/sources/{源}/test`、连接型提供方的子进程运行器（统一的
   `conn.Context`：发记录、进度、清单、访问审计、限流、截止时间、范围匹配）、出口白名单与套接字审计钩子。
2. 提供方 `db-mysql`、`db-postgres`（discover / snapshot / sample / test）、`code-repo`（snapshot / test）。
3. 内核：EV-06、EV-07 接网关；任务说明带凭据引用、出口、限流、脱敏策略与盐；EV-08 走网关；EV-09 用快照包里的访问审计；
   EV-25、EV-27、EV-28 给数据库的 DDL、样本、画像、外键邻居和 ER；`package_mapping` 认「数据来源」里的 `db:` 锚点。
4. 前端：数据库、代码仓库的登记抽屉、凭据写入与轮换、测试连接结果、ER 与样本对接真实接口；代码快照在证据浏览器里看代码片段。
5. rev 包：取证命令和守则覆盖数据库、代码；新增 `/rev-reconcile` 三方对账（文档、数据库、代码互相印证与矛盾），只写报告。
6. 测试床：合成的 MySQL、PostgreSQL（只读与非只读两个账号、含假个人信息）和带令牌的 git HTTP 服务，放在 `connectors/testbed/`。

## Alternatives considered

- **提供方跑在旁路容器里**：和 REA 一样隔离更彻底，但凭据就要离开网关，违背约束 1。
- **内核直连数据库**：最省事，但主容器要接业务网络、要拿凭据，智能体与业务库之间就只隔一层守卫。
- **用 SQL 解析库做语句白名单**（sqlglot 等）：解析更准，但语句都是提供方自己生成的，词法检查加只读账号、只读会话已经够；少一个依赖。
- **代码分析用 tree-sitter**：多语言、准确，但要编译原生扩展、离线交付麻烦，原生解析器本身也是攻击面。第一版用纯 Python，覆盖 Java、
  Python、TypeScript 的常见写法（JPA / Spring、SQLAlchemy / Django / FastAPI、TypeORM / NestJS）。

## Consequences

- 部署多一个网络 `biz-egress`、一个卷 `connector-secrets`、一个主密钥（`ONTO_CONNECTOR_MASTER_KEY_FILE`，丢了只能重新录入凭据）。
- 网关镜像多 git 和两个驱动，约 40 MB。
- 主密钥和凭据卷要分开备份（方案第 6 章）。
- 词法检查和正则识别会有漏判：语句白名单靠只读账号兜底；代码分析识别不了的写法记进快照的局限，不硬猜。
- 脱敏会误判：宁可多遮。被遮的列在证据浏览器里标出来，需要看原值的到业务系统里看，平台不提供解除遮蔽。
- 详设 5.8.9 的缺口仍在：伪造票据最多在白名单范围内只读采集，且留审计。
