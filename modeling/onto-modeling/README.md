# Onto Modeling — 本体建模工具 Web 版

基于 Claude Agent SDK 的本体建模 Web 工作台。设计方案见
`/mnt/jianguoyun/meta/design/本体建模工具Web版-方案设计-20260918.md`。

## 结构

```
onto-modeling/
  backend/    FastAPI 服务：项目/工作区管理、Agent 会话编排（会话池 + SSE）、文件与版本 API
  frontend/   React 19 + Vite 7 + antd + @ant-design/x 三栏工作台
  assets/     提示词资产（同步自本体建模工具集，挂载进每个任务工作区）
  deploy/     离线交付包构建、预检与部署脚本
  docs/       架构决策记录
```

## 启动（开发）

后端（默认 127.0.0.1:8100）：

```bash
cd backend
python3 -m venv venv && ./venv/bin/pip install -r requirements.txt
./venv/bin/python run.py
```

前端（默认 127.0.0.1:5180，/api 代理到后端）：

```bash
cd frontend
npm install
npm run dev
```

模型接入通过环境变量注入（见 `.env.example`），不落盘、不进仓库。

模型上下文约束按 配置中心「模型接入 → 上下文与自动压缩」> `.env` 中的 `ONTO_WEB_CONTEXT_*`
（见 `.env.example`，变量名与会话引擎无关）> 内置默认 逐项生效。配置页只填模型真实窗口和最大输出，
内置默认分别为 200000 和 32000；压缩窗口与触发百分比只能在 `.env` 配置，两者都没配时服务端按生效的
窗口与最大输出自动推算，使压缩前的请求仍给模型窗口留至少 10% 余量（压缩窗口向下取 10000 的倍数，
低于 CLI 下限 100000 时改推触发百分比，向下取 5 的倍数），配了任一项就完全按 `.env`。稳定引擎把
生效值转成 CLI 的环境变量注入会话（Claude 官方模型名不读窗口变量，仍按 CLI 内置窗口）。接入窗口
小于生效窗口的模型时必须配置真实窗口，否则自动压缩来不及触发，请求会因超出模型窗口被网关拒绝；
窗口更大的模型可配置以用满窗口。配置页按输入框里的值实时提示自动压缩的触发点。`.env` 改动需重建
容器（`docker compose up -d`）才生效，非法值会被忽略并在服务日志中告警。

内测引擎（Jiuwen）的窗口与最大输出在配置页另存一组，留空时同样回落 `ONTO_WEB_CONTEXT_*`，都没配时
最大输出按 `ONTO_WEB_JIUWEN_MAX_TOKENS`（默认 32000，与稳定引擎一致；输出上限更小的模型须填写，
否则请求会被网关拒绝）。引擎内置的压缩器在上下文达到「窗口 × 触发比例」
时压缩，比例按同样的 10% 余量推算，限定在 0.3–0.8（向下取到 0.01）；`ONTO_WEB_CONTEXT_COMPACT_*`
只作用于稳定引擎。两个引擎在会话里显示同样的上下文用量与「上下文已自动压缩」提示。内测引擎会话
重建（服务重启、改配置、切换会话）时优先从框架存档续接，存档里就是压缩后的上下文；存档不可用时
退回历史回放，从会话历史里最近一次压缩摘要接续，不再只靠截断的原始历史。

配置页填写模型名后会查模型上下文推荐表：命中时填入窗口和最大输出，可手改，与网关配置一起保存；
没命中时清空这两项（原值属于之前的模型）；改回已保存的模型时恢复已保存的值。推荐表只做预填，
不参与上面的生效顺序，打开配置页也不会自动改已保存的值。匹配规则：不区分大小写，忽略 `provider/`
前缀、`.` 与 `_` 写法差异和网关追加的 6 或 8 位日期后缀，其余须与 id 或表中别名完全一致。

推荐表分两层：内置表（`backend/app/services/model_context_presets.json`，随版本发布，数值取自厂商
官方文档，最大输出取官方默认值，思考与非思考默认值不同时取思考模式的）和数据目录下的自定义表
`model-context-presets.json`（同 id 整条替换内置条目，新 id 追加）。管理员可在配置页「查看或编辑
推荐表」中覆盖内置条目、恢复内置、新增或删除模型；运维也可参照数据目录下的
`model-context-presets.example.json`（每次启动按内置表重写，本身不生效）直接编辑自定义表。
自定义表改动在下次查表时生效，无需重启；文件有误时整份不生效、沿用上一次合法的结果，页面显示错误且
不能编辑。页面保存带上读取时的版本号，文件已被改过时拒绝保存，每次保存前把上一版存为同目录的
`model-context-presets.json.prev`。「停用自定义表」把文件改名为 `model-context-presets.json.bak-日期-时间`
备份，改回原名即重新启用。
聊天面板顶部的上下文环显示当前会话最近一次模型调用的已用量、
模型窗口、剩余量和距自动压缩的余量（新会话发出第一条消息前显示空环）；发生压缩时对话里插入「上下文已自动压缩」提示。
环旁边的 token 数是项目累计用量，含全部会话和已删除会话。内测引擎每次模型调用返回后就计入，
长命令运行中也会增长，被打断或服务重启时只丢正在进行的那次调用；稳定引擎每轮结束时计入。

启用登录鉴权后，成员可在「设置 → 我的模型配置」填写自己的 API Key（可选再填网关地址、
模型，留空沿用管理员配置）。个人 Key 只用于本人发送的消息：同一项目换人发消息且配置来源
不同时，会话断开后用 resume 续接；本轮未结束时拒绝换人（409）。没有个人 Key 的成员、
未启用鉴权的部署，以及管理员关闭个人 Key 后，行为都与管理员统一配置时一致。个人配置不含
上下文参数，两个引擎都沿用管理员配置页的窗口与最大输出；个人模型的窗口与之不同时，以管理员配置为准。

数据评测的问答模型由评测向导选择 Consumer 全局模型池中的启用配置。判分模型按发起评测的
用户和项目当前会话引擎，从 onto-modeling「我的模型配置」解析；未设置个人覆盖时沿用
onto-modeling 管理员配置。判分不读取 mw-modeling 的模型设置，配置不完整时提示补齐后再评测。
判分配置只在后端内存中随本轮传递，不返回前端，也不写入评测状态、报告或数据库。
向导可选择 1～16 条用例并发，默认 4 条；结果按原用例顺序保存。支持异步运行协议的
Consumer 会在停止评测时收到取消请求；较早版本沿用同步调用。

## 会话池（方案 4.1.1）

每个活跃建模会话 = 一个 CLI 子进程（均值约 400MB）。会话池按
`ONTO_WEB_MAX_SESSIONS`（默认 12，对应 8G 内存）限制并发：超限先驱逐最久
空闲的会话，全部在跑则排队并在前端显示位次；空闲超过
`ONTO_WEB_SESSION_IDLE_TTL`（默认 600 秒）的会话被回收，下次发消息用
resume 续接模型上下文，界面无感。运行中的会话连续 `ONTO_WEB_SESSION_STALL_TIMEOUT`
（默认 1800 秒，0 关闭）没有任何模型或工具响应时判定执行超时并终止引擎，用户可以直接发消息继续。

每个项目可有多条会话（聊天面板顶部下拉：新建、切换续聊、重命名、删除），各自保存历史与模型
上下文，但同一时刻只有一个在线引擎。往另一条会话发消息时，原会话空闲就换绑，忙则返回 409。
存储与取舍见 `docs/decisions/0013-multi-conversation-sessions.md`。

提取对象、质量检查等入口在提交期间阻止重复点击；会话连接、排队或运行期间，连续提交
相同消息会返回 409，并只显示 toast 提示，不在对话区创建后又删除临时消息。提交其他
消息后可以再次主动提交原命令；本轮结束、停止或发送失败后也可以重试。连接失败会清空
待发队列，避免重试时再次执行旧命令；已受理消息和失败记录仍保留在会话历史中。

## 场景、来源与评测结果核验

网页保存 `ontology/scripts/*.py` 时，后端先编译并核对输入契约和可确定的输出字段；失败返回错误位置，保留原脚本、描述符和历史版本，编辑器中的修改可继续修复。注释或 docstring 中的 TODO/FIXME 允许保存并提示行号。保存成功代表工作区修订已记录；无法静态确认的动态输出会提示未验证，发布前须用 `script_verify.py run` 取得当前源码及依赖的通过记录。运行验证检查实际 JSON 输出的字段和类型，旧记录须重验。发布使用冻结的源码及对应记录，验证记录不进入知识包。

- 场景走查由 `trace_inputs.py` 统一读取已保存确认稿，保留字段类型与尾注，派遣前及报告前核对源文件修订和初始输入回执。解析或对账失败不计通过。
- 来源核验使用 `source_extract.py` 抽取 UTF-8 文本、DOCX 正文/表格和 XLSX 单元格，返回原文件摘要与定位锚点；无法读取或定位时明确标记“无法核验”，不以新增 ID 声明或历史基线免检。
- 页面及新报告不再展示覆盖率统计，仍展示具体缺项、推演通过率与数据评测分数；旧报告原文保留。
- 数据评测区分有效判分与技术异常：无有效结果显示“未形成有效评测”，混合结果标明仅为有效子集得分，不把技术异常当业务零分。

升级时需匹配工作区工具箱版本；旧回执保留但须重新核验。实现与兼容边界见
[`modeling-review-integrity.md`](../../docs/decisions/modeling-review-integrity.md)。

## 数据评测前的对象关系检查

启动数据评测前，服务检查包内关系的源对象、目标对象和重复声明。结构错误会返回 HTTP 422
和 `EVALUATION_PACKAGE_INVALID`，并给出对象文件及行号，不创建后台评测任务或新轮次。
检查适用于所有数据源模式，允许对象未绑定数据表也不能跳过关系结构检查。

关系声明按规范化后的“源对象、关系名、目标对象、源关联字段、目标关联字段”检查重复；
这些字段全部相同才阻止启动，并同时提示首次声明和重复声明的源文件及行号。同一对对象
允许存在同名但关联字段不同的关系。箭头括注和标准表会解析为相同的字段对；未写字段按
空字段对比较，不从其他声明补猜。普通导出仅归并完整身份相同的双端声明。

评测允许自关联；自关联的重复声明同样按上述完整身份检查。图模式有明确字段时按字段值
建立关联，未写字段时沿用同表同一行的关联语义。

Studio 图接口 `GET /api/projects/{pid}/studio/graph` 中对象之间的关系与导出用同一套身份：源对象、
关系名、目标对象和两端关联字段都相同才算同一条。两端重复声明只画一条；名称或关联字段不同的关系
各画一条，同一对对象的同名关系在边标签里注明字段，如 `上级仓区（parent_area_id → area_id）`。
同一对节点之间的多条关系画成分开的弧线。对象类型自关联（如仓区的上级仍是仓区）同样返回，画成节点
上方带箭头的环线，多条环线由内到外嵌套。导出不认的声明（如关联字段不在属性清单里、旧产物
「# 文档名 + ## 关联对象」里的写法）退回逐行扫描：同方向已有正式关系时不再显示，否则显示一条；
自关联不走这条退路。正文里提到对象自己、操作调用自己等自引用不成边。

正常关系会在导出、导入后保留；存量关系名称包含端点名称或基数时仍允许评测。
后台导出使用已检查的对象内容快照；对象内容变化后不会自动续接旧轮次。
实现和验证范围见 [issue #367 修复记录](../../docs/issue-367-regression-review.md)。

## 构建与部署

完整安装和升级统一部署 Consumer、Onto Modeling、知识包 Hub、独立评测四个必需服务。
分离安装脚本的 `--consumer-package`、`--onto-modeling-package`、`--knowledge-hub-package`、`--evaluation-package`
四项必填。安装脚本不部署、不升级 Modeling Workbench。
部署顺序：Consumer → Hub → Onto Modeling → 评测。安装入口须与发布包版本一致。

```bash
./build.sh <version> [amd|arm]     # 产出 dist/onto-modeling-<version>-linux-<arch>.tar.gz
docker compose up --build          # 本地从源码起全栈（onto-modeling + auth-server）验证
```

依赖复用（需 BuildKit，Docker Desktop / buildx 默认开启）：

- pip 索引源默认华为云 PyPI 镜像，可用 `ONTO_MODELING_PIP_INDEX_URL`（或 `PIP_INDEX_URL`）覆盖，
  例如 `ONTO_MODELING_PIP_INDEX_URL=https://pypi.example.com/simple ./build.sh <version>`；
- 宿主 pip 运行在 Python 3.11 及以上时，构建脚本先把目标平台 wheel 供应到 `vendor/wheels/`
  （含约 100MB 的 claude-agent-sdk，命中宿主缓存则零下载），镜像内经 bind mount 作为 find-links，
  索引不可达时兜底；宿主 Python 更低时环境标记无法按 3.11 求值、供应不完整，脚本跳过这一步，
  避免大包在宿主和镜像内各下一遍；
- 运行镜像基于 `python:3.11-slim`、前端构建用 `node:22-slim`，与 auth-server /
  consumer / modeling 同基础镜像，复用已拉取的层；
- npm 与 pip 均挂 BuildKit 缓存，同机重复构建不再重新下载。

目标机部署流程与容量规划（含 AVX 预检、降级兼容包）见 `deploy/README.md`。

### 构建进度提醒与 HTTPS

构建跑完一步、agent 提问或请求确认、构建出错时，如果用户不在工作台页面，
前端会弹出系统通知，并让标签页标题和图标按提醒色闪烁。浏览器只允许 HTTPS 或 localhost 页面弹系统通知：
用 HTTP 加 IP 访问时只有标题和图标闪烁，设置页“通知”里会提示原因。需要系统通知时请为工作台配置 HTTPS。
提醒只覆盖标签页当前显示的会话；同时跟进多个项目时，每个项目各开一个标签页。

## 项目级本地 MCP

在项目设置的 MCP 页面创建 Token 并复制 Read / Change 地址。MCP 直接读写当前
Onto 工作区，新建、导入和克隆项目无需创建 Modeling 关联。旧 Modeling MCP
地址及 Token 不会自动迁移，请为本地端点重新创建 Token。

- HTTP：`/api/onto-mcp/{project_id}/{read|change}/mcp`。
- SSE：`/api/onto-mcp/{project_id}/{read|change}/sse`。
- Token 通过 `Authorization: Bearer <token>` 传递，按项目隔离；读、校验、保存
  分别要求 `ontology.read`、`ontology.change.validate`、`ontology.change.apply`。
- 写操作必须提供最新 `expected_revision`；修改保存到本项目的 Git 工作区。
- 默认按访问工作台的地址生成 MCP 地址。反向代理部署可选用
  `ONTO_WEB_MCP_PUBLIC_BASE_URL` 指定公开地址，例如 `https://example.com`。
- 本次独立化仅针对 MCP；原有 Modeling 评测配置仍按原流程使用。

设计与兼容边界见 [本地 MCP 设计说明](docs/decisions/onto-local-mcp.md)。

## 领域资料上传与来源核验

创建项目、资料栏、聊天附件（含拖放和截图粘贴）及发布检查使用统一的上传校验。
支持 `.csv`、`.doc`、`.docx`、`.drawio`、`.jpeg`、`.jpg`、`.md`、`.pdf`、
`.png`、`.txt`、`.webp`、`.xls`、`.xlsm`、`.xlsx`，扩展名不区分大小写。
每个文件最多 20 MiB（界面显示为 20 MB），没有新增批次或项目累计大小限制。
不支持的类型和超限文件会返回具体原因；被拒绝的替换不会覆盖原文件。
JSON、YAML、GIF、SVG 等不在上传白名单内的格式不再接受上传。

上传成功不代表文件可以用于确定性来源核验。`/ontology-research` 会在派遣任务前
逐个检查本地来源；PDF、图片和旧版 Office 等可保留为辅助资料，但用于确定性
核验时需转换为 DOCX、XLSX、Markdown、TXT 或 CSV。无法抽取的来源会说明原因并停止流程。
来源抽取输入上限为 20 MiB，Office 包解压总量上限为 256 MiB，DOCX 正文
`word/document.xml` 单独限制为 32 MiB；二进制附件计入总量，但不抽取为正文。
来源哈希和正文基于同一临时快照生成，避免文件替换导致证据不一致。

## 规则的原始资料来源

规则文档在「来源」之后有「原始资料来源」一节，逐条写用户上传资料的 `resource/` 路径和定位锚点
（`#L12`、`#p:12`、`#table:1/row:2/cell:3`、`#sheet:规则!B3`），取自资料分析报告的
「业务项清单」来源位置和「详细信息」出处，合并去重；没有对应资料时写 `无（来源位置原文）`。
指标、对象、操作不加这一节，存量规则不自动补，重做提取后带上。

- 知识包预览和 Studio 详情里，这些路径显示为芯片：文本和 Word 分段预览并高亮锚点位置，
  Excel 切到对应工作表并高亮单元格（落在合并区时高亮整块），PDF、图片在平台内打开，
  旧版 Office、PPT 等给下载入口；文件已删除时芯片置灰，锚点失效时提示并显示开头。
  预览上方的「返回」回到点进来的文档。分段预览接口为 `GET /api/projects/{pid}/source-preview`。
- 「来源」节写成 `research/报告.md#小节名` 时，芯片打开报告并定位到该小节。
- `research_checker.py` 同时核对「详细信息」里的出处：文件不存在、锚点找不到、省略文件路径都不放行。
- 上传 `.doc`、`.xls` 时提示另存为 `.docx`、`.xlsx`，否则无法分析和预览。
- 发布包里规则正文原样带出，consumer 按 Markdown 显示这一节，不提供跳转。

## Studio 表格的最后更新时间

Studio 表视图在「名称」后有「最后更新时间」列（精确到秒，可排序）。已提交的文档取最后一次改动它的
提交时间，同内容重复保存不产生提交、时间不变；已写入工作区但未提交的文档（如 AI 改了还没确认）取
文件修改时间；纯移动或改名不算更新。Studio 草稿和编辑器里没保存的内容不算。时间来自
`GET /api/projects/{pid}/studio/updates`，只在表视图请求，git 不可用时整列显示 `—`。

## Studio 表格的规则筛选

规则的责任部门、维护人有两种写法，结果合并去重：
- 规则文档末尾的「责任部门」「维护人」两节，多个值用顿号或逗号分隔，写「无」（可带括号说明）或留空算
  未填写。规则提取只照抄资料里明确写出的部门和维护人，资料没写就填「无」；用户可在 Studio 结构化
  编辑里补填。存量规则不自动补这两节。
- 正文任意位置的登记行，如备注里写 `维护部门：合成仓储组；维护人：测试员甲`。部门认「责任部门」
  「维护部门」，维护人认「维护人」；标签前须是行首、空白或标点，「设备维护人：」这类业务描述不算。

Studio 表视图的类型筛选只选「规则」时，「最后更新时间」后多出「责任部门」「维护人」两列，表头筛选
可多选并含「未填写」；切到其他类型或取消类型筛选时，这两列和它们的筛选条件一起去掉。「最后更新时间」
表头可按日期范围筛选（起止两天都包含，按浏览器时区），对所有类型生效。类型、责任部门、维护人、更新
时间各自生效，组合使用时取交集，再与顶部搜索叠加。从条目详情返回时，表格、筛选、排序和页码保持进入
前的状态。部门和维护人取自 `GET /api/projects/{pid}/studio/graph` 规则节点的 `departments`、
`maintainers` 字段。

## Hub2 知识包

建模发布统一保存到当前用户所属的独立 Hub 包，项目成员不会自动继承个人包权限；删除建模项目不删除 Hub 包。项目进度区和首页菜单中的「已发布版本（知识包评测）」按当前用户查询并下载指定版本；发布成功后自动打开「已发布版本」，不自动下载。左栏「历史」页签由 `GET /api/projects/{pid}/history` 按时间倒序合并工作区迭代与已发布版本并分页返回；迭代编号为第几次提交（「迭代 N」），不随分页和新保存变化。

首页「导入已有知识包」提供「已发布知识包」和「本地知识包」两个入口。「已发布知识包」可分页选择当前账号拥有的 Hub 包及固定版本，导入为本地建模项目并继续修改；后续发布保留包身份和基础版本，选择弹窗不提供评测入口。「本地知识包」选择本地 ZIP 文件后进入原有导入向导，自动识别知识包或建模任务工作区内容。导入与发布共用基于 `crypto.getRandomValues` 的请求 ID 生成逻辑，失败重试复用原请求 ID。列表列名为「知识包名称 / 版本 / 知识包 ID」，知识包 ID 对应本体标识，版本列缩窄，将更多空间留给 ID。所有包操作要求统一账号登录，无鉴权开发模式不能访问包 API。没有旧项目包接口、迁移、复制或发布位置选择。

Hub 不可用时发布失败；Hub 已提交、本地关联尚未写入时提示待恢复，并由定时任务或原请求重试收敛。最新项目资料独立同步、失败后台重试；当前建模内评测使用 Hub2 快照，执行编排及 MCP 草稿不变。独立 eval1 和消费侧接入后续实施。

部署配置 `ONTO_HUB_URL`、`ONTO_HUB_SERVICE_TOKEN`（对应 Hub `HUB_SERVICE_TOKEN`）和统一账号认证；包操作和项目资料共用建模服务身份，部署脚本沿用原有 token 自动生成逻辑。Hub 不在本项目的源码/发布 Compose 中，而是独立 compose 项目（`knowledge-hub/deploy/docker-compose.knowledge-hub.yml`、独立离线包），需与本服务同处一个 Docker 网络；整栈 `deploy/deploy.sh` 与安装脚本先部署 Hub，再把本服务的 `ONTO_HUB_SERVICE_TOKEN` 对齐为 Hub 实际使用的值。评测服务凭据由 Hub 部署脚本生成并由评测部署沿用，消费服务凭据按后续接入配置。启动、部署、API、限制与备份见 [Hub README](../../knowledge-hub/README.md)。

建模备份包含 `hub-tasks/` 中的主体包关联、冻结发布输入及恢复记录，不保存用户令牌；Hub 卷单独备份。发布门槛继续提示资料分析、对象提取、操作提取和质量检查；示例数据、场景验证及可选步骤不阻塞发布。带发布副作用的 GET `export?scope=package` 已取消，应先 POST 发布，再下载指定版本。

发布前结构自检：发布检查和提交 Hub 前，都会按与正式发布相同的参数导出知识包，再用 consumer 自己的导入规则检查。consumer 导入时会拒绝的包（数量或大小超限、别名冲突、文件名只差大小写、求解布局错误等）列在发布检查的「知识包结构」一栏，不能降级发布；提交时发现问题则返回 `package_structure_invalid`，不会向 Hub 预留版本。规则是 consumer 上游代码的副本，位于 `backend/app/services/consumer_package_rules/`，由人工同步，来源与同步步骤见其中的 `PROVENANCE.md`。部署调整了 consumer 的数量上限时，要在本服务设置同名环境变量：`ONTOLOGY_OBJECT_MAX_COUNT`（默认 200）、`ONTOLOGY_OPERATION_MAX_COUNT`（默认 100）、`ENTITY_ATTRIBUTE_MAX_COUNT`（默认 100）、`ONTOLOGY_OPERATION_MAX_CHARS`（默认 15000）。


## 独立评测入口（eval1）

本地开发时直接打开本机 5180 的独立评测服务；不在建模 Vite 中代理评测路径。先构建评测前端并启动评测服务，见 [评测服务说明](../../eval-service/README.md)。

评测入口地址只由部署变量 `ONTO_WEB_EVAL_PUBLIC_URL`（写在 `.env`）决定，页面不提供修改入口。这个地址由用户浏览器访问，不是容器网络地址；修改后须重启建模服务。

- 直连（默认）：未设置时，浏览器打开与建模页面同主机的 `http://<主机>:5180/evaluation/`，整栈同机部署无需配置。评测在其他主机、端口或经 HTTPS 时设为完整地址（如 `http://eval.example.com:5180/evaluation/`），须为 http(s)、不含账号和查询参数，路径固定为 `/evaluation/`。点击评测时打开新窗口，登录经 `postMessage` 只交给该地址的来源；评测侧的来源限制见评测服务说明。

默认全栈 `bash deploy/deploy.sh` 包含评测；仅部署建模不会启动评测。也可从仓库根执行 `bash deploy/deploy.sh --eval-only` 独立部署评测，并按说明注入受保护的运行配置。健康检查返回 404 时检查路由，502/503 时检查评测上游，返回 HTML 时检查是否误入建模页面回退。正确响应应为 `{"status":"ok","service":"evaluation"}`。

求解知识包（启用了求解契约）发布不再要求先通过端到端验证：发布只受求解契约静态检查与结构自检约束，发布检查中须勾选“求解能力尚未经端到端验证”的确认，后端未确认时返回 `solver_validation_acknowledgement_required`（409）；当前求解契约修订最近一次求解验证已通过时免确认。MCP 发布遵守同一规则：`preview_package_publish` 返回 `solver.requires_acknowledgement`，需要确认时 `publish_package_version` 须带 `solver_unverified_acknowledged: true`，否则返回 `SOLVER_VALIDATION_ACKNOWLEDGEMENT_REQUIRED`（409）。发布后在「已发布版本（知识包评测）」或求解模型面板点“去评测”，在评测页面以“求解验证”类型对该版本执行；版本列表显示每个版本的求解验证状态与验证报告。每次发布记下当时的求解契约修订（含对象的数据绑定），求解模型面板据此提示当前修改是否已发布并通过验证。建模侧原有的验证用例只读，可导出 JSON 后导入评测页面的求解验证集；保存用例与发起验证的接口返回 `solver_validation_moved`（410）。

进度栏不再提供“数据评测（可选）”和数据源编辑。项目「已发布版本」列表提供「评测」入口，仅携带 Hub 包/版本引用跳转生效的评测入口，不自动执行，URL 中不含令牌或项目 ID。未配置独立评测时明确提示，不回退到 Core。

评测服务自行管理用例、数据源、mapping 与运行结果，直接访问账号、Hub 和 consumer。任务中心与执行详情直接显示本轮知识包名称和本体标识。建模服务保留只读接口 `GET /api/hub/package-projects?ontology_id=...`（每次 1 到 20 个包），按当前用户登录返回本人可访问且关联到这些包的项目名称，每包最多 5 个并附总数。登录统一由建模窗口经跨源消息交接。评测地址必须为不同来源的完整 HTTP(S) 地址，HTTPS 建模页面必须配置 HTTPS 评测地址。部署见 `../../eval-service/README.md`，使用 `--eval-only`，不随 `--onto-modeling-only` 启动。

旧版评测记录按明确的历史入口查看；旧任务停止和对账接口保留。新的旧评测创建、用例/数据源修改接口返回 410。旧工作台和 MCP 的 Core 调用仍保留，不能据此下线整个 Core。评测服务不接管历史项目成员关系，也不随建模项目删除独立记录。


### 项目成员共享与知识包删除

项目首次发布（含首次评测快照）后初始化所有者和 Editor 的 Hub 授权；后续成员增删、角色变化按增量同步，Viewer 不自动获权。同步失败不会回滚已生效的本地成员或已发布包，可在“成员共享”查看状态并重试最新变更。普通发布不会全量恢复其他渠道撤销的授权。

新增授权使用已配置的统一账号目录验证账号，沿用账号服务当前 username 即 JWT sub 的契约，需要建模已有的账号管理凭据配置。Hub 授权仍以可信 issuer + sub 校验；服务身份不能代替当前用户的包权限。Hub 授权包含全部版本读写、授权管理及整包删除权限。

删除项目默认保留 Hub 包。勾选“同时删除本项目发布的知识包”并确认消费和评测不再使用后，先调用原 Hub DELETE 接口完成整个本体的物理清理，再删除项目。远端失败保留项目和删除进度，再次操作可重试；不会删除其他本体、外部备份或已安装副本。Hub 删除已完成而本地删除失败时，再次确认可继续本地删除。

对象关系导出保留原名称和完整语义声明，包括没有绑定物理表的概念关系；图模式的不可导入提示与语义关系分开记录。导出前拒绝缺失端点、完整字段对重复和非法显式关联字段，避免结构错误在标准化时静默丢失。合法自关联及同名不同字段对关系保留。此检查不修改生成、编辑路径的关系命名提示或脚本安全校验。
