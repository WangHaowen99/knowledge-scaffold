# Operation 书写风格指南

> 本文件规范 `ontology/operation/*.md` 中**逻辑描述**段落的书写风格。目的是让 LLM 读取/执行/校验 Operation 时不被口语化表达和歧义符号干扰。
>
> **不强制要求所有 Operation 用 if/then 表达**——当 Operation 以脚本为 SSOT（如调用外部服务、流式计算），允许 prose 描述 + 调用指令的混合形态。本指南只约束**当业务规则确实用 if/then 形式表达时**的写法。

## 一、关键词统一小写

逻辑关键词 `if / then / else / and / or / not` 一律小写。辅助结构关键词 `exists / loop / end loop / prior` 使用时也统一小写。

```
✅ if 库存 >= 安全库存 then 标记为充足
❌ IF 库存 >= 安全库存 THEN 标记为充足
❌ 若 库存 >= 安全库存 则 标记为充足
```

> 注：自然语言叙述段落（在逻辑描述之外的章节，如"业务描述"）不受此约束。

## 二、用符号替代中文比较词

在条件表达式中优先使用符号：

| 符号 | 含义 | 不推荐的中文 |
|------|------|------|
| `==` | 等于 | "等于"、"为" |
| `!=` | 不等于 | "不等于" |
| `>=` `<=` `>` `<` | 大小比较 | "大于等于"、"小于"等 |
| `&&` | 与 | "且" |
| `\|\|` | 或 | "或者" |

```
✅ if 库存数量 >= 需求量 && 状态 == "可用" then 可用周期 = 0
❌ if 库存数量大于等于需求量 且 状态为可用 then 可用周期为0
```

> `and`/`or` 也可保留作为关键字使用；但**不要把 `>=` 写成"大于等于"**这种中文化。

## 三、嵌套层级 ≤ 3

if/else 嵌套不超过 3 层。超过的处理方式（按优先级）：

1. **拆子流程**：把内层嵌套抽成独立 operation，用 `调用[[子流程名]]逻辑文档`
2. **改决策表**：当业务本质是"多维条件 → 决策结果"时，用 markdown 表格（完整规范见 §八）
3. **扁平化首匹配**：把规则按优先级从严到宽排列，第一条命中即停止

```
✅ 拆子流程
   if 物料是采购件 then 调用[[采购件可用周期]]逻辑文档
   else if 物料是自制件 then 调用[[自制件可用周期]]逻辑文档

✅ 决策表（多维条件）
   | 信用分 | 负债率 | 审批结果 | 利率 |
   |--------|--------|----------|------|
   | >= 700 | < 50%  | 自动批准 | 5%   |
   | >= 700 | >= 50% | 人工审核 | 6%   |
   | < 600  | 任意   | 拒绝     | -    |
```

## 四、禁用口语化表达

| 禁用词 | 替换为 |
|--------|--------|
| 先看 / 再看 | "if ..." / "then ..." 显式条件 |
| 够的话 / 不够的话 | `if X >= Y then ... else ...` |
| 比如 / 例如（混在规则里） | 拆到独立"示例"区块 |
| 可能 / 大概 / 估计 | 删除，或明确为具体条件/数值 |
| 尽量 / 通常 | 删除，或写成显式规则 |
| 部分 / 一些 | 给出具体范围（如 `状态 in ["A", "B"]`） |

```
❌ 先看库存够不够，够的话直接出货，不够的话可能要紧急采购
✅ if 库存 >= 需求 then 出货
   else 触发紧急采购
```

## 五、示例与规则分离

具体数据/案例不要混在规则正文里——单独放在"示例"区块（用块注释或独立小节）。

```
❌ 混在一起
   if 工序.下一架次 exists then 最优切换架次 = 工序.下一架次
   （比如当前是F021，下一架次就是F022）

✅ 分离
   # 规则
   if 工序.下一架次 exists then 最优切换架次 = 工序.下一架次

   # 示例
   # 输入：当前架次 = F021，工序 = "装翼盒"
   # 输出：最优切换架次 = F022
```

## 六、不强制结构化的场景

以下情况允许 prose 描述代替 if/then：

- Operation 以脚本为 SSOT（脚本头部注释 + CLI 调用指令已说明全部业务规则）
- Operation 调用外部服务/流式接口，业务规则在服务端，本地只是输入组装与输出解析
- Operation 是"步骤化流程"且每步无显式条件分支（顺序读-算-写）

此时"逻辑描述"可用 1./2./3. 编号列出步骤，不要求 if/then 关键字，但仍**遵守规则 4（禁用口语化）**。

Markdown 排版要求：

- 编号步骤必须每项独占一行，不得把多个编号合并到同一物理行（如 `1. ... 2. ... 3. ...`）。
- 编号步骤下的子项使用缩进列表，并与下一个编号步骤换行分隔。

## 七、Agent 应用要点

### 7.1 数据流与参数来源（生成约束）

Operation 文档是运行时执行规范，生成时必须以"较弱模型也能按文档执行"为底线。不要依赖读者自行从很远的上下文里推断字段来源。

**子流程入参来源追溯**：调用句 `调用[[子流程名]]逻辑文档，传入{参数}，获取{结果}` 中的每个传入参数，都必须能追溯到以下来源之一：

| 来源类型 | 说明 | 示例 |
|---------|------|------|
| 正式输入 | 当前流程 `# 输入` 表格中声明的参数 | `传入Mpart编码`，且 `Mpart编码` 在 `# 输入` 中 |
| 迭代变量 | `loop` 遍历集合时产生的当前项 | `传入当前子ECO编号`，来自 `loop 遍历 子ECO编号集合` |
| 前序步骤产出 | 前序活动、查询或子流程调用返回的结果 | `传入变更后Mpart编码`，来自上一步 Epart 到 Mpart 转换 |
| 数据对象属性 | 从业务对象直接读取的字段值 | `传入机型编号`，来自 `[[机型]].机型编号` |

生成逻辑描述时，写完每个调用句后都要自查：传入参数是否能追溯到上述来源之一。若不能，应在 `# 输入` 的 `输入源` 列补充来源，或在逻辑描述中补出读取/转换步骤；仍无法确认时写 `TODO: 待补充字段来源`，不要编造隐含来源。

**多跳映射必须显式写出**：对象间的多跳关系路径如果影响执行正确性，必须在逻辑描述中写出中间映射步骤，不得只写最终查询。

| 规则 | 要求 |
|------|------|
| 定位键值需中间步骤 | 若键值不直接在当前上下文中，先写出如何取得该键值，再用它定位目标对象 |
| 同义字段必须显式转换 | 字段名不同但语义相同时，写出等价或转换关系 |
| 下游调用使用当前值 | 如果上游节点已产出中间值，下游调用应使用该中间值，而不是跳回最上游原始输入 |

示例：

```
基于受影响对象ID，从[[ECO受影响对象]]读取变更前Epart编码、变更前Epart版本号。
调用[[Epart到Mpart转换]]逻辑文档，传入变更前Epart编码、变更前Epart版本号，获取变更前Mpart编码。
基于子ECO编号、变更前Mpart编码，查询[[在制品处理结论]]。
```

### 7.2 Agent 应用要点

- **extract-operation-agent**：生成"逻辑描述"段时按本指南。先判断 Operation 的组织类型：判断密集型使用 if/then + 符号；多维条件密集型优先决策表；端到端 SOP 流程型可参考 §九 的推荐骨架；顺序流程或脚本驱动使用编号步骤的 prose。
- **semantic-check-agent**：检查 operation 文档的"逻辑描述"段是否违反上述规则；命中"禁用口语词"、"嵌套 > 3 层"、"中文比较词"等任一条，按下表报告。§九 的 SOP 骨架是可选组织建议，不因 operation 未套用该骨架而报告问题。
- **trace-agent**：遇到 `prior` 按 §十 的首条命中语义执行；遇到 `loop` 按 §十一 的集合遍历语义执行。若集合、优先级或兜底未在文档中定义，不要补常识，按 trace 规则记录问题。

| 违反规则 | severity | category |
|---------|----------|----------|
| 关键字大小写不一致（如 IF / THEN） | 建议 | 风格不规范 |
| 用中文比较词代替符号 | 建议 | 风格不规范 |
| 嵌套层级 > 3 | 警告 | 风格不规范 |
| 出现禁用口语词且导致歧义 | 警告 | 风格不规范 |
| 示例数据混在规则里且可能被误当规则执行 | 警告 | 风格不规范 |

> "风格不规范" 不是必须修复——但 LLM 解读这类 operation 时容易出错，建议人工评估后清理。

## 八、决策表写法（多维条件密集时的可选格式）

当业务本质是"多维条件 → 离散结果"且改写成嵌套 if-else 会 ≥ 3 层时，用 markdown 决策表替代嵌套 if-else。

### 8.1 何时用决策表（三条须同时成立）

1. **≥ 2 个独立条件维度**——单条件直接 if-then 即可
2. **决策结果是离散的**——分级 / 状态 / 推荐方案 / 分类，而非连续计算
3. **改写成嵌套 if-else 至少 3 层**——否则普通 if-then 已经够清晰

### 8.2 何时不用决策表

- 单元格里要塞复杂副作用链（修改对象 + 调子流程 + 触发动作多步并存）
- 条件之间有顺序依赖（A 的判断结果影响 B 的判断逻辑）
- 业务本质是顺序流程，不是"维度组合 → 结果"

### 8.3 格式约定

列顺序：**先所有条件维度，再决策结果，最后可选的下游动作列**。

```
| 条件维度1 | 条件维度2 | ... | 决策结果 | 下游动作（可选） |
|----------|----------|-----|---------|----------------|
| 值/范围  | 值/范围  | ... | 离散结果 | 调用[[子流程]]逻辑文档 |
```

单元格允许的写法：
- 精确值：`"高"`、`"在职"`
- 比较表达式：`>= 700`、`< 50%`
- 范围：`600-700`、`[18, 30)`
- 占位词 `任意`：此行对该维度不做约束
- 本体引用：`[[对象名]]`、`调用[[子流程名]]逻辑文档` 均合法，rule-check 会正确识别

### 8.4 完备性要求

- 必须覆盖所有可能的条件组合，或显式给出**默认行**兜底
- 多行同时命中时按从上到下首匹配；建议严格条件放前面、宽松条件放后面

### 8.5 多步动作的处理

markdown 表格单元格不支持换行。单行决策需要多步副作用时，**抽成子流程**，单元格里只放调用引用。

❌ 错误：

```
| ... | 拒绝 | 标记状态为拒绝 + 通知客户 + 写审计日志 |
```

✅ 正确：

```
| ... | 拒绝 | 调用[[拒绝处理]]逻辑文档 |
```

### 8.6 示例

决策表是 operation「逻辑描述」段里的一种写法，不是独立文档。示例下面的标题是该
operation 的名字——**不要照抄成「规则：XXX」**：以「规则」「指标」命名的独立文档属于
`ontology/rule/`、`ontology/metric/`，写进 operation 目录会被目录归属检查判错。

```
# 贷款审批

| 信用分    | 负债率 | 审批结果 | 利率 | 下游 |
|----------|--------|---------|------|------|
| >= 700   | < 50%  | 自动批准 | 5%   | 调用[[发放贷款]]逻辑文档 |
| >= 700   | >= 50% | 人工审核 | 6%   | 调用[[转人工审核]]逻辑文档 |
| 600-700  | < 50%  | 自动批准 | 6%   | 调用[[发放贷款]]逻辑文档 |
| 600-700  | >= 50% | 人工审核 | 7%   | 调用[[转人工审核]]逻辑文档 |
| < 600    | 任意   | 拒绝     | -    | 调用[[拒绝处理]]逻辑文档 |
```

## 九、SOP 流程型 Operation 的推荐骨架（可选）

本骨架不是所有 Operation 的必填结构，也不作为 rule-check / semantic-check 的形式要求。它只适用于**有明确起点、输入准备、业务决策、结果校验、输出闭环**的端到端 SOP 流程型 Operation。

以下 Operation 不应强行套用本骨架：

- 以判定为主的 operation（其「逻辑描述」整段都在做条件判断）：使用 if/then、扁平化首匹配或决策表。注意这说的是 operation 内部的写法——规则本身作为实体文档属于 `ontology/rule/`。
- 多维条件决策：优先使用 §八 的决策表。
- 有优先级且互斥的规则：按优先级从严到宽平铺，第一条命中即停止。
- 脚本 SSOT / 外部服务包装：用编号步骤说明输入组装、调用脚本或服务、输出解析。
- 异步回调 / 定时任务 / 外部推送：只写清触发、输入、处理、输出，不必补齐完整 SOP 阶段。

适用时可按以下顺序组织"逻辑描述"，但要按源材料删减，不要为了套骨架编造源材料没有的步骤：

1. **前置校验与流程启动**
   - 明确本流程可执行的先决条件。
   - 校验输入数据与关联实体状态的合法性。
   - 不满足前提时终止流程并输出异常说明。

2. **数据准备与上下文初始化**
   - 加载本流程所需的关联实体数据。
   - 按需调用基础校验、数据准备类子规则。

3. **核心决策与分支执行**
   - 根据业务策略或场景完成顶层决策判断。
   - 对所有可能场景做分支处理，确保分支全覆盖、无模糊逻辑。
   - 满足分支场景时执行对应逻辑或调用相关子规则，输出阶段结果。
   - 其他场景执行兜底逻辑，输出默认结果。
   - 记录决策结果与关键中间信息。

4. **结果校验与确认**
   - 对阶段计算或决策结果进行合规性校验。
   - 校验不通过则回退调整或标记异常。
   - 校验通过后进入结果汇总。

5. **结果汇总与流程结束**
   - 汇总全流程最终结果。
   - 明确输出参数或实体对象。
   - 结束流程。

Agent 使用要求：

- extract-operation-agent 生成前先判断是否为 SOP 流程型；只有适用时才参考本骨架。
- semantic-check-agent 不检查"是否套用了本骨架"。只有当源材料明确要求某个前置校验、分支兜底、结果校验或输出，而 operation 未写时，才按业务缺失报告。
- ontology_checker.py 不为本骨架新增确定性规则。

## 十、扁平化首匹配（prior）写法（可选）

`prior` 用于**规则多、有优先级、且规则互斥**的判断场景。它的执行语义是从上到下依次判断，第一条命中即执行并停止。

适用条件：

- 多条规则之间有明确优先级。
- 命中一条规则后不应继续执行其他规则。
- 后续规则不依赖前一条规则的输出。

不适用场景：

- 一个输入可能同时触发多条规则，且多条动作都要执行。
- 后续规则需要前一条规则先计算出中间结果。
- 业务本质是多维条件组合，且用决策表更清晰。

推荐格式：

```
prior 员工状态 == "离职"
then 收回所有系统权限

prior 职级 == "总监"
then 赋予全部门审批权限

prior 职级 == "主管"
then 赋予本组审批权限

prior 默认
then 赋予基础操作权限
```

书写要求：

- 严格条件放前面，宽松条件放后面。
- 建议提供 `prior 默认` 作为兜底；没有兜底且没有规则命中时，trace 会记录分支缺失。
- 不要把多个本应同时执行的规则改成 `prior`。这种情况应写成多个独立 `if ... then ...`。

## 十一、批量遍历（loop）写法（可选）

`loop` 用于对同一集合中的每个元素执行相同逻辑，并记录或聚合结果。

推荐格式：

```
loop 遍历 所有组成零件
    调用[[零件准备时间计算]]逻辑文档
    记录 该零件准备时间
end loop
总准备时间 = max(所有零件准备时间)
```

书写要求：

- 循环集合必须来自输入、对象属性、上游 operation 输出或源材料明确给出的集合。
- 循环体内要写清每个元素如何命名、读取哪些字段、产出什么中间结果。
- 循环后的聚合方式要显式写出，例如 `max(...)`、`sum(...)`、逐条输出、全部通过/任一失败。
- 集合为空时如果业务有特殊处理，应显式写出；否则 trace 不会自行补默认行为。
- 循环体内调用子 operation 时仍使用 `调用[[子流程名]]逻辑文档`，并在 `与operation的关联` 中列出该子 operation。

## 十二、Data / AI / Operation 分工与术语口径

Operation 层只书写**业务规则**，不要重复 Data 层已经定义的实体层次、属性继承或纯关联查询。

分工原则：

- **Data 层**：定义对象、属性、枚举值、单位、层次结构、对象间可由数据支撑的关系。
- **AI**：可基于 Data 层定义完成层次关系推理、属性继承、实体关联查询。
- **Operation 层**：定义 Data 层无法自动推出的业务规则，例如什么条件触发什么判断、计算、更新、拦截、推荐或流程推进。

不应写进 Operation 的内容：

- 纯层次关系推理：如 `if A 是 B 的子类 then A 也是 C`，除非源材料把它定义为业务判定规则。
- 纯属性继承：如 `if X 属于 Y then 自动拥有 Y 的通用属性`。
- 只需要查对象属性或关联即可回答的查询规则。

Operation 中使用 Data 术语时要保持口径一致：

- 对象名、属性名、枚举值优先使用已存在 object 文档中的名称。
- 不在 Operation 中临时创造 object 未定义的新字段、新枚举或别名。
- 计算公式、单位、时间口径要与 object 属性规则一致；如果源材料要求新口径，应同步更新 Data 层定义，而不是让 Operation 隐式改口径。
- 发现同名异义、异名同义、单位不一致、公式不一致时，优先标记为需业务确认，不要在 Operation 中自行选择一个口径。

Agent 使用要求：

- extract-operation-agent 生成 operation 前应先读取 object 文档，对齐对象名、字段名、枚举值、单位和公式口径。
- semantic-check-agent 可将明显的 Data / Operation 口径不一致作为语义问题报告；不因措辞风格不同而报告。
- trace-agent 按文档原文执行，不做语义等价替换。例如"库存不足"和"库存为零"只有在文档明确定义等价时才可视为同一条件。
