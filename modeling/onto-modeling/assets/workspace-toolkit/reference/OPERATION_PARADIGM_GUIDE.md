# Operation 范式识别参考

> 本文件为可选参考。建模人员在着手提取或验证 Operation 时，可先判别业务属于哪种 Operation 范式，以选择合适的建模与验证策略。不强制使用。

## 一、为什么要识别范式

不同业务的 Operation 在结构上有本质差异，对应的验证策略也完全不同：

- 有些业务是**按步骤推进**的（例如订单履约、生产执行、变更影响分析、审批流）—— 验证时应穷举场景分支
- 有些业务是**由事件/条件触发判定器组合**的（例如风控规则引擎、资源调度、应急响应、意图识别）—— 场景不可穷举，验证时应改为"测规则而非测路径"

若不先识别范式就盲目建模与验证，会出现两种典型问题：

- 按穷举策略验证规则引擎类业务 → 组合爆炸，工作量失控
- 按规则覆盖策略验证流程类业务 → 漏覆盖正常分支，假阳通过

## 二、两种范式特征对比

| 维度 | 📋 SOP 流程型 | ⚡ 断言驱动型 |
|------|--------------|--------------|
| 典型业务 | 订单履约、生产执行、变更影响分析、审批流 | 风控规则引擎、资源调度、应急响应、意图识别 |
| Operation 结构 | 按步骤顺序执行，有明确的执行链 | 事件/条件触发，多个判定器自由组合 |
| 判断节点 | 有限、离散（是/否、满足/不满足） | 连续值 + 离散值混合（距离、速度、金额） |
| 场景因子 | 可枚举（变更类型 = 删除/升级/新增） | 不可全枚举（金额 = 9999 是临界值，但金额取值无界） |
| 组合数量 | 有限组合（几十~几百） | 组合爆炸（连续值 × 多判定器） |
| 典型风险 | 分支遗漏、兜底缺失、隐式依赖 | 规则冲突、约束越界、审计链断裂 |
| 安全机制 | 兜底（异常时跳过/空值传递/默认值） | 红线拦截（强制性规则一票否决） |

## 三、范式识别判断准则

拿到一组 Operation 后，依次回答以下问题：

| 问题 | SOP 流程型的回答 | 断言驱动型的回答 |
|------|----------------|----------------|
| Operation 是否有明确的执行顺序？ | 是，按步骤 1→2→3 执行 | 否，由事件/条件触发，可自由组合 |
| 场景因子是否可完全枚举？ | 是，每个因子只有几种取值 | 否，存在连续值或无限组合 |
| 是否存在"红线拦截"机制？ | 通常没有 | 有，强制性规则一票否决 |
| 异常时系统怎么处理？ | 兜底（跳过/空值/默认值） | 拦截（终止流程/上报违规） |
| 删除某个判定节点，系统是否还能运行？ | 不能，流程会断 | 能，只是少了某个维度的判断 |

**判别规则**：上表 5 个问题中至少 3 个倾向于同一列，即可判定为该范式；若两列各有 2~3 个，按混合型处理（见第五章）。

## 四、不同范式的建模与验证策略

### 4.1 SOP 流程型

| 环节 | 策略 |
|------|------|
| 场景设计 | 场景因子穷举 + 排列组合 → 剔除不可能/低价值组合 |
| 覆盖率目标 | 分支覆盖率 ≥ 95% |
| 异常重点 | 兜底机制（跳过 / 空值传递 / 默认值是否完备） |
| 边界关注 | 0 值语义歧义（"真为 0" vs "查询失败返回 0"）、状态边界、时间边界 |
| 端到端验证 | 按 SOP 步骤全流程贯通 |
| 一致性检查 | 术语一致性、数据口径一致性 |

### 4.2 断言驱动型

| 环节 | 策略 |
|------|------|
| 场景设计 | 规则覆盖 + 约束边界 + 退化逻辑 —— 每条强制规则一个拦截 Case；每个约束边界两侧各一个 Case；每条退化路径专门 Case |
| 覆盖率目标 | 规则覆盖率 100% + 审计链覆盖率 100% |
| 异常重点 | 红线拦截（强制性规则是否正确拦截违规） |
| 边界关注 | 约束边界值（如 ≤0.54 vs >0.54 等硬约束的两侧临界值） |
| 端到端验证 | 审计链贯通（判定 → 拦截 → 执行 链路完整，跳过任何一步都视为违规） |
| 一致性检查 | 规则不冲突（不同强制规则的红线是否矛盾）、全局约束统一 |

### 4.3 核心原则

- **SOP 流程型**：穷举是可行的，应该穷举
- **断言驱动型**：穷举不可行，应该"测规则而非测路径"——确保每条规则都被验证过，确保每条审计链贯通

## 五、混合型说明

实际业务中很多系统是混合型：SOP 流程中嵌入了断言驱动的判定器，或断言驱动系统中有 SOP 流程的调度。

**典型例子**：审批流（SOP）中嵌入风控规则（断言驱动）；订单履约（SOP）中嵌入定价规则引擎（断言驱动）。

**混合型策略**：

1. 对 SOP 部分按流程型策略验证（穷举场景）
2. 对判定器/规则部分按断言驱动型策略验证（规则覆盖 + 约束边界）
3. 两者独立验证后，在端到端层做"判定 → 拦截 → 执行"贯通验证

## 六、实操建议

- **何时判别**：在 Operation 提取完成、进入验证阶段之前判别一次即可
- **谁来判别**：建模人员人工根据第三章问题做判断；范式不会随版本频繁变化，无需在每次 trace 时重判
- **如何记录**：可在 `ontology/operation/` 下任选一个总览位置（例如 `_范式.md` 或现有 README）记录判定结论与依据，方便团队成员复用
- **当前工具默认假设**：现有 `/ontology-trace` 与 `/ontology-validate` 主要面向 SOP 流程型设计。若判定为断言驱动型或混合型，需要建模人员在场景设计阶段额外补充"规则覆盖"和"约束边界"两类 Case —— 详细方法见 `ASSERTION_DRIVEN_TESTING_GUIDE.md`

## 七、命令接入约定

> 本节是命令端"何时主动提示用户参考 Operation 范式"的单一事实源。新增触发点请改本节，不要把触发逻辑散落到各命令。

### 7.1 触发时机

以下节点可软提示本文件；提示不阻塞当前流程，用户忽略即继续：

1. `/ontology-extract-operation` 完成 Operation 提取、即将展示"下一步建议"前。原因：这是进入校验/追踪前判别范式的最佳时机。
2. `/ontology-validate` 完成全部校验、即将建议测试数据/追踪前。原因：追踪前仍可补一次范式判断，避免把断言驱动型业务只按 SOP 分支验证。
3. `/ontology-trace` 的场景设计确认前，包括单条追踪、批量追踪和交互走查。原因：此时用户还可以补充测试场景或调整覆盖策略。

任何一个命令对本文件单次执行最多提示一次；若用户在当前会话中表达过"不需要 / 知道了 / 已判别"含义，本会话内不再提示本文件。
