# 断言驱动型 Operation 测试方法参考

> 本文件为可选参考。当 Operation 范式被判定为断言驱动型或混合型时，建模人员可参考本文设计场景与验证方案。判别范式的方法见 `OPERATION_PARADIGM_GUIDE.md`。

## 一、适用场景与基本假设

**适用场景**：风控规则引擎、信贷审批、资源调度、应急响应、定价策略、安全策略等"由事件/条件触发判定器组合"的业务。

**基本假设**：业务已（或可以）按以下三层架构建模：

- **判定器（Assessor）**：负责将原始数据转化为逻辑结论。多个判定器可被任意组合调用，互不依赖
- **约束法官（Guardrail）**：强制性规则的拦截层，一票否决违规方案
- **写入器（Mutator）**：唯一的物理状态改写入口，写入前必须验证约束法官审计通过

三者构成一条**安全审计链**：判定 → 拦截 → 执行。跳过任何一步都视为违规。

> 若业务未按三层架构建模，本文中的"规则覆盖""约束边界""退化逻辑"等技术仍可参考；但"审计链贯通""写入器专项"需结合实际架构调整。

## 二、为什么不能照搬 SOP 流程型的穷举策略

断言驱动型业务有两个特征会让穷举失效：

1. **连续值判断**：判定条件涉及金额、时长、距离等连续变量，取值无界
2. **自由组合**：多个判定器可被任意组合调用，组合数随判定器数量指数级增长

正确策略是 **"测规则而非测路径"**——不试图覆盖所有可能的执行路径，而是确保：

- 每条强制规则被验证过
- 每个约束边界被验证过
- 每条审计链贯通

## 三、四类原子测试方法

### 3.1 规则覆盖：每条强制规则至少一个拦截 Case

对约束法官中的每条规则，设计至少一个 Case 验证其拦截行为。

**举例**：信贷审批的金额拦截法官

| 规则编号 | 规则内容 | Case 设计 | 预期 |
|---------|---------|----------|------|
| R1 | 单笔贷款 > 100 万禁止线上审批 | 申请金额 = 100.01 万 | 拦截线上，转人工 |
| R2 | 申请人年龄 < 18 禁止放款 | 申请人年龄 = 17 | 拦截放款 |
| R3 | 同一申请人 30 天内申请 > 3 次禁止再申请 | 第 4 次申请 | 拦截 |

**核心原则**：不穷举金额取值，只覆盖每条规则的拦截行为本身；规则边界值由 3.2 专门验证。

### 3.2 约束边界：在硬约束的临界点设计 Case

对判定器/法官中的连续值约束，识别其硬边界，在临界点两侧各设计一个 Case。

**举例**：信贷审批的额度判定器

| 硬约束 | 临界值 | Case-1（边界以内） | Case-2（边界以外） |
|--------|--------|-----------------|-----------------|
| 单笔上限 100 万 | 100 万 | 99.99 万 → 允许 | 100.01 万 → 拦截 |
| 单笔下限 1 万 | 1 万 | 1.01 万 → 允许 | 0.99 万 → 拦截 |
| 月收入阈值 1 万 | 1 万 | 1.01 万 → 通过 | 0.99 万 → 拒绝 |

**核心原则**：每个边界两侧必须各有一个 Case，验证"刚好满足"与"刚好不满足"的判定。边界值的开闭区间（≤ 还是 <）也必须明确并被 Case 覆盖。

### 3.3 退化逻辑：验证"正常路径走不通时的降级行为"

退化逻辑（fallback）是断言驱动型 Operation 的常见模式——首选路径不可用时降级到备选路径。退化逻辑是高风险点，**必须**专门测试。

**举例**：资源调度的退化逻辑

| 退化场景 | 正常路径 | 退化路径 | Case 设计 |
|---------|---------|---------|----------|
| 主资源池为空 | 从主池分配 | 退化到备用池 | 构造主池所有资源 = 已占用 |
| 高优先级任务为零 | 调度高优先级 | 退化到中优先级 | 构造所有任务优先级 = 中 |
| 所有候选方案不达标 | 选最优方案 | 退化到"无方案，回滚" | 构造所有方案分数 < 阈值 |

**核心原则**：每条退化路径必须有专门 Case；退化触发条件必须文档化明确，不能依赖隐式行为。

### 3.4 安全审计链：验证"判定 → 拦截 → 执行"链路完整

任何写入必须经过"判定器推理 → 约束法官审计 → 写入器执行"。跳过任何一步都是违规。

**审计链测试三类 Case**：

| 链路类型 | Case 构造 | 预期 |
|---------|----------|------|
| 正常链路 | 合规数据 | 判定器推理 → 约束法官通过 → 写入器执行 |
| 拦截链路 | 违规数据 | 判定器推理 → 约束法官拦截 → 写入器不执行 |
| 跳过审计（负面） | 尝试直接调用写入器，不经过约束法官 | 系统应拒绝执行 |

**第三类是关键**——很多缺陷是因为系统允许某条路径绕过审计直接写入。必须专门设计负面测试验证"不允许跳过"。

## 四、联合验证

### 4.1 多判定器协同

多个判定器的输出被同一约束法官消费时，需验证它们之间的数据传递与优先级。

**举例**：风控拦截法官消费"用户信用判定器"的[信用等级]和"交易行为判定器"的[异常等级]

| 协同场景 | 判定器 1 输出 | 判定器 2 输出 | 法官行为 |
|---------|-------------|-------------|---------|
| 高信用 + 低异常 | 信用 = 高 | 异常 = 低 | 通过 |
| 高信用 + 高异常 | 信用 = 高 | 异常 = 高 | 拦截（异常优先于信用） |
| 低信用 + 低异常 | 信用 = 低 | 异常 = 低 | 拦截 |

**关键检查点**：多个判定器输出冲突时，法官的优先级规则必须文档化明确，不能依赖"业务常识"。

### 4.2 全局约束（宪法层）

当存在全局统一约束（如全局豁免、监管要求、节假日策略），需验证不同场景下宪法规则被一致遵守。

**举例**：风控系统宪法规则"VIP 用户单日交易额度自动放宽 10 倍"——需验证所有触发金额判定的场景都一致应用了该规则，而不是某些判定器漏掉了 VIP 标签处理。

**核心方法**：列出所有受宪法约束的判定器/法官，构造同一宪法触发条件下各路径的 Case，验证行为一致。

## 五、端到端审计链贯通

不做场景穷举，而是验证从事件触发到最终动作执行的安全审计链完整贯通。

**举例**：信贷审批端到端

| Case | 触发事件 | 判定链 | 约束法官审计 | 写入器执行 | 预期 |
|------|---------|-------|------------|----------|------|
| 正常贯通 | 用户提交，资料完整，金额合规 | 信用判定 = 合格 → 额度判定 = 可放 | 金额合规 → 利率合规 | 写入审批通过 + 放款 | 全流程通过 |
| 审计拦截 | 用户提交，金额 = 200 万 | 信用判定 → 额度判定 | R1 拦截（>100 万禁止线上） | 不执行，转人工 | 流程终止，输出拦截原因 |

### 5.1 Context 切换验证

断言驱动型系统通常有全局状态（环境/模式/注册表），不同状态下激活的判定器/法官不同。

**举例**：风控系统"正常模式"切换到"应急模式"（如大促当天），应激活所有"应急"标签的判定器和法官，禁用"正常"标签的部分判定器。

**测试方法**：构造 Context 切换前后的 Case，验证：

- 切换后正确激活的判定器/法官生效
- 切换前激活的判定器/法官正确卸载
- 切换中途的请求按哪个 Context 处理（设计必须明确）

## 六、写入器（Mutator）专项检查

写入器是唯一的物理状态改写入口，必须包含审计校验逻辑。

| 检查项 | 判断标准 |
|--------|---------|
| 写入前置条件 | 写入器执行前是否验证了约束法官的审计通过结论 |
| 数据回写规范 | 判定结论是否实时回写，后续模块直接读取回写值而非重新计算 |
| 权限隔离 | 写入器是唯一写入入口；其他层级只读，不得直接改写状态 |
| 幂等性 | 同一审计结论重复触发写入时，是否产生重复写入 |

## 七、回归与一致性

### 7.1 变更回归（与 SOP 不同）

- 当某条**约束法官规则**变更时：回归所有被该法官审计的"判定 → 写入"链路，而非按调用链回归
- 当某个**判定器**变更时：回归所有消费该判定器输出的法官，以及对应的写入路径

### 7.2 跨 Case 一致性

| 一致性维度 | 检查方法 | 典型问题 |
|-----------|---------|---------|
| 规则不冲突 | 不同约束法官的红线是否矛盾 | 法官 A 说"必须 X"，法官 B 说"禁止 X" |
| 宪法统一约束 | 所有判定器/法官是否遵守宪法层 | 应急场景下某判定器未执行自动豁免 |
| 边界值口径一致 | 相同业务量的阈值在不同规则中是否一致 | R1 用 100 万，R2 用 1000000，应统一 |

## 八、覆盖率目标

| 维度 | 目标 |
|------|------|
| 规则覆盖率 | 100%（每条强制规则必须被验证） |
| 审计链覆盖率 | 100%（每条"判定 → 拦截 → 执行"链路必须贯通） |
| 约束边界覆盖率 | 100%（每个约束边界必须被验证） |
| 退化逻辑覆盖率 | 100%（每条退化路径必须有 Case） |
| 拦截 Case 覆盖率 | 100%（每条红线必须有拦截 Case） |
| 跳过审计的负面 Case | 100%（每个写入入口必须有"绕过审计"的负面测试） |

> 断言驱动型覆盖率目标普遍 100%——因为穷举不可行，所以一旦决定"测规则"就必须每条规则都测到，不能像 SOP 流程型那样允许 5% 的缺口。

## 九、与 SOP 流程型的差异速查

| 维度 | SOP 流程型 | 断言驱动型 |
|------|----------|----------|
| Case 设计起点 | 判断节点的分支 | 强制规则 + 约束边界 |
| 覆盖率目标 | 分支覆盖率 ≥ 95% | 规则覆盖率 100% |
| 异常重点 | 兜底机制 | 红线拦截 + 跳过审计的负面测试 |
| 边界关注 | 0 值语义歧义、状态边界 | 约束硬边界两侧 |
| 端到端 | SOP 步骤全流程贯通 | 安全审计链贯通 |
| 回归 | 按调用链回归 | 按"被法官审计的链路"回归 |
| 一致性 | 术语 + 数据口径 | 规则不冲突 + 宪法统一 + 边界值口径 |
| 写入器 | 通常不专门检查 | 必须有专项检查（唯一写入入口） |

## 十、当前工具集的能力边界

- 当前 `/ontology-trace` 与 `/ontology-validate` 主要面向 SOP 流程型设计，trace 的自动场景生成是按"判断节点的分支"展开的
- 断言驱动型业务在使用现有工具时，建模人员需要：
  - 在 trace 的 Step 4（设计阶段确认）手工补充"规则覆盖 + 约束边界 + 退化逻辑 + 跳过审计的负面测试"四类 Case
  - 在 validate 阶段额外人工核对"审计链贯通"和"规则不冲突"
  - 写入器专项检查需要独立于工具，人工 review
