# Interaction Conventions

本文档规定所有命令（`.claude/commands/*.md`）与 agent（`.claude/agents/*.md`）面向用户输出的约定。**任何命令/agent 被修改时都应先参考本文，不在本文列出的约定需在此增补后再使用，避免多处自行约定造成漂移。**

## 适用对象

- `.claude/commands/**` 所有斜杠命令
- `.claude/agents/**` 所有子代理
- 所有 Python 脚本打印给最终用户看的文本

## 核心原则

1. **终端内完成交互** — 不依赖 VSCode / drawio 等外部编辑器做决策。文件只作为最终产物存放；选择/确认/纠正一律在对话里完成。
2. **关键词优先、斜杠命令可选** — 每次需要用户作选择时，给出 `回复 **关键词**（/斜杠命令）→ 动作` 的完整提示；用户任选其一都能推进。
3. **肯定词等价处理** — 凡需用户"确认"的提示，都接受 `确认 / 好 / 好的 / 可以 / 没问题 / 继续 / 是` 等等价表达。
4. **技术术语不外泄** — 面向用户的文本必须经过 `USER_VOCABULARY.md` 过滤。

## 标准交互词汇

### 确认类

| 场景 | 统一用法 | 禁止 |
|------|---------|------|
| 确认继续/保留修改 | `回复 **确认**` | 回复"提交 / 保存 / OK / 好" 单独出现 |
| 取消/放弃 | 接受 `取消 / 不 / 否 / no / n` 等表达，但常规引导里不主动展示 | 回复"否 / 返回 / 退出" |
| 暂停当前阶段 | 接受 `暂停 / 完成 / 停止` 等表达，但常规引导里不主动展示 | "停"、"先别弄" |
| 继续下一阶段 | `回复 **继续**` | "下一步"、"往下"（仍允许作为等价） |

**等价词白名单（肯定）：** 确认 / 好 / 好的 / 可以 / 没问题 / 继续 / 是 / yes / y
**等价词白名单（否定）：** 取消 / 不 / 否 / no / n

命令/agent 在解析用户回复时须接受全部等价词。

### 选择类

| 场景 | 统一用法 |
|------|---------|
| 列表多选 | `[全部 / 输入编号如 1,3 / 跳过]` 或 `回复 **全部** / **1,3** / **跳过**` |
| 单选（少量选项） | `[选项1 / 选项2 / 选项3]` 或依需求给出 `回复 **关键词** → 动作` 列表 |
| 两项确认 | `回复 **是** 或 **否**` |

编号列表规则：
- 编号从 1 开始，连续递增（校验中跨批次不重置）。
- 逗号分隔（`1,3,5`），允许空格被忽略（`1, 3, 5`）。
- 支持范围（`1-5`）由具体命令决定，实现须在提示中明示。
- 非法编号一律提示"编号 X 不存在，已忽略"，不中断流程。

### 命令推进类

标准格式：

```
**下一步建议：**
- 回复 **关键词**（/斜杠命令）→ 简短动作说明
- 回复 **关键词**（/斜杠命令）→ 简短动作说明
上述选项只是参考，你也可以直接说明想修改、补充、校验或调整的内容，不必局限于这些建议。
```

要求：
- 每条都给关键词和对应斜杠命令。
- 关键词用中文，2–4 字。
- 动作说明以动词短语开头（如"开始提取"、"查看整体视图"）。
- 不要把 `完成` / `取消` 作为常规选项展示；命令仍应接受这些词作为停止/放弃意图。
- 若某条需要额外输入（如 `/ontology-trace 全部`），在动作说明中注明。
- 每个阶段完成后的建议块，最后一行都要写：`上述选项只是参考，你也可以直接说明想修改、补充、校验或调整的内容，不必局限于这些建议。`

### 非选项回复类

当用户在建议块之后回复的内容不属于上方选项时，不要强行要求用户改用固定关键词。按自由建模请求处理：

- 自由意图通常包括：修改 / 补充 / 校验 / 调整。
- 涉及修改已有 ontology / 文档：执行有明确范围的小修改；范围较复杂时转入 `/ontology-update`。
- 涉及补充知识、补充对象或补充逻辑：转入 `/ontology-research`、`/ontology-extract-object` 增量模式或 `/ontology-extract-operation` 增量模式。
- 涉及校验、检验、检查：转入对应校验命令（对象/逻辑用 `/ontology-validate`，流程图用 `/ontology-validate-diagrams`）。
- 涉及调整流程、暂停、回退、查看历史：按 `/ontology`、`/version` 或当前命令已有处理路径执行。
- 意图不清时，只问一个简短澄清问题。

处理原则：优先响应用户的自然语言意图；固定选项只是快捷入口。

### 跳步守卫类

当命令检测到前置阶段缺失时，统一格式：

```
⚠️ 跳步提醒：当前没有 {缺失阶段}（如 `research/` 为空）。
继续会导致：{具体后果，如"流程图可能遗漏关键对象"}。

- 回复 **继续** → 忽略提醒继续
- 回复 **先做 <关键词>**（/斜杠命令）→ 补齐后再继续
```

### 错误恢复类

命令检测到残留状态（执行锁、残缺文件等）时：

```
⚠️ 发现上次未完成的 {命令名}：
- 进度：{已完成步骤/总步骤}
- 时间：{开始时间}

- 回复 **续执** → 从中断处继续
- 回复 **清理重来** → 清理残留并重新开始
```

### 参考资料提醒类

命令在合适节点可向用户**软提示**可选的参考资料（如建模规范、风格指南）。提醒**不阻塞**用户当前回复；用户忽略即继续。

通用模板：

```
💡 可选参考：{触发理由（可选，一句话）}
可参阅 `{资料路径}`（{章节锚点}）{核对/排查的对象简述}。无需中断当前流程。
```

约束：
- 任何一个命令对同一份参考资料，**单次执行最多触发一次**，避免连续阶段重复打断。
- 不要把提示包装成必须回答的问题（不要加 `回复 是/否`）。
- 触发条件、措辞与覆盖的时机必须在被引用的资料文件中**显式定义**（单一事实源），命令端只调用，不内嵌新触发逻辑。
- 用户在当前会话中表达过"不需要 / 知道了"含义后，本会话内不再触发同一份资料的提示。

当前已接入的参考资料：

| 资料 | 触发约定位置 | 接入的命令 |
|---|---|---|
| `.claude/reference/BFO_MODELING_GUIDE.md` | 该文件 §10 | `/ontology-extract-object`、`/ontology-extract-operation`、`/ontology-validate`、`/ontology-overview` |
| `.claude/reference/OPERATION_PARADIGM_GUIDE.md` | 该文件 §七 | `/ontology-extract-operation`、`/ontology-validate`、`/ontology-trace` |
| `.claude/reference/ASSERTION_DRIVEN_TESTING_GUIDE.md` | 该文件 §十一 | `/ontology-extract-operation`、`/ontology-validate`、`/ontology-trace` |

### 业务知识确认类

命令在用户对话中识别到候选业务知识时：

```
💡 检测到一条业务知识候选：
{识别到的原话或要点摘要}
类型推测：{correction | convention | terminology | domain-rule}
适用范围推测：{scope 列表}

- 回复 **是** → 立即沉淀为业务知识
- 回复 **否** → 不沉淀，继续当前任务
- 回复 **修改后再记** → 给出修订内容后沉淀
```

记入成功后回应：`已沉淀业务知识：{name}（{type}）`。
等价词：`是 / 好 / 沉淀 / 记 / 记下`；否定：`否 / 不 / 不记`。

### 请专家确认卡类

用确认卡（AskUserQuestion）向用户提问时，卡片是给业务专家看的，不是工作记录：

1. **先判断要不要问。** 有明确默认做法、且不改变业务结论的事项，直接按默认处理，并在报告或结果里记一笔，不弹卡片。只有需要专家做业务判断的事项才问。
2. **问题用业务语言写清三件事**：这是什么（用对象、文档、规则的中文名称）、现在打算怎么处理、为什么需要专家判断。
3. **不出现内部写法**：内部编号（如 `ITEM-14`、`OBJ-03`）、文件名与配置（如 `materials.json`、各类 `.json` 回执）、标签取值（如 `purpose=term`）、英文表名列名、「引用字段」「拆分到来源表」这类实现说法，以及「模型不得…」这类给助手自己的约束。
4. **选项写成专家会做的业务判断**，推荐项放第一个并在说明里标「（推荐）」；需要用户在界面上操作时，指明界面位置（如「在资料区把这份文件的用途改为『术语表』」），不提文件名。
5. 一张卡只问真正待决的事项；同一类事项合并成一问。

示例（改写前 → 改写后）：

- ❌「条目1：订单汇总（ITEM-07）是多表组装的输出文档，无单一数据来源。引用字段现填『无』，是否确认？」选项「保持不拆分 / 拆分到来源表」
- ✅「『订单汇总』是根据订单、商品等多张表的数据汇总生成的文档，它本身不需要单独存成一张数据表，对吗？」选项「对，不单独存表（推荐）/ 不对，它有自己的数据表」
- ❌「条目2：商品术语.xlsx 在 materials.json 未标 purpose=term，怎么处理？」——不该问：按内容当作术语表使用即可，在报告「数据与术语来源」里注明。

## 文件与命令术语

所有用户可见文案的词汇约束（技术术语 → 业务用语替换表、完整名称约定、动作语句模板、错误信息模板）以 `.claude/USER_VOCABULARY.md` 为单一事实源。本文不复述具体词条——要新增 / 修改用户文案词汇，直接改 USER_VOCABULARY。本文 L16「技术术语不外泄」是对该词汇表的硬约束声明。

## 命令开头通用模板

所有 ontology 命令的 Step 0 流程以 `.claude/STEP0_TEMPLATE.md` 为单一事实源（含 check-lock / check-prereq / acquire / release / 业务知识加载等 6 步、stale 锁处理、只读命令的特殊路径）。本文不复述具体步骤以避免漂移——要新增或修改 Step 0 行为，直接改 STEP0_TEMPLATE。

本文与 STEP0 的分工：本文是话术权威（错误恢复 / 跳步守卫 / 等价词等措辞），STEP0 是流程权威（步骤顺序、脚本调用、锁状态机）。STEP0 顶部的话术对齐规则与本节互为映射。

## 呈现约定

- Markdown 报告文件统一命名 `reports/{YYYYMMDD}-{HHMMSS}-{scope}-{phase}.md`：
  - `{scope}` 标注检查对象范围：`objects` / `operation` / `actions` / `diagrams` 或 `all`（跨多个分类时）。
  - `{phase}` 标注阶段：`rule`（规则/结构检查）、`semantic`（语义检查）、`trace`（场景追踪）、`overview`（整体视图）。
  - 示例：`20260422-143022-operation-rule.md`、`20260422-143022-diagrams-semantic.md`。
  - 旧格式（`structure-*.md` / `analyze-*.md` / 无 scope 的 `-rule.md`）已废弃。
- 所有报告文件名中的日期时间、报告正文中的生成时间/日期/时间戳，统一使用 `Asia/Shanghai`。shell 里生成时间戳时使用 `TZ=Asia/Shanghai date ...`；Python 脚本使用 timezone-aware 的 `Asia/Shanghai` 时间，不依赖运行环境默认时区。
- 终端输出使用 `❌ / ⚠️ / 💡 / ✅ / ⏭️ / 🔧` 表情分别表示 错误/警告/建议/已修复/已跳过/已自动修复，与 `ontology_checker.py` 的 `SEVERITY_ICON` 保持一致。
- 中文报告/提示默认，偶有英文术语需用代码块包裹（如 `HEAD~1`、`[[link]]`）。

## 版本行为（汇总）

- 所有 commit 由命令内明确触发，用户侧看到的文案由 `.claude/scripts/post_commit_hook.sh` 统一输出 `已保存版本 N：…`。
- `/version` 命令提供历史/回退/对比/标记四个子命令（详见命令文件）。
- **回退会生成新版本 N+1** 的文案必须出现在所有回退确认处。

## 变更此规范

修改本文等价于修改所有命令/agent 的默认行为，任何改动都应：
1. 先在本文里写明新增/变更的约定；
2. 批量改动涉及的命令/agent；
3. 在 `TODO.md` 或后续计划中留下变更记录。
