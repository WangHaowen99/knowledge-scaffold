# 校验规则 vs 语义边界

本项目中有两类检查器：**确定性规则**（Python 脚本）与**语义判断**（LLM agent）。此前职责有重叠，本文是单一事实源，规定每一条规则归属哪一类。

## 判定原则

| 问题类别 | 归类 | 原因 |
|---------|------|------|
| 只需读文件结构即可判断 | 规则检查 | 无歧义，自动化可靠 |
| 需要理解业务语义/合理性/一致性 | 语义检查 | 依赖 LLM 的判断力 |
| 规则可判但消除歧义后还需人工确认 | 规则检查提示 + 语义检查复核 | 让两层结合 |

## 规则检查（Python）职责

由 `.claude/scripts/ontology_checker.py` 的 `run_checks(...)` 独立完成，**不依赖 LLM**。涵盖：

### 结构
- 必需章节是否存在（`OBJECT_REQUIRED_SECTIONS` / `OPERATION_REQUIRED_SECTIONS`）
- 表格是否存在、列是否完整
- 主键是否标注

### 引用
- `[[link]]` 目标文件是否存在
- 子流程调用、流程关联中的链接是否都能解析
- 子流程调用是否被列入 `与operation的关联`

### 契约
- 子流程输入参数是否能由调用者的输入/输出提供
- 子流程输出是否被调用者引用

### 派生
- 判断节点分支完整性（>=2 个分支，分类判断允许多于 2 个分支，是否有默认/其他分支）
- 逻辑描述中使用的字段名是否在对象属性中存在

### 数据来源与列名对账
与发布包导出（后端 `package_mapping`）同一口径，表头来自 schema 表格资料与评测数据源上传的数据表：
- 「# 数据来源」首行写成说明句 → `警告 / 数据来源格式`；句中反引号标出的现有表仍按声明处理
- 有数据表可核对、声明的表不存在，或声明的表一列都对不上属性英文名称 → `错误 / 列名对账`（发布时会被阻断）
- 项目里还没有任何数据表、对象却声明了表 → `警告 / 列名对账`（无从核对，发布包不绑定该对象；不确定时填「无」，不编造表名）
- 真实列名只出现在属性别名里 → `错误 / 列名对账`；其余属性没有同名列 → `警告 / 列名对账`
- 主键属性的英文名称不是所声明表的列（派生/非库字段标记也不豁免）→ `错误 / 列名对账`（图评测按主键建节点）

### 关联对象的关联字段
与后端 `package_mapping._relation_join` 同一口径。关联字段写在关系名后的括注里：`关系名（源对象字段 → 目标对象字段）`，字段用两端属性清单的「英文名称」：
- 两端「数据来源」是同一张表 → 不需要括注（图导入按同一数据行关联），不报
- 跨表、未声明括注，但一端的单字段主键在另一端有同名属性 → 后端能推断，不报
- 跨表、未声明括注、同名推断也不成立 → `警告 / 关联字段`（图模式数据评测会报「找不到关联字段」并跳过这条关系，发布包里这条关系也连不上）
- 括注声明的字段不在对应对象属性清单的「英文名称」列里 → `警告 / 关联字段`
- 括注字段写成 `表名.字段` → 去掉前缀只取字段；但前缀只对得上另一端的对象名或「数据来源」表名（方向写反）→ `警告 / 关联字段`
- 括注里取不出唯一的一对字段（如一侧有多个标识符）→ `警告 / 关联字段`
- 括注当纯说明用（两端清单都没有括注里的词）→ 不是关联字段声明，不报
- 同一关系（源对象, 关系名, 目标对象）在多处写出不同的字段对（同一文件两行，或两端各一行）→ `警告 / 关联字段`，冲突各处所在文件各报一条（后端两处都不导入、不拦整轮）；只有一端写括注时按该端补齐，不算冲突
- 自关联（源对象 = 目标对象）未写出关联字段 → `警告 / 关联字段`（会把节点连到自己，后端跳过）
- 同一文件里同一关系写了两行（源对象、关系名、目标对象和关联字段都相同）→ `错误 / 重复关系`，报出两处行号（发布和数据评测都会拒绝）；源对象和目标对象的文件各写一次是同一关系的两端描述，后端合并为一条，不报

### 属性类型与取值证据
口径在 `scripts/field_semantics.py`，取值画像来自登记的数据表（每表最多读 2000 行，只统计取值形态，不保留原值）。类型词表：`字符串 / 整数 / 小数 / 布尔 / 日期 / 枚举 / 对象引用`，存量的 `数字` 照认：
- 类型留空、填模板占位，或写了多个候选（如 `字符串/整型/布尔`）→ `错误 / 类型非法`；写了词表外的类型 → `警告 / 类型待确认`
- 声明为整数 / 小数，但有前导零、小数（整数列）或非数值取值；声明为布尔却有非布尔取值；声明为日期却有非日期文本 → `错误 / 类型冲突`
- 声明为字符串，但取值全是数值，且不是标识字段（主键、对象引用、编号 / 编码类命名）、没有超过 15 位的长整数、数据表类型说明行不是字符串、属性规则也没写 `文本保留` → `警告 / 类型待确认`
- 数值列有超过 15 位的长整数、数据表类型说明行写的是字符串；布尔取值是 `t/f`、`y/n`、`0/1` 而属性规则没写取值含义；日期列有纯数字取值而属性规则没写格式 → `警告 / 类型待确认`
- 标识字段里数字与文本混用、前导零与无前导零并存、取值只差大小写或前导零，且属性规则没写 `混合标识` → `警告 / 标识混合`（归一化口径要业务确认，不自动补零、去零、改大小写）
- 对象未绑定数据表、表未读取、表只有表头、列不存在、整列为空 → 结论「未验证」，不报问题，也不算通过；`field_semantics.py types` 逐字段列出原因。登记的表缺失、无法解析或缺解析依赖时整体「无法核验」（退出码 2），`verify_artifacts.py` 同样不给通过
- 只看取值形态，不判断业务上该用哪种类型；业务口径冲突仍归语义检查

### 字段等价关联
operation / rule 文档的正文逐行扫描（不含标题与 frontmatter）：同一子句里把两个对象字段当作同一个值核对、比对或关联（「A 与 B 核对」「A 应等于 B」「A 和 B 无法交叉核对则报资料冲突」等）：
- 两个字段同名、互为属性别名，或已在对象「# 关联对象」声明为关联字段（任一方向）→ 不报
- 否则 → `错误 / 字段关联`：没有依据的等价不得作为拦截或报错条件；资料确有此关联时先在对象里声明关联字段
- 同一行标了「待确认」→ 降为 `警告 / 字段关联`，确认前不得作为拦截或报错条件
- 用两个条件定位一个对象（「按 A 和 B 匹配 [[对象]]」）不是等价声明，不报
- 规则是句式启发，不做语义理解；漏报的等价关系仍由语义检查兜底

### 候选修订
`scripts/candidate_revision.py` 修改已生成或已确认的本体文档：登记修正计划 → 在候选副本上改 → 差异 → 整计划校验（确认版本与叠加候选后的版本各跑一遍全量规则检查，候选引入新的「错误」即不通过）→ 接受或拒绝。校验结论绑定候选、确认版本与全部输入的指纹，任一变化都要重新校验；拒绝不改工作区文件；数据表读不了时结论是「无法核验」，不能接受。

### 关联对象的关系名称
名称先做 NFKC 归一化，比较时忽略大小写、空白和标点符号：
- 关系名包含源或目标对象名称 → `警告 / 关系名称`。发布包里对象的 key 与标题都取文件名、不带别名，所以端点名称就是两端的文件名；归一化后不足 2 个字符的端点名称不参与比较
- 关系名只写了基数（`一对多`、`1:N`、`0..1` 等）→ `警告 / 关系名称`
- 关系行格式错误、关系名为空、模板占位符未填写 → 不报，由发布与评测侧负责
- 定为警告而不是错误：演进流程要求清零全部错误，改名须两端对象一起改，不应在无关的修改中被迫批量改名

### 图标识符与知识包 key
图标识符与后端 `package_mapping.GRAPH_IDENTIFIER` 同一字符集（字母、数字、下划线、汉字，不以数字开头）；知识包 key 的约束如下：
- 声明了数据表的对象，属性英文名称不合规 → `错误 / 图标识符`
- 关系名不合规（含括注没紧跟关系名、被整串当成关系名）→ `警告 / 图标识符`（该条关系被跳过）
- 对象/操作/规则/指标/脚本文件名、属性英文名称超过 80 字符，或含 `/ \ # ? & |`、`..`、控制字符 → `错误 / 命名约束`

### consumer 容量上限
与 consumer 后端 `LimitsConfig` 默认值一致，超出时提示 `警告 / 容量上限`：对象 > 1000 个、操作 > 500 个、单个对象属性 > 300 个、单个操作文档 > 30000 字符。工具箱使用固定默认值，不读取部署环境变量；正式发布门禁以建模后端同名环境变量或默认值为准，实际安装以 consumer 配置为准。

### 脚本契约、安全与绑定（`--include-scripts`）
- `ontology/scripts/*.py` 可解析、可执行脚本使用 argparse 长选项、CLI 输出单个 JSON → 缺失为 `错误 / 脚本契约`
- 头部「输入参数」与 argparse 声明一一对应，类型、必填一致 → 不一致为 `错误 / 脚本契约`；解析逻辑在 `.claude/scripts/script_contract.py`，与知识包导出共用
- Web 保存 `ontology/scripts/*.py` 前只编译、不执行源码；语法错误和明确的输入/输出契约错误返回 422，保留原脚本、描述符和 Git 版本，编辑器保留未保存内容。保存成功只表示工作区修订已记录，不等于运行验收或发布。
- CLI 输出可静态追踪到的字典键与头部输出声明不符 → `错误 / 脚本契约`。只检查输出路径，辅助函数、动态键、循环、可变字典或外部调用无法确认时为 `警告 / 脚本契约`（未验证）；不推断全部 Python 行为。
- 对外脚本的动态输出在导出前必须有当前源码及同目录依赖哈希一致、支持输出契约检查的运行验证记录；运行验证按完整 JSON 检查声明字段和类型，再截断展示。参数错误响应独立于业务输出契约。旧记录须重验；发布冻结时一并复制验证记录，记录不进入知识包。
- 禁用规则（子进程、系统命令、网络、高风险模块、写模式 open、递归删除、动态执行、源码超 100000 字符）→ `错误 / 脚本安全`；写模式按语法树判定，逐字正则匹配会误判的写法（如 `open` 同行的 `encoding="ascii"`）→ `警告 / 脚本安全`
- 头部「关联operation」写的 operation 不存在 → `错误 / 脚本绑定`；写「无」→ `建议 / 脚本绑定`（不作为独立脚本导出，只能被其他脚本复用）
- pre-commit 暂存脚本时，`脚本契约` / `脚本安全` / `脚本绑定` 的 `错误` 都会拦下提交

### 脚本运行验证（pre-commit 门禁）
- 提交新增或修改的 `ontology/scripts/*.py` 时，脚本（以及 import 了改动模块的脚本）必须有与当前源码一致的 `script_verify.py run` 通过记录（`.ontology-state/script-verifications.json`），否则拦下提交
- 验证经脚本验证网关在 jiuwenbox 沙箱中执行，网关或 jiuwenbox 不可用时在 onto-modeling 容器内执行；规则检查（`ontology_checker.py`）只做静态检查，不运行脚本

### 打包范围
- 白名单内但不进知识包的目录（如 `ontology/knowledge/`）存放知识文档 → `警告 / 打包范围`；只有 `ontology/{object,operation,logic,rule,metric}` 与 `ontology/scripts/*.py` 会导出给 consumer

### 流程图（合并后）
- 开始/结束节点存在性
- 孤立节点、死路节点
- 悬空连线
- 判断节点有效出边数 < 2（分类判断允许多于 2 个分支）
- 图例 `resource/diagrams/图示说明定义.drawio` 中标为"虚拟项"的样式不作为真实流程节点；`offPageConnector` 是透传虚拟项，按输入输出直接相连理解
- 流程图与 Excel 对齐时，Excel「业务活动」列覆盖 drawio 中所有非虚拟有标签节点，而不是只覆盖"业务活动"矩形节点

所有以上检查在 **Python 层输出确定性结论**，必要时直接分类为"简单问题（可自动修复）"。

## 演进期专项规则检查（Python）

`run_checks(...)` 之外的脚本，只在 `/ontology-evolution` 的一致性复检中跑。

`check_eval_generalization.py` 判"修订是否泛化"，共享同一 `Issue` 字段（发现问题时 exit 1）：

| 规则 | severity | category |
|---|---|---|
| 修订文档与评测用例原文连续雷同 ≥ 阈值（默认 30 字） | 错误 | 应试痕迹 |
| 修订文档出现面向考核的表述（标准答案/评测用例/判分/用例编号；得分、评分标准等业务两用词仅在与考核语境同行时判定） | 错误 | 应试措辞 |

`check_eval_data.py` 输出评测数据列 ↔ schema ↔ 属性英文名的三方对账差异清单（不带 severity），差异项必须清零。`--profile` 输出各列取值形态的计数（不含原值），供对象抽取定类型；类型核验见上文「属性类型与取值证据」。

以上只判"知识是否普适、映射是否对得上"，不判业务对错；业务合理性仍归语义检查。

## 语义检查（Claude）职责

由 `.claude/agents/semantic-check-agent.md` 执行，**只在规则检查通过后跑**。涵盖：

### 逻辑文档
- 逻辑步骤完整性（异常分支、不完整条件）
- 输入参数是否被实际使用
- 输出是否可由逻辑推导
- 子流程调用合理性
- 前提与逻辑一致性
- 对象关联分类是否正确
- 流程关联完整性
- **兜底完整性**：识别异常子逻辑调用点（转换型/判断型/数值计算型/查询型），判断是否命中天然保护（前置过滤、成熟态数据、防火墙拦截、参数无关、纯查询/计算）或显式兜底（跳过/空值传递/估算值/默认值）；两者皆无 → "兜底缺失"
- **空值语义区分**：`∅_zero`（确定为零）可参与计算；`∅_unknown`（未读取/未同步）必须先兜底；若 `∅_unknown` 被当 0 直接参与下游聚合/阈值判断 → "空值语义模糊"（高置信，因可能掩盖风险）

### 对象文档
- 属性描述歧义性
- 关联合理性
- 整体业务合理性
- **关联对象数据支撑**：对每条 `关联对象` 关系按 4 维度判断（源/目标外键、中间对象、共同维度）。
  - 无支撑且无推理路径 → "关系无数据支撑"（high，建议删除）
  - 无外键但业务上可推理 → "关系应转Operation"（medium，message 中给出转写模板：触发条件/计算逻辑/输入对象/输出属性/业务说明）
  - 防错：时序体属性也算外键；已有外键的不要降级为 Operation

### 跨文档
- 对象生命周期（是否缺创建/读取/更新/删除路径）
- 字段类型兼容性
- **规则冲突检测**：扫描 operation 中的阈值/授权/降级/优先级类规则，同名规则有不一致定义 → "规则冲突"（high）；只指出不一致，不判对错；不同业务场景下的合理差异不算冲突

### 置信度分层（新增）
语义检查输出必须带 `confidence` 字段：
- `high`：规则佐证充分（如对象生命周期检查，同时参照规则检查结果）
- `medium`：依赖启发式判断
- `low`：需人工判断，不建议自动修复

UI 呈现时按置信度分组显示，`low` 默认折叠。

## 边界案例

| 场景 | 处理 |
|------|------|
| 链接失效 | 规则（现在） |
| 字段名歧义（"订单号" vs "订单编号"） | 规则检测到"字段不存在"，语义判断是否同义 |
| 命名一致性（"取消订单" / "撤销订单"） | 语义检查 |
| 缺失分支（仅 0-1 个分支，或分类判断缺少必要分类/默认分支） | 规则（至少 2 个分支）+ 语义（判断业务分类是否覆盖） |
| Mock 数据外键完整性 | 规则（新增） |

## 权威严重性矩阵（语义检查）

下表是语义检查每条规则的 `severity` + `category` + 默认 `confidence` 的**唯一权威**。`semantic-check-agent.md` 的 prompt 必须与本表完全一致；任何冲突一律以本表为准修正 agent。

### Operation 检查

| 规则 | severity | category | 默认 confidence |
|---|---|---|---|
| 逻辑步骤完整性（缺分支/异常路径） | 错误 | 逻辑缺陷 | high |
| 输入参数使用 | 警告 | 参数未使用 | medium |
| 输出可推导性 | 警告 | 输出不可达 | medium |
| 子流程调用合理性 | 警告 | 子流程不匹配 | medium |
| 前提与逻辑一致性 | 警告 | 前提不一致 | medium |
| 对象关联分类 | 警告 | 对象关联不合理 | medium |
| 流程关联完整性 | 警告 | 流程关联不完整 | medium |
| 兜底完整性 | 警告 | 兜底缺失 | medium |
| 空值语义区分（∅_unknown 被当 0 用） | 错误 | 空值语义模糊 | high |

### Object 检查

## 约定

- 规则检查 = 静默、可重复、零歧义。
- 语义检查 = 出具建议、标置信度、用户决定是否接受。
- 两者共享同一 `Issue` 结构（`severity / category / file / message / source`），新增 `confidence` 可选字段。
- 严重性归口：**本文档「权威严重性矩阵」是唯一来源**；其他文件出现的 severity 字面值视作引用，不视作另立标准。
