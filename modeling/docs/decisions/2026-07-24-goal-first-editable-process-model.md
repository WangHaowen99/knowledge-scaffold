# 建模目标先行并采用可编辑的结构化流程模型

本决策只取代旧决策中的两项内容：固定里程碑由“资料就绪 → 建模目标确认”改为“建模目标确认 → 资料就绪”；流程图首版由“不提供完整拖拽编辑器”改为提供结构化可视化编辑器。旧决策的其余内容继续有效。

## Context

原有 AI 辅助构建先分析资料，再从资料中推断建模目标；流程图确认阶段以 Mermaid 源码为事实来源，用户主要通过文字要求模型修改。该方式存在三个问题：资料分析容易偏离用户真正要解决的问题；一个确认交互难以逐张追加多个核心流程；用户无法直接修改节点、连线、分支文字和业务条件。

同时，Mermaid 适合展示和交换，但不适合作为拖拽编辑器的双向事实模型。直接解析和重写 Mermaid 会丢失稳定边 ID、布局位置、边类型与完整条件，也难以实现乐观并发和不可变修订。

## Decision

新建项目先收集并确认一段自由文本建模目标。服务端把目标整理为版本化的建模目标说明；目标确认后才创建资料分析任务，资料分析、候选流程和 AI 新增流程都必须携带当前已确认目标。修改已确认目标时保留历史，并使下游资料分析和流程任务过时。

流程确认采用唯一的结构化 `FlowchartDocument` 作为事实源。一份文档可以包含多张流程图；节点和边都有稳定 ID，边保存类型、图上文字和完整业务条件，布局单独保存。Mermaid、流程目录和 `processes.json` 都由该文档派生生成，不再反向解析 Mermaid 作为编辑事实。

流程图在确认交互下维护独立草稿和不可变修订。用户可以在中间画布增删改节点和边、编辑边文字与条件、拖动布局并显式保存。每张流程可以单独追加，来源可以是资料分析候选、围绕建模目标的 AI 推荐或空白流程。右侧建模助手只提交当前最新且已保存的整份流程文档。

资料分析候选由服务端分配稳定候选 ID；标题只用于展示且允许模型优化。候选 ID 贯穿候选列表、新增请求和流程图来源记录，因此同名候选可以分别添加，模型改写标题也不会让已使用候选重新出现。旧客户端按标题新增时仅在唯一匹配时兼容。

草稿保存采用乐观并发。重复 ID、悬空边和非法类型属于结构错误并阻止保存；空白图、缺少开始或结束、孤立节点、循环和判断分支缺少文字属于非阻断提示。最终提交把同一修订投影为知识包 Mermaid 资源并记录提交标记。

所有建模项目使用同一任务图和流程文档模型。部署前如存在旧格式数据，应执行一次性离线迁移；应用运行时不保留旧格式读取或版本分流。

## Alternatives considered

- 继续把 Mermaid 作为唯一事实源并直接编辑源码：实现简单，但无法可靠保存布局、稳定边 ID 和结构化业务条件。
- 为每个节点和边提供聊天修改指令，不提供画布编辑：审计容易，但高频小修改效率低，且无法满足直接增删改需求。
- 每张流程单独提交知识包：会产生大量不完整的中间知识包修订，难以保证多流程的一致确认。
- 对所有业务完整性问题做强校验：会再次导致可用草稿因非关键缺项被阻断，不符合渐进建模和人工完善的使用方式。

## Consequences

- 后端维护流程草稿、草稿修订和提交记录，运行时只接受唯一的 `FlowchartDocument` 结构。
- 前端编辑器不直接写知识包；保存草稿和提交确认是两个独立动作。
- Mermaid 仍可流式展示 AI 生成过程，但流式内容完成后由结构化文档接管编辑。
- 后续知识构建直接读取已确认流程；完整结构信息保留在 `diagrams/processes.json`，operation 和证据可引用节点与边 ID。
- 目标修改必须触发下游失效分析，不能静默沿用旧资料结论或旧流程草稿。
