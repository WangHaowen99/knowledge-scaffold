# 全文资料分析采用并发 Map-Reduce 与持久化断点

## 状态

已采纳，2026-08-19。

替代 `2026-08-04-document-full-read-gate.md` 中由单个 Agent 串行翻页完成全文覆盖的实现；保留“覆盖必须由后端事实证明”的目标。

## 背景

旧资料分析让一个 Agent 以固定 6,000 字符分页串行通读全部文档；领域分析读一遍，材料分类又按批次重复读取。大项目可能包含上百万字符，需要数百次模型回合，进度长期停留在固定阶段值。模型限流、额度不足、进程重启或普通网络失败后，已完成阅读只存在于 Agent 上下文中，重试必须从头开始。

直接提高单页大小或回合上限只能缓解耗时，不能提供并发、完整覆盖证明和可恢复性。保留新旧两套全文路径还会造成相同资料在初步分析、增量建模和直接聊天中产生不同事实与进度。

## 决策

- 全文分析只有一条生产路径：动态分段 Map → 文档 Reduce → 领域 Reduce。
- 分段大小根据当前模型 `contextWindow`、输出预算、提示预算和安全余量计算，限制在 2,000–16,000 token；优先在章节、空行和句子边界切分，并保留小范围重叠。
- Map 使用有限并发，默认 3。遇到 429 时降低并发并指数退避；普通临时失败自动重试有限次数；额度耗尽立即暂停。
- 每个分段、文档汇总和完整运行持久化到 SQLite。检查点绑定项目、资料内容哈希、文档修订、模型、分段协议和建模目标。服务重启将 `running` 分段恢复为 `pending`，重试只领取未完成分段。
- 同一项目内内容、模型和协议完全相同的已完成分段与文档汇总可以跨运行复用。增加资料只分析新增资料；修改资料只重跑变化文档；领域 Reduce 根据当前完整资料集重算。
- 文档 Reduce 必须均衡保留每个分段的代表信息，且所有分段候选由后端确定性合并，不能通过截取 JSON 前缀丢掉文档后半段。
- 领域 Reduce 消费所有文档汇总和表结构；初步分析输出继续作为后续知识生成的对象、规则、指标、操作和流程候选来源。
- 直接聊天、增量建模和初步分析复用同一全文事实源。`read_document` 仅用于按需核对具体章节或条款，不再承担全文通读。
- 进度按去重后的已覆盖字符计算，Map 阶段持续映射到 5%–65%，随后展示文档汇总、领域汇总和质量检查。
- 删除旧串行全文会话、全文读取门禁、四份一批缓存、旧提交工具以及只验证旧协议的测试，不保留测试专用旧路径。

## 考虑过的方案

### 只增大固定分页大小

改动小，但仍是串行、不可恢复，也不能根据 32K 与 1M 上下文模型自动选择安全输入规模。

### 只提高 Agent 回合上限

可以让单次任务运行更久，但上下文继续增长，失败后仍从头开始，也无法证明所有文档连续覆盖。

### 新旧全文流程并存

短期迁移风险较低，但会让测试与生产、初步分析与聊天使用不同事实源，长期产生重复成本和不一致结论，因此不采用。

## 后果

- 长文档与多文档可以并发处理，实际吞吐取决于模型端并发和限流策略。
- 模型失败、额度恢复或服务重启后可以从持久化断点继续，不重复已完成模型调用。
- SQLite 会新增运行、分段和文档汇总记录；备份 Modeling 数据卷时会自然包含这些检查点。
- 改变提示、分段算法或模型时必须更新协议指纹，避免复用不兼容结果。
- Map 结果保持目标无关，便于建模目标变化时复用原始事实；领域 Reduce 仍必须按新目标重算。
