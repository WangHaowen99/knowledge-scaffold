# 人工编辑草稿后端

## Context

当前人工文件修订以项目级 `package_overrides` 保存，并跨知识包版本持续覆盖同一路径。包修缮读取最新版结构化规格，而展示、导出和评测会叠加 override，可能形成两个事实来源。

本阶段先建设独立的人工编辑草稿后端，不切换现有编辑、修缮或消费链路，避免一次性改变线上行为。

## Decision

- 每个项目同一时间最多有一个活动人工草稿。
- 草稿绑定创建时的不可变知识包版本 ID 与版本号。
- 草稿只保存相对基线版本变化的文件；恢复基线内容时删除对应草稿文件记录。
- 每次有效文件变更递增草稿 revision，写接口使用乐观锁拒绝过期客户端覆盖新内容。
- 草稿支持查询、创建或恢复、文件读取、文件保存、单文件撤销和整份放弃。
- 本阶段不修改 `package_overrides` 的现有行为，也不对修缮、导出、评测等入口增加门禁。

## Alternatives considered

- 继续扩展全局 override：无法解决跨版本覆盖与事实来源分叉。
- 每次保存文件立即生成版本：多文件编辑会产生大量碎片版本。
- 只在浏览器保存草稿：刷新、崩溃或更换设备后无法可靠恢复，也无法做服务端并发控制。

## Consequences

- 后续可以在不改变草稿数据模型的前提下增加发布事务、统一门禁和前端恢复流程。
- 发布阶段仍需把草稿内容固化回正式版本的权威规格，不能把草稿变成新的跨版本 override。
- 历史 `package_overrides` 的迁移和旧链路清理留到兼容迁移阶段处理。
