# 知识结构并发生成与局部断点恢复

## Context

旧链路把对象、规则指标和业务操作固定拆成小批次并串行调用模型。包含 Schema 工作簿时，确定性 Sheet 对象之外又生成大量文档逻辑对象，造成对象膨胀和数小时等待。检查点绑定整个生成计划，任一候选变化都会让全部批次失效。

## Decision

- 存在来自已上传 Excel/CSV 资料的 Sheet 时，对象目录只由业务 Sheet 确定性生成；Schema Manifest 不生成对象，文档只补充说明和证据，不新增对象。
- 没有结构化 Sheet 时，才生成文档逻辑对象。
- 对象、规则指标、业务操作使用统一生成单元；批大小根据模型上下文和候选体积计算。
- 三个阶段内部采用受控并发，完成后按原始顺序进行全局 key、来源和引用校验。
- 每个生成单元保存独立依赖指纹。服务重启或输入局部变化时，只恢复依赖未变化的完成单元。
- 继续保留来源映射、候选 disposition、业务流程覆盖和整包完整性门禁。

## Alternatives considered

- 仅增大固定批次：减少请求次数，但不能解决串行等待、候选膨胀和局部恢复。
- 所有候选完全并发：速度快，但容易触发限流，也无法稳定控制全局引用冲突。
- 保留新旧两套路径：回滚容易，但会形成行为分叉；本次直接替换旧串行循环。

## Consequences

- Schema 工作簿项目的对象阶段不再调用模型，生成对象数量等于业务 Sheet 数量。
- 规则指标和业务操作耗时主要由最慢并发波次决定，而不是所有批次耗时相加。
- 模型平台并发能力较低时，需要通过三个环境变量降低并发。
- 并发单元发生跨批 key 冲突时，整包保存前会明确失败，不会静默覆盖。
