# 阶段外受控写入：确定性重定向、共用恢复预算与措辞门禁

## Context

一次修复回合停在了没有出口的状态：验证阶段完成评测、用户选定修复方案后，助手连续 6 次写入失败，
把它判定成「平台侧能力缺失」，停止重试，并让用户等待平台开放写入能力。流程卡在「修复待落盘」，
进度条停在「知识建模阶段」，界面上没有重试、重新触发或导出的入口。

根因不在写入本身，而在工具面按业务阶段收敛（`core_tool_specs_for_phase`）：
受控写入链路不属于当前阶段时，工具直接从工具面消失。模型看到的不是「这件事要换个阶段做」，
而是「这个能力不存在」，于是把内部阶段边界讲成平台缺陷，再把责任推给用户等待。
一旦这句话说出口，本轮就没有任何可操作出口了。

主干做法是：不属于当前阶段的受控写入注册成确定性拒绝的同名工具
（`PhaseUnavailableTool` / `phase_capability_redirect`），回答「这项能力在哪个阶段」，
并交给自动恢复去切阶段。随后的复核暴露了这条链路上几处仍会把用户带回同一个死结的地方，
本记录覆盖主干设计和这几处收口。

## Decision

**阶段外的受控写入永远有一个确定性答复，而不是一个不存在的工具。**
缺席的写入链路注册同名占位工具，返回 `TOOL_PHASE_UNAVAILABLE`、承载阶段和重提指引。
两条拦截路径——工具未注册（占位工具）和已注册但阶段不对（`WriteSafetyRail`）——共用同一份出口，
否则模型仍会在其中一条上撞到「这件事做不了」。

**承载阶段是一张多值表，按当前阶段一跳可达优先选。**
`PHASE_CAPABILITY_HOSTS` 把每条受控链路映射到它真正落地的若干阶段
（如脚本修复同时在确定性验证和增量建模里），`phase_capability_host(name, phase)` 优先挑
`BUSINESS_PHASE_EDGES` 里一跳可达的那个。阶段边定义单点存放在 `tools.py`，service 层复用同一份。

**走不通的一跳不消耗恢复预算。**
承载阶段一跳不可达时，重定向直接声明 `autoRecoverable: False`，`_autonomous_recovery` 立刻转成
用户可操作的选择，而不是先烧完 2 次尝试。这种情况下收尾指令保留策略自己的那句
（先读状态、按可走的路径推进），不换成通用的「停止并等待用户」——否则模型手上唯一真能走的路也被抹掉。

**一个承载阶段上的写入共用一条 issue 和一份恢复预算。**
`issueId` 取 `phase-capability-{host_phase}` 而不是带工具名。按工具名分账时，模型在同一条受控链路里
换个工具重试就能各拿一份预算，用户要看着十几次失败才等到出口。
任何一个承载阶段转换成功都关闭这条 issue（`hostPhases`），而不只认 `requiredPhase`。

**转换被门禁挡回时立刻转成带未满足项的用户选择。**
入口门禁（如 `validation` 的 `knowledge_confirmed`）可能挡住自动切阶段。这时这条 issue 已经没有
自愈路径，继续放模型回去重提写入只会把剩余预算烧完，用户点「继续」还会回到同一个循环。
`block_phase_capability_issues` 把它标成 `blocked` 并带上真正的 `blockers`，服务端据此渲染恢复卡，
恢复提示改成「先读状态、按未满足项推进、必要时回到用户」，不再重提同一次转换。

**平台能力声明的措辞门禁按共现判定，不做裸短语匹配。**
「未注册」「不可用」「缺失」本身是正常业务表述——建模对象里就有「该企业尚未注册」
「该流程存在能力缺失」这种正文。裸短语匹配会把业务内容误判成平台能力声明，
整轮被强制纠偏、可见推理还被整段隐藏。只有点名平台/工具/会话环境的措辞单独成立，
其余要求这些词挂到平台、工具、写入、落盘这类主语上才算数。清单与正则同时供可见文本脱敏和
rails 的能力声明门禁使用，避免两处措辞各自漂移。

## Alternatives considered

- **把缺席的写入工具全量放开**：等于取消阶段收敛。工具面收敛本身有效——它压住了跨阶段乱写，
  代价只是「消失」这个表现形式不可解释。要修的是表现形式。
- **只在提示词里禁止模型声称平台缺能力**：已经试过，不够。模型确实看到工具不在，
  提示词与它观察到的事实冲突时，观察赢。必须让它观察到的事实本身是「换个阶段做」。
- **让模型自己判断阶段是否可达**：阶段边和门禁是服务端事实，交给模型判断等于让它猜，
  猜错就是又一轮死循环。可达性在重定向里算好，随结果一起给出。
- **恢复预算按工具名分账（原实现）**：看起来更细，实际是给同一条链路发了十几份预算。
  用户等待时间按链路里的工具数量线性放大。
- **门禁挡回后继续自动重试**：门禁的未满足项要用户或后续工作去满足，重试不会改变结论。
- **保留裸短语清单、只加白名单**：业务正文里这类表述是开放集合，白名单永远补不全。

## Consequences

- 阶段能力占位工具扩展到融合与评测链路，承载阶段覆盖 `knowledge`/`increment`/`validation`/
  `evaluation`/`release` 五个后段阶段。前段阶段（`intake`/`goal`/`process`）工具面保持收敛。
- 关系审阅（`review_object_relations`，`apply=true` 时写工作版本）也在这张表上。它和另外两条
  链路不同：确定性验证和评测阶段按只读保留它做失败归因，只有发布阶段不承载，那里重定向回
  知识建模。新增受控写入口时要一并登记，否则它在缺席的阶段又只剩「工具不存在」这一个解释。
- 占位工具与其他有持久化副作用的工具一样受运行取消围栏约束（`cancel_event`）。
  越过取消点再落 issue 的话，用户停掉的那一跳会在下次恢复这次运行时重新弹出恢复卡。
- 恢复卡新增 `blockers` 字段（后端 `_suspend_technical_recovery` 下发，前端 recovery 块渲染
  「未满足条件」）。用户看到的是差哪一项，而不是一句「已停止」。
- 措辞门禁放宽后，只点名「不可用」而完全不提平台/工具/写入的极短句子不再拦截。
  这是有意的取舍：误伤正常业务正文的代价（整轮纠偏 + 推理被隐藏）高于漏掉一句模糊表述。
- 旧格式的持久化 issue id（带工具名）仍能正常恢复，恢复动作按 id 查找，不解析格式。
- 仍未处理：门禁未满足项的文案来自确定性核心，措辞质量取决于那一侧；恢复卡只做转述。
