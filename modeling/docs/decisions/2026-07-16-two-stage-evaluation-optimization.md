# ADR：评测优化改为“先诊断、再建议”

## 状态

已采纳，2026-07-16。

## 背景

旧优化器把所有未通过结果直接交给模型生成知识包修改建议。实际失败可能来自用例答案冲突、认证或连接错误、输入数据缺失、判分依据问题、知识缺失、路由错误、口径错误，以及需要确定性脚本的复杂计算。直接改包会把运行故障和数据缺失误写成业务规则，也容易把单条用例的标准答案、批次范围和日期常量硬编码进知识包。

## 决策

评测优化固定分为两个持久化阶段：

1. 失败原因诊断：结合用例、Judge 理由、Consumer 运行标识与工具时间线、当前完整知识包规格，以及材料分析阶段记录的数据缺口，输出结构化根因和证据。
2. 优化建议生成：只处理诊断为可通过知识包或脚本修复、且没有被数据或用例问题阻断的结果。

两个阶段使用独立工作流步骤和独立页面。评测轮次未通过，或在准备数据源、导入知识包等基础设施阶段失败后，流程先进入“失败诊断”；只有诊断确认存在可由知识包或脚本修复的问题时，才开放“优化更新”。评测运行失败的轮次也必须可诊断，不能因轮次状态不是 `done` 而被挡在诊断入口之外。

诊断按影响范围分为评测用例、运行环境、数据资料、知识包、计算脚本和判分依据。用例冲突、运行错误和数据缺失不会转成知识包修改。

阻断诊断表示“该问题未修复前不能证明复评通过”，不应吞掉同一用例上独立的可优化诊断。例如既缺价格数据、又需要多批次计算脚本时，可先生成通用脚本，但页面必须继续提示补齐数据后才能验证结果。

每条优化建议必须关联诊断 ID，并包含证据、通用化方案和样例外验证方案。系统拒绝直接复制完整标准答案，以及硬编码某条用例的批次编号范围或日历常量。

复杂的多批次计算、聚合、排序和规划优先生成受控 Python 脚本。脚本作为知识包一等资源持久化，必须绑定 operation，并经过静态安全检查；禁止子进程、动态执行和危险文件删除。知识包修改助手必须完整保留脚本，删除 operation 时须同步删除或重新绑定脚本。

## 结果

- 页面先展示可回看的失败原因，再开放建议生成。
- 评测失败后自动定位到失败诊断页，诊断与优化更新不再共享页面。
- 权限、连接、数据和用例问题不会污染知识包。
- 优化建议具有明确证据和验收方法，便于人工审核。
- 新增脚本能够随知识包导出，并在后续修改和版本迭代中保持完整。
- 旧数据库通过可重入 SQLite 列迁移原地升级，不清理历史项目、轮次或建议。
