# 旧版人工覆盖迁移与链路收敛

## Context

历史人工编辑保存在项目级 `package_overrides` 中，并在文件查看、导出、评测、consumer 同步和图导入时跨版本叠加。前三阶段已经建立版本草稿、发布事务、统一门禁和刷新恢复，但旧数据仍需安全迁移，运行时也仍存在两个事实来源。

## Decision

- 服务注册路由前扫描旧 `package_overrides`，迁移以项目为单位并保证重复执行无副作用。
- 每条旧覆盖先完整写入 `package_override_migration_archive`，记录原始内容、基线版本、迁移草稿、处置结果和目标正式版本。
- 仍存在且相对最新正式版本发生变化的文件批量进入一个系统迁移草稿；同一批迁移只递增一次 revision。
- 仅包含对象、操作、规则或指标详情文件且通过解析与确定性校验时，迁移草稿自动发布为一个正式新版本。
- 派生文件覆盖、解析失败或校验失败时保留活动草稿并触发既有消费门禁。派生文件只允许审阅和撤销，不能发布。
- 已失效路径、与正式版本一致的覆盖以及无知识包版本的孤立数据仅归档，不继续影响运行时内容。
- 旧 `PUT/DELETE /package/file` 返回 `410 PACKAGE_FILE_OVERRIDE_REMOVED`，防止旧客户端产生“成功但未生效”的假象。
- 文件查看、体检、导出、评测、consumer 同步和图导入全部只读取正式版本渲染结果；`package_overrides` 仅保留为空的升级迁移源，不再作为运行时状态。

## Alternatives considered

- 直接删除旧 override：无法证明人工内容已经安全进入正式版本，存在不可恢复的数据丢失风险。
- 所有旧覆盖都自动发布：派生文件无法回写权威规格，解析或映射错误也可能生成无效版本。
- 继续保留只读叠加兼容：仍然维持两个事实来源，无法彻底解决修缮与消费内容不一致的问题。

## Consequences

- 可表达且有效的历史人工修改在升级后成为普通正式版本，后续修缮和消费读取同一份规格。
- 无法自动固化的内容不会静默丢失，而是以归档和活动草稿形式等待人工决策。
- 新旧客户端都不能再创建全局 override；所有新增人工编辑必须通过草稿发布流程。
- 迁移归档随项目删除级联清理，不参与任何知识包运行时读取。
