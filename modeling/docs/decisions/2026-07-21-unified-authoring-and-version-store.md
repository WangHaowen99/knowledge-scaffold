# 统一建模任务与版本存储

## 背景

建模服务已经使用 Pi 完成资料分析、访谈、知识包生成、评测和优化。同时，计划吸收 Claude Code 路径中的任务恢复、修改前确认、内容检索、影响分析、文件差异和历史恢复能力。

如果继续保留两套运行路径，同一个项目会出现两套状态、两种提问方式和两份修改记录。原有 `package_versions` 与 `package_overrides` 也只能表达知识包版本和当前覆盖稿，无法准确回答某次人工修改改了哪些文件，也无法可靠恢复。

Web 服务部署环境不保证安装 Git CLI。要求用户或容器额外安装 Git，会增加部署差异并使功能在部分环境直接失败。

## 决定

- Pi 是唯一的建模运行路径，不新增第二套 Claude Code 执行流程。
- Claude Code 中有价值的能力以通用服务接入 Pi，包括持久化任务、七类待办、项目事件、内容检索、影响分析、修改计划、文件差异和版本恢复。
- 每个项目在 `DATA_DIR/artifacts/<project-id>` 下拥有独立版本库。
- 版本库由 `isomorphic-git` 直接读写，不调用本机 `git` 命令。
- 结构化规格放在 `model/package-spec.json`，覆盖检查放在 `model/coverage.json`，最终知识包文件放在 `package/`。
- SQLite 只保存查询索引和业务关联，不重复保存版本文件内容。知识包版本、评测轮次和检查结果记录所使用的修订号。
- 所有写入和恢复都携带页面读取时的当前修订号。内容已经变化时返回冲突，要求页面重新读取。
- 恢复旧内容会创建一个新修订，不删除或改写已有历史。
- 旧 `package_versions` 和 `package_overrides` 在项目首次访问时自动迁移，避免一次性停机转换。
- 前端统一从项目会话恢复任务和待办，通过可重放事件续接变化。用户只看到“协作”“版本”“修改”“恢复”等业务用语。
- 用户可见流程固定为 9 步。AI 辅助构建阶段直接读取唯一任务图，后续步骤直接读取场景、数据源、评测、诊断、候选和发布记录，不再从旧工作流节点二次投影。
- 新建项目和知识包导入分别显式初始化 `new` 与 `package_import` 任务图；历史 `legacy_projection` 只做一次来源标记迁移，项目查询本身保持纯读。
- Git 工件 revision 是知识包文件的事实源；人工草稿、候选、检查、评测、图导入和发布都绑定 revision，并通过 CAS 阻止旧快照覆盖当前内容。
- SQLite 项目租约保证多个服务进程之间同一项目只有一个写操作，长任务结束或失败后释放。

## 考虑过的方案

### 直接调用 Git CLI

优点是与运维人员熟悉的命令一致。缺点是依赖宿主机安装、版本和权限配置，容器与桌面环境行为不一致。它不适合作为 Web 请求的基础依赖。

### 只在 SQLite 保存完整快照

实现简单，但文件历史、差异、恢复和外部检查都需要自行实现。数据量增长后，重复内容较多，也很难直接检查项目目录。

### 同时保留 Claude Code 与 Pi 两套适配器

短期改动少，但任务状态、确认交互、工具能力和版本写入会长期分叉。用户无法判断同一操作应该进入哪条路径，维护成本也会持续增加。

## 影响

- 部署不再要求安装 Git CLI，但安装依赖时必须包含 `isomorphic-git`。
- `DATA_DIR` 需要持久化 SQLite 数据库和 `artifacts` 目录，备份时两者必须一起备份。
- 多实例共用同一 SQLite 和 artifacts 目录时，项目租约负责写操作互斥；仍需保证共享存储本身支持 SQLite 文件锁。
- 版本库目前只服务本地历史，不承担远程推送、拉取或代码托管同步。
- 旧的同步仓储函数暂时保留给兼容测试和迁移读取，生产读写逐步收口到统一存储。
