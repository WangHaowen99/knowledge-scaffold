# 人工编辑草稿前端交互

## Context

后端已经提供绑定正式知识包版本的人工编辑草稿、乐观锁、发布事务和统一消费门禁。前端旧流程仍把单文件修改写入跨版本 `package_overrides`，刷新后也不会主动恢复草稿，无法向用户清楚表达“保存草稿”和“发布正式版本”的边界。

## Decision

- 只有对象、操作、规则和指标的详情 Markdown 文件可进入编辑；索引、manifest、mapping 和脚本等派生文件只读。
- 用户首次点击“编辑”时创建草稿，文件修改自动保存并携带当前 revision；切换文件和发布前强制刷新当前未保存内容。
- 工作台进入项目时查询活动草稿。存在草稿则恢复到知识包完善，并优先打开最近修改的文件。
- 草稿状态条统一提供发布新版本和放弃草稿两个出口。发布可填写说明，多文件修改只产生一个正式版本。
- 活动草稿期间，修缮对话、体检和进入数据源配置在界面上禁用；其他后端门禁错误由 API 客户端统一派发事件，工作台展示返回知识包完善的提示。
- 浏览器只在自动保存尚未完成时提示离开；已保存的活动草稿可以安全刷新，并由服务端恢复。
- 兼容迁移前不再创建新的旧版 override。检测到历史 override 时禁止开始草稿编辑，但保留逐文件清除入口。

## Alternatives considered

- 每次文件保存立即发布：多文件修改会产生碎片版本，用户也无法在发布前整体审阅。
- 仅把草稿保存在页面状态或浏览器存储：刷新、崩溃和跨设备后无法可靠恢复，也不能与服务端 revision 协作。
- 活动草稿存在时自动发布再执行消费操作：可能发布用户尚未审阅或尚未完成自动保存的内容。

## Consequences

- 人工编辑、正式版本和知识消费的边界在界面上可见，刷新不会丢失已保存草稿。
- revision 冲突不会静默覆盖其他页面的修改，当前输入仍保留供用户检查后重试。
- 旧 override 仍需在第四阶段完成迁移和后端链路清理；本阶段只阻止新增并提供显式清理入口。
