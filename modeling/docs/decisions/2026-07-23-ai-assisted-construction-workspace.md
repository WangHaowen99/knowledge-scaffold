# 将建模收敛为工作区内的 AI 辅助构建

建模界面拟保留“准备”阶段，并把原来分散的专家访谈、流程图绘制与确认、知识包生成等用户可见步骤收敛为单一的“AI辅助构建”阶段。知识包工作区成为建模主界面，知识包建模助手通过可持久化、可调整、可回退的任务流程主动推进访谈、流程确认、知识提取、确定性脚本决策、校验与修复；场景推演、数据源绑定和评测继续归入验证阶段，失败诊断与优化继续归入改进阶段。

采用这个方向是为了让用户围绕正在形成的知识包和业务流程工作，而不是理解内部算法步骤；同时保留人工确认、版本历史和验证门禁，避免把自主建模退化成不可审计的一次性对话生成。

动态工作流采用“任务类型封闭、任务实例与依赖动态”的边界。系统维护可校验、可渲染、可恢复的任务类型目录；AI 可以按项目情况创建、重排、重复、跳过或替代任务实例，但不能发明系统无法解释的新执行语义。这样既保留自适应能力，也使进度、权限、校验、回退和历史迁移有稳定边界。

助手与用户通过结构化建模消息协作。一条消息可以组合状态、说明、问题、证据、产物、校验和动作等多个受控内容块；内容块由服务端验证和持久化，模型不能直接输出任意 UI 组件或执行代码。该模式避免把一次完整协作拆成大量孤立卡片，也使消息可恢复、可审计和可交互。

回退以人工确认点为最小单位。确认点绑定任务图版本、知识包修订和确认记录；回退时从目标确认点创建新的恢复修订，不删除原历史，并将受影响的后续任务、确认和校验结果标记为过时。普通说明消息和未确认草稿不单独形成回退点。

每个人工确认点都必须运行知识包校验，但校验规则按当前任务分层。节点校验检查单个产物，增量校验检查本次修改及引用，里程碑校验检查当前阶段应完成的内容，完整校验用于进入验证阶段前，发布校验用于正式交付。尚未进入当前范围的知识包内容不作为错误报告。

校验修复采用三级权限：可唯一确定的安全结构问题允许自动修复并创建独立修订；会改变知识语义的修改必须先展示方案并由用户确认；阈值、流程分支、计算口径、冲突裁决等业务决策必须由专家明确回答。自动修复达到重试上限后停止，并展示已尝试动作和下一步选择。

新项目初始化为最小草稿模板：知识包目录、必需元信息、空索引和空 mapping 结构完整且可通过草稿级结构校验，但不包含任何未经确认的对象、流程、规则、指标或脚本。Mermaid 源文件作为知识包资源保存在 diagrams 目录。已有知识包和导入项目直接以当前修订为基线，不能被模板覆盖。

AI辅助构建必须依次满足六个固定里程碑门禁：资料就绪、建模目标确认、业务流程确认、知识结构确认、确定性能力确认和建模完成确认。AI 可以在门禁之间动态插入、调整或重复任务，但不能删除、重排或绕过门禁。

每个核心业务流程保存为一个独立的 Mermaid 源文件，由 `diagrams/index.md` 统一索引。图中使用稳定节点 ID，operation 和其他依赖知识通过流程 key 与节点 ID 建立关联。跨流程总览可以派生生成，但不作为知识事实来源。

流程图默认通过中间区域的 Mermaid 渲染结果审阅。用户可以针对节点或连线提交结构化修改意见，由助手修改源文件、重新校验并突出本轮变化；高级用户可以直接编辑 Mermaid 源码并实时预览。首版不提供完整拖拽式图编辑器，避免引入布局持久化和双向转换复杂度。

知识生成采用流程驱动顺序：先把已确认业务流程的节点划分为 operation，再从 operation 的输入、输出、步骤、判断和异常中提取对象、关系、规则、指标与确定性计算。每个核心流程形成一个知识构建批次，共享知识优先复用，定义冲突通过人工交互裁决。

助手主动识别数值计算、聚合、日期换算、排序、分配、格式转换和其他需要稳定重复执行的逻辑，并提出 script 建议。用户选择生成后，先确认输入输出契约和测试，再生成受控脚本；脚本通过安全检查和沙箱测试后才能绑定 operation。业务经验判断、开放式语义分析和未确认口径不进入脚本。

助手保留自由文本输入，用于回答、补充、解释和流程控制，但关键业务决定必须通过结构化问题或确认动作提交。对建模相关追问正常回答并恢复当前任务；对无关闲聊简短引导回 workflow，不改变任务状态，也不锁死输入框。

进度由固定里程碑、当前里程碑内的动态任务和区间 ETA 共同表达。ETA 根据剩余任务、待确认问题和历史耗时估算，并在任务图变化时说明调整原因；等待人工确认期间暂停系统任务计时。连续进度事件合并展示，避免消息刷屏。

建模、验证、改进和交付共用统一建模工作台。界面由可收缩的顶层流程栏、知识包目录树、中间产物画布和知识包建模助手组成；各区域独立滚动，目录和助手宽度可调且有限制，中间画布保留最低宽度。知识包工作区不再作为独立页面，也不再保留“打开知识包工作区”入口。

进入 AI辅助构建时，系统自动创建或恢复项目的主动建模运行。资料分析、生成、校验和脚本测试等安全系统任务可在服务端继续执行，不依赖浏览器保持打开；遇到业务判断或固定里程碑门禁时必须暂停。一个项目同时只允许一个写入型建模运行，其他页面仍可只读浏览。

新项目直接使用新的工作流模型和最小草稿模板。历史项目首次进入时，根据旧节点、访谈、确认、知识包修订、校验和评测等明确证据幂等投影出新任务图；原记录永久保留且不被改写。已有知识包成为迁移基线，导入项目不伪造访谈和流程确认，缺少证据的里程碑保持待补充。

验证阶段中，场景推演与数据源绑定可以并行准备。数据源只在知识包需要真实业务数据时成为必选；所有适用前置条件满足后，验证汇合门禁解锁评测。评测是正式发布前的必选门禁，优化产生新修订后按影响范围使相关验证结果过时。

AI辅助构建进入验证阶段前，错误、未确认业务决策和未完成必选任务必须清零。非阻断警告只有在用户查看影响并明确接受后才能带入验证，接受记录绑定知识包修订并持续展示；发布阶段可以将特定警告升级为阻断项。

核心 operation、对象关系、规则、指标和 script 必须关联知识证据，包括材料位置、访谈回答、已确认流程节点或用户裁决。无法找到充分证据的模型推测只能保存为待确认假设，不能直接成为确认知识或通过知识结构门禁。证据绑定来源版本和知识包修订，使上游变化可以精确传播失效状态。

人工确认采用角色化权限。项目负责人、建模人员、领域专家、验证人员和只读成员拥有不同操作边界；每个交互声明所需角色，确认记录保存实际用户、角色、时间和修订。首版可以让项目负责人默认拥有全部角色，但数据模型和协议从一开始支持多角色。

AI 产生的文件修改先保存为候选修订，不立即改变当前确认知识包。候选修订可以完整渲染、执行分层校验并展示文件、结构化配置和 Mermaid 可视化差异；用户确认后才成为新的当前确认修订，拒绝后保留审计记录但不影响当前包，也不能作为后续任务的有效基线。

候选修改可以按原子变更组部分接受。变更组按业务意图和任务划分，并携带文件范围、依赖和校验结果；系统阻止会造成引用断裂的组合，并自动包含必要依赖。用户选择后重新形成候选修订并校验，通过后才能成为当前确认修订。

用户只看到一个知识包建模助手，后台由确定性建模编排器协调任务规划、材料分析、流程访谈、知识构建、脚本生成和独立校验等专业执行角色。只有编排器能推进任务状态、检查门禁和修改有效修订；规划结果必须使用封闭任务类型，校验角色不能复用构建角色的自我结论。

对象关系继续保存在对象定义中，不新增 `relations/` 目录或独立关系文件。具有业务语义的关系在源对象中记录目标、含义、条件、证据和引用；物理外键与数据连接细节保留在 mapping。对象关系图可以从对象定义派生展示，但不成为新的知识包事实来源。

评测出现失败、部分通过或运行错误后，系统自动启动只读失败诊断。诊断区分知识包、script、数据、数据源、用例、标准答案、Judge 和系统问题；只有知识包或 script 可修问题进入优化，其他问题回到对应配置、用例、判分或重试路径。诊断本身不能修改知识包。

知识包可修诊断完成后，系统自动生成结构化优化建议，包含根因证据、修改目标、影响文件、预期修复用例、已通过用例风险和验证计划。建议不能自动应用；用户选择后才按原子变更组生成候选修订，并按影响范围执行增量校验、场景推演和定向重评。

内部修订、建模确认点和知识包版本分别管理。内部修订记录每次写入，确认点绑定用户批准的任务图与修订，知识包版本只用于评测、激活、导出和发布并指向一个已确认修订。恢复历史确认点会创建新修订，不覆盖已经发布的知识包版本。

新项目从 `0.1.0 draft` 开始，进入验证阶段时创建 `1.0.0-rc.n` 发布候选，验证和优化形成新确认修订时递增 RC。首次正式发布为 `1.0.0`；后续兼容修复、兼容新增和破坏性变化分别使用 patch、minor 和 major，并先经过对应 RC。助手可以建议版本类型，项目负责人最终确认。

正式发布不区分评测用例等级。当前知识包版本与修订关联的全部用例必须执行完成且全部通过，`partial`、`fail` 和 `error` 均阻断发布；不使用总通过率阈值或抽样通过替代全量门禁。

验证人员或项目负责人可以对 Judge 的 `partial` 或 `fail` 作有理由、可审计的人工改判，并计入全量通过；原始结论、理由、改判人、角色、时间、版本和修订永久保留。运行错误不能改判，标准答案错误必须修改用例后重跑，知识包修订变化会使旧改判失效。

建模资料采用不可变资料修订。新增、替换或删除资料后，系统根据语义差异和知识证据执行影响分析，只使受影响的任务、确认点、知识文件和验证结果过时；格式变化不传播语义失效，资料冲突由领域专家裁决，用户仍可以主动选择全部重新规划。

人工编辑与 AI 修改共用候选修订机制。用户编辑先保存为草稿，提交后创建人工候选修订并运行影响分析和分层校验，通过所需角色确认后才成为当前确认修订。安全修改可以一键校验并采用，业务语义修改仍需相应确认角色；编辑与确认作为两个独立审计动作保存。

用户可以新增、重排、暂缓、跳过、恢复、拆分、合并或重做动态任务，但不能删除或重排固定里程碑门禁。AI 可以自动插入不改变业务范围的只读任务；会改变范围、时长或下游有效性的调整必须先展示影响并确认。所有任务图调整保存前后差异、操作者和原因。

最终知识包只包含 Consumer 运行所需的 manifest、索引、流程图、对象、operation、规则、指标、脚本、mapping 和必要的简要证据引用。原始资料、完整访谈、任务图、候选历史、确认审计、校验、评测、诊断和执行记录保留在建模工作区；需要归档时通过更高权限单独导出建模审计包。

正式发布时重新评估验证阶段的警告。发布阻断警告必须清零；非阻断警告只有经项目负责人再次确认后才能成为发布已知限制，并随发布摘要保存。全部评测用例仍必须执行完成且全部通过，当前修订不能存在候选修改或待确认任务。

资料分析和用户回答形成可版本化的建模目标说明，包含核心问题、目标用户、触发场景、期望输出、业务动作、范围、非目标、成功标准、约束、证据和待确认假设。用户确认后通过建模目标门禁；完整内容保存在工作区，摘要同步到知识包根索引，后续流程、知识和评测均引用该说明。

场景推演由 AI 根据已确认目标、流程、分支、异常、规则和 script 构造推演案例，用于发现覆盖缺口，但不作为正式评测数据。正式评测只使用用户录入或导入的真实业务场景用例；AI 不能从待评知识包反向生成用例并以此证明知识包正确。

真实评测用例以真实问题和用户提供的自由文本参考答案为基本格式，关键点、数值容差、数据说明和 operation 关联均为可选。缺少参考答案的用例可以运行，但必须由用户人工判定后才计入全量通过；AI 只能协助整理，不能编造参考答案。

AI辅助构建只有在资料、建模目标、核心流程、流程图、operation、对象关系、规则、确定性能力、证据、业务冲突、必选任务、人工交互、候选修订和完整校验全部满足建模完成契约后才能结束。用户确认完成时创建建模完成确认点、锁定验证基线并创建 `1.0.0-rc.1`；后续返回修改会按影响范围使验证结果过时。

敏感数据分级策略暂不纳入本次方案范围，后续单独讨论，不阻塞首版实施。
