# 候选修订与受控知识包修复

## Context

智能修缮和确定性结构修复都可能一次修改多个相互依赖的知识资源。直接覆盖当前知识包会让专家在修改生效后才能审查，也无法区分系统可自动恢复的结构问题、需要批准的语义修改和必须由领域专家裁决的业务口径。

知识包文件由 Git 保存，修订索引、交互和审计记录由 SQLite 保存。两者不能参加同一个底层事务，但候选接受不能留下只有 Git 提交或只有数据库状态的半提交。

## Decision

- 候选修订以不可变变更组保存于 SQLite，绑定创建时的 Git 基线修订；预览和退回、拒绝都不移动当前 Git HEAD。
- 变更组显式声明依赖。专家选择某个变更组时自动包含其依赖，接受后所有选中内容只形成一个正式 Git 修订。
- 接受候选必须通过基线 CAS、候选校验和知识包结构解析。Git 提交、正式修订索引和候选状态使用提交意图与补偿回滚收敛。
- 受控修复按权限分为确定性自动修复、用户批准的语义修复和领域专家决策。自动修复限制同一根修订链的尝试次数，所有动作和输出修订都保留审计记录。
- 运行时只使用当前 `FlowchartOutput` 业务流程结构，不增加版本字段、双模型读取或旧结构兼容分支。

## Alternatives considered

- 让修缮直接写入当前知识包：实现简单，但专家无法在生效前比较差异，失败也难以恢复。
- 为每个变更组创建临时 Git 分支：可以隔离内容，但会把短期审批状态扩散到仓库引用和清理流程，增加恢复复杂度。
- 在运行时同时读取多代业务流程模型：能兼容历史数据，但会让每个修复和投影路径长期维护分支逻辑；历史数据应通过一次性迁移处理。

## Consequences

- 专家可以按内聚变更组预览、接受、退回或拒绝，当前知识包只在明确接受后变化。
- 基线变化会使旧候选明确失效，避免把旧补丁静默套到新内容上。
- Git 与 SQLite 之间仍需提交意图和失败补偿；进程恢复必须继续检查并回滚未建立索引的尾部提交。
- 自动修复仅处理可由当前规格唯一生成的结构，语义和业务决策会增加一次人工交互，但避免系统越权修改知识。
