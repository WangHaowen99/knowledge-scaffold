# Agent 领域增量修改与受管文件决策

## 状态

已实现，分阶段启用。

## 背景

原有 Agent 同时存在两类写入方式：

- `write_file` 让模型生成完整 Markdown、YAML、Mermaid 或 Python；
- `upsert_*` 让模型提交完整对象、规则或操作，再由 Core 渲染文件。

前者把格式、索引和跨文件一致性交给概率模型；后者虽然能确定性渲染，但修改一个字段也要重传
完整资源，容易覆盖未涉及内容。指标没有等价领域入口，删除也只理解文件路径，不理解引用。

Studio 已经具备候选事务、乐观并发、成功幂等、关系校验、删除预览和确定性渲染。重复建设一套
Agent 存储会产生两种候选语义，因此本次复用 Studio 事务内核，并把 Agent 参数适配成领域动作。

## 决策

### 1. 资源读取先于修改

Agent 使用统一读取工具取得：

- 当前 working revision；
- `kind:key` 资源 ID；
- 规范化资源快照；
- 单资源 SHA-256；
- 字段 key 或快照稳定子项 ID；
- 当前资源允许的动作。

Patch 同时匹配 working revision 和资源哈希。前者发现整包并发变化，后者防止同一资源被静默覆盖。

### 2. 模型提交受限领域动作

对象、规则、操作和指标分别提供 create/patch 工具。Patch 不接受 JSON Pointer 或数组下标，只接受
白名单动作，例如增加字段、更新条件、插入步骤、更新指标边界。未出现在动作中的值由服务端保留。

对象数据源绑定仍要求提交全部字段的一一映射和主键。这不是普通文本 Patch：只有完整映射才能证明
字段、真实列和主键闭合，因此使用独立工具并以资源哈希防并发覆盖。

### 3. 共享 Studio 事务内核

Agent 与 Studio 都通过 `StudioWriteService` 执行：

1. 校验 expected revision；
2. 应用 typed mutation；
3. 校验本地结构和跨资源引用；
4. 只阻止本次新增的完整性问题；
5. 分别编译修改前后的结构化规格，只写入编译结果真正变化的路径；
6. 在一个 SQLite 事务中写入候选及成功回执。

候选中的隐藏 PackageSpec 与详情、索引和映射同事务更新。结构化读取优先使用隐藏规格；历史包没有
隐藏规格时才从文件反解析。隐藏规格不参与 working revision 的公开内容哈希，避免内部投影改变导致
Studio、Review 和 Agent 对同一候选计算出不同 revision。

不能用“新编译的全包”直接和存量文件比较。历史包可能来自旧版渲染器，即使语义没变，排版或缺省值也可能不同；
这种比较会把无关对象、脚本和清单误纳入候选。改造后先用同一编译器生成“修改前投影”和“修改后投影”，两者的差集才是本次可写路径。
已在候选中但与本次领域动作无关的文件按字节保留。

### 4. 成功和失败都可重放

- 成功 mutation 由 Studio 回执按业务 mutation ID 和规范化请求哈希重放；
- 同一 ID 携带不同请求时返回 `MUTATION_ID_REUSED`；
- 确定性失败按请求、working revision 和资料依赖修订保存负回执；
- 状态未变化时直接返回原失败，状态变化后允许重新执行；
- 修订冲突、资源哈希冲突和参数错误都标记为不可原样重试。

### 5. 删除必须先预览

领域删除分为 preview 和 apply。preview token 绑定 working revision、删除目标和当前入站引用；引用图
变化后 token 失效。apply 原子删除资源并清理显式引用，不允许按路径删除受管详情或索引。

### 6. 受管写入按 run 接管

全局立即禁止旧写法会中断历史 checkpoint，因此采用运行级接管：

- run 第一次调用 v2 领域工具后记录契约版本；
- 该 run 不能再直接写或删对象、规则、操作、指标的详情和索引；
- 未接管的历史 run 继续得到弃用警告，保留恢复窗口；
- 内部规格和对象数据映射始终禁止自由写入。

### 7. 脚本先契约后源码

脚本使用三段式流程：

1. 读取 operation 的脚本契约哈希；
2. 定义 CLI 参数、结构化输出、超时、边界和证据；
3. 提交源码并原子生成脚本说明、入口文件、索引和 operation 双向绑定。

源码在形成候选前检查 Python 语法、危险能力、`argparse`、JSON 输出字段以及演示/占位实现。候选确认
仍要求当前源码哈希对应的沙箱测试回执，契约检查不能替代真实用例。

### 8. 工具面按业务阶段过滤

生产 Leader 只在知识/增量阶段看到领域写工具，只在验证/增量阶段看到脚本工具，只在增量阶段看到
融合工具，只在验证、评测或发布阶段看到评测工具。没有阶段信息的历史调用保留完整工具面；显式用户意图
或服务端恢复事件声明的本轮必需工具会覆盖阶段过滤，避免旧状态把恢复动作和确定性执行锁死。

## 改造前后

| 场景 | 改造前 | 改造后 |
| --- | --- | --- |
| 对象增加字段 | 重传完整对象或重写 Markdown | `add_field`，其他字段保持不变 |
| 规则增加例外 | 重传全部条件、引用和证据 | `add_exception` |
| 操作插入步骤 | 重传完整有序数组 | 使用快照稳定步骤 ID 插入 |
| 新建指标 | 手写详情和索引 | create metric 后确定性渲染 |
| 对象绑定表 | 模型维护对象和 mapping | 完整绑定校验后同时重建 |
| 删除指标 | 按路径删除，可能留下引用 | 预览引用后原子删除并清理 |
| 并发修改 | 后写覆盖先写 | revision 与资源哈希显式冲突 |
| 重复失败 | 再次执行相同校验 | 相同状态命中负回执 |
| 生成脚本 | 先写源码，后发现契约不符 | 先定契约，再校验源码和测试 |
| 修改受管文件 | 模型维护语法和索引 | Core 维护唯一派生投影 |
| 修改存量旧包中的一条资源 | 全包重渲染可能带入无关格式漂移 | 只写修改前后编译结果的差集 |

## 好处

- 未涉及字段不会因完整替换而丢失；
- 详情、索引、映射和隐藏规格来自同一事务状态；
- 引用错误在候选提交前被确定性拒绝；
- Patch 比完整文件短，降低模型输出超时和上下文增长；
- 重试有稳定语义，服务重启或响应丢失后可以按回执判断结果；
- 确认卡继续使用现有候选和版本机制，不让 Agent 直接改正式 revision；
- Agent 与 Studio 修复同一套变更逻辑即可同时受益。
- 存量包的旧格式不会因一次局部 Patch 被顺带重写，无关候选也不会被撤销。

## 代价与限制

- 后端 schema 和动作编译器更复杂，新增领域字段必须同步扩展；
- Patch 前多一次结构化读取；并发冲突会比静默覆盖更显眼；
- 字符串列表的稳定 ID 在当前版本是快照 ID，文本被修改后需要重新读取；
- 对象表绑定为保证闭合，仍需提交完整映射，不是单列 Patch；
- 脚本流程多一个契约步骤，换来可执行边界和测试可追溯性；
- 旧 run 与新 run 在兼容期行为不同，需要保留契约版本观测。
- 每次变更需要在内存中各编译一次修改前和修改后规格；换取更小、更可解释的写入集。

## 明确边界

流程图当前由独立的人工草稿、修订和确认子系统管理。Agent 直接把流程 Patch 写进知识候选会形成
第二套流程版本语义，因此本次不旁路该子系统；原 Mermaid 写入继续使用现有路径和确定性校验。后续
应先抽取共享 Flowchart mutation service，再让 Agent 和人工画布共同调用。

跨资源 batch、领域 rename、结构化建模目标和受限 manifest Patch 也保留为后续里程碑。本次不使用
不完整的通用 JSON Patch 代替它们。

## 回滚

- 停止向生产 Agent 暴露 v2 工具即可回到兼容入口；
- run 级接管记录和回执都是附加数据，不修改正式 revision；
- 未确认候选可以整体放弃；
- 数据库新增表可由旧代码忽略，不需要破坏性逆迁移；
- 内部规格和对象映射的自由写禁令不随回滚解除。

## 验证

自动化测试只使用合成资源，覆盖：四类资源创建、对象/规则/操作/指标 Patch、字段完整保留、资源哈希
冲突、成功重放、负回执、完整表绑定、删除预览与清理、受管写门禁、存量格式漂移隔离、无关候选保留、脚本占位拒绝、脚本原子投影及
未测试脚本不能确认。部署验证必须在隔离副本或合成项目上执行，不修改参考项目。
