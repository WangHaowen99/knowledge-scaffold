# ADR: 知识包修复使用候选质量门禁和可见待办队列

状态：已实现，待发布验证

## 背景

历史修复记录把“代码执行结束”与“错误确实消失”合并为 `completed`。因此候选仍有
原错误、引入新错误或修订已经变化时，界面仍可能显示“已完成”。多个待办又只展示
一项，用户无法判断后续还有什么。

## 决策

1. 修复尝试分别记录 `executionStatus` 和 `qualityOutcome`。
2. finding 使用稳定 fingerprint 比较修复前后，不使用临时 id 或展示文案。
3. 自动修复与专家确认方案都先形成隔离候选；只有目标 fingerprint 消失、没有新增
   阻断错误、且实际修改路径不超出计划范围时，候选才提升为当前修订。
4. 候选复检结果只计算一次。提升后直接将同一份结果绑定到正式修订，避免第二次语义
   模型调用产生不一致结论。
5. 项目会话和知识包检查接口统一返回当前修复步骤、质量审计、完整待办队列和下一步。
6. 助手头部展示全部当前待办。依赖项保持可见但锁定，独立项可以查看；所有写操作仍
   由项目租约串行化。
7. `stale` 显示为“已失效”，错误的“忽略”统一改为“暂缓并记录理由”。
8. 历史状态迁移默认 dry-run；没有 before/after 事实的记录保持 `unknown_legacy`，不得
   根据旧 `completed` 字段猜测修复成功。

## 质量门禁

```text
目标 fingerprint 全部消失
AND 新增 blocking fingerprint = 0
AND changedPaths 是 allowedPaths 的子集
AND 候选格式、引用、来源映射、脚本安全和规则检查均完成
AND 候选基线仍是当前修订
```

不通过时拒绝候选，当前知识包保持不变，并返回调整方案、人工修改和查看复检差异的
结构化动作。

## 兼容与迁移

- 旧 `status` 保留，供现有查询兼容；新逻辑只以执行状态和质量结论判断成功。
- 旧 finding 没有结构化 `disposition` 时才使用文本规则分类。
- `npm run repair:history` 输出 dry-run JSON；显式增加 `-- --apply` 才回填历史审计并
  对账旧待办。脚本不调用模型、不自动修改知识包。

## 验证重点

- 目标未解决或新增阻断错误时，候选不得提升。
- 候选修改计划外文件时，候选不得提升。
- 修订变化或 finding 消失后，旧题卡不可继续提交。
- 多个待办的真实数量、顺序和依赖必须可见。
- 前端只有 `resolved/improved` 才显示“本项已解决”。
