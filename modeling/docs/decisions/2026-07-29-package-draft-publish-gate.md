# 人工编辑草稿发布事务与统一门禁

## Context

人工编辑草稿已经绑定正式知识包基线并支持多文件保存，但在发布前不能参与知识消费。若修缮、重新生成、导出、评测或数据同步继续读取正式版本，就会让用户看到草稿与实际消费内容不一致；若逐文件创建版本，又会产生碎片版本。

## Decision

- 仅允许 `objects/`、`operations/`、`rules/`、`metrics/` 下已有详情文件回写正式规格；索引、manifest 和数据 mapping 等派生文件不能发布。
- 发布使用一个 `BEGIN IMMEDIATE` 事务完成 revision 校验、最新基线校验、Markdown 解析、完整包渲染与校验、正式版本写入和草稿关闭。
- 解析器只接受渲染器定义的固定格式。不可回写字段、未知章节或 frontmatter 与正文冲突均明确报错，不静默忽略编辑。
- 对象文件未表达的 `sourceTable`、`primaryKey` 和已有字段 `sourceColumn` 从基线规格保留；发布后重新派生索引、manifest 和 mapping。
- 活动草稿存在时，服务端统一阻止包修缮、旧版文件覆盖、重新生成、体检、导出、数据源同步、图导入、评测和优化操作，返回 `PACKAGE_DRAFT_REQUIRES_PUBLISH`。
- 发布和放弃是解除门禁的两条路径；发布还要求显式确认和匹配当前 revision。
- 旧版全局 `package_overrides` 与版本草稿不能混用。兼容迁移完成前，存在旧 override 时拒绝创建或发布草稿，避免新版本继续被全局覆盖遮挡。

## Alternatives considered

- 发布时直接保存 Markdown 文件：正式版本仍缺少权威结构化规格，修缮与消费会继续分叉。
- 仅由前端阻止消费：API 调用、刷新恢复或其他客户端仍可绕过。
- 发布时自动删除旧 override：可能不可逆地丢失尚未迁移的用户修改，留给兼容迁移阶段处理更安全。
- LLM 语义检查已从知识包检查链路移除；发布和手动检查都只执行确定性解析、映射、格式和规则错误检查。

## Consequences

- 多文件人工编辑只产生一个正式版本，成功后所有后端链路重新以同一版本规格为事实来源。
- 任一解析或校验失败均回滚，版本数不增加，草稿保持 active，用户可继续修正。
- 第三阶段前端可以依据统一 409 错误展示发布或放弃提示，并使用发布接口完成交互。
- 第四阶段仍需迁移旧 override 并清理旧编辑链路；本阶段用冲突门禁保证迁移前不产生新的跨版本遮挡。
