# 建模助手自主推进空转的根因分析与修复方案

## 状态

本文针对建模助手在自主推进阶段长时间空转、反复向专家重复提问、却不产出交付物的问题，
记录根因分析、已实施的修复与后续计划。

对应现象：专家确认脚本契约后，助手连续数小时反复读取资料、反复向专家询问同一件事，
最终运行状态标记为完成，但核心产物一行未写；页面上还出现过待办卡片消失、既无下一张卡也无报错。

本文只讨论助手在自主推进时「这一轮该做什么、做到什么程度算完」的机制，以及与之直接相关的
上下文保留策略，不讨论模型本身的生成质量，也不放宽知识包修订的并发保护。

相关背景：

- [Agent 受控修改、计划生成与浏览器验收方案](agent-controlled-change-set-problems-and-browser-e2e.md)
- [建模服务重启后的 Run / 计划恢复一致性修复方案](agent-run-recovery-consistency-plan.md)

## 1. 问题概述

### 1.1 现象

单用户、单项目、确定性验证阶段，专家全程配合回答：

1. 专家输入「继续」后，助手连续运行四小时余，调用工具一千余次；
2. 其中约 98% 是读取类调用，提交脚本源码的工具一次未调用；
3. 助手就「业务数据以什么形式交给脚本」这一件事，先后向专家提问五次，
   专家五次都给出了明确答案，最后两次甚至是同一个选项值；
4. 运行最终标记为完成，项目摘要却写着核心脚本「待实现」，与四小时前的状态相同；
5. 另有一次同类运行中，专家确认脚本契约后待办卡片消失，既没有下一张卡，也没有任何报错。

### 1.2 影响

- 专家被反复打断，同一问题回答多次后仍无进展，信任受损；
- 单次运行消耗大量模型调用与 token，却零交付；
- 运行状态显示「完成」，与实际产出不符，掩盖了失败，后续排查困难。

## 2. 根因分析

按对行为的影响排序，共七条。前两条是行为的直接驱动，第三条是放大器。

### 2.1 停滞反馈失效，而且把空转误报成了进展

自主续跑提示词中，「你连续 N 轮只做读取、没有写入任何候选」这句警告被包在
「受控建模计划仍有待办」的条件里。而受控计划只存在于知识建模阶段——代码注释已写明
确定性验证阶段没有计划。因此在验证阶段，这句警告从未发出。

助手每轮实际收到的是固定开头：「服务端检测到项目已经取得实质进展，立即继续执行下一步」。

**服务端内部判定它在空转（停滞计数在累加），发出去的却是肯定。** 这是七条里唯一主动推着它
继续的一条。

### 2.2 读取零风险，写入高风险，且写失败后被要求重读

同一次运行中，读取类调用失败率为 0%，写入类失败率约 13%。全部写入失败都是乐观并发的
版本冲突，补救提示统一是「请重新读取」。

由此形成闭环：想写 → 版本冲突 → 被要求重读 → 读的过程中版本可能再变 → 再写再失败。
写入的挫折被系统直接转化成读取动作。

这个循环是自我强化的：写失败越多越谨慎，越谨慎越取证，越取证上下文压力越大，越不确定越不敢写。

### 2.3 每一轮没有目标，终止条件永不满足

自主续跑发给模型的指令是「立即继续执行能自行完成的下一步」，终止条件写的是
「直到调用 ask、request_confirmation，或确实没有可执行动作」。

这句话有三个问题：内容是空的（下一步是什么由模型自己猜）；没有完成判据；
而**「再读一份资料」永远算得上可执行动作**，所以这一轮在逻辑上不会自然结束，
只能撞到框架的单轮迭代上限才停。实测单轮持续三十余分钟、上百次工具调用。

与此同时，任务清单其实是现成的：门禁 blockers 就是服务端算出来的待办，
在同一次运行中明确列出了还差哪几个脚本、每个的标识是什么。但它只作为
`get_project_state` 返回值里的一个字段，和文件正文一样是普通工具消息，
很快被后续读取挤出上下文窗口——整整四小时里，助手只查过一次门禁。

### 2.4 上下文按到达顺序淘汰，专家的回答没有任何特权

专家的回答以 `ask` 工具返回值的形式进入上下文，格式与一次文件读取的返回值完全相同，
也享受完全相同的（没有）保留待遇。

上下文截断是两级尾部切片：先保留最近若干对话轮，再按消息条数卡上限，先进先出。
不区分内容价值。

实测从专家首次回答到第五次重复提问之间，间隔了两百余次工具调用、约五百条消息，
而消息窗口只有数十条。**专家的答案早已被助手自己产生的读取洪流冲掉**，它问第五遍时
主观上确实是第一次问。

这里还有一个反向激励：**读得越多，忘得越快；忘得越快越不确定，就读得更多。**

### 2.5 长期记忆通道本身不可靠

跨窗口的记忆只有项目状态摘要一处，由模型主动调用工具更新。同一次运行中它尝试更新五次、
失败两次（全部是版本冲突），四小时只成功写入三次，而同期有上千次工具调用。

更根本的是：**失忆的模型无法准确总结自己失忆的部分**——它只能总结窗口里还看得见的东西，
而窗口里恰恰没有被冲掉的那些。让它自我总结，等于让它报告自己不知道的事。

此外，当前工具集中没有任何一个可以查询「专家之前说过什么」或「本轮已经读过什么」。
事实全部完整落在数据库里，模型却没有手段去看。

### 2.6 打转检测的判据、窗口与时机三重失效

- **判据**：要求「最后一个调用往前数有若干个完全相同的」。实测打转形态是交错重复
  （A、B、A、C、A……），最长连续只有 2 次，永远够不到阈值；
- **窗口**：打转痕迹只保留最近十余条，看不到「最近一百次里只有二十个不同参数」这类全局模式；
- **时机**：只在每一轮结束时检查，而单轮内部允许上百次迭代，这期间完全无人监督。

结果是整次运行中打转告警触发 0 次，日志里一条都没有——而同期约六成的工具调用是重复的。

### 2.7 专家在输入框中的回答被降级为「插话」

只要界面上有待回答的卡片，专家从输入框发出的任何消息都被无条件判定为「插话」，
处理完之后把原卡片原样重新发出。

实测有一次，专家在输入框中打字回答，内容逐字就是助手推荐方案的原文，明显是「按你说的办」。
系统判定为插话，十余秒后同一张卡片再次弹出，专家只好再答一遍。

## 3. 修复方案

### 3.1 已实施

**（1）思维链输出预算余量**

思维链内容与正文、工具参数共用同一个 `max_tokens`，而按角色和阶段设定的预算只按正文估算。
推理占满预算时，正文和工具调用一个 token 都产生不了。

新增 `Settings.resolved_output_budget()`，在思维链开启时为阶段预算追加余量，
并始终受部署级上限约束；思维链关闭时行为完全不变。空正文恢复所用的紧凑摘要不走统一构造路径，
已一并按同一份配置换算。

**（2）零产出轮次的识别与专门重试**

判据是「推理 token 占满全部输出 token 且正文为零」。两个条件缺一不可：
只看「预算用满」会误判——实测有多次调用把预算用尽却仍正常产生了工具调用；
只看字符数更不行——零产出轮与正常轮的推理字符数互有高低，分界线在 token 上。

识别后放在守卫链最前面处理：用一段要求小步推进、先取证再下结论的提示词重试，
最多两次；仍然零产出则落一张可操作的复核卡，保留已有成果并把下一步交还专家，
而不是静默结算为完成。

**（3）产物判定修正**

专家批准契约后，重新定义一遍契约不算交付物——该动作产出的正是被批准的对象本身。
原先它留在期望产物集合里，使得「确认完又原地重定义一次契约」通过了检查，
这正是待办卡片消失、运行被判成功完成的直接成因。

**（4）脚本候选缺输入拦在知识阶段**

脚本契约的参数只能来自业务操作已声明的输入。确定性验证阶段只保留领域只读工具，
到那时发现操作缺输入既查不到也补不了，模型只能在契约里自行编造数据来源。

改为在知识阶段的门禁就拦下：被识别为脚本候选的业务操作必须已声明输入，否则列为阻断项。
判定逻辑提取为纯函数并附单元测试。

**（5）自主续跑时由服务端指派单轮目标**

从当前阶段「向前推进」那道门禁的未完成项中取第一条，作为本轮的指派目标，
连同边界（只推进这一项）与卡住时的出口（前提不具备就调用 `ask`，不要反复读资料自行补齐）
一并写入 system 段。

放 system 段是因为上下文截断时 system 消息优先占配额，普通消息会被工具返回值挤掉——
目标一旦被挤掉，模型就会自己另找事做。

专家刚下达指令或刚回答完问题的那一轮不指派：那时专家的话本身就是目标，
再指派反而会覆盖专家的意图。

**（6）门禁待办区分主语**

原有 blockers 面向用户，说的是「还差什么」，其中不少条目的主语是用户而非助手。
直接拿来当助手的目标会出两类问题：一是让助手去做它做不了的事（例如由项目负责人完成发布）；
二是诱导它替专家做决定（例如「确认当前计算范围」），而系统别处明令禁止这件事。

在门禁结果中新增 `agentActionable` 字段，逐条标注助手可独立推进的事项，措辞按助手的动作写：

- 目标确认：用户看到「确认当前建模目标」，助手拿到「起草或修订建模目标，完成后发起确认卡」；
- 发布：显式给空数组，表示助手没有可推进的事；
- 计算范围待专家拍板时：给空数组，避免助手替专家确认；
- 评测未通过：原文一句话包含三个条件，拆为一个入口动作。

单轮目标改为优先取 `agentActionable`，并区分两种情况：字段不存在时退回 blockers 保持兼容；
字段存在但为空表示「这道门禁当前没有助手能独立推进的事」，此时不指派，
**不能退回 blockers**，否则又把用户的事派给了助手。

### 3.2 已实现但默认关闭，待真实环境验证

框架本身提供了完整的上下文处理能力（按阈值卸载超长消息并留摘要与句柄、分级压缩、
按内容类型的规则压缩、归档检索与重注入），当前一项都没有启用，只剩最基础的窗口滚动截断。

新增三个配置开关，默认全部关闭：

- 是否启用上下文处理器预设链，开启时同步允许卸载内容回灌
  （否则模型会看到句柄却取不回原文，比直接截断更糟）；
- 显式声明模型上下文窗口——压缩器按「占用达到窗口的百分之多少」触发，不声明则永不触发；
- 免卸载工具名单，默认保护 `ask` 与 `request_confirmation`。

最后一项替换了框架默认值。框架默认保护文件读取类工具，但实测这类调用读的全是知识包内部制品，
随时可以重新读回，且其中约九成是重复读取——保护它等于让重复内容常驻。
判据应当是「丢了能不能重新拿到」：专家的回答只有一份，丢了只能再问一次。

## 4. 验证

- 前述已实施项均有单元测试与端到端测试，在真实依赖下执行；
- 其中零产出识别与产物判定两项做过修复前后对照：同一个回归测试在未修复代码上失败、在修复后通过；
- Core 与 Agent 两侧全量测试无新增失败。

尚未完成的验证：

- 全部改动都还没有在真实环境运行过；
- 上下文预设链在构造负载下可将单次输入规模显著压低，但真实环境的延迟与调用增量未测；
- 预设链开启后，测试环境出现过两次单轮跑不完的现象，原因未定位，可能是测试替身的假象，
  也可能是真实的性能问题，需在真实环境重点观察；
- 卸载内容目前存放在内存中，进程重启后句柄失效；正常运行不受影响，
  但服务重启后恢复被中断的运行时，模型会看到句柄却取不回原文。

## 5. 后续计划

按优先级：

1. **部署已实施项并在真实场景回归**：重点观察单轮时长、单轮工具调用数、
   产出类调用占比、同一问题的重复提问次数；
2. **目标达成检测**：当前「完成后即可结束本轮」仍是提示词，靠模型自觉，
   系统不检测目标是否达成，也不会主动收束轮次。若真实验证发现「有目标但仍跑很久」，
   这一项应当优先于其他改动；
3. **写入版本冲突的自动重试**：版本冲突是可自动化处理的，不该甩给模型，
   更不该用「请重新读取」把写入挫折转化为读取动作；
4. **专家决策的检索接口**：从交互记录与工具回执派生，纯读、纯派生，不需要模型总结；
5. **插话判定**：优先用界面区分（卡片自带输入框与全局输入框分离），
   而不是引入额外的模型判断；
6. **打转检测改造**：判据换为窗口内去重率，窗口扩大到覆盖单轮规模，
   检测下沉到工具调用回调；
7. **上下文策略放开**：视第 1 项的结果决定是否需要，以及需要到什么程度。

## 6. 一句话总结

这次故障中助手的每一个局部决策都是合理的——「我不确定，再查一下」「这个细节没确认，再问一下」，
单独看都对。问题在于它的记忆被系统结构性地冲刷掉，而系统既没有告诉它这一轮该做什么，
也在它空转时反过来肯定了它。于是一串局部合理的决定，连起来成了四小时空转。

修复的重心不是让模型更聪明，而是**让每一轮有明确且可判定的目标，让专家说过的话在上下文里
有不可驱逐的地位，并在它准备重复劳动时用机制拦住它**——而不是指望它自己记得。
