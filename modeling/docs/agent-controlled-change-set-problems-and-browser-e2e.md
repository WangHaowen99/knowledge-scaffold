# Agent 受控修改、计划生成、前端易用性与 OpenJiuwen 落地及浏览器黑盒验收方案

## 状态

问题清单、方案和第一阶段改造已经实现，并已部署到 cs 验收环境。浏览器黑盒本地全量回归已通过，
cs 严格重复回归也已以 61/61 个用例、83 次浏览器旅程全部通过；实施内容和验证证据见第 10 节。

## 1. 目的与范围

本文为 Agent 受控修改、计划生成与前端交互改造建立统一的问题清单和端到端验收基线，覆盖三类业务场景：

- 专家在建模助手对话框中明确要求修改已有资源；
- Agent 根据目标和资料执行正常的全量或增量生成流程；
- 用户在桌面网页、窄屏网页和手机浏览器中查看进度、审阅变更、处理失败、停止任务和恢复工作。

本次改造要保证：即使模型理解错误、工具调用失败、模型或子任务超时，也不能产生越界修改、半成品、
重复写入、提前确认或无法停止的运行。

本文的所有验收用例都是浏览器黑盒用例。测试人员只能像普通用户一样通过可见页面操作和判断结果，
不能通过接口、脚本、数据库、日志或容器内部状态完成准备、执行或验收。

前端验收优先保障桌面网页端。常用桌面视口中的登录、建模、Diff、确认、评测和停止流程属于第一优先级；
窄屏网页和手机端不能阻断同一条核心业务闭环，但不得以牺牲桌面网页的信息完整性为代价。

相关设计背景见 [Agent 领域增量修改与受管文件决策](decisions/2026-08-30-agent-domain-mutation-v2.md)。

## 3. 浏览器唯一操作规则

### 3.1 允许的操作

测试人员只允许执行以下动作：

1. 在真实浏览器中打开可见页面；
2. 用鼠标点击当前页面或浏览器自身的可见控件；
3. 在获得焦点的可见输入框中键入文本，并使用 Enter、Tab、Escape 等普通键盘动作；
4. 点击页面的上传按钮后，在可见的系统文件选择器中用鼠标和文本输入选择合成文件；
5. 点击浏览器刷新、前进、后退、新建标签页和关闭标签页；
6. 通过页面可见的 Studio、Diff、版本历史、计划、确认卡、评测页和审计页判断结果；
7. 对只包含合成数据的页面拍摄截图，作为测试报告证据。

如果使用浏览器自动化驱动，定位器只能用于找到可见元素和读取已渲染文本。所有会改变系统状态的动作必须
最终表现为真实鼠标点击或逐字符键盘输入。

### 3.2 明确禁止的操作

以下任一行为都会使该次用例无效：

- 使用 `curl`、Postman、HTTP 客户端、浏览器请求上下文或其他方式直接调用接口；
- 在地址栏拼接内部接口路径或直接打开内部接口响应；
- 在开发者工具 Console 执行 JavaScript、`fetch`、XHR、WebSocket 或 SSE 调用；
- 使用 `page.evaluate`、DOM 属性赋值、事件派发或隐藏表单提交改变页面状态；
- 直接注入 Cookie、Token、Local Storage、Session Storage 或 IndexedDB；
- 绕过文件选择器直接设置文件 input；
- 直接读取或修改数据库、运行时目录、候选文件、Checkpoint 或缓存；
- 通过 SSH、Docker、进程命令、服务日志或 Trace 准备数据、注入故障或判断结果；
- 使用后端脚本批量创建项目、账号、候选、测试用例或评测数据；
- 通过隐藏内部 ID、工具回执或数据库行证明用例通过，而页面上没有对应证据。

### 3.3 阻断原则

如果某个前置条件、故障场景或验收结果无法通过可见页面完成，该用例必须标记为 `BLOCKED`。不能为了让
测试继续而改用接口、SQL、日志或脚本。`BLOCKED` 不是通过，说明产品或测试环境仍缺少浏览器可测试性。

## 4. 合成场景和测试环境要求

### 4.1 数据安全要求

- 所有账号、项目、知识包、资料、表格、用例和脚本必须是人工构造的合成内容；
- 合成数据不得复制或改写任何真实客户、个人、生产环境或内部系统数据；
- 名称统一使用“浏览器验收”“合成会员”“合成订单”“测试操作”等通用表达；
- 截图和报告不得出现真实地址、凭据、内部服务信息或真实项目标识；
- 测试文件不默认提交到仓库。确需提交时必须另行完成安全检查和审批。

### 4.2 合成基线场景

测试环境需要通过正常页面导入下列预审合成包，或在仅测试环境可见的“验收场景”页面中点击创建。测试人员
不能直接调用场景创建接口。

| 场景 | 合成内容 |
| --- | --- |
| SCN-CLOSED | 会员档案对象、折扣资格规则、订单复核操作、复核通过率指标，各包含可定位的字段、例外、步骤和边界 |
| SCN-AMBIGUOUS | 两个不同 key、相同可见标题的指标，以及两个同名操作步骤 |
| SCN-REFERENCES | 一个被规则和操作引用的对象，以及一个没有引用的指标 |
| SCN-BINDING | 一个包含三个字段的对象，以及列名一一对应、主键明确的合成表格 |
| SCN-GENERATION | 三份互不冲突的合成文本资料，明确描述对象、流程、规则和指标 |
| SCN-LONG | 多份较长的合成资料，包含重复章节和三项独立校验问题 |
| SCN-SCRIPT | 一个尚未绑定脚本的“合成汇总”操作及明确的输入输出样例 |
| SCN-EVALUATION | 已确认知识包、至少三条从页面录入的合成评测用例，以及页面上选择的“无数据源”配置 |
| SCN-UI-BATCH | 五个合成资源、八组可独立审阅的候选变化、长短混合标题和至少一个需要人工确认的高风险组 |
| SCN-UI-RESUME | 至少二十条合成对话记录、一项进行中任务、一项待用户决定和可见的历史版本 |

### 4.3 浏览器可见故障场景面板

模型超时、提交后响应丢失、固定校验指纹等故障无法通过普通业务页面稳定制造。测试环境必须提供一个仅在
非生产验收环境启用的可见页面，测试人员通过下拉框和按钮选择下一次故障。面板只能提供固定合成场景，不能
输入任意请求、代码、数据库语句或内部地址。

面板至少需要提供：

| 故障编号 | 浏览器可选择的固定行为 |
| --- | --- |
| F01 | 下一次模型调用在首个可见输出前超时 |
| F02 | 下一次模型调用在已经输出部分内容后空闲超时 |
| F03 | 下一次 Core 写入在事务提交前返回暂时失败 |
| F04 | 下一次 Change Set 已提交，但响应在返回 Agent 前丢失 |
| F05 | 下一次只读子任务超时，不产生写入 |
| F06 | 下一次模型方案额外加入一项未授权修改 |
| F07 | 下一次多动作 Change Set 在最后一项应用前失败 |
| F08 | 下一次模型只准备任务清单中的前两项并尝试确认 |
| F09 | 下一次校验连续返回相同 finding fingerprint |
| F10 | 下一次候选预检一次返回三项独立 finding |
| F11 | 下一次候选在确认卡生成后变为过期状态 |
| F12 | 下一轮脚本沙箱测试返回失败 |
| F13 | 下一轮评测持续运行，直到用户点击停止 |
| F14 | 下一轮评测全部返回运行环境错误 |
| F15 | 下一轮正常生成停在最后一项计划任务之前，允许从页面验证阶段门禁 |
| F16 | 下一轮正常生成在每个业务批次之间保持可见等待，直到用户继续或停止 |
| F17 | 下一次从建模助手发送的消息在创建运行前返回可重试失败 |
| F18 | 下一次页面内容读取失败，但项目其他区域仍可正常浏览 |

面板必须可见地显示“故障尚未消费、已消费次数、已关闭”，但不得显示内部接口、数据库行或敏感配置。每个
故障默认只消费一次，避免后续步骤继续受影响。

### 4.4 网页显示验收环境

前端显示用例必须使用装有真实浏览器的固定测试终端。视口通过测试终端分辨率或鼠标拖动浏览器窗口获得，
不能通过开发者工具、启动参数、页面脚本或自动化代码伪造。浏览器缩放通过可见菜单设为 100%。

| 优先级 | 可见内容区域 | 用途 | 发布要求 |
| --- | --- | --- | --- |
| W0 | 1440×900 | 桌面网页主验收环境 | 所有前端和业务核心用例必须先通过 |
| W0 | 1366×768 | 常见低高度桌面网页 | 登录、建模、确认、评测和停止必须通过 |
| W1 | 1920×1080 | 宽屏回归 | 不能出现内容过度拉伸、关键信息相距过远 |
| W1 | 1024×768 | 窄屏网页 | 必须自动收起次要栏，核心审阅区保持可用 |
| W1 | 901×800 | 响应式边界回归 | 不能落入三栏都显示但中栏不可用的区间 |
| W2 | 390×844 | 手机浏览器回归 | 登录、查看状态、确认、停止和发送消息必须可完成 |

除用例另有说明外，现有 `E2E-BOOT`、`E2E-EDIT`、`E2E-GEN`、`E2E-VAL`、`E2E-REL`、
`E2E-SCRIPT`、`E2E-EVAL` 和 `E2E-AUDIT` 用例都先在 1440×900、缩放 100% 的桌面网页执行。
桌面网页显示门禁不通过时，不继续用更大屏幕掩盖问题。

## 5. 统一执行与取证要求

### 5.1 每个用例的通用前置步骤

1. 用浏览器页面注册或登录合成测试账号；
2. 点击“新建项目”，输入用例指定的通用项目名称；
3. 通过页面导入指定合成场景，或从可见验收场景页点击创建；
4. 打开 Studio 和版本历史，确认基线没有待确认候选；
5. 记录页面展示的基线版本标签和资源数量，不记录内部 ID；
6. 返回建模助手，开始执行用例步骤。

### 5.2 统一通过标准

- 所有“预期页面结果”必须同时满足，不能只以 Agent 回复“成功”为依据；
- 修改类用例必须在 Studio 和 Diff 中核对实际内容；
- “无额外修改”必须通过页面 Diff 的资源、字段和文件列表逐项确认；
- 确认前的当前已确认版本必须保持不变；
- 取消、失败和回滚后至少连续刷新两次，页面资源数量和候选内容都不得继续变化；
- 页面缺少必要证据时判定 `BLOCKED`，不能查后端补证；
- 自然语言编排核心用例至少在五个全新项目中连续通过五次；
- 故障恢复用例至少连续通过三次；
- 任意一次出现越界写入、重复写入、提前确认或停止后继续写入，该用例即失败，不能用平均成功率覆盖。

### 5.3 网页显示统一通过标准

在 W0 和 W1 桌面网页环境中，所有用例还必须同时满足：

- 页面主体、顶部栏、三栏工作区、抽屉和弹窗之间没有遮挡、重叠或意外横向滚动；
- 项目名称很长、按钮进入忙碌状态、状态数字变化和异步消息到达时，布局不会把主操作挤出可见区域；
- 1440×900 和 1366×768 下顶部栏保持单行，当前阶段、运行状态和待处理决定始终有可见入口；
- 中间审阅区优先获得空间。空间不足时应收起或覆盖显示次要栏，不能把 Diff、流程图或 Studio 压成窄条；
- 问题卡、确认卡和错误卡出现时，卡片标题、原因、当前状态和主操作不需要猜测滚动方向即可找到；
- 重要文字不能只靠省略号隐藏；确需缩略时必须能通过可见点击查看完整内容；
- 禁用、加载、成功、失败、正在停止和已取消必须有文字状态，不能只依赖颜色或降低透明度；
- 页面刷新、前进、后退和重新进入项目后，主布局及当前任务入口保持稳定。

在 W2 手机环境中，允许重新排列或切换内容区，但必须满足：

- 登录表单、当前待办、停止入口和发送入口无需横向滚动即可到达；
- 不强迫用户在两个固定高度的嵌套滚动区之间猜测当前内容；
- 桌面端可完成的确认、退回、重试和停止流程在手机端仍有明确入口；
- 状态可以压缩展示，但不能把当前阶段、待决定和运行状态全部隐藏。

### 5.4 测试证据

每个用例至少保留以下合成页面证据：

- 用户在对话框中提交的完整可见文本；
- 修改前 Studio 页面；
- 修改计划或 Change Set 预览；
- 候选 Diff；
- 确认、错误、停止或恢复后的最终页面；
- 版本历史或审计页面。

### 5.5 每个用例的统一清理步骤

1. 完成取证后返回项目列表；
2. 点击当前合成项目的可见操作菜单，再点击删除；
3. 按页面要求输入合成项目名称并确认；
4. 返回验收场景页，通过页面点击关闭尚未消费的故障预置；
5. 刷新项目列表，确认该合成项目不再显示。

不得使用删除接口、数据库命令或文件清理脚本代替上述步骤。产品没有可见项目删除入口时，需要保留合成项目并
将清理能力记为测试环境缺口；不得私下通过后端删除后声称用例已经完整执行。

## 6. 浏览器黑盒测试用例

### 6.1 基础可操作性

#### E2E-BOOT-01：所有准备工作都能从页面完成

覆盖：浏览器唯一操作约束和后续全部用例的可执行前提。

操作：

1. 打开登录页，点击注册，逐项输入合成账号信息并提交；
2. 登录后点击“新建项目”，输入“浏览器验收基础项目”；
3. 点击页面上传入口，在系统文件选择器中选择 SCN-CLOSED 合成包；
4. 等待页面显示导入完成，点击进入 Studio；
5. 依次点击对象、规则、操作、指标和版本历史标签。

通过标准：

- 不借助任何脚本或接口完成账号、项目和基线准备；
- Studio 可见地展示一项对象、一项规则、一项操作和一项指标；
- 版本历史没有测试人员无法解释的待确认修改；
- 任一步必须依赖后台准备或日志判断时，本用例为 `BLOCKED`。

### 6.2 专家明确修改

#### E2E-EDIT-01：四类资源严格闭域修改

覆盖：P01、P05、P15、P19、P40。

操作：

1. 在 SCN-CLOSED 项目的建模助手中输入：
   “把会员档案的描述改为‘记录合成会员的基础资料’；给折扣资格规则增加例外‘会员状态为冻结时不适用’；
   在订单复核的‘读取订单’步骤后插入‘核对测试标记’；把复核通过率的第一条边界改为
   ‘只统计已完成复核的合成订单’。只做这四项，不得修改其他内容，也不要生成脚本。”
2. 点击发送，等待页面出现修改计划或候选状态；
3. 点击 Studio 的对象、规则、操作、指标逐项查看候选；
4. 点击 Diff，展开全部变更；
5. 只有四项都正确时才点击确认卡中的批准按钮；
6. 打开版本历史和脚本列表。

通过标准：

- 计划明确显示四项任务，完成状态为四项全部完成；
- Diff 只包含指定描述、例外、步骤和边界的变化；
- 没有新增字段、资源、脚本或删除；
- 确认卡只能在四项全部通过后出现；
- 确认后只新增一个已确认修订，四项内容各出现一次。

#### E2E-EDIT-02：单字段修改不得带入其他变化

覆盖：P02、P21。

操作：

1. 在 SCN-CLOSED 项目输入：“只把会员档案描述改成‘合成会员资料’，其他字段、关系和资源保持不变。”；
2. 点击发送，打开对象详情和 Diff；
3. 展开对象的全部字段、关系和来源信息；
4. 点击确认后再次打开同一对象。

通过标准：

- Diff 只有一个业务属性变化；
- 字段数量、字段 key、关系、来源绑定和其他资源均保持不变；
- 页面不能出现“系统顺便补全”的额外候选。

#### E2E-EDIT-03：同名目标必须先澄清

覆盖：P03。

操作：

1. 在 SCN-AMBIGUOUS 项目输入：“把处理时长的单位改成分钟。”；
2. 点击发送；
3. 在页面出现的问题卡中查看两个具有业务区分信息的选项；
4. 暂不选择，点击 Studio 和 Diff；
5. 返回问题卡，点击其中一个目标并提交；
6. 查看候选 Diff。

通过标准：

- 目标不唯一时必须出现可见澄清卡；
- 澄清前没有任何候选修改；
- 选定后只有对应指标变化；
- 页面不要求用户填写资源 ID、Hash 或内部 key。

#### E2E-EDIT-04：用户只说业务锚点，系统负责解析稳定位置

覆盖：P04。

操作：

1. 在 SCN-CLOSED 项目输入：“在订单复核的‘读取订单’后面增加一步‘核对测试标记’。”；
2. 点击发送并打开操作流程视图；
3. 查看插入前后相邻步骤；
4. 打开 Diff 并确认候选。

通过标准：

- 用户全程不提供任何内部标识；
- 新步骤准确位于指定业务步骤之后；
- 原有步骤顺序和内容保持不变；
- 不出现目标不存在、稳定子项 ID 缺失或模型要求用户补 Hash 的错误。

#### E2E-EDIT-05：四项中的最后一项失败时整批回滚

覆盖：P11、P12、P14。

操作：

1. 在浏览器的验收场景页选择 F07，点击“仅下次生效”；
2. 返回 SCN-CLOSED 项目，提交 E2E-EDIT-01 的四项修改文本；
3. 等待页面显示整批失败；
4. 点击 Studio、Diff 和版本历史并连续刷新两次；
5. 返回验收场景页确认 F07 已消费一次并关闭；
6. 回到项目，点击页面提供的重试按钮；
7. 查看新的 Diff。

通过标准：

- 第一次失败后四项修改全部不可见，不能留下前三项；
- 当前已确认版本不变，候选区没有半成品；
- 重试后四项一次性出现且各出现一次；
- 不能要求测试人员通过数据库清理失败现场。

#### E2E-EDIT-06：模型漏项时禁止提前确认

覆盖：P01、P20、P22。

操作：

1. 在验收场景页启用 F08；
2. 返回项目，提交 E2E-EDIT-01 的四项修改文本；
3. 等待模型只准备前两项并尝试结束；
4. 查看对话区、计划状态、候选区和确认区域。

通过标准：

- 页面明确显示仍有两项未完成；
- 不出现可批准的候选确认卡；
- 前两项不能被描述为整批完成；
- 系统继续受控补齐或以明确失败结束，不能把判断交给用户猜测。

#### E2E-EDIT-07：重复发送和重复点击不得重复生效

覆盖：P27。

操作：

1. 输入“给折扣资格规则增加例外‘合成订单标记为演示时不适用’。”；
2. 用鼠标快速连续点击发送按钮两次；
3. 页面稳定后点击浏览器刷新；
4. 如页面显示重试按钮，再点击一次重试；
5. 打开规则详情和 Diff。

通过标准：

- 页面最多形成一个有效运行和一条例外；
- 不出现重复例外、重复候选或两个确认卡；
- 刷新和重试不会再次写入同一内容。

#### E2E-EDIT-08：两个浏览器会话并发修改产生可恢复冲突

覆盖：P04、P24。

操作：

1. 用两个独立浏览器窗口通过页面登录两个合成账号，并打开同一个可协作项目；
2. 窗口 A 输入并确认会员档案描述修改；
3. 窗口 B 在仍显示旧内容时输入另一个描述并提交；
4. 在窗口 B 查看冲突提示；
5. 点击页面提供的“读取最新内容”或等价按钮；
6. 重新提交窗口 B 的明确修改并查看 Diff。

通过标准：

- 窗口 B 不能静默覆盖窗口 A；
- 冲突提示使用业务语言，不要求用户处理 Hash；
- 重新读取后基于最新内容形成新候选；
- 最终版本历史能看到两次独立人工确认。

#### E2E-EDIT-09：退回候选后不污染已确认版本

覆盖：候选冻结、退回和重新调整边界。

操作：

1. 提交一个合法的单字段修改；
2. 在确认卡中点击退回，输入“保持原描述，不需要本次修改”；
3. 查看 Studio、Diff 和版本历史；
4. 再提交另一项无关的合法修改并确认。

通过标准：

- 被退回内容不会进入已确认版本；
- 页面没有残留的旧确认卡或旧候选；
- 后续新修改不携带被退回内容。

#### E2E-EDIT-10：删除资源必须先展示引用影响

覆盖：P03、P11、P14、P18。

操作：

1. 在 SCN-REFERENCES 项目输入：“删除被业务规则和操作引用的测试对象。”；

## 9. 基于 OpenJiuwen 的落地方案

### 9.1 方案结论

本项目不需要再自建一套 Agent 框架。当前代码已经接入 OpenJiuwen，后续应当在现有基础上收口，而不是推倒重来：

- OpenJiuwen 负责“Agent 怎么运行”：模型调用、ReAct 循环、流式输出、Skill、只读子任务、session、checkpoint、挂起和恢复；
- 建模 Agent Runtime 负责“怎样把框架能力接入产品”：运行状态、Rail、工具分级、交互记录、事件转换、重试账本和取消协调；
- Modeling Core 负责“知识包什么才算正确”：结构化计划、领域 Patch、Change Set 事务、修订、引用、确定性校验、确认和发布；
- 前端只消费稳定的产品状态和事件，不直接理解 OpenJiuwen chunk、tool call、session 或 checkpoint。

当前运行时锁定 `openjiuwen==0.1.16.post5`。即使官方已经发布更新版本，本次业务改造也不顺便升级框架；
升级必须作为独立兼容性任务，先通过本文全部浏览器阻断用例，再改变版本锁定。

本方案继续保留现有 Node Modeling Core 和 Python Agent Runtime 的边界，不借机进行全量语言迁移。
JiuwenSwarm 只作为后续只读多 Agent 能力候选，当前主链路继续使用已经落地的 `create_deep_agent` 和
`SubAgentConfig`。

### 9.2 第一性原理：概率层不能拥有最终事实

模型的本质是根据上下文预测下一步，因此它适合判断、拆解和选择工具，不适合独自保证事务、完整性和幂等。
系统必须把每类事实交给能够确定性回答它的组件：

| 需要回答的问题 | 唯一事实源 | 原因 |
| --- | --- | --- |
| Agent 当前在思考、调用工具还是等待输入 | OpenJiuwen execution session 和 checkpoint | 这是框架执行状态 |
| 项目处于目标、流程、知识、验证还是发布阶段 | `project_agent_state` | 业务阶段不能从模型对话推断 |
| 用户本轮要求做哪些事、还差哪些事 | 结构化 Change Plan | 自由文本计划无法逐项验收 |
| 哪些内容实际写入候选 | Modeling Core 的 Change Set 和执行回执 | 写入必须是事务事实 |
| 候选是否允许确认 | 当前 revision 对应的确定性校验回执 | 模型说“检查过了”不能作证 |
| 当前需要用户决定什么 | 持久化 interaction 记录 | 问题卡不能只存在于一段流式文字中 |
| 前端应该显示什么 | 产品快照和有序事件流 | 页面不能依赖框架内部对象结构 |

最重要的边界是：**OpenJiuwen checkpoint 只能证明“Agent 可以从哪里继续”，不能证明“业务修改已经完整提交”。**
业务写入是否成功，必须看 Change Set 回执；项目能否前进，必须看业务门禁。

- 正常生成和人工修改共用的结构化 Change Plan；

### 9.4 总体架构

```text
浏览器
  ├─ 页面快照：当前阶段、当前 run、当前 interaction、Change Set、版本
  └─ 有序事件：消息增量、进度、待办、停止、错误、焦点
         │
         ▼
Modeling API / Core
  ├─ 项目鉴权、资料和知识包事实
  ├─ Change Plan / Change Set / StudioWriteService
  ├─ revision、resource hash、mutation receipt
  ├─ 确定性校验、评测和发布门禁
  └─ 知识包候选与正式版本
         ▲
         │ 只有结构化领域工具可以写候选
         ▼
建模 Agent Runtime
  ├─ OpenJiuwenRuntimeAdapter
  ├─ project_agent_state 和结构化状态转换
  ├─ create_deep_agent + SkillUseRail
  ├─ Ask / Confirmation / Safety / Activity Rails
  ├─ 只读 SubAgentConfig
  ├─ retry ledger / interaction / event store
  └─ OpenJiuwen Runner + session + checkpoint
         │
         ▼
模型服务
```

这条链路中没有任何一层允许模型自由写正式知识包。模型只能提交结构化工具参数；Core 校验并生成候选；
用户在前端审阅实际 Diff 后，候选才可能成为新的当前版本。

### 9.5 OpenJiuwen 与产品代码的职责分配

| 能力 | 直接复用 OpenJiuwen | 建模侧必须补充 |
| --- | --- | --- |
| 模型调用 | `Model`、流式输出、客户端重试和超时 | 业务错误分类、用户可见错误和重试账本 |
| Agent 循环 | `create_deep_agent` / ReAct 迭代 | 最大业务续跑次数、必须执行工具证明、完成门禁 |
| 上下文 | ContextEngine 的窗口和压缩能力 | 确定性 Execution Brief、资料分页、校验报告分页 |
| Skill | `SkillUseRail` | 建模方法、触发规则、版本和安全审查 |
| 子 Agent | `SubAgentConfig`；后续可评估 JiuwenSwarm | 角色最小权限、只读约束、超时和结果结构 |
| 工具 | `Tool`、`ToolCard`、Rail 回调 | 领域 Patch、Change Set、revision、幂等和引用校验 |
| 挂起恢复 | `BaseInterruptRail`、`InteractiveInput`、checkpoint | interaction 持久化、过期校验、重复回答防护和页面卡片 |
| 运行恢复 | Runner session/checkpoint | 项目唯一状态、凭据恢复、业务回执核对 |
| 工具审批 | 可借鉴 allow / ask / deny | 业务变更分组和确认策略不能退化为工具名审批 |
| 事件流 | OpenJiuwen chunk 和 callback | 稳定产品事件、脱敏、持久化、顺序和断线重放 |
| 取消 | 框架任务取消和 checkpoint | 停止新工具、取消 Core 长任务、等待在途回执并结算状态 |
| 事务与发布 | 不属于 OpenJiuwen 职责 | Modeling Core 独占 |

`project_agent_state` 继续由 Agent Runtime 持有。模型每轮先用 `get_project_state` 读取带 revision 的当前状态，
再通过 `transition_project_state(expected_revision, to_phase, ...)` 提出转换；Runtime 校验允许边、业务门禁和并发 revision
后才更新唯一状态行。OpenJiuwen checkpoint、普通回复、Markdown 计划和前端按钮都不能直接修改业务阶段。

### 9.6 运行时适配层

新增单一的 `OpenJiuwenRuntimeAdapter`，业务服务不再分散调用 OpenJiuwen 内部类。适配层只暴露：

```text
start(run, execution_brief) -> event stream
resume(run, interaction_answers) -> event stream
steer(run, message) -> accepted / queued
request_stop(run) -> stopping
recover(run) -> resumed / suspended / failed
close() -> settled
```

适配层承担以下兼容工作：

1. 统一创建 `Model`、Leader、Skill、Rail 和 session；
2. 在启动时探测 pinned 版本所需 API，缺失时直接健康检查失败，不在运行中猜兼容分支；
3. 把 OpenJiuwen chunk 归一成内部 `RuntimeChunk`，不让前端或 Core 依赖框架类名；
4. 统一识别首包超时、空闲超时、上下文超限、interaction、正常结束和框架异常；
5. 统一 Runner 生命周期，避免跨事件循环复用全局 Runner；
6. 记录框架版本、适配器契约版本和 checkpoint schema，用于恢复兼容判断。

当前版本不升级到最新 OpenJiuwen。后续升级流程固定为：构建隔离镜像、运行适配器契约测试、执行本文
61 条浏览器黑盒用例、比较运行与停止指标，全部通过后才修改版本锁。

### 9.7 结构化 Change Plan 与 Change Set

#### 9.7.1 统一两种入口

“用户点名修改一个规则”和“Agent 根据资料正常生成十个资源”看起来不同，本质上都是：

1. 把目标拆成可验收任务；
2. 读取当前事实；
3. 形成有限范围的领域动作；
4. 原子生成候选；
5. 校验实际 Diff；
6. 等待用户审阅。

因此两种入口必须共用 Change Plan 和 Change Set，不能让正常生成继续走自由写文件。
OpenJiuwen Harness 的通用 task planning 继续关闭；业务计划必须通过下表的结构化工具进入 Core，不能同时保留第二份
框架 Todo 作为完成依据。

#### 9.7.2 新增领域工具

| 工具 | 作用 | 确定性约束 |
| --- | --- | --- |
| `create_change_plan` | 把用户目标拆成任务、依赖、允许范围和完成条件 | Core 分配 plan/task ID，模型不能伪造完成状态 |
| `get_change_plan` | 读取任务状态和剩余项 | 返回有界摘要，可分页读取任务 |
| `revise_change_plan` | 增删计划范围 | 必须记录原因；扩大范围需要用户决定 |
| `stage_change_set` | 一次提交一个依赖闭合批次的 typed actions | 同一 mutation ID、expected revision 和资源哈希；整批成功或整批失败 |
| `get_change_set_receipt` | 查询未知提交结果 | 响应丢失后先查询，不盲目重写 |
| `validate_change_set` | 对当前候选执行完整预检 | 回执绑定 candidate revision、validator version 和 finding fingerprint |
| `discard_change_set` | 放弃失败或退回批次 | 不影响已确认版本和其他批次 |
| `request_confirmation` | 挂起并让用户审阅实际变更 | 分组和影响由 Core 根据真实 Diff 生成，模型只提交业务摘要 |

`stage_change_set` 不是通用 JSON Patch。每个 action 仍然使用对象、规则、操作、指标、脚本等白名单领域动作；
未列出的字段由 Core 保留。超大计划按依赖切成多个原子批次，每个批次确认后才能成为后续批次的稳定基线。

#### 9.7.3 完成判断

模型不能调用“任务完成”工具直接把任务改成完成。计划任务状态只根据以下事实推进：

- `pending`：只有计划定义；
- `staged`：Change Set 已产生成功回执；
- `validated`：当前候选通过绑定 revision 的校验；
- `waiting_user`：已经生成持久化确认卡；
- `accepted`：用户接受并产生新修订；
- `rejected`：用户退回；
- `failed`：达到有限重试边界；
- `cancelled`：停止结算完成。

整份计划只有所有必需任务处于 `accepted` 或明确允许的 `skipped`，才允许进入下一业务阶段。

### 9.8 人机交互与确认

继续复用现有 `AskRail`、`ConfirmationRail`、`BaseInterruptRail` 和 `InteractiveInput`，但把产品交互契约补完整。

每个 interaction 至少持久化：

```text
interaction_id、run_id、tool_call_id、kind、status
业务问题或确认摘要、互斥选项、输入约束
change_set_id、candidate_revision、expected_project_state_revision
created_at、expires_at、answer_id、最终答案
```

处理流程如下：

1. Rail 在工具边界创建 interaction，OpenJiuwen 保存挂起 checkpoint；
2. Runtime 先持久化 interaction，再发布 `interaction.opened`；
3. 前端把当前 interaction 固定为待办，滚动到卡片标题而不是消息流底部；
4. 用户在页面本地选择，只有点击提交才发送结构化答案；
5. Runtime 使用 `answer_id` 去重，并核对 interaction、candidate revision 和项目状态是否仍有效；
6. 通过 `InteractiveInput.update(tool_call_id, answer)` 恢复原 session；
7. 过期或冲突时不恢复旧决定，而是生成新的可见问题卡。

长期自动确认策略不放在本次确认卡里。工具级 allow / ask / deny 只解决“某类工具能不能调用”；
业务级策略仍由 Modeling Core 按项目、变更层级和有效期保存，并在独立设置页修改。

### 9.9 超时、失败与重试

重试首先要回答两个问题：上一次有没有产生副作用，以及同样的输入再执行是否可能变好。

| 失败类型 | 处理方式 | 最大边界 |
| --- | --- | --- |
| 模型首包或空闲超时 | 由 OpenJiuwen `ModelClientConfig` 做有限 SDK 重试；仍失败则保存 checkpoint 和业务进展 | SDK `max_retries=3`，应用层只允许一次受控恢复，不无限重开 run |
| 模型已经输出部分文字后超时 | 文字标记为未完成，不形成确认；从同一业务检查点继续 | 不把半段回复当完成证明 |
| 只读子 Agent 超时 | 取消该子任务，保留其他只读结果，按同一任务 ID 恢复或转 Leader 处理 | 子 Agent 永远没有写工具 |
| Core 明确返回可重试且事务未提交 | 使用相同 mutation ID 和参数哈希退避重试 | 固定有限次数，页面显示当前次数 |
| Core 响应丢失、提交结果未知 | 先调用 `get_change_set_receipt` | 没有回执查询结果前禁止重新提交 |
| revision 或 resource hash 冲突 | 重新读取并生成新 Change Set | 不原样重试旧参数 |
| 参数、目标或业务语义错误 | 转问题卡或明确失败 | 不自动重复相同调用 |
| 候选校验失败 | 按 finding 分页修复，记录 fingerprint | 同指纹重复或达到契约轮数后停止 |
| 上下文过长 | 用 Execution Brief 开新 execution session，引用原业务计划和回执 | 不重新回放完整历史和资料正文 |

所有重试状态写入 `run_id + operation_id` 维度的 retry ledger，至少记录类别、次数、最后错误指纹、
下次允许时间和最终结论。OpenJiuwen 的模型重试不能替代工具回执；工具回执也不能替代模型 checkpoint。

### 9.10 上下文治理

OpenJiuwen ContextEngine 用来控制“送给模型多少历史”，但不能承担业务记忆。每次模型调用前由服务端生成
一个确定性的 Execution Brief，内容只包括：

- 当前项目阶段和允许转换；
- 当前 Change Plan 摘要、已完成任务和下一批任务；
- 当前 candidate revision、Change Set 和成功/未知回执；
- 未解决 interaction；
- 最近一次校验 fingerprint、剩余 finding 页和修复轮次；
- 当前阶段允许的工具和本轮必须执行的工具；
- 最近少量与当前任务直接相关的用户消息。

资料正文、完整 Diff、完整评测日志和大型 finding 报告都留在外部事实源中，只给模型稳定引用和分页读取工具。
只读子 Agent 返回结构化证据摘要，Leader 不接收其完整对话历史。

实施时通过适配层验证 pinned 版本的 ContextEngine 接口，目标配置原则是：保留最近 8 至 12 轮、限制总消息数、
默认不自动把已卸载历史重新塞回上下文。具体数值通过 SCN-LONG 和 `E2E-GEN-08` 压测确定，不能仅采用框架默认值。
如果 `create_deep_agent` 在当前锁定版本不能显式注入 ContextEngine 配置，先在适配层做 capability spike，
不能私自复制一套框架内部上下文引擎。

### 9.11 停止、取消和恢复

停止不是把数据库状态提前改成 cancelled，而是一段需要结算的协议：

1. 用户点击停止，状态从 `running` 进入 `stopping`；
2. Runtime 设置 cancel event，Safety Rail 拒绝新的写工具；
3. 取消 OpenJiuwen 当前执行任务、只读子任务和 Core 长任务；
4. 等待在途 Core 调用返回或达到停止超时；
5. 对结果未知的写调用逐项查询 Change Set 回执；
6. 保存最后 checkpoint、计划进度和候选事实；
7. 只有确认不再产生新写入后，状态才进入 `cancelled` 或可恢复的 `suspended`；
8. 发布 `run.stopped`，前端再显示“已停止”。

服务重启时继续使用当前机制：先把运行标为 suspended，再用原 session ID 和 checkpoint 恢复。恢复前必须核对
项目状态、候选 revision、凭据和在途回执；任何一项不一致都停在页面可见的“需要重新核对”，不能静默重放。

恢复历史知识包版本是独立的确定性命令。恢复成功后 Agent 保持空闲；只有用户点击“让助手核对恢复结果”才创建新 run。

### 9.12 子 Agent 与 JiuwenSwarm 的使用边界

当前 `SubAgentConfig` 方案保持不变：子 Agent 同步执行、只读、按角色注入最小工具面，Leader 是唯一写入发起者。
`enable_async_subagent` 和外层 task loop 继续关闭，避免形成第二套运行状态和无法解释的后台写入。

JiuwenSwarm 的 Leader/Teammate、渐进式工具暴露和工具权限可以降低大工具面和复杂并行任务的成本，
但不能直接替换现有主链路。启用前必须完成四项 capability spike：

1. 每个 Teammate 能否获得不同且不可扩大范围的工具集；
2. HITL 挂起、checkpoint 恢复和当前 interaction 能否保持一一对应；
3. 取消能否传播到全部 Teammate，并在停止后保证没有迟到写入；
4. 团队事件能否形成稳定全序，供前端断线重放和审计。

即使四项都通过，第一阶段也只把 JiuwenSwarm 用于多资料阅读、表格盘点和跨来源比较等只读任务。
所有写入仍由 Leader 汇总成一个 Change Set 后提交。JiuwenSwarm 的通用工具权限只做工具级防线，
不能替代 revision、领域动作白名单、Change Set 事务和业务确认。

### 9.13 前端事件协议与网页优先

OpenJiuwen 的原始 chunk 先经过 Activity Rail 和 Runtime Adapter，再转换成以下稳定产品事件：

```text
message.delta / message.done
run.state_changed / run.stop_requested / run.stopped
task.progress
interaction.opened / interaction.updated / interaction.closed
change_plan.updated / change_set.updated
focus.changed
error.raised / recovery.available
```

每个事件带项目内递增序号。前端进入项目时先读取完整快照，再从 `last_seq` 之后重放事件；断线重连不重复消息、
问题卡或确认卡。事件桥只传业务显示字段，OpenJiuwen session ID、checkpoint ID、工具参数和内部异常不进入主界面。

前端协议必须直接支撑第 2.11 节的问题：

- `interaction.opened` 带待办类型、组数、卡片锚点和主操作，页面定位卡片标题；
- `change_set.updated` 带总组数、已查看数、已选数和当前组，支持完整批次审阅；
- `run.state_changed` 明确 queued、running、waiting、stopping、cancelled、failed 和 completed；
- `error.raised` 带错误作用域、是否产生写入、恢复动作和用户可见说明；
- 快照带当前待办和离开期间摘要，重新进入项目不依赖翻找聊天历史。

实施顺序仍以网页显示为先：先让 1440×900 和 1366×768 的 W0 用例通过，再扩大 Agent 能力。
框架事件接得再完整，如果确认卡主操作仍在屏幕外，也不能进入后续验收。

### 9.14 改造前后变化

| 场景 | 当前方式 | 改造后 |
| --- | --- | --- |
| OpenJiuwen 接入 | `agent.py`、`service.py` 分散依赖具体 API | 单一 Runtime Adapter 隔离版本和 chunk 差异 |
| 正常生成计划 | Markdown 计划和模型循环，完成语义不够强 | Core 持久化结构化 Change Plan，按回执推进 |
| 人工修改 | 多个独立领域工具调用 | 同一计划下形成一个原子 Change Set 批次 |
| 写入结果未知 | 可能依赖模型再次尝试 | 先查 mutation/Change Set 回执，再决定恢复 |
| 校验修复 | 已有 fingerprint 和有限轮次，但与计划完成未完全绑定 | 修复状态、Change Set 和计划任务一一关联 |
| 上下文 | 框架上下文加人工摘要和分页措施 | ContextEngine 窗口加确定性 Execution Brief，不回放长历史 |
| 等待用户 | 已用 Interrupt Rail，但卡片显示和长期策略混在产品层 | 持久化 interaction、显式提交、过期校验和独立策略页 |
| 停止 | 先标 cancelled，再取消在途任务 | running → stopping → 结算回执 → cancelled/suspended |
| 子 Agent | 同步只读 SubAgentConfig | 保持主链路；JiuwenSwarm 通过 spike 后只承担读任务 |
| 前端事件 | 已有消息、活动和 focus 事件 | 稳定判别式协议、快照加序号重放、当前待办优先 |
| 版本恢复 | 恢复后可能自动触发 Agent | 恢复是独立确定性动作，Agent 默认不启动 |

### 9.15 好处和代价

好处：

- 复用 OpenJiuwen 已有 Runner、session、checkpoint、Skill、Rail 和流式能力，减少自建循环；
- 正常生成和人工修改走同一条受控链路，工具和校验投入可以同时覆盖两类场景；
- OpenJiuwen 负责执行恢复，Core 负责事务恢复，两者边界清楚后不会把 checkpoint 误当写入成功；
- 结构化计划和 Change Set 缩短工具参数与上下文，减少漏项、重复写入和长对话回放；
- 只读子 Agent 可以并行分析，写入仍集中到 Leader 和 Core，扩大效率而不扩大写权限；
- 前端得到稳定状态和事件，桌面网页可以优先做好显示，不受框架小版本 chunk 变化影响。

代价和限制：

- 同时存在 OpenJiuwen checkpoint、RuntimeStore 和 Core revision，必须维护清楚的关联和一致性检查；
- Runtime Adapter、Change Plan 和 Change Set 增加了代码与数据模型，短期开发量会上升；
- 每个原子批次前需要读取 revision、资源哈希和计划，单步延迟会略有增加；
- ContextEngine 压缩可能丢失自然语言细节，因此仍要维护确定性 Execution Brief；
- 固定 OpenJiuwen 版本提高稳定性，但新能力不能立即使用，升级需要完整回归；
- JiuwenSwarm 若引入过早，会增加检查点、取消、事件排序和调试复杂度；
- 通用工具权限无法表达业务确认范围，领域 Rail 和 Core 校验仍然必须自研。

这套方案接受少量确定性读写开销，换取可恢复、可审计和不会静默改错的运行。对于长时间建模任务，
一次安全的额外读取通常比失败后人工清理半成品更便宜。

## 10. 实施结果与验证记录

### 10.1 实际采用的方案

实现采用“模型提议、Core 裁决、浏览器确认”的分层方案，没有让模型直接自由写入知识包：

1. OpenJiuwen Agent 负责理解用户意图、读取事实、选择领域动作并提交结构化工具参数；
2. Core 持久化 Change Plan、任务、Change Set、动作、回执、校验回执和最终确认；
3. 所有受管对象、规则、操作、指标、数据绑定和脚本仍通过确定性领域工具编译；
4. 写入先进入候选工作区，只有通过完整计划校验并由用户确认后才形成当前 Git 修订；
5. 前端只显示业务状态、任务、Diff、决定和恢复动作，不显示工具参数、运行 ID 或内部异常；
6. 正常生成和专家人工修改共用同一套计划、批次、校验、确认和审计链路。

Core 新增并统一暴露七个计划/批次工具：

| 工具 | 确定性职责 |
| --- | --- |
| `create_change_plan` | 把用户目标冻结为带目标资源、允许工具、依赖和验收条件的任务清单 |
| `get_change_plan` | 从 Core 读取唯一当前计划，不依赖对话记忆猜测进度 |
| `revise_change_plan` | 对新增范围形成显式计划增量，并在需要时重新等待批准 |
| `stage_change_set` | 在一个事务边界内编译并暂存整批领域动作 |
| `get_change_set_receipt` | 在超时或响应丢失后先查询原批次结果，禁止盲目重交 |
| `validate_change_set` | 同时核对计划完整性、范围闭合、引用、脚本回执和实际 Diff |
| `discard_change_set` | 在未确认时确定性放弃整批修改和对应计划 |

已有细粒度领域工具继续负责资源内部修改。例如对象绑定使用字段映射 Patch，脚本使用契约、源码、
JiuwenBox 测试三段工具。自由 `write_file` 只保留给未受管文件，不能绕过领域工具维护受管资源。

### 10.2 正常生成现在怎样执行

正常生成不再是“模型边想边写直到它自称完成”，实际顺序如下：

1. 浏览器提交目标和资料；
2. Agent 读取项目状态、资料清单和需要的分页正文；
3. Agent 调用 `create_change_plan`，Core 按资源类型形成可验收任务；
4. 生成模式的计划先在网页等待用户批准；
5. 批准后 Agent 把同一业务批次的领域动作一次交给 `stage_change_set`；
6. Core 在事务中核对任务 ID、目标 key、允许工具、基线 revision、资源 Hash 和幂等 mutation ID；
7. `validate_change_set` 证明每个必选任务都完成、没有计划外变化，脚本还必须具有当前源码测试回执；
8. 网页逐组展示整批 Diff，用户接受后 Core 再提交修订；退回后冻结候选关闭，明确放弃时 Agent 调用受控丢弃工具；
9. 版本、确认方式、计划、Change Set、动作和回执保留在活动记录中。

因此，用户临时让 Agent 改资源和 Agent 正常生成资源现在使用同一条安全链路，区别只在计划模式和是否先批准计划。

### 10.3 OpenJiuwen Workflow 的实际用法

本次没有把整个建模主链硬塞进一个固定 Workflow。建模需要模型在领域工具之间动态选择，而固定 DAG 更适合
确定性、输入输出清楚的恢复步骤。实际实现保留 OpenJiuwen Runner、Rail、Interrupt 和 checkpoint 作为主执行框架，
新增 `execution-brief-workflow-v1` 专门处理恢复摘要：

```text
Start -> 从持久化业务事实生成 Execution Brief -> End
```

Workflow 输入是服务端生成的结构化 JSON，不是旧对话全文；输出限制在 12,000 字符内，并明确要求先核对
`get_project_state`、`get_change_plan` 和不确定 Change Set 回执。这样使用 Workflow 的好处是恢复过程固定、可测试，
又不牺牲主 Agent 对复杂建模任务的动态工具选择。

JiuwenSwarm 没有进入写链路。现阶段同步只读子 Agent 已能满足资料分析隔离；在角色工具隔离、HITL、取消传播和
事件排序未完成 spike 前，引入 Swarm 会扩大状态空间，收益不足以抵消风险。

### 10.4 改造中额外发现并修复的问题

完整浏览器回归发现了若干仅靠单元测试不容易暴露的问题，均已纳入实现和回归：

| 发现 | 根因 | 处理 |
| --- | --- | --- |
| 普通“同名列”被误判为目标歧义 | 文本分类使用过宽的“同名”关键词 | 只对明确的同名业务资源触发决定卡 |
| 数据绑定用例形成空修改 | 合成基线已经绑定到目标表 | 基线改为待绑定对象，并独立保留目标表资料 |
| 过期确认故障触发时机不对 | 故障应在提交确认而不是展示确认卡时生效 | 用例改为真实审阅并提交，再验证旧确认拒绝 |
| 自动查回执过程在成功后消失 | 活动行结束时清除了恢复错误 | 将修复/失败工具事件作为持久消息保留 |
| 相同校验问题仍做第三次盲重试 | 框架按无进展指纹提前停止，故障预期不一致 | 初次加一次修复后无变化即停止，并显示明确出口 |
| 生成脚本只能命令行运行 | JiuwenBox 调用公共 `main(**input)`，旧源码只有 CLI 入口 | 同时提供结构化 `main` 和独立 `cli` |
| 编译器产生的未变化索引导致候选被拒 | 工作区包含与基线相同的 no-op 写入 | 冻结确认前删除 no-op 写入和无效删除 |
| 第二版脚本被隐藏操作绑定阻断 | 阶段门禁把编译器隐藏组当成待确认业务知识 | 阶段判断排除隐藏编译组，业务变化仍受门禁 |
| 源码变化后重放旧脚本测试回执 | Agent 工具回执只按显式参数缓存，未包含候选源码 | `run_script_test` 设为上下文依赖工具，始终由 Core 测当前候选 |
| 明确“放弃”后退回内容仍显示 | 退回结果没有把用户反馈交回续跑模型 | Core 回传结构化反馈，Agent 调用受控丢弃并刷新候选视图 |
| 上一条停止用例污染下一项目 | 一次性故障可能在停止前尚未消费 | 验收页增加“关闭全部故障”，每条用例先用可见点击清理 |
| 页面提示先出现、列表后刷新导致偶发失败 | 用例依赖瞬时文案或异步列表时序 | 等待持久状态/真实列表元素后再做数量和内容断言 |

### 10.5 前端实际变化

网页端已实现以下改造：

- 桌面、窄屏和手机分别使用稳定布局，手机在“知识内容/建模助手”之间显式切换；
- 当前问题或确认固定显示为可定位待办，确认组必须逐组查看后才能接受；
- 多文件 Diff 显示整批数量、当前文件和前后导航，长期确认策略移到独立入口；
- Agent 一开始运行就显示停止入口，停止先进入 `stopping`，完成结算后才显示已停止；
- 发送失败保留原消息和输入框内容，文件读取、确认、评测等失败分别给出就地恢复动作；
- 正式评测由确定性页面动作创建，显示唯一轮次和停止按钮，不再靠给 Agent 发一句话间接触发；
- 版本恢复不创建 Agent run；活动记录按时间展示计划、工具回执、校验、确认和修订；
- 主流程隐藏 candidate ID、tool call ID、checkpoint ID 和原始堆栈，保留业务诊断。

### 10.6 真实模型探针结论

在启用确定性浏览器验收模型前，曾在 cs 合成项目中通过建模助手输入真实修改要求。探针确认浏览器到 Agent、
OpenJiuwen Runner、工具注册、Core 领域工具和事件流可以连通，真实模型能够调用资源列表和读取工具。

同时也观察到一个仍需后续优化的问题：真实模型连续重复列表/读取探索超过 6 分钟，没有进入写入计划，最终由测试人员停止。
这说明受控工具链已经可用，但真实模型的工具发现效率、提示收敛和探索预算还需要独立评测。确定性验收模型只对页面明确创建、
数据库标记且部署开启验收模式的合成项目生效；普通项目始终使用真实模型配置，因此它不会掩盖生产模型问题。

### 10.8 部署与回滚

cs 部署前已通过 SQLite 在线 `VACUUM INTO` 创建一致性快照。替换时复用原 Core 数据卷、Agent 数据卷、

回滚时应停止新容器，把保留的旧容器恢复原名并启动；只有确认新版本稳定且备份留存策略满足要求后，才能清理旧容器。

### 10.9 实际收益与代价

实际收益是错误被尽可能提前变成确定性拒绝：漏项不能确认、越界动作整批拒绝、响应丢失先查回执、脚本回执绑定源码、
停止后不再写入、退回和放弃不污染已确认版本。用户可以从网页看到当前计划、待办、Diff、错误作用域和恢复入口。

代价也已出现：每批修改多了状态读取、计划、Hash、预检和回执查询，单次简单修改会增加少量延迟；Core、RuntimeStore、
OpenJiuwen checkpoint 三套持久状态需要维护关联；严格浏览器套件本身运行时间较长。当前选择接受这些开销，
因为它们换来可恢复、可审计和不会静默改错。后续优化应优先减少重复只读探索和并行化独立读取，不能删除事务、Hash 或确认门禁。

### 10.10 数据 Schema 与虚拟对象互斥策略

对象来源现在只有两种互斥模式，不再由模型自行混用：

| 条件 | 改造前 | 改造后 |
| --- | --- | --- |
| 存在任意已解析且 `purpose=schema` 的 Sheet | 模型可能挑选部分 Sheet、合并多个 Sheet，或额外生成派生对象；mapping 依赖后续手工绑定 | Core 把生成计划规范化为唯一 `sync_schema_objects` 任务；每张 Sheet 恰好生成一个物理对象，字段、主键、来源和 mapping 确定性生成，只有表头的空 Sheet 也必须保留 |
| 完全没有确定数据 Schema | 模型可能把普通 Excel 表误当物理 Schema，生成 `sourceTable/sourceColumn` 和空 mapping | 只允许虚拟对象；服务端清除表来源、字段物理列和 value binding，不生成 mapping 文件 |

Schema 模式下，模型不能调用 `create_object`、旧 `upsert_object` 或 `write_file` 绕过同步；候选确认前还会再次按当前资料核对 Sheet 集合、对象集合、全部字段、来源版本和 mapping。少 Sheet、多对象、错误绑定、缺 mapping 任一情况都会阻断确认。重新同步会在同一事务内删除不对应物理 Sheet 的旧派生对象，并更新对象索引、内部规格和 mapping。

无 Schema 模式下，`patch_object_source_binding`、`bind_object_source` 和 Schema 同步工具会被拒绝。mapping 从知识包必选文件改为条件文件：有物理 Schema 时必须存在，没有物理 Schema 时必须不存在。Agent 主链和旧 M2 批生成在保存前执行同一来源策略，避免旧入口成为旁路。

该策略使用纯合成数据验证：本地 61/61 条浏览器用例通过；9 Sheet 场景连续 3 次均生成 9 个已绑定对象并移除旧派生对象；无 Schema 场景连续验证对象正常生成且 mapping 数量为 0。cs 部署后又执行 8 次严格浏览器旅程，Schema 3/3、无 Schema 5/5，全部通过。报告位于 `modeling/tmp/browser-acceptance-cs/schema-object-policy-strict/report.json`，测试产物不纳入版本库。

部署不会自动接受或重写存量业务候选。此前已经生成错误对象的项目应先在确认卡退回或放弃旧候选，再重新发起对象生成；新一轮计划会按当前数据 Schema 确定性重建。
