# 建模工作台改造 · 设计文档集

> 状态：设计草案 · 2026-08-22
> 方向：把建模助手从「确定性编排器 + 模型填表」改为「agent 驱动 + 少量 harness 约束」

## 背景判断

现状的控制流是编排器决定做什么、组 prompt、让模型在 12 轮内填完一张结构化表单（`modeling/src/workflow/agent.ts:67` 的 `MAX_TURNS=12`），编排器接过 payload 渲染成知识包文件并推进状态机。模型可用的工具只有 6 个只读检索和 17 个 `submit_*` 提交，没有任何能改变世界状态的能力。

结果是全部建模流程知识被编译进 TypeScript：15 种任务类型、10 种任务状态、6 个固定门禁、8 类待确认事项、三级修复权限。后端 49k 行、前端 16k 行、测试 38k 行，每加一种建模情形就要加一条代码路径。

改造方向：**知识包仓库是事实源，agent 是建模者，harness 只保留确定性不变量。**

## 后端设计理念

**尽量基于 openJiuwen agent，去掉硬码。** 凡是"agent 怎么跑"的问题——模型客户端、循环控制、上下文裁剪、检查点、子 agent 编排、工具审批、事件流、脚本沙箱——全部交给 openJiuwen / JiuwenSwarm / JiuwenBox，不自建（清单见[功能地图 §2.4](02-feature-map.md)）。

只有"知识包是什么、什么绝对不允许"才是我们的代码，且有明确下界（[功能地图 §9](02-feature-map.md)），防止去硬码把不变量一起去掉。

按这条理念，确定性核心从最初估的 7–9k 行收到约 **4.5–5k 行**。

## 四条核心约定

1. **分界线**：失败是静默的、不可逆的、或者会让模型给自己打分的，归确定性核心；失败是可见的、专家能当场纠正的，归 agent。
2. **门禁顺序是硬的，通往门禁的路径是软的。** 门禁是纯谓词，不推进任何东西，只回答能不能过。
3. **计划是文件。** `.modeling/plan.md` 由 agent 维护，因此天然有版本、diff、回退和审计，不需要任务图表。
4. **v1 删除全部校验器。** 只保留 5 条写入安全 Pre-hook（路径穿越、key 重复等失败静默且不可逆的）。判断包对不对的标准是 consumer 能否导入 + 评测通过率，不是能否过校验器——校验器是代理指标，评测是目标。后续按真实失败数据逐条加回，见[功能地图 §2.3](02-feature-map.md)。

## 与现有决策记录的关系

本文档集取代 `docs/decisions/2026-07-23-ai-assisted-construction-workspace.md` 中关于任务图编排、里程碑回退、三级修复权限、分层校验和消息块目录的部分。

该决策中以下内容**继续有效**：修订不可变、确认绑定修订、失效传播、门禁不可绕过、脚本受控执行、消息块由服务端校验。

**证据强制**降级：evidence 仍然记录并在前端展示，但 v1 不做非空强制——现有实现只检查数组非空，模型填任意字符串即可通过，属于"可被编造的内容满足"的检查。后续要加回时，应升级为**可解析性校验**（`material:<filename>` 必须命中已上传资料、`table:<name>` 必须命中数据字典、`user-decision:<id>` 必须命中真实确认记录），那个版本编不出来，才配阻断。

**技术栈方向调整**：Node 后端从"长期保留"改为"过渡态"，终态是全 Python 双进程，分两步走，见[技术选型 §2.4](04-tech-stack-and-implementation.md)。
