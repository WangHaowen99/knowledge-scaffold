设计要点

  1. 不问分类。不让用户选"这是流程文档还是数据字典"——助手自己判断，判错了用户会说。多问一个问题就多一道摩擦。
  2. 传完立刻解析并反馈。扫描版 PDF、加密文件、空表格这类问题在这一步暴露成本最低。等助手跑起来才发现，用户已经等了五分钟。
  3. 解析失败给三个出口，其中「我口头说明内容」最重要——很多资料本来就不完整，堵死这条路用户只能放弃。
  4. 可以不传直接开始。有些项目的知识全在专家脑子里。资料不是建模的前置条件。
  5. 这是唯一的全屏上传页。之后补资料全部在对话流里完成，不回到这里——见屏 2。

设计要点

  1. 活动行说人话，不显示工具名。「正在读《X》第 3/6 份」而不是 read_document(filename=...)。这要求工具返回值带一个 display 字段，不能让前端解析工具名拼文案。
  2. 活动行带耗时。长任务里「已 1分12秒」比转圈有用得多——用户据此判断是不是卡了。
  3. 三级递进。活动行 → 展开最近几条 → 「看全部」才进过程抽屉。日常只需要第一级。并行任务显示进度（「3 个并行中，2 完成」）而不是列三行。
  4. 活动行不进历史。它是临时行，任务结束后折叠成一条正常消息（「分析了 6 份资料，3 处需要你决定」）。
  5. 助手可以主动要资料。这是资料的第二个时间点，也是最高频的一个——建模过程中才知道缺什么。
  6. 「我口述」必须有。很多领域知识只在专家脑子里，从来没有文档。缺这个出口，用户会卡在「我没有这个文件」然后放弃。口述记成 user-decision 证据，与文档证据同等。
  7. 输入框接受拖放。用户想补材料时最自然的位置就是他正在说话的地方。工作台任何位置拖入文件也都能传。

设计要点

  1. 源头限流优先于前端折叠。Skill 里写死「一次 request_confirmation 不超过 5 个变更组，超过就拆多轮」。前端做再好的分诊，也救不了一个 17 项的确认请求——这里演示的是兜底，不是常态。
  2. 按判断难度分诊，不按文件。每个变更组带一个 tier 字段（口径 / 结构 / 索引），由助手标注、服务端校验（改了 rules/ 却标 index 会被拒）。
  3. 三种批量模式。「全部接受」给信任的；「逐条过」像 code review 的 file-by-file，给谨慎的；「抽检 3 条」承认现实——用户不可能真看 17 条，与其假装看了，不如随机抽检并把复核方式留痕。
  4. 常设策略是显式开关，不是隐藏偏好。常驻在确认卡下方，用户随时看得见自己授权了什么。「改口径」和「脚本」两档标为不可关闭——那是写在核心里的硬约束，不是策略。
  5. 策略不回溯。改了策略只影响之后的确认，已生效的确认记录不动。
  6. 每条口径变更都带影响提示。「⚠ 这会改变已有查询结果」比 diff 本身更能让专家停下来看。

§3.2 可用量与占用

仓库现有库存并不等于可以领用的数量。可用量指扣除已被工单占用之后、当前可以立即发放的部分。已占用包含已审批未领取和在途调拨两种情况。

盘点期间库存冻结，冻结期内所有可用量按盘点开始时刻的快照计算，不随实时出入库变动。

§3.3 安全库存

安全库存由各仓库根据历史月均消耗量与供货周期自行设定，报备后生效，原则上每季度复核一次。

设计要点

  1. 双向反查是这一屏的全部理由。知识条目 → 点 evidence → 跳资料原文并高亮；资料段落 → 看到引用它的知识条目。这让 evidence 从「一个字符串」变成可验证的东西。
  2. 「引用 N」是最重要的元数据。它让用户知道哪份资料是核心、删了会炸。删除前必须提示引用数并给出后续处理。
  3. 口述证据和文档证据同列。专家口述记在 .modeling/decisions/，在这里作为一类证据来源展示，不藏起来。
  4. 范围克制。只做列表、原文查看、替换、删除、搜索。不做重命名、打标签、分组、文件夹、独立权限——资料量级是几份到几十份，不是文档库。
  5. 作为左栏第二个 tab，不是独立页面。唯一的例外是项目创建时的全屏上传（屏 1），那时候要一次整理十几份。

设计要点

  1. 主视觉翻转。原来的表格把「受影响」做成主体、「保持有效」挤在最后一行，恰好放大了用户的恐惧。现在两栏对照，绿色的 11 在左，待办的 4 在右——情绪从「完了要重做」扭到「处理这 4 个」。顶栏也先报「11 项保持有效」。

  4. 直接/间接要分开标。「同上（间接）」让用户明白这一项不是新冲突，是连带失效，心理负担完全不同。
  5. 「保留现行口径」也要留痕。不是静默忽略，写进 decisions 并在发布摘要里列为已知不一致。

设计要点

  1. 融合 = 差量的另一种来源。复用增量建模的全部机制（冲突裁决 → 候选修订 → 确认），不新建一套流程。
  2. 冲突分类是确定性的（key 撞、别名撞、引用断、mapping 指向不同源），由融合自带的引用解析算出，不依赖通用校验器；只有"两个业务口径哪个对"需要模型解释、用户裁决。
  3. 选择性导入放在左栏。先缩小范围再谈冲突，能把 5 个冲突降到 2 个的操作，比让用户裁决 5 次更有价值。
  4. provenance 必须保留。融合进来的条目带来源包和版本，将来来源包升级时能再算一次增量。
  5. 命名空间前缀是有代价的选择，界面要说出代价（近义对象会让检索命中错误），而不是默认加前缀了事。

设计要点
