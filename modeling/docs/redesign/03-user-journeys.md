## 贯穿全程 · 等待时用户看到什么

这一节不属于任何单条旅程，但它决定用户敢不敢把长任务交出去。助手跑起来可能是几十秒到几分钟，中间必须持续可见。

| 层级 | 位置 | 内容 | 何时用 |
| --- | --- | --- | --- |
| 一级 | 对话流底部**活动行** | 「正在读《安全库存管理办法 v3》· 第 3/6 份 · 已 1分12秒」 | 常驻，日常只看这一级 |
| 二级 | 活动行展开 | 最近 5 条工具调用（人话，不是工具名） | 觉得有点慢时点一下 |
| 三级 | 过程抽屉（屏 8） | 全部调用、子 agent 树、检查点、上下文占用 | 排障与审计 |

三条约束：

- **说人话。** 「正在读《X》」而不是 `read_document(filename=...)`。工具返回值带 `display` 字段，前端不解析工具名拼文案。
- **带耗时。** 长任务里「已 1分12秒」比转圈有用得多——用户据此判断是不是卡了。
- **并行显示进度不显示列表。** 「3 个分析并行中（2 完成）」而不是列三行。

任务结束后活动行不进历史，折叠成一条正常消息：「分析了 6 份资料，3 处需要你决定」。

## 贯穿全程 · 用户只表达业务意图

本文件表格里的「助手」和「核心」列会记录工具与状态机实现，**这些内容仅供研发和审计，不是用户操作说明，也不得原样出现在界面或助手回复里**。用户只需要说明目标、补充事实和做业务判断；如何选工具、如何跳状态、如何恢复运行全部由 Agent 运行时负责。

| 规则 | 合格表现 | 不合格表现 |
| --- | --- | --- |
| 一个点击就是完整意图 | 用户点上传、确认、退回、恢复、重试后，动作立即进入唯一消息流，Agent 自动处理后续 | 点完以后再要求用户输入“调用某工具”“切到某状态” |
| 只说业务语言 | 显示「正在核对发布条件」「已恢复到 v1.0.0」 | 在主界面或回复里显示工具函数名、API 路径、数据库表、`evaluation:running` |
| 语义信息优先 | 顶栏显示 `v1.0.0 · 已发布` 和「发布交付」 | 把 Git 哈希、run、session、checkpoint 当主信息 |
| 技术细节按需下沉 | 用户主动打开过程或审计信息后，先看到人话摘要；唯一标识只作为次要审计字段 | 在消息正文、问题卡或下一步选项里要求理解内部编号 |
| 选项互斥且被尊重 | 选择「继续补充用例」后本轮停止发布，不重复弹同一确认 | 用户拒绝后，Agent 没有新事实就再次问同一问题 |
| 错误先说影响和出口 | 「当前版本读取失败，可刷新后重试；已发布版本未受影响」 | 只抛错误码、堆栈、修订冲突或内部服务名 |
| 下一步不转嫁编排 | 能自动完成就直接继续；确需决定时给少量互斥业务选项并保留自由输入 | 回复“请告诉我下一步调用什么”或让用户替 Agent 排步骤 |

横切验收要求，适用于 A–F 每一条旅程：

1. 只用鼠标点击和文本输入即可完成，不要求用户输入命令、工具名、API、状态编码或内部 ID。
2. 用户发送消息或点击动作后，250ms 内出现本地消息、已处理态或忙碌态；服务端失败再原位恢复。
3. 上传、确认、退回、恢复和重试成功后，系统自动形成一条自然业务消息并让 Agent 主动继续，不要求用户补一条“继续”。
4. 助手流式回复中不得出现内部工具名、参数、数据库表名、编码状态、run/session/checkpoint 或裸修订哈希；语义版本和业务阶段可以出现。
5. 主界面不得用内部标识代替用户要判断的信息；审计标识仅在用户主动展开时作为次要信息出现。
6. 每个问题卡的选项必须互斥，选择后产生不同且稳定的后续行为，同时始终保留自由输入。

## 旅程 A · 从零建一个知识包

**角色**：领域专家（兼项目负责人） **耗时**：半天到两天，分多次 **终点**：`1.0.0` 正式发布

### A1 创建与上传（屏 1）

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| 建项目，写一句建模目标；拖入 6 份资料 | 未启动 | 逐份解析 pdf/docx/xlsx；xlsx 提取可预览的工作表与字段，只有用户指定或 Agent 判定为 Schema 后才作为对象/属性事实源；建空 git 仓库 | 每份实时显示解析状态；扫描版 PDF 当场报错 |
| 扫描件选「先留着，我口头说明内容」 | | 标为不可解析，不阻塞 | 该行变提示态 |
| 点「开始建模」 | 取单写者租约，启动 run | | 进入主界面 |

**关键点**：解析失败当场说，不要等助手跑起来才发现。资料**不是**前置条件——一份都不传也能开始，很多项目的知识本来就全在专家脑子里。

这是唯一的全屏上传页。之后补资料一律在对话流里做。

**资料的三个时间点**：项目创建（本步）· **建模过程中**（A4，最高频）· 建模完成后（旅程 B）。

### A1.1 指定材料作用与阅读方式

材料有两个互相独立的设置：**作用**是单选，默认「由助手判断」，可选「建模目标依据」「数据 Schema」「通用业务依据」；**阅读方式**是「按需读取 / 全文精读」，默认按需。两者都不是上传前置问题，用户不设置也能继续；用户仍可在输入框用自然语言说明更具体的用途。

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| 在创建页、全局拖放区或对话输入区加入资料 | 不等待全部解析就继续回应当前对话 | 每份资料独立入队解析，保留用户指定的作用和阅读方式 | 文件立即进入唯一消息流并显示逐份进度；输入框始终可用 |
| 把《管理办法》设为「建模目标依据 + 全文精读」 | 全文读完后据此生成或复核目标 | 记录材料指令；完整阅读成功前不得声称已读完 | 作用单选与全文开关同时可见，互不冲突；设置后 250ms 内反馈 |
| 把 `对象定义.xlsx` 设为「数据 Schema」 | 以工作表和列为事实源抽取对象及属性 | 仅表格材料允许该用途；保存工作表、原始列名、Excel 列号和来源资料 | 解析结果直接预览“工作表 → 字段”，允许改回「由助手判断」 |
| 上传后再修改作用或阅读方式 | 自动按新事实继续，不要求用户再说“继续” | 用乐观版本保存同一材料记录；冲突时拒绝覆盖 | 设置变化作为一条自然业务消息进入流；失败时原位恢复 |

**Schema 精确性约束**：标为数据 Schema 的 Excel 中，每个生成对象和属性都必须能反查到具体资料、工作表、Excel 列号和原始列名；不得新增工作簿中不存在的业务属性。类型、主键候选或约束必须明确标为“推断”，与原始字段分开展示。多工作表、空列、重名列和合并单元格不能静默丢失，无法确定时在消息流里请用户裁决。

**上传不阻塞**：解析成功、部分成功或失败都作为一条消息进入流，例如「解析成功 5/6，1 份扫描版 PDF 无法解析」。用户在解析期间可以继续发消息；系统不得要求用户先给每份资料分类。

### A2 目标确认（第一个门禁，屏 2）

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| 等 1–2 分钟 | Leader 按材料作用分派 `material_analyst` Teammate：默认按需读取相关片段，标为全文精读的材料先完成全覆盖，再汇总目标依据并写 `.modeling/goal.md` 草案 | 每个 Teammate 的分析落 `.modeling/analysis/*.md`（候选修订） | 消息流末尾的活动消息显示「3 个分析并行中（1 完成）· 已 47 秒」 |
| | `request_confirmation` | 挂起 | 计划块 + 目标草案卡；中栏渲染 goal.md；顶栏「待确认 1」 |
| 改了两句范围描述，确认 | 更新 goal.md | 确认记录绑定修订 | `goal.md` 变绿；门禁「建模目标确认」通过 |

**关键点**：目标确认之前助手不动知识包正文。第一个产物就是可读可改的 `goal.md`，这是消解「它会不会乱写一通」的最有效方式。

### A3 流程访谈与确认（屏 2）

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| 回答一批访谈问题（成批卡片，可跳过） | 从资料 + 回答草拟 3 条流程，`write_file` 到 `diagrams/*.mmd`，`focus` 到第一条 | 候选修订；写入安全 Pre-hook | 中栏渲染流程图，助手指向哪条就显示哪条并高亮到节点 |
| 看图说「D2 这个判断不对，应该分仓库级别」 | 改图、改规则、`request_confirmation` | 候选修订 + diff | 中栏切 diff（渲染前后对照）；右栏确认卡 |
| 确认 3 条流程 | | 门禁「业务流程确认」重算 | 三个 `.mmd` 变绿 |

**中栏文件渲染验收**：

- `.md` 默认按标题、段落、列表、表格、引用、代码块和链接进行语义化渲染，同时提供源码视图；知识包内链接留在工作台并切换中栏，外部链接单独打开，远程图片不得静默发起请求。
- `.yaml` / `.yml` / `.json` 默认显示可折叠、分批展开的结构树和关键字段摘要，保留标量类型、数组顺序与完整源码；解析失败时显示可理解的错误并保留源码出口，合法的 `__proto__` 等键不得造成白屏。
- `.mmd` 使用 Mermaid 渲染为可缩放流程图，保留源码视图；Agent 聚焦节点后中栏自动打开对应图、高亮并滚动到节点。渲染失败时显示错误和简化视图，不能只显示空画布。
- 所有流程图文件只能写入 `diagrams/*.mmd`；core 拒绝其他目录下的 `.mmd`，Agent 收到拒绝后自行改到正确目录，不把路径规则转嫁给用户。
- 渲染内容不得执行任意 HTML 或脚本；切换“渲染 / 源码”、缩放和定位都不改变文件内容，不产生候选修订。

**关键点**：这一段往返最多。必须做到**用户说一句自然话就能改图**，而不是回到某个「访谈步骤」重答一遍。助手控制中栏焦点（`focus`）在这里价值最大——用户说「D2」时图已经指向那里了。

### A4 助手主动要资料（屏 2）

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| — | 发现资料里没说明「安全库存本身怎么定的」，`ask(kind='material_request')` | 挂起 | 对话流里的资料请求卡：拖放区 + 「我口述」+「让我先找找」+「跳过」 |
| 没有文档，选「我口述」，说了两句 | 记成证据继续 | 写 `.modeling/decisions/`，evidence 前缀 `user-decision:` | 卡片折叠成一条已答记录；资料界面的「口述证据」计数 +1 |

**关键点**：**「我口述」这个出口不能省。** 很多领域知识只在专家脑子里，从来没有文档。堵死它，用户会卡在「我没有这个文件」然后放弃整条流程。口述证据与文档证据同等对待。

### A5 知识抽取与批量确认（屏 3）

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| 基本旁观 | 按流程派 `knowledge_extractor` Teammate → operation → object/rule/metric，每条带 evidence | 写入安全 Pre-hook；evidence 记录但 v1 不强制 | 目录树逐个文件从灰变黄；活动行报进度 |
| 遇到「同一字段两份资料口径不同」→ 裁决 | `ask(kind=冲突裁决)`，附两处原文 | 裁决写入 `.modeling/decisions/` | 问题卡带证据引用，可点开原文 |
| 确认这一批 | 每组标 `tier`，口径类单独成组，一批 ≤ 5 组 | core 校验 `tier` 与实际改动相符 | 确认卡分诊：口径展开 / 结构折叠 / 索引隐藏 |
| 组数偏多时选「抽检 3 条」 | | 记 `review_mode='sampled'` + 实际抽到的组 | 发布摘要会体现哪些是抽检通过 |
| 把「结构变更」也设为不用问我 | | 写 `confirm_policy`，只影响之后的确认 | 常设策略开关就在确认卡下方，随时看得见授权了什么 |

**关键点**：确认疲劳在这里最严重，三道防线依次生效——

1. **源头限流**：Skill 里写死一批 ≤ 5 组，超过就拆多轮。前端分诊是兜底不是常态。
2. **分诊**：按判断难度分三档，十几项在视觉上只剩两三条要看的。
3. **批量模式**：全部接受 / 逐条过 / 抽检。抽检是有意提供的——用户不可能真看 17 条，与其假装看过，不如随机抽检并诚实记录复核方式。

「改口径」和「脚本」两档标为**必须问、不可关闭**，那是核心里的硬约束不是策略。

### A6 脚本决策

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| 决定哪些算逻辑要固化 | 识别出 3 处数值计算，先确认输入输出契约和测试 | — | 契约卡 |
| 确认契约 | 生成脚本，跑测试 | **JiuwenBox 沙箱**执行 | 测试结果逐条显示 |
| 选 1 个采纳，2 个保持规则描述 | 绑定 operation | 门禁「确定性能力确认」重算 | `scripts/` 出现文件 |

**关键点**：脚本是少数「生成成本低、错了代价高」的产物。契约先行、沙箱测试、显式绑定，三步都不能省。沙箱测试通过是 v1 仅有的两道真实质量闸门之一。

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |

## 旅程 B · 增量补充资料（屏 5）

**触发**：知识包已发布 `1.2.0`，业务方发来改版的管理办法
**核心诉求**：别把我确认过的东西推翻

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| 直接把 2 份新资料拖进对话流 | 读新资料，与现有知识包逐条比对语义差异 | 解析；建立新资料修订 | 活动行「正在比对《管理办法 v3》· 已 38 秒」 |
| 等 1–2 分钟 | 用 `who_references` 逐跳展开，自己判断传播到哪停 | 一跳引用查询（确定性原语） | **中栏两栏对照：绿色「11 项保持有效」在左，「4 项需处理」在右** |
| 一眼看到「11 项保持有效」，放心了 | | | 左栏变影响热图：4 个文件标红、其余变淡、新资料高亮 |
| 想知道为什么这 4 项受影响 | | | 中栏证据链三列：资料段落 → 传播路径 → 知识条目；**直接冲突与间接连带分开标** |
| 裁决冲突 1：可用量是否扣在途退货 | `ask`，摆出现行口径的来源（你三个月前的裁决）和新资料原文 | 裁决留痕 | 三选项含「保留现行，记为已知不一致」 |
| 裁决冲突 2：仓库分级 | | | |
| 确认增量方案 | 生成候选修订：改 3 文件、新增 1 规则 | 定向重评 4 例（只跑引用了受影响内容的用例） | 确认卡显示「失效 0 已发布用例，需重跑 4 例」 |
| 重评通过，发布 `1.3.0` | 建议 minor | 发布门禁 | |

### B 的失败分支

| 情况 | 处理 |
| --- | --- |
| 新资料与现有包大面积冲突（>30% 受影响） | 助手主动说「这更像一次重建而不是增量」，给两条路径让用户选 |
| 新资料只是排版改动 | 报告显示「0 项受影响」，一分钟结束，不生成候选修订 |
| 用户选「保留现行口径」 | 写入 `decisions/`，标为已知不一致，发布摘要里列出——**不是静默忽略** |
| 已发布版本 | 在用户确认新修订之前始终可用 |

**关键点**：这条旅程的成败取决于**「保持有效」清单是否可信，以及它是否占主视觉**。

两件事缺一不可：它必须由确定性的 `who_references` 逐跳查出来（不能是模型说「我觉得没影响」），并且必须做成绿色大字放在左边——原设计把受影响项做成表格主体、把「保持有效」挤在最后一行，恰好放大了用户的恐惧。

## 旅程 C · 融合另一个知识包（屏 6）

**触发**：另一个团队做了「库存盘点包 0.9.0」，要并进来
**核心诉求**：别把两个包搅成一锅粥

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| 导入来源包 zip | 解析条目 | 打 provenance 标记；zip 路径安全检查 | 左栏出现「来源包」树，逐项可勾选 |
| **先缩范围**：不要 scripts 和 mappings | | 未勾选内容不参与冲突检测 | **取消勾选时冲突数实时从 8 降到 5** |
| 看冲突清单 | 逐条读两侧定义，给分类与建议 + 理由 | 集合运算给出 key 撞 / 别名撞 / 引用断（约 60 行）；**语义判断由 `merge_analyst` 做，不写相似度算法** | 中栏冲突表 5 行，每行一个下拉处置 |
| 设融合策略：同名不同义默认重命名共存；不加命名空间前缀 | 解释前缀的代价（近义对象会让检索命中错的那个） | | 策略卡 |
| 逐条裁决 2 个必须人工定的（互斥规则、别名撞车） | `ask(kind=冲突裁决)`，摆出两个包各自的定义和证据 | 裁决留痕 | 冲突卡 |
| 其余 3 条按建议自动处置 | | | |
| 生成融合候选 | 写文件 | 融合自带的引用解析重算（非通用校验器） | 融合后引用解析预演 |
| 确认 | | 新已确认修订 | 目录树多出 4 个对象、2 条流程 |
| 跑一次全量评测确认没退化 | | | |

### C 的失败分支

| 情况 | 处理 |
| --- | --- |
| 融合后出现引用断裂 | 阻断确认，回到冲突清单，指出是哪条裁决导致 |
| 来源包引用了未勾选的条目 | 提示「引用断裂」，两个出口：补勾选 或 剔除该条目 |
| 用户中途放弃 | 候选修订整体丢弃，当前包零影响；来源包始终只读 |
| 来源包后续升级到 1.0.0 | 凭 provenance 再走一次**增量旅程**，只算 0.9.0 → 1.0.0 的差量 |

**关键点**：融合和增量是同一套机制的两个入口，差量来源从「资料」换成「另一个包」。做对这一点，融合的增量成本只有集合运算 + 选择性导入 UI。

**选择性导入必须前置。** 把 8 个冲突降到 5 个的一次勾选，比裁决 8 次有价值得多，所以勾选时冲突数要实时反馈。

## 旅程 D · 评测失败后的修复（屏 7）

**触发**：13 例跑完，11 通过、1 partial、1 fail

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| 看门禁面板，「全部用例通过」是红的 | | 门禁实时重算 | 每条阻断项带 Judge 理由和可执行出口 |
| 点「让助手修」 | 读两条用例的执行轨迹，定位到同一根因 | 只读诊断，**不能改包** | 右栏诊断说明 |
| 看修复方案 | 给出：改 2 个文件、预期修复 #7 #12、**已通过用例风险 #3 #9** | | 方案卡 |
| 同意 | 生成候选修订 | 候选修订 + diff | diff |
| 确认后自动重评受影响用例 | | 定向重评 #3 #7 #9 #12 | 进度 |
| 13/13 通过 | | 发布门禁重算 | 全绿 |

### D 的分支：不是知识包的问题

| 诊断结论 | 出口 |
| --- | --- |
| 用例本身错 / 标准答案错 | 回到用例编辑，改完重跑 |
| 数据源问题 | 回到数据源绑定 |
| Judge 判错 | 验证人员人工改判（有理由、可审计；原始结论永久保留） |
| 运行错误 | 重试，不可改判 |

**关键点**：诊断必须先分类再修复，**只有包和脚本的问题才进入修复回路**。否则会出现改包去迎合一条写错的用例。

「已通过用例风险」必须提前显示——修复会动到别的用例引用的规则，说在前面比事后回归失败好。

## 旅程 E · 追溯：这条规则的依据是什么（屏 4）

**触发**：三个月后有人质疑「可用量为什么要扣在途退货」
**核心诉求**：证据要能一路查到底

| 用户 | 助手 | 核心 | 界面 |
| --- | --- | --- | --- |
| 打开 `rules/安全库存判断.md`，点它的 evidence 引用 | — | `GET /evidence/locate` | 左栏切到资料 tab，中栏跳到《作业手册》§3.2 并高亮该段 |
| 发现原文只说「扣除已占用」，没提在途退货 | — | — | 右栏提示「这段和现行知识不完全一致」 |
| 点「看那次裁决」 | — | 读 `.modeling/decisions/d-014` | 显示 2026-08-22 的裁决记录：问题、选项、你选了什么、当时的理由 |
| 反过来问「这一段还被谁引用了」 | — | `GET /materials/:id/referrers` | 右栏列出 3 条引用它的知识条目，可跳转 |
| 决定这条口径要改 | → 转入**旅程 B** 或直接改 | | |

### E 的相邻场景

| 场景 | 处理 |
| --- | --- |
| 想删掉一份过期资料 | 删除前提示「会让 14 条知识失去证据」，逐条重新指认或标为待补 |
| 想知道哪份资料最关键 | 资料列表的「引用 N」计数直接回答 |
| 资料有了新版本 | 「上传新版本」→ 走增量旅程，不是删了重传 |

**关键点**：**双向反查是资料界面的全部理由**，比列表重要得多。它让 evidence 从「一个字符串」变成可验证的东西。

顺带一说：一旦这个界面存在，evidence 的可解析性校验就有了用户价值支撑——将来把「evidence 必须指向真实存在的资料/表/裁决」加回成阻断检查会顺理成章，而那个版本是编造不出来的。

## 旅程 F · 中断与恢复

没有独立界面，但决定用户敢不敢把长任务交出去。

| 情况 | 行为 |
| --- | --- |
| 用户关掉浏览器 | run 在服务端继续，遇 `ask` 挂起等待 |
| 用户第二天回来 | 从最近检查点恢复：计划、待答问题、候选修订、中栏焦点全部还原 |
| 服务重启 | 从最近检查点续跑，**不重放**此前的工具调用 |
| 用户从版本历史点「恢复」 | 250ms 内显示「正在恢复」；成功后消息流自动记录「已恢复到 vX.Y.Z，请以该版本继续」，Agent 自行对齐项目进展，不要求用户再输入任何运行指令 |
| 上下文压缩触发 | 新执行 session 注入项目唯一业务状态；助手按需重读 plan 和证据，不携带全部资料历史 |
| 用户在任意阶段说「请全文精读《对象定义.xlsx》，按它修正模型」 | 250ms 内消息入流；Agent 自行识别材料、切换为全文精读并主动继续。若新事实影响已确认内容，唯一项目状态只回退不前跳：目标依据回到目标阶段，Schema 或一般证据回到知识阶段；不得另建“阅读状态”或要求用户指定状态/工具 |
| 同时全文精读多份或单份超长资料 | 文档之间受控并发、长文分块并执行树形多层汇总；以覆盖账本证明全部可解析单元均已处理。20 万字以上不得抽样、截断或只读首尾；任一分块失败就不能声称完成，恢复后只补未完成分块 |
| 用户在助手跑的时候插话 | 消息在下一个工具边界插入；未答问题保持挂起，答完插话后重新推到流底 |
| 用户发送消息或点击确认 | 页面先乐观写入同一消息流，再等待服务端对账；失败才恢复，不让网络往返阻塞点击反馈 |
| 助手生成自然语言 | openJiuwen chunk 逐段进入同一条助手消息，实时增长；结束事件只收口光标，不补发重复全文 |
| 助手绕圈 | 无进展保护：连续 N 轮无写入且无新证据 → 中止并报告已尝试的动作 |
| 超出 token 预算 | 挂起并告知，由用户决定继续还是收敛范围 |
| 两个人同时打开同一项目 | 单写者租约：一人可写，其他人只读浏览，明确显示「XX 正在建模」 |
| 持有租约的人失联 | 租约超时（默认 30 分钟）后可被接管，接管时提示存在未答问题 |

**关键点**：Agent 运行时的 `project_agent_state` 是唯一当前状态。`state` 把业务阶段和执行状态编码为一个值（例如 `goal:waiting`）；摘要、开放问题和版本也只在该行更新。`project_agent_state_transitions` 仅追加审计，run、plan 与对话不得成为另一份当前状态。

全文阅读进度、分块覆盖和失败检查点是可重建的执行事实，不是第二份项目当前状态；阶段回退仍只更新 `project_agent_state` 那一行，并追加转换审计。新 Agent 工作台项目不得初始化或更新旧任务图、旧阶段列或旧工作流节点。

## 本轮专项验收

| 场景 | 验收证据 |
| --- | --- |
| 可选材料用途 | 不选择任何用途可以直接开始；选择用途后 250ms 内看到结果；作用单选互斥，全文开关与作用可组合，并始终保留自然语言输入 |
| Excel 作为 Schema | 用含两个工作表、空列和重名列的工作簿验收；对象/属性逐项可反查原始资料、工作表、Excel 列号和列名，新增业务属性数为 0；类型和主键候选单独标为推断 |
| 全文精读 | 只输入「请全文精读《X》并据此修正目标/模型」即可完成设置、完整阅读、状态回退和后续推进；页面与回复中不出现内部工具名、API、状态编码或数据库表名 |
| 超长与并发 | 至少一份超过 20 万字且在首段、中段、末段埋入可核对事实；三处都进入阅读结果，覆盖率为 100%；多文档读取存在重叠执行且不超过配置的并发上限 |
| 中栏渲染 | 通过浏览器分别打开真实 `.md`、`.yaml` 和 `diagrams/*.mmd`，验证语义渲染、源码切换、错误降级、缩放与节点聚焦；桌面和移动页面无空白、遮挡和不可达横向区域 |
| 即时与流式 | 上传、改用途、切全文、发送精读请求均在 250ms 内反馈；活动进度位于唯一消息流；长任务期间输入框可继续发送插话；同一条 Agent 消息在结束前至少两次增长且最终不重复全文 |
| Agent 模型 | 验收环境明确配置 `deepseek-v4-flash`（或经确认的 `glm-5.2`），审计记录中的实际模型 ID 与配置一致；从浏览器完成至少一轮含读取、写入和状态推进的真实调用，模型不可用时显式失败，不得静默回落到旧模型 |

## 跨旅程的情绪与风险节点

| 节点 | 用户在想什么 | 设计对策 |
| --- | --- | --- |
| 第一次点「开始建模」 | 它会不会乱写一通 | 目标确认前不动正文；第一个产物就是可读可改的 `goal.md` |
| 助手跑了两分钟没动静 | 是不是卡了 | 活动行：说人话 + 带耗时 + 三级递进 |
| 点发送或确认后没有变化 | 到底点上没有 | 250ms 内先显示本地消息或已处理状态；失败时原位恢复并给出错误 |
| 点恢复、重试后又让我输入指令 | 为什么还要我懂系统内部 | 点击动作自动进入消息流并触发 Agent 续跑；用户只看到语义版本、业务影响和下一步 |
| 助手开始回答 | 是不是又要等完整结果 | 同一条消息逐段增长，输入框始终可用 |
| 抽取阶段连续确认 | 又来？还有多少？ | 源头限流（≤5 组）+ 分诊 + 批量模式 + 常设策略常驻可见 |
| 助手说「需要补充资料」 | 我没有这个文档 | 「我口述」出口，与文档证据同等对待 |
| 上传新资料 | 我三个月的确认会不会白费 | 「11 项保持有效」占主视觉 + 左栏影响热图 |
| 融合别人的包 | 会不会污染我的包 | 选择性导入前置且冲突数实时反馈；来源包只读；候选可整体退回 |
| 评测没过 | 是包错了还是用例错了 | 诊断先分类再修复 |
| 有人质疑某条口径 | 依据在哪 | 双向反查：evidence → 资料原文 → 当初的裁决记录 |
| 发布前 | 有没有我不知道的坑 | 全量用例通过 + 用例覆盖人工确认（v1 两道真实闸门）；发布摘要列已知限制与抽检记录 |
