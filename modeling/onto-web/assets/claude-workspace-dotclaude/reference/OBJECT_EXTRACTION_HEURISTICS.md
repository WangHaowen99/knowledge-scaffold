## 一、决策驱动判断（实体 vs 属性）

候选对象 X 是实体还是属性？依次问以下四个问题，**任意一项命中**即建议建为实体：

1. 系统是否要对它做决策（查询/筛选/比较/触发动作）？
2. 是否被多个 logic / 多个流程引用？
3. 是否有唯一 ID 可全域标识？
4. 是否有独立的状态与生命周期？

**全部否** → 该 X 应建为属性，挂在承载它的实体上。

### 辩证补丁

这套原则的原始语境是"AI 自主决策"——"凡是系统需要自动推理/分配/判别的对象,必须建为独立 Class"。通用化时应放宽:

- 业务知识建模里,即使 X 不参与"机器自主决策",只要被**多个 logic 引用**或被**业务专家反复指涉**,即可视为实体。
- 不必强求每个实体都"能驱动机器决策"。

### 反例集

| 候选 | 决策驱动 | 多 logic 引用 | 独立 ID | 独立生命周期 | 结论 |
|---|---|---|---|---|---|
| 订单 | 是 | 是 | 是 | 是 | 实体 |
| 订单金额 | 否（仅作判断条件中的数值） | 否（只通过订单访问） | 否 | 否 | 属性 |
| 客户 | 是 | 是 | 是 | 是 | 实体 |
| 客户性别 | 否 | 否 | 否 | 否 | 属性 |
| 海浪高度 | 否（被读取，本身不被决策） | 多个流程读取 | 否 | 否 | 属性（或归属于"海域环境"实体的属性） |
| 供应商 | 是（选哪个供应商是决策） | 是 | 是 | 是 | 实体（即使当前只在一个合同里被引用） |

## 二、能力差异判断（同类 vs 异类）

候选 X 和 Y 看起来是"同一概念的不同子类"时，应拆为不同实体类，还是同一实体类 + 属性区分？

**能力不同 → 拆为不同子类**：例如侦察无人机 / 攻击无人机（虽都是飞行器，但承担的任务、需要的传感器、决策路径完全不同）

**能力相同、仅型号/参数不同 → 同一类 + 型号属性**：例如翼龙-2 / CH-4 都是侦察机，差异只在制造商和参数

### 辩证补丁

对**业务流程层**（不涉及自主任务分配）而言,本条不必严格按"能力"判断。更通用的标准是:

> **下游 logic 对两类对象是否写出截然不同的处理分支?**

- **是** → 拆类
- **否** → 同类加属性

### 反例集

| 候选 X / Y | 下游分支是否截然不同 | 结论 |
|---|---|---|
| 侦察无人机 / 攻击无人机 | 是（整个任务分配链都不同） | 拆类 |
| 翼龙-2 / CH-4 | 否（都是侦察机） | 同类（无人机） + 型号属性 |
| VIP 客户 / 普通客户 | 否（只是折扣规则不同） | 同类（客户） + 等级属性 |
| 个人客户 / 企业客户 | 是（风控/信贷/税务分支完全不同） | 拆类 |
| 已下单 / 已支付 / 已发货（同一订单的状态） | 否（是同一订单在不同阶段） | 同一类（订单） + 状态属性 |

## 三、判断流程

```
候选对象 X
   │
   ▼
是否任一决策驱动条件满足？
   │ 否 → X 是属性，挂在承载它的实体上
   │ 是
   ▼
是否与已有实体 Y 在下游处理分支上截然不同？
   │ 是 → 拆为新实体类
   │ 否 → 并入已有实体类，添加属性区分子类型
   ▼
确定为实体
```
