# Consumer、Auth 与建模服务的交互式部署、升级说明

本文说明以下两个交互式入口。它们收集参数后统一调用 `install-consumer-modeling.sh`。
新环境使用独立 Auth 发布包首装；旧合并环境通过 `--upgrade-from` 自动迁移 Auth 所有权。Consumer 包须为不含 Auth 的 external 模式。

```text
install-consumer-modeling-interactive.sh
upgrade-consumer-modeling-legacy-interactive.sh
```

两个脚本用途不同：

| 脚本 | 用途 |
| --- | --- |
| `install-consumer-modeling-interactive.sh` | 新架构分离部署的首次安装，以及已有分离部署的升级 |
| `upgrade-consumer-modeling-legacy-interactive.sh` | 旧合并目录自动迁移 Auth 所有权后原地升级；已迁移环境直接升级 |

## 1. 现场依赖

现场主机需要：

```text
Linux
Bash 3.2 及以上
Docker Engine 20.10 及以上
curl
tar
gzip
sha256sum
flock
python3
awk
sed
mktemp
```

Docker daemon 必须处于运行状态。发布包路径应使用绝对路径，或者使用当前目录下的相对路径。

Consumer 发布包应包含：

```text
onto-agent/
onto-agent/deploy/install.sh
onto-agent/deploy/opsctl
onto-agent/deploy/manifest.json
onto-agent/backend/.env.example
```

独立 Auth 发布包 `onto-auth-<版本>-<架构>.tar.gz` 应包含 `auth-release.json`、`images/auth-server.tar`、`deploy/auth-install.py` 和 `deploy/auth-upgrade.sh`。首次安装由联合脚本在独立 Auth owner 目录创建包外 `.env`，权限为 `0600`。

Onto Modeling 发布包应包含：

```text
onto-modeling/
onto-modeling/deploy.sh
onto-modeling/docker-compose.release.yml
onto-modeling/.env.example
onto-modeling/images/
```

知识包 Hub 发布包（`bash knowledge-hub/build.sh <version> [amd|arm]` 生成）应包含：

```text
knowledge-hub/
knowledge-hub/deploy.sh
knowledge-hub/docker-compose.knowledge-hub.yml
knowledge-hub/images.env
knowledge-hub/images/
```

独立评测服务发布包由 `bash eval-service/build.sh <version> [amd|arm]` 生成，位于
`eval-service/dist/evaluation-<version>-linux-<arch>.tar.gz`，顶层目录为 `eval-service/`，与其他组件
发布包一样支持通配符；也可使用完整发布包解压后的 `eval-service/` 子目录。发布包或目录中必须包含：

```text
deploy/deploy.sh
deploy/docker-compose.eval-service.yml
evaluation-image.tar
IMAGE
```

## 2. 新架构首次分离部署

执行：

```bash
bash install-consumer-modeling-interactive.sh
```

交互流程：

```text
1. 选择“首次部署”
2. 选择默认安装目录 /opt/onto-agent-stack 或自定义目录
3. 选择默认端口或自定义端口
4. 输入 Consumer、独立 Auth、Onto Modeling、Hub 和评测发布包路径
5. 新环境由联合脚本自动创建独立 Auth owner 的 `.env`；交互脚本会提示该路径
```

Consumer、独立 Auth、Onto Modeling、知识包 Hub、独立评测共五个发布包，均须提供。
首次安装由 Auth 包自带工具创建独立 owner，随后部署 Consumer → Hub → Onto Modeling → 评测；已有独立 owner 时，使用 Auth 包先升级 Auth。联合升级同样先升级 Auth，再升级其余服务；镜像相同时跳过 Auth 升级。
非交互参数为 `--consumer-package`、`--auth-package`、`--onto-modeling-package`、`--knowledge-hub-package`、`--evaluation-package`，五项均必填。新环境首次安装时，联合脚本自动在 `AUTH_OWNER_DIR/.env` 创建 `0600` 配置文件；未设置 `AUTH_OWNER_DIR` 时，默认位置是 `<INSTALL_ROOT>/independent-auth/.env`。默认 issuer 为 `http://auth-server:5056`、audience 为 `knowledge-scaffold`，管理令牌和初始管理员密码随机生成。已有 `.env` 的非空字段保持不变，缺失的必填字段补齐。生成的初始管理员密码应由部署方从仅限授权人员访问的 `.env` 中妥善保存，脚本不会输出密码。
不再提供省略 Consumer 包、仅附加部署组件的模式。
使用与发布包同版本的安装脚本。联合入口会验证 Consumer 的 external Auth 模式、URL、管理令牌与独立 Auth owner 的一致性，并核对共享网络和签发身份；Onto 单包部署还会检查发现文档与 JWKS。实际账号连续性在业务验收时验证。

首次安装默认端口如下：

| 服务 | 默认宿主端口 | 容器端口 |
| --- | ---: | ---: |
| Consumer Backend | 5055 | 5055 |
| Consumer MCP | 7488 | 7488 |
| Consumer Frontend | 8888 | 80 |
| Onto Modeling | 5100 | 8100 |
| 独立评测服务 | 5180 | 5180 |

选择自定义端口时，脚本会逐项询问四个端口。端口输入会自动去除首尾空格，并校验为 `1` 到 `65535` 的整数。
Onto Modeling 的端口不能与 Consumer 的三个端口相同，相同时会要求重新输入。

首次安装会依次执行：

```text
校验五个发布包和 external Consumer 清单
校验 Onto Modeling、Hub 与评测容器归属并执行 Onto 预检
解压 Consumer 发布包
从 Auth 发布包首装独立 owner，或升级已有 owner；等待健康并检查网络、别名和签发身份
生成 Consumer 的 MODELING_SERVICE_TOKEN
生成独立的 EVALUATION_SERVICE_TOKEN
部署 Consumer
部署知识包 Hub，等待容器内健康检查通过
部署 Onto Modeling，等待 /api/health 就绪
部署独立评测服务，等待容器内 /evaluation/api/health 就绪
```

Onto Modeling 排在 Consumer、Hub 之后部署，因此它的预检放在服务变更之前：已有 `onto-modeling` 容器
必须属于 `<安装根目录>/onto-modeling`，否则拒绝接管；随后运行发布包自带的
`preflight.sh`（AVX、内存、磁盘）。预检失败时会在 Consumer 业务容器变更前退出。已有 `knowledge-hub` 容器同样必须属于
`<安装根目录>/knowledge-hub`。

Onto Modeling 共享 Consumer 的账号中心：脚本读取 `onto-agent-backend` 容器的实际网络，
写入 `onto-modeling/.env` 的 `ONTO_MODELING_EXTERNAL_AUTH_NETWORK`，并核对独立 Auth owner。
Consumer 尚未运行时，首次安装从独立 Auth owner 记录中读取网络；Consumer 已运行时取双方网络交集。

知识包 Hub 是独立 compose 项目（容器 `knowledge-hub`，数据卷 `knowledge-hub_knowledge-hub-data`），
部署在 `<安装根目录>/knowledge-hub`，同样加入 Consumer 的实际网络，Onto Modeling 经服务名访问它。
Hub 的服务凭据保存在 `knowledge-hub/.env`：首次部署时沿用 Onto Modeling 已有的
`ONTO_HUB_SERVICE_TOKEN`，没有时生成；随后脚本把 Onto Modeling 的该值对齐为 Hub 实际使用的值。
凭据只写入权限 600 的 `.env`，不会打印。

独立评测服务部署在 `<安装根目录>/eval-service`，使用独立的 `knowledge-evaluation` Compose
项目和 `knowledge-evaluation_evaluation-data` 数据卷。脚本读取 Consumer 的实际网络，将
Consumer、Hub 的评测凭据和 Onto Modeling 接收评测完成通知的凭据（`ONTO_EVALUATION_SERVICE_TOKEN`，
由 Onto Modeling 部署生成）传给评测部署脚本；凭据不出现在交互输出中。Onto Modeling 先于评测部署，以提供完成通知凭据。已有评测容器的 Compose
工作目录必须是 `<安装根目录>/eval-service/deploy`，否则在变更服务之前拒绝接管。

评测配置由 `<安装根目录>/eval-service/deploy/.env` 保存（权限 600）。升级只复制镜像、清单和
部署文件，保留原加密密钥、端口及其他运行配置，不复制发布包或目录中可能存在的 `.env`。
默认界面地址为 `http://localhost:5180/evaluation/`，绑定所有网卡；远程机器使用部署主机的
地址访问。通过 `EVAL_PORT`、`EVAL_BIND_ADDRESS` 或评测运行配置调整端口和监听地址。
评测端口与四个交互端口分开配置；更改后需相应设置建模入口 `ONTO_WEB_EVAL_PUBLIC_URL`。
Judge 模型可由管理员登录评测页面后配置。

设置 `EVAL_ENV_FILE` 可使用已有受保护的外部配置，脚本提前校验并原样沿用；外部配置中的
加密密钥、依赖地址和评测凭据须自行配齐。部署失败或健康检查超时会停止流程，不报告交互部署完成。

联合入口会在变更 Consumer 前检查五个交付包和已有 Auth owner。新环境会创建独立 Auth owner 和账号卷；旧环境的 Auth 容器缺失或归属不符时会阻断。Auth 包升级失败会阻断 Consumer 升级；Consumer 自身安装器的预检和报告以随包交付的 Consumer 操作手册为准。

## 3. 旧合并部署升级

此流程用于旧合并目录：Auth 仍由 Consumer 管理时，脚本先迁移所有权，再在原目录升级 Consumer 并部署建模服务；已有独立 owner 时直接进入五包升级。迁移中断时保留状态和工具备份，修复原因后重跑同一命令。

执行：

```bash
bash upgrade-consumer-modeling-legacy-interactive.sh
```

交互输入：

```text
旧的合并部署根目录
新的 Consumer 发布包路径
独立 Auth 发布包路径
新的 Onto Modeling 发布包路径（必填）
新的知识包 Hub 发布包路径（必填）
新的独立评测服务发布包路径（必填）
Onto Modeling 宿主端口（已有配置时沿用原端口）
```

脚本会依次执行：

```text
校验旧安装目录和发布包
确认 Onto Modeling 端口并执行其预检
校验已有 knowledge-hub 容器归属
若旧 Auth 仍归 Consumer 管理，从新版 Consumer 包准备 external 工具并调用 Auth 包迁移工具；中断时按原 owner 记录续跑
验证独立 Auth owner，必要时启动已停止的容器，再检查网络和签发身份
核对已配置的 Onto、Hub、评测 Auth 引用
使用 Auth 发布包升级独立 owner，确认健康
读取旧 Consumer 的配置；Consumer 升级与备份由其安装器执行
升级 Consumer
部署知识包 Hub
部署 Onto Modeling，等待 /api/health 就绪
部署独立评测服务，等待容器内 /evaluation/api/health 就绪
```

如果旧环境仍有占用 5100 的服务，须为 Onto Modeling 选另一个宿主端口；交互脚本在无现有 Onto 配置时询问端口，联合入口会在升级前检查与旧服务的冲突。
Onto Modeling 部署在 `<旧安装根目录的上级目录>/onto-modeling`，知识包 Hub 部署在
`<旧安装根目录的上级目录>/knowledge-hub`，均共享 Consumer 网络，接线方式与首次部署相同。
独立评测服务部署在 `<旧安装根目录的上级目录>/eval-service`；Consumer 评测凭据在其升级
重启前补齐，已有评测密钥和运行配置保留。

该脚本只处理旧合并部署。已经分离的部署应改用新架构交互脚本执行升级。

## 4. 新架构分离部署升级

执行：

```bash
bash install-consumer-modeling-interactive.sh
```

交互流程：

```text
1. 选择“升级部署”
2. 输入已分离部署的安装根目录
3. 输入 Consumer 发布包路径（必填）
4. 输入 Onto Modeling 发布包路径（必填）
5. 输入知识包 Hub 发布包路径（必填）
6. 输入独立评测服务发布包路径（必填）
```

升级时不会询问端口，也不会重新指定端口。脚本会读取并保留：

```text
<安装根目录>/onto-agent/backend/.env
<安装根目录>/onto-modeling/.env
```

其中的 Consumer 和 Onto Modeling 端口配置。

首次加入 Onto Modeling 时若还没有 `.env`，默认宿主端口为 5100；已有服务占用时应先设置空闲端口。
Onto Modeling 的预检同样在业务容器变更之前执行，见第 2 节。
五个发布包同时交付；Auth 由包内独立升级工具管理。目标镜像与当前一致时跳过 Auth 升级。
已有 Consumer、Onto Modeling 配置、Hub 数据卷和评测加密密钥继续保留。
评测发布包必须提供，更新交付物时保留 `eval-service/deploy/.env`。

## 5. 常见问题

### 5.1 `BUNDLE-CHECKSUMS: 发布包校验和失败`

说明发布包中的文件内容与 `checksums.txt` 不一致。常见原因包括：

```text
手工修改了发布包目录中的文件
发布包传输不完整
解压后覆盖了文件
```

应重新获取或重新构建完整发布包，不要直接修改发布包中的受校验文件。

### 5.2 `PORT-* 端口值无效`

首次安装自定义端口必须是 `1` 到 `65535` 的整数。输入前后带空格时脚本会自动清理；如果仍然失败，应检查是否混入了其他字符。

### 5.3 端口被占用

首次安装时更换自定义端口。升级时脚本会沿用已有端口；如果端口被其他服务占用，应先处理占用服务或修正已有 `.env`，再重新升级。

Onto Modeling 与本套部署内其他服务的端口冲突由脚本在动手前检测并要求重新输入；被本套部署之外的
进程占用时，`deploy.sh` 拉起容器会失败，此时 Consumer 已完成，处理占用后可单独执行
`bash <安装根目录>/onto-modeling/deploy.sh`。

## 6. 非交互式分离部署与升级

`install-consumer-modeling.sh` 支持首次安装、`upgrade` 分离升级和 `--upgrade-from` 旧版迁移，三种流程都要求独立 Auth 发布包。
五项必填：`--consumer-package`、`--auth-package`、`--onto-modeling-package`、`--knowledge-hub-package`、`--evaluation-package`。
缺少任一必填参数会在解压或停止容器前退出。

首次安装示例（以下路径为通用占位路径）：

无需手工创建 Auth 配置文件。联合脚本会在启动服务前生成 `/opt/onto-agent-stack/independent-auth/.env`；需要自定义 issuer、audience 或密码策略时，可在首次安装前预建权限为 `0600` 的文件，联合脚本保留其中非空的必填字段。

```bash
INSTALL_ROOT=/opt/onto-agent-stack \
bash deploy/install-consumer-modeling.sh \
  --consumer-package /path/to/consumer-release.tar.gz \
  --auth-package /path/to/onto-auth-release.tar.gz \
  --knowledge-hub-package /path/to/knowledge-hub-release.tar.gz \
  --onto-modeling-package /path/to/onto-modeling-release.tar.gz \
  --evaluation-package /path/to/evaluation-release.tar.gz
```

升级已分离的部署时，在脚本名后添加 `upgrade`，继续提供五个发布包；使用现有 Auth owner 配置：

```bash
INSTALL_ROOT=/opt/onto-agent-stack \
bash deploy/install-consumer-modeling.sh upgrade \
  --consumer-package /path/to/consumer-release.tar.gz \
  --auth-package /path/to/onto-auth-release.tar.gz \
  --onto-modeling-package /path/to/onto-modeling-release.tar.gz \
  --knowledge-hub-package /path/to/knowledge-hub-release.tar.gz \
  --evaluation-package /path/to/evaluation-release.tar.gz
```

Consumer 已运行时执行 `upgrade` 并继续提供五个必填发布包；不再通过省略 Consumer 包进入附加部署模式。

旧合并部署，或业务服务已分离但 Auth 仍由 Consumer 管理时，不使用 `upgrade` 子命令，改为添加 `--upgrade-from <现有 Consumer 安装目录>`。该目录必须存在，路径写错会直接报错。脚本会先从新版 Consumer 包准备 external Auth 生命周期工具，再调用独立 Auth 包中的 `auth-offline.py` 迁移原容器的所有权；迁移完成后才升级 Auth 镜像和其他服务。中断重试沿用记录的 owner 目录和项目名。
默认在旧目录旁创建独立组件目录，也可用 `INSTALL_ROOT` 指定目标根目录。
评测的 Consumer 凭据在其安装或升级重启前写入，已有合法值保持不变。
可通过 `EVAL_PORT`、`EVAL_BIND_ADDRESS` 或 `EVAL_ENV_FILE` 配置评测运行参数；不会输出凭据值。
